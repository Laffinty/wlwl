# v0.10.1 第三方合规审查(源材料)

第三方以**黑盒**方式对 v0.10.1 做规范符合性审查的产出。审查方在一个独立工作目录里
**解包了本仓库的完整快照**(含自建的 `wlwl.exe`)并在其上编写 `.wll` 程序,观测退出码 /
stdout / stderr / JSON 诊断 —— 全程未读任何 WLWL 源码。

- **报告**:[`wlwl-spec-v0.10-合规审查报告.md`](wlwl-spec-v0.10-合规审查报告.md)
  (13 条确认缺陷:4×P0 / 5×P1 / 4×P2;761 个用例)
- **本仓库的核验与修复**:`../../plan/wlwl-spec-compliance-修复计划.md`

## 核验结论:不要照单全收

逐条重跑报告自带的用例 + 回源码定位后:**13 条里 8 条属实、2 条根因判错、3 条不成立**,
另发现 2 条报告漏掉的真缺陷。5 处分歧已留档在 `CHANGELOG.md` 的 v0.10.2 条目里。

其中三处值得单独记住:

| 报告 | 实际 |
|---|---|
| P0-1「具名 `FUN` 完全未实现」 | **不成立** —— 一直有实现(`FUN(name(params), body)`),错的是规范 A.2 的文法与同章正文自相矛盾;报告只测了 `FUN f(x) x` |
| P1-3 / P2-1「`W0051` / `W0066` 未实现」 | **根因错** —— emit 点一直都在,断的是出口:CLI 全仓零处调用 `take_warnings()`。改一处,三条立即转绿 |
| P1-4「模块契约需要先知道导出面,本实现做不到」 | **推理错** —— `check_exports` 的导出面来自纯静态、顺序无关的 AST 遍历,早已实现 |

## 本目录只入库了什么、为什么

审查方留下的是**整个仓库的快照**,不是一个补丁。入库时只保留**报告本身**:

| 内容 | 处置 | 理由 |
|---|---|---|
| 审查报告 | ✅ 入库 | 本次工作的唯一一手输入,计划书与 CHANGELOG 都引它 |
| `wlwl.exe`(3.4 MB 被审二进制) | ❌ 不入库 | 编译产物不入库;体积与二进制检测都会给仓库添麻烦 |
| `LICENSE` | ❌ 不入库 | **一个仓库里两份 LICENSE 是有害的** —— 读者无法判断哪份权威 |
| `README.md` / `CHANGELOG.md` | ❌ 不入库 | 与仓库根同名文件重复,必然分叉 |
| `docs/standard/wlwl-spec-v0.10.md` | ❌ 不入库 | 审查当时的规范基线副本。**活文档才是权威**;本次已按核验结论改过多处,留一份旧副本只会误导 |
| `examples/` / `wlwl-skill/` | ❌ 不入库 | 同上,仓库快照而非审查产出 |
| `_audit/`(935 个用例 + 39 个驱动脚本) | ❌ 不入库 | 审查方的工作语料。**其中的价值已被提炼进 `impl/tests/probe/cases/`** —— 28 条 `P_v10_2_*` 夹具,每条修复至少一条、每条都配反向守卫,那是本仓库真正的回归套件 |

需要复现报告的某条原始用例时,从报告 §7 列的路径取;需要防止回归时,用
`cargo test -p wlwl-cli --test probe`。
