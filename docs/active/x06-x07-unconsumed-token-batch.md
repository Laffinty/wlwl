## 1. 背景：v1.0 的差异登记

v1.0 一致性册 §5.4 登了 15 条「规范条款 ↔ 参考实现差异」。其中 6 条与本仓的
**未消费 `ERR`** 机制相关：

| 编号 | 要求 | 状态 |
|---|---|---|
| **X-06** | 未消费状态是**集合**；汇入取并集；丢弃逐个报告 | **第一步已收敛**（集合化 + 逐个报告 + 多诊断通道）；**身份**那半步待口径（见 §3.1） |
| **X-07** | 标准库回调的实参通道须携带令牌 | **本批已收敛**（实现仓 `wip0.11.4` 的 `b48a442`） |
| **X-16** | 内建 `CALL(f, …)` 的实参通道须携带令牌 | **本批已收敛**（内建 `CALL` 的实参通道现在带集合） |
| **X-17** | 持有未消费 `ERR` 的**容器 / 字典**被丢弃时也须报 `E0103` | 本批新登记（见 §4）；**本批已收敛**（语句丢弃判据改成「集合非空」） |

另 5 条（X-01 / X-02 / X-14 / X-15 与 X-06 的身份部分）不在本批。

## 2. 本批已落地

### 2.1 X-07（已收敛，待并入上游基线）

**根因**：`eval_call` 早已算出每个实参的令牌（`tokens`），但 `invoke_std` 只把
`args` 交给 stdlib 成员 ⇒ 成员不知道「我的实参带着未消费的 `ERR`」⇒ 按
§8.6.3「读入其它任何位置 → 由接收方承担」的转发链在**第一跳**就断了。

**修法**（两条通道，均在 `StdHost` 上带**默认实现** ⇒ 仓内 8 处手写
`NullHost` 零改动）：

- `StdHost::arg_tokens()` —— 求值器 → 成员；
- `StdHost::call_with_tokens()` —— 成员 → 回调的**形参绑定**。

**先只做 5 个迭代型成员**（`MAP` / `FILTER` / `GROUP_BY` / `DEDUP_BY` /
`KEY_BY`）—— 一上来全铺会改变一大批既有行为。

**语义核对**（实测）：

| 形态 | 结果 |
|---|---|
| 回调**消费**那个 `ERR`（`ERR_PAYLOAD(x)`） | **不报**（无假阳性） |
| 回调**观察**那个 `ERR`（`IS_ERR(x)`） | **报**（§8.6.1 观察型不解除状态） |
| 容器里**候选不唯一** | **不猜**（猜错会把早已被消费的 `ERR` 报出来 = 假阳性）⇒ 归 X-06 |

⚠ **消息形态两处不同是对的**：直接调用户函数时整个数组进形参 ⇒ 被处置的是
**容器** ⇒ `[ERR(boom)]`；走标准库成员时回调收到的是**元素** ⇒ 被处置的是那个
`ERR` 本身 ⇒ `boom`。各自都是「被处置的那个值」。

**契约**：`impl/crates/wlwl-eval/tests/x07_arg_token_contract.rs`（12 例，
一例一 `#[test]`；负向验证：断掉通道 ⇒ 7/12 变红）。

### 2.2 X-06 第一步：令牌集合化（**已收敛**）

`impl/crates/wlwl-value/src/lib.rs` 已把「令牌」从 `bool` 改成**有序集合**：

```rust
pub type UnconsumedErrs = Vec<Value>;
pub fn union_unconsumed(base: &[Value], extra: &[Value]) -> Vec<Value>;  // 并集，不去重
pub fn find_unconsumed_index(set: &[Value], value: &Value) -> Option<usize>;
```

六条语义（§8.6.1 / §8.6.2 / §8.6.3 / §8.6.5）各自落点 + 8 条自测，
负向验证 6 组全部「改坏即红」。

**三个丢弃点改成「逐个报告」**（`wlwl-eval`）：

| 丢弃点 | 判据 | 措辞 |
|---|---|---|
| 语句值丢弃（§8.6.2 第 1 项） | **集合非空**（不再看「值本身是不是 `ERR`」）⇒ 顺带**修掉 X-17** | 被处置的**那个值** |
| 绑定被覆盖（第 2 项） | 旧绑定的集合非空 | 旧绑定持有的**那个值** |
| 作用域结束（第 3 项） | 每个持有未消费 `ERR` 的绑定各报一遍 | 该绑定持有的**那个值** |

⚠ **措辞报的是「被处置的那个值」，不是「里面那个 `ERR` 的载荷」** —— 依据
§8.6.3「容器装盛……该 `ERR` 继续到**容器**；容器本身在丢弃点被处置」+ 冻结
契约自带注释（「被丢弃的值是**容器**……不是里面那个 `ERR`」）。这与 `b48a442`
的旧口径**逐字一致** ⇒ 不是新行为。

### 2.3 多诊断基础设施

`impl/crates/wlwl-error/src/lib.rs` 加 `WlwlError::Diagnostics(Vec<WlwlDiagnostic>)`
变体 + `diagnostics()` 方法；`diagnostic()` 在多条时返回**第一条** ⇒ 仓内
**390+ 处** `.diagnostic()` 调用点**零改动**。

`impl/crates/wlwl-cli/src/diag_output.rs`（新）把这批诊断**逐条**打印：
`report_error` / `tooling.rs` 走 `render_error_text`，LSP 走 `publishDiagnostics`
（原生就是数组 ⇒ 一次全量）。**退出码按第一条**的类别定（§11.4 按故障类别给码）
—— 未改退出码表本身。

### 2.4 `Consume` 语义下沉到值层（本轮修掉的两条**真回归**）

集合化第一版把 `Env::read_binding` 的 `Consume` 分支收窄成「只在**读到的值本身**
是 `Value::Err(_)` 时才从源集合里移除它」⇒ **两处破口**：

| 破口 | 现象 | 违 |
|---|---|---|
| 读到的值是 `OK(ERR(x))` | 取走型消费者（`UNWRAP_OR` / `TRY` / `UNWRAP` / `WRAP` …）剥掉 `OK` 外壳拿到的是**内层**那个 `ERR`；源集合里那一份移不掉 ⇒ 源绑定与结果值各留一份 | §8.6.5（一个 `ERR` 至多报一次） |
| 同上 | `std.result` 的 `FLATTEN` 是 **wlwl 级闭包** ⇒ `UNWRAP_OR(r, NULL)` 读形参 `r` 时移不掉 ⇒ 形参作用域结束时那一份还在 | §8.6.3（读入取走型 ⇒ 该 `ERR` 视为已消费） |

⇒ **修法**（`wlwl-value` 的 `read_binding`，**一处**定义）：`Consume` 分支除
「值本身是 `ERR`」外，再加「值是 `OK(ERR(..))` ⇒ 移除**内层**那个 `ERR`」这一支；
容器等其它形态**不动**（§8.6.3「取走型消费者取走的是它拿到的那个 `ERR` —— 容器里
还剩几个，不受它影响」）。

⚠ 语义**只留一处定义**：eval 侧原本有一份同义补偿（`consume_carried_err`），
值层补丁落地后**已删**（两处同义实现迟早分叉）。

## 3. ⚠ 未决口径（**需要业主裁决 / 与规范仓对齐**）

### 3.1 身份语义 —— 规范侧**缺口**

§8.6.5 要求「一个 `ERR` **至多**被报告一次」⇒ 需要能区分「同一个 `ERR`」与
「两个内容相同但来源不同的 `ERR`」。

而 v1.0 规范**没写**：

> **一个持有未消费 `ERR` 的容器被复制到另一个容器时**（§2.1 的值语义 ⇒ 深拷贝），
> 那个 `ERR` 是**同一个**（报一次）还是**两个**（报两次）？

一致性册 §6.1 的七条机械检查也**未覆盖**这一项。

⇒ 已登记到规范仓路线图 §3.2「未消费 `ERR` 的**身份**语义」候选（规范仓提交
`5cf187b`，**未 push**）。

⇒ **本仓的应对**：X-06 第一步**先不带身份** ⇒ 集合元素是 `Value`，身份靠
`PartialEq` 判定 ⇒ **两个内容相同但来源不同的 `ERR` 无法区分**。此局限已在
`wlwl-value` 的模块文档与相关函数处**显式写明**（不是悄悄过去）。

### 3.2 身份的实现代价

`Value::Err(` 有 **111 处**（20 个文件）⇒ 给它加身份 ⇒ 改动面就是这个量级。
且需决定「值语义复制 ⇒ 新副本是新 `ERR` 还是同一个」的语义。

⇒ **X-06 第三步**（身份）等口径定了再开。

## 4. 本批新发现的两条差异（已登记到规范仓）

实测基线 `b48a442`（实现仓 `wip0.11.4`）。⚠ 这两条**不在** X-07 的修复路径上
⇒ 在上游基线 `46b153b` 上**同样存在**。

| 编号 | 复现 | `b48a442`（本批之前） | 本批之后 |
|---|---|---|---|
| **X-16** | `LET(f, FUN((x), 0)); CALL(f, [ERR("boom")]);` | **不报** `E0103`（内建 `CALL` 的实参通道不带令牌） | **报** `E0103` ⇒ **已收敛**（见 §4.1） |
| **X-17** | `LET(a, [ERR("boom")]); a;` | **不报** `E0103`（语句值丢弃点只认 `Err` 形态的值 ⇒ 容器持有的状态在语句处被丢） | **报** `E0103` ⇒ **已收敛**（语句丢弃判据改成「集合非空」） |

⚠ **已排除的怀疑对象**（实测**均正常报出** `E0103`）：`REDUCE` / `ANY` /
`FIND` / `FOLD_RIGHT` / `POSITION` / `SORT` 等 R1 集合成员 ⇒ 「R1 成员结构上拿
不到数组令牌」这一怀疑**不成立**。

⇒ 三者（X-06 / X-16 / X-17）同源：**未消费状态挂在「绑定」上，而不是挂在
「值」上** ⇒ 值穿过容器、穿过实参通道时状态无处附着。

⚠ **X-16 为什么没跟着 X-17 一起好**：X-17 走的是**语句丢弃点**（判据一改就好），
X-16 走的是**内建 `CALL` 的实参通道** ⇒ 那条通道**根本不传令牌**
（`eval_call` 只把 `args` 交给被调方）⇒ 与本批的集合化无关，要**另开一刀**。

### 4.1 X-16 收敛：内建 `CALL` 的实参通道

**根因**：内建函数的签名是 `fn(&mut Evaluator, Vec<Value>)` ⇒ **没有**传未消费
集合的参数位 ⇒ 集合在**进入内建**时被丢掉 ⇒ 被调方的形参绑定拿不到 ⇒ 漏报。

⇒ 与 X-07 的形状不同：X-07 修的是「标准库成员回调用户函数」（成员侧那条通道由
`StdHost` 承载），X-16 修的是「语言内建 `CALL` 调任意可调用值」。

**修法**（三处，一处语义）：

1. `dispatch_call` 的**内建分支**：在 `b(self, accum)` 前后 save/replace
   `Evaluator::current_arg_unconsumed`（= 本次调用的每参集合）与
   `current_arg_tokens`（布尔投影）⇒ 内建**能读到**本次调用的集合
   （与 `invoke_std` 同一族机制）；
2. `builtin_call`：从 `current_arg_unconsumed` 取集合并**跳过第 0 个实参**
   —— 那是**被调者**自己，不是 `CALL` 的实参；
3. `call_value_with_receiver`：新增 `arg_sets` 参数 ⇒ 闭包分支传给
   `invoke_closure`（形参绑定）、原生成员分支传给 `invoke_std`（成员侧通道）。
   ⚠ receiver 注入时**同步**在集合表里插一个**空集**（否则形参绑定会**错位**
   拿到下一个实参的集合）。

**语义核对**（实测）：

| 形态 | 结果 |
|---|---|
| 被调方**消费**了那个 `ERR`（`MAP(x, FUN((e), ERR_PAYLOAD(e)))`） | **不报**（无假阳性） |
| 被调方**显式丢弃**（`LET(_, x)`，§8.6.4） | **不报** |
| 实参**没有**未消费的 `ERR` | **不报** |
| 被调方**返回**那个实参 | 状态**转给调用方** ⇒ 由调用方持有 ⇒ 在调用方处置 ⇒ 报 |
| **逐参对齐**（两个实参、只有第二个持有状态） | 集合落在**第二个**形参上 ⇒ 报 |

**契约**：`impl/crates/wlwl-eval/tests/x16_builtin_call_token_contract.rs`（9 例，
一例一 `#[test]`）；**负向验证 3 组**「改坏即红」：① 内建分派不投递集合 ⇒ 5 红；
② 集合表不跳过被调者（对齐偏移）⇒ 5 红；③ 集合到不了形参绑定 ⇒ 4 红
（原生成员那条仍绿 —— 它走成员自己的通道）。

## 5. 门禁口径

- 既有 `e0103_contract.rs` 的 27 条**期望值一个字不许动**（除非与新语义冲突 —— 那种情况**报告**给集成者，不自行改）。
- 负向验证是硬要求：每条新守卫都要能「改坏即红」。
- 本仓的差异登记项**只承诺假阴性**（漏报），**不承诺假阳性**（误报）⇒ 一个会误报的修法比不修更糟。

## 6. 本批之后的**剩余缺口**

| # | 缺口 | 影响 | 为什么没在本批修 |
|---|---|---|---|
| **G-1** | **`StdHost` 两条通道仍是 `bool`** —— `arg_tokens() -> &[bool]` / `call_with_tokens(..., Vec<bool>, ...)` | 集合**跨不过** eval ↔ std 通道 ⇒ 一个容器里**多个**未消费 `ERR` 的**逐元素归属**收不掉 | trait 在 `wlwl-value`（本批已改过一处）；本批先在边界投影 + 按实参值**重建**集合（近似，**漏报不误报**）⇒ 要彻底修得改 trait 签名（影响所有手写 `NullHost`） |
| **G-2** | **`TRY(OK(ERR(x)))`** | `TRY` 是取走型但**不**取内层那个 `ERR`（它原样返回那个 `OK`）⇒ 值层的 `Consume` 规则会把它一并消费掉 ⇒ **假阴性** | ⚠ **不是回归**（`b48a442` 的 bool 规则清空整个源令牌，更粗）⇒ 要修得让 `Consume` **知道消费者是哪个** ⇒ 与 G-1 同一刀 |
| **G-3** | **X-16**（内建 `CALL` 的实参通道不带令牌） | 漏报 | ✅ **本批已收敛**（见 §4.1） |
| **G-4** | **X-06 的身份那半步** | 见 §3.1 | **等业主裁决**（规范侧缺口） |
| **G-5** | **X-18 / X-19**（内建 `CALL_METHOD` / `NEW` 的实参通道同样不带令牌） | 漏报 | 与 X-16 **同根同形** ⇒ 但**不在 X-16 的登记范围** ⇒ 已作为新差异项登记进规范仓（见 §7）⇒ 要修就是 X-16 那三处的同款改动 ⇒ 建议**与 G-1 同批**（改 `StdHost` trait 时一并把内建侧三条通道一次收齐） |
| **G-6** | **标准库成员的实参边界把集合吞了** —— `LET(a, [ERR("boom")]); PRINT(a);` **不报**（而 `LET(b, a);` 报） | 漏报 | 洞精确地在**成员边界**：实参的集合进了成员，却没有落到任何地方（成员不建绑定、结果又不是那个值）⇒ 与 **G-1** 同根（通道承载不了集合）⇒ ⚠ **规范侧也有缺口**：§8.6.3 第三条只写了「接收位置**建立绑定**时」与「接收位置**是语句值**时」两种去向，**没写**「实参进成员时那份状态落在哪」⇒ 已登记进规范仓路线图 §3.2 |
