# wlwl agent spec v0.11 —— 给 AI agent 的工作说明

> **这份文档不是规范。**
>
> 规范性内容唯一住在 [`wlwl-spec-v0.11.md`](wlwl-spec-v0.11.md)(下称**人读规范**)与
> [`../stdlib/wlwl-stdlib-spec-v0.11.md`](../stdlib/wlwl-stdlib-spec-v0.11.md)。
> 那两册是给人看的、严肃的、权威的,改动需要裁决与登记。
>
> 这份文档是**给 AI agent 看的**:`实现机制`、`为什么这么写`、`踩过的坑`、
> `实测数据`、`待核实的假设`。这些东西**不该**进人读规范 —— 它们描述的是
> 当前实现而非语言本身,会随实现变化而陈旧,而规范的措辞不该绑在实现上。

## 0 优先级与冲突裁决

| 冲突时 | 以谁为准 |
|---|---|
| 本文档 ↔ 人读规范 / stdlib 规范 | **人读规范**。本文档错了就改本文档,不动规范 |
| 本文档 ↔ `docs/plan/deviations-v0.11.md` 台账 | 台账记「已发生的事实与裁决」;本文档记「怎么干活」。两者都改,别只改一处 |
| 本文档 ↔ 源码实测 | **实测**。本文档的每条机制描述都可能被代码推翻,推翻就改本文档 |
| 人读规范 ↔ 实测 | 走偏差流程:登记台账,不要在本文档里悄悄「修正规范」 |

**硬规则:本文档永远不得成为可观察行为的第二来源。** 当它与代码不一致时,
修代码或修本文档,**不要**去改人读规范 —— 除非走完裁决并登记。

## 1 编辑约定

- **可以随时改,不需要任何人批准。** 改完照常 `git add + commit`,commit
  message 说清改了什么、为什么。
- **不复制人读规范的条文。** 要引用就写「见人读规范 §X」,不要把条文抄过来 ——
  抄一份就会漂一份。
- **机制描述带核实日期。** 形如 `> 最后核实:2026-10-01 · commit 45cc592`。
  没有日期的机制描述一律视为可疑,用到就重新核。
- **区分「实测」与「推断」。** 写「实测」必须有可复现的观测;写「推断」就明说。
- 已知的**假阴性**教训要留档:曾因某特性默认关闭、代码路径根本没被执行,
  而把「没报错」误读成「没坏」。

## 2 文本输入与 BOM(D11-023 / D11-026)

### 2.1 现状

人读规范 §1.1 **只**对 `.wll` 源文件有明文承诺:「一个 WLWL 源文件是一个
**必须**为 UTF-8 编码(带或不带 BOM)的字节序列」。

`.wll.sig`、`wlwl.toml`、`wlwl.lock` 三类**规范未作任何规定**,本项目的
实践是「接受至多一个前导 BOM」,理由见 §2.3。这是**工具选择**,不是规范承诺。

> 最后核实:2026-10-01 · commit `45cc592`

### 2.2 规则

剥除**恰好一个**前导 `U+FEFF`(UTF-8 BOM)。第二个及之后的是普通字符,按内容
处理;文件任何位置的 `U+FEFF` 都不剥。

> 这一条**曾在人读规范里短暂存在过**(commit `45cc592`),业主 2026-10-01
> 裁决撤回:人读规范不写实现机制与工具选择,这类内容归本文档。`.wll` 那条原有
> 的承诺不受影响。

### 2.3 为什么是「恰好一个」

| 输入 | 首字符是否文法受限 | 前导 BOM 是否可能是合法内容 |
|---|---|---|
| `.wll.sig` | 是(`sig_line` 只以 `EXPORT` / `#` / 空起头) | 否 ⇒ 剥它无条件正确 |
| `wlwl.toml` | 是(TOML 文法) | 否 ⇒ 同上 |
| `wlwl.lock` | 是(必须以 `{` 起头) | 否 ⇒ 同上 |
| **`.wll`** | **否** | **可能是** |

`.wll` 那一行是关键:人读规范 §3.1 的 P3-011 **允许标识符以任意非 ASCII 字母
起头**(为中文标识符),而 `wlwl-lexer` 是**字节级**的,分不清「以 `U+FEFF`
打头的标识符」和「BOM + 标识符」。所以 `.wll` 只能约定剥一个,剩下的交给文法。

推论(已由实现确认):`LET\u{FEFF}x, 1)` 会把 `\u{FEFF}x` 认成**一个完整标识符**。
这是 P3-011 的既有后果,不是新引入的。

### 2.4 实现地图

| 入口 | 做法 |
|---|---|
| `wlwl-lexer::lex()` | 入口 `strip_prefix('\u{FEFF}')`,**在 `Lexer::new` 之前** |
| `wlwl-toml` | `pub(crate) strip_bom`,`manifest::parse` / `parse_features` / `lock::read` 三处共用 |
| `wlwl-types::parse_module_sig` | 内联一行,**不**引入 `wlwl-toml` 依赖(依赖方向是 ast/error/parser) |

两个容易写错的点:

1. **必须在 `Lexer::new` 之前剥。** `Lexer` 的 `col` 按**字节**递增,U+FEFF 占
   3 字节;晚剥会让首行所有列号偏 3。
2. **必须用 `strip_prefix` 而非 `trim_start_matches`。** 后者会静默吃掉多个。

### 2.5 为什么这些测试长这样

- **判别力靠变异验证,不是靠「测试通过」。** 每条锁测试都要对若干种错误实现
  跑一遍,确认会变红。D11-023 的四变异矩阵记在 `wlwl-lexer` 的测试块注释里。
- **`toml` 路径上「剥一个 vs 剥全部」不可观测** —— `toml` 把多余的 U+FEFF 当
  空白。该路径**不能**写假装能判别的断言;真能判别的是 `lock`(serde_json 严格)
  与 `sig`(自家解析器)。这条事实已写进 `manifest.rs` 的测试注记。
- **不在仓库里提交带 BOM 的夹具。** U+FEFF 在 code review 里是**不可见字节**;
  且 `.gitattributes` 的 `*.wll text eol=lf` 会规范化提交的 CRLF。
  probe 驱动器因此有 `bom` 键:BOM 注入**暂存副本**,夹具字节保持干净。
- **换行等价性(§1.1 另一条条款)没做成 probe,走 lexer 单测** —— 同一个
  `.gitattributes` 原因:提交的 CRLF 夹具会被规范化,测试会静默失效。

### 2.6 钉住点

| 层 | 位置 |
|---|---|
| 规范级 | probe `P_d11_026_bom_source_and_manifest_load` / `P_d11_026_bom_module_signature_loads` |
| crate 级 | `wlwl-lexer`(6 条 BOM + 2 条换行)、`wlwl-toml`(8 条)、`wlwl-types`(3 条) |
| 台账 | D11-023 / D11-026 |

## 3 层归属速查(ADR-0021 §0.1)

| 层 | 判据 | 典型 |
|---|---|---|
| **R0** | 语言核心语义,或与编译器强耦合 | 词法/语法/求值器、类型检查 |
| **R2** | 触系统调用 / OS 资源 / 进程·网络·时间·随机,或需复用成熟 crate | `std.io` `std.fs` `std.json` `std.ai` `std.agent` |
| **R1** | 其余:不触系统调用且非性能敏感 | `std.collection` `std.str` `std.math` `std.test` |

常见误判:

- **「纯字符串处理所以一定 R1」** —— 先过性能关。一个 16,000 元素的 `PUSH`
  累积在 R1 里要 3.9 s(D11-012 实测),那就该下沉 R2。判据是**实测**不是直觉。
- **「R2 也可以调 R1」** —— 不行,R2 默认禁止调 R1(确需时走白名单并登记偏差)。
  R1 调 R0/R2 则是允许的。

## 4 解释器性能实测档案

release 档、单线程、`wlwl` 二进制直跑。**这些数字会随实现变,用到先复测。**

### 4.1 建数组是二次的(D11-012 同源)

wlwl 数组不可变,`PUSH` 每次复制整个数组。

| 元素数 | 耗时 |
|---|---|
| 2,000 | 108 ms |
| 8,000 | 751 ms |
| 16,000 | 3,859 ms |

⇒ **R1 代码里不要用大数组做累积。**

### 4.2 建字符串是二次的,但真实规模无感

| 形态 | 节点数 | 产物 | 耗时 |
|---|---|---|---|
| 平铺追加 `s = s + x` | 5,000 | 134 KB | 164 ms |
| 平铺追加 | 20,000 | 549 KB | 1,434 ms |
| 平铺追加 | 50,000 | 1.39 MB | 22,448 ms |
| 递归二分构造 | 50,000 | 1.39 MB | 4,239 ms |

⇒ 1–5k 节点的真实页面两种写法都在 200 ms 内。**性能对代码生成类任务不是瓶颈**,
设计约束只有「别用大数组」这一条。逐码点循环约 **2 µs/码点**。

> 最后核实:2026-10-01 · commit `9280946`

## 5 已知的坑与未决项

- **BOM 之前只修了 `.wll` 一处**就发过一次(D11-023),另外三处拖到 D11-026。
  教训:发现一类缺陷时,**先把同一类的所有落点列出来**,再决定本轮做几个。
- **`.wll.sig` 仅在 `gradual_typing` 开启时才被读取**。默认档下测「签名能不能
  解析」会得到假阴性(见本文档 §1 的假阴性约定)。
- **P3-011 与 BOM 冲突**:不要试图在标识符扫描器里过滤 U+FEFF(§2.3)。
- **`git status` 的「已修改」清单是下界,不是全集**(stat 缓存会掩盖反向的
  不一致)。行尾问题一律用 `git ls-files --eol` 作权威判据,别信 `git status`。
- **`Get-Content | Set-Content` 改源码会写 BOM**(PowerShell 5.1)且可能丢行。
  用文件编辑工具,别用 shell 文本管道。已因此损坏过一次 `wlwl-types/src/sig.rs`
  (掉了 395 行),从 git 恢复后重做。
- **规范条款可能没有钉住它的机制。** §1.1 的换行等价性自项目起就没有任何测试
  覆盖,直到 D11-026 才补上(实测三种换行本来就都正常)。做「规范说了 → 实现
  做了」的修复时,顺手确认这条有没有对应的强制机制。
