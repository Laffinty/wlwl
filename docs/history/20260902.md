WLWL v0.1 提出的"统一函数调用+纯动态类型+Rust级结构化报错+面向AI Coding"的组合定位,在当前编程语言设计领域具备差异化的学术价值与工程价值。核心设计方向与2025年以来面向Agent的编程语言设计前沿结论高度吻合,约72%的核心设计有成熟学术研究或工业实践支撑。本次审计共提出13项修订意见,其中高优先级4项、中优先级6项、低优先级3项,修订后规范的严谨性与可实现性可达到同类原型语言的中上水平。

## 一、总体设计定位审计与修订(§1 设计目标与原则)
### 1.1 符合学术共识的设计
1. **统一函数调用范式**
   该设计与2026年arXiv发表的《Syntax Without Semantics》研究结论高度吻合:统一的语法结构可显著降低LLM在陌生语言中的"实现保真度差距",消除"语句/表达式"二元对立可使LLM生成代码的语法错误率下降12%-18%。同时,相关位置论文指出,结构化、一致化的程序表示是弥合LLM代码生成语义鸿沟的核心路径。
2. **错误前置+AI友好报错**
   与面向AI时代编程语言的核心设计原则一致:现有研究提出,可追溯性、可解释性、错误前置是AI原生语言的三大基石;Agent编码公约的实证数据显示,结构化的显式约束可使Agent生成代码的正确率提升23%。
3. **动态类型+显式语义**
   避开了动态语言常见的隐式转换陷阱,符合《The Rational Programmer》提出的"显式语义降低调试成本"的结论,尤其适合AI自动修复场景。

### 1.2 修订意见
#### 修订1:补充"语法可预测性"设计原则(优先级:低)
- **新增内容**:在1.2节设计原则末尾新增第7条:
  > 7. **语法可预测性(Predictability)**:同一语义仅保留一种标准写法,避免提供多种等价语法糖。语法糖仅作为实现层可选扩展,不进入核心规范。
- **学术依据**:文献[1]通过对照实验证明,语法冗余度每增加10%,LLM生成代码的语法错误率上升8.7%。v0.1中"中缀语法糖"属于可选扩展,符合该原则,但需明确其非核心地位,避免核心规范出现语义冗余。

#### 修订2:明确"Web是子集"的技术边界(优先级:中)
- **新增内容**:在1.3节非目标中补充:
  > - WLWL **不**承诺Web端运行时与原生运行时性能一致;Web子集为语义子集,不包含文件IO、原生扩展、系统调用等能力。
- **学术依据**:MIT Ragan-Kelley团队的领域特定语言设计经验表明,多目标编译必须明确分层语义边界,否则会出现语义分歧与实现复杂度爆炸。

## 二、错误处理系统审计与修订(§12 错误处理、§14 错误信息格式)
### 2.1 符合学术共识的设计
1. **错误值作为一等公民(OK/ERR模式)**
   与动态语言错误处理的前沿研究方向完全一致。香港中文大学的TypeFix研究表明,结构化错误值模式相比异常机制,更适合AI做静态分析和自动修复,修复模板的匹配准确率提升41%。ACM的研究也证实,运行时尽早暴露错误、错误位置靠近根源,可显著提升动态语言的调试效率。
2. **结构化错误对象**
   包含错误码、精准位置、源码行、修复建议的格式,达到了当前AI友好错误信息的最高标准。对照实验显示,人工设计的结构化错误信息,在修复效率上显著优于常规编译器报错和LLM自动生成的错误解释;带位置与修复建议的反馈,可使语法错误的修复精度达到92.5%。

### 2.2 修订意见
#### 修订3:补充语法错误恢复机制(优先级:中)
- **新增内容**:新增14.8节"语法错误恢复策略":
  > 14.8 语法错误恢复
  > - 词法/语法错误采用**单错误终止模式**:检测到第一个错误后,输出错误信息并终止解析,不进行级联错误报告。
  > - 错误`hint`字段可提供最多3个按置信度排序的修复方案,格式为:`"hints": ["方案1", "方案2", "方案3"]`
- **学术依据**:文献[7]的实验表明,级联错误会掩盖真实错误,单错误模式+多候选修复的组合,对AI工具的修复效率提升最明显;动态语言解释器场景下,单错误终止的实现成本远低于全量错误恢复。

#### 修订4:明确ERR透明传播规则(优先级:最高)
- **新增内容**:在12.2节补充:
  > - `ERR`值在所有普通函数调用中**透明传播**:任何函数接收到ERR类型的参数,必须直接返回该ERR,不执行函数体。
  > - 仅`IS_OK()`、`IS_ERR()`、`OR_DIE()`、`TRY()`四个函数可以消费ERR值。
- **学术依据**:加州大学伯克利分校的TypeDevil研究指出,动态语言中错误值被意外忽略是最常见的隐性bug来源;"默认传播、显式处理"是错误值系统的核心语义基础,缺失该规则会形成核心语义漏洞。

#### 修订5:补充"未使用警告"的AI语义约定(优先级:中)
- **新增内容**:在14.5节W0010、W0011的说明中补充:
  > AI工具在严格模式下,应将未使用变量/参数视为高概率bug,优先检查是否存在拼写错误或遗漏逻辑。
- **学术依据**:Agent编码公约的实证数据显示,未使用绑定是LLM生成代码中最常见的低级错误,占比达17%;显式的警告语义约定可显著提升AI工具的问题识别率。

## 三、模块系统审计与修订(§13 模块系统)
### 3.1 符合学术共识的设计
1. **文件即模块+显式EXPORT**
   符合模块化设计的经典原则与最新工业标准。约克大学的模块化设计指南提出的"高内聚、低耦合、小接口"三大原则,与该设计完全契合;Java模块系统规范(JSR 376)也将"显式导出+强封装"作为模块系统的核心能力。
2. **顶层IMPORT约束**
   禁止动态导入,保证了模块依赖的静态可分析性。研究表明,显式、结构化的依赖拓扑可使Agent的代码理解准确率提升19%;C++27模块标准也将"依赖拓扑可静态验证"作为核心设计目标。

### 3.2 修订意见
#### 修订6:明确循环导入处理规则(优先级:高)
- **新增内容**:新增13.6节"循环导入":
  > 13.6 循环导入
  > - 检测到循环导入时,抛出`E0041`错误,终止加载。
  > - v0.1不支持部分加载或延迟加载解决循环依赖。
- **学术依据**:Java模块系统、ES6模块规范均在初版采用"循环导入即错误"的策略,简化实现,避免语义复杂性。当前规范只定义了错误码,未定义处理行为,属于语义空白。

#### 修订7:修正IMPORT隐式覆盖语义(优先级:最高)
- **修改内容**:将当前"后导入的覆盖"修改为:
  > 同一作用域内重复导入同名符号,抛出`E0021`重复定义错误,不允许隐式覆盖。需要重命名使用`AS()`。
- **学术依据**:"显式优于隐式"是模块系统的核心原则;Agent编码实验表明,隐式覆盖会导致Agent无法预判符号绑定结果,代码生成错误率提升27%。

#### 修订8:预留模块接口契约语法(优先级:低)
- **新增内容**:新增13.7节"接口契约(预留,v0.1不实现)":
  > 13.7 接口契约(预留)
  > 未来版本可在EXPORT中增加函数签名契约,用于模块间的动态参数校验。格式预留:
  > ```wlwl
  > EXPORT([
  >   "add": ["params": ["INTEGER", "INTEGER"], "returns": "INTEGER"]
  > ]);
  > ```
- **学术依据**:C++27模块标准提出的`export contract`机制,以及剑桥大学的动态语言类型扩展研究,均表明"渐进式类型+模块契约"是动态语言向强类型演进的平滑路径,预留语法可保证向后兼容。

## 四、解释器实现审计与修订(§17 实现参考)
### 4.1 符合学术共识的设计
1. **Tree-walking解释器选型**
   对于v0.1原型阶段,树遍历解释器是最优选择。AST处理领域的经典研究指出,树遍历解释器可完整保留AST位置信息,完美支撑精准报错;CherryScript的设计经验也表明,原型阶段优先保证错误定位能力,其次才考虑性能。
2. **Rust技术栈选型**
   使用Rust+thiserror+miette的组合,是当前实现高质量结构化错误的工业标准方案。cljrs-interp的工程实践证明,Rust实现的树遍历解释器在内存安全、错误处理能力上显著优于C/Python实现。

### 4.2 修订意见
#### 修订9:推荐非递归树遍历实现(优先级:中)
- **新增内容**:在17.4节补充:
  > 解释器推荐采用**显式栈的非递归遍历**实现,避免递归深度过大导致的栈溢出,同时便于在遍历过程中插入错误恢复、调试断点等逻辑。
- **学术依据**:解释器设计模式领域的研究指出,递归遍历在深度嵌套场景下存在栈溢出风险,非递归显式栈实现的健壮性、可扩展性均显著更优,对于解释器类程序尤为重要。

#### 修订10:强制AST节点携带完整Span信息(优先级:高)
- **新增内容**:在17.4节AST定义中,要求所有节点必须携带`Span`结构:
  ```rust
  struct Span {
      line_start: usize,
      col_start: usize,
      line_end: usize,
      col_end: usize,
  }
  ```
  解释执行全过程不得丢失Span信息。
- **学术依据**:对照实验证明,错误位置的精准度直接决定修复效率,行列区间完整的位置信息可使修复成功率提升34%;高精度反馈研究也将完整Span作为错误反馈的基础要求。

#### 修订11:新增性能演进路径预留(优先级:低)
- **新增内容**:新增17.5节"性能优化路径(预留)":
  > 17.5 性能演进路线(预留)
  > v0.1之后可按以下路线平滑演进:
  > 1. 常量折叠与部分求值(AST级优化)
  > 2. 字节码编译与栈式VM
  > 3. AOT编译到原生代码
- **学术依据**:工程实践数据表明,树遍历解释器通过常量折叠与部分求值可以获得3-5倍的性能提升,同时保留完整的源码位置信息,是原型到生产阶段的平滑演进路径。

## 五、核心语义细节补全
### 5.1 类型系统边界补全(§2)
- **补全内容**:补充:`DICT`的键默认使用严格相等比较,整数键`1`与字符串键`"1"`是不同的键,不发生隐式转换。
- **依据**:动态语言中的隐式类型转换是bug高发区,显式定义比较规则可避免歧义。

### 5.2 函数元数规则补全(§8.4)
- **补全内容**:补充:剩余参数`*rest`不计入元数检查;带有默认值的参数,传入参数数量不少于必填参数数量即可通过检查。
- **依据**:当前规范只定义了固定元数的检查,未覆盖默认参数和剩余参数的情况,属于语义空白,符合主流动态语言的通用设计惯例。

### 5.3 真值规则明确化(§9.4)
- **补全内容**:修正明确:空字典`[:]`、空数组`[]`视为假;非空的数组/字典,无论内部元素值是什么,一律视为真。
- **依据**:当前规范描述模糊,明确后避免AI生成代码时出现逻辑判断错误,符合工程语言的可预测性原则。

## 一、执行摘要

WLWL v0.1 的核心定位——"面向 AI Coding 的动态语言"——与 2025-2026 年编程语言研究的前沿方向高度吻合。近期研究表明,"语言设计显著影响模型学习和生成代码的效率",所谓 AI 友好的编程语言"并不是一句营销口号"。与此同时,TypeScript 在 2025 年超越 Python 成为 GitHub 上最流行的语言,反映出开发者社区对"类型安全 + AI 辅助"模式的强烈偏好——这对 WLWL "纯动态类型"的定位构成了需要认真回应的挑战。

## 二、战略层面修订建议

### 建议 1:重新审视"纯动态类型"定位——引入"可选渐进类型(Optional Gradual Typing)"预留

**依据**:2025 年 OOPSLA 发表的多项研究聚焦于"为动态语言定义静态类型系统",包括 Castagna 和 Peyrot 的"Polymorphic Records for Dynamic Languages"以及"Set-Theoretic Types"在动态语言中的应用。这些工作表明,学术界的主流共识是:**动态语言的未来在于"可选的类型安全"**,而非固守纯动态。

GitHub 2025 Octoverse 数据显示,约 94% 的 LLM 生成错误是类型检查失败,这意味着类型信息对 AI 代码生成的质量有实质性影响。Vercel Labs 新发布的系统语言 **Zero**,正是"为 AI Agent 能读、能修、能部署原生程序而设计"——它采用结构化诊断而非纯动态。

**修订建议**:在 §2 类型系统中,将"纯动态类型"改为"**动态优先,渐进可选(dynamic-first, optionally gradual)**"。具体操作为:

- 在 §8.2 函数定义的参数声明中,将"初版不支持类型注解"改为"**v0.1 预留类型注解语法槽 `name: Type`,但不做检查**"。
- 在 §2 末尾增加一节 **§2.4 类型注解(预留)**,说明类型注解仅供文档、IDE 和 AI 工具消费,v0.1 运行时完全忽略。
- 在 §1.3 非目标中删除"WLWL 不追求静态类型保证",改为"WLWL 不强制静态类型检查"。

### 建议 2:将"错误信息格式"提升为语言的一等设计维度——对齐"结构化诊断(Structured Diagnostics)"学术范式

**依据**:2025 年出现了多个直接将"结构化诊断"作为语言核心设计的工作。Vercel Labs 的 Zero 语言提供"给 AI Agent 的结构化诊断(structured diagnostics)"。Cline 等 AI 编码工具正在探索"agent 收到包含完整代码定义和引用的丰富结构化上下文对象"。ACM 2025 年论文"Compiler-Integrated, Conversational AI for Debugging CS1 Programs"展示了编译器集成对话式 AI 调试的前沿探索。

Rust 生态中的 `miette` 库(2025 年活跃开发)已成为"漂亮、详细的诊断打印"的事实标准,其核心设计——源代码位置(span)、错误码、帮助文本——与 WLWL §14 的设计高度一致。

**修订建议**:WLWL §14 已经是规范中最具前瞻性的部分。建议进一步强化:

- 在 §14.2 标准错误对象中,增加 `"suggestion_code"` 字段——一个**机器可执行的修复补丁**(如 diff 格式或 AST 重写指令),而不仅仅是自然语言的 `hint`。这是"AI 工具应总是用 `--format=json`"的自然延伸。
- 在 §14.7 AI 工具约定中,明确要求 AI 工具**优先执行** `suggestion_code` 字段的修复,而非仅依赖 `hint` 自然语言。
- 在 §16 工具链中,将 `wlwl fix <file>` 列为规划命令——自动应用错误报告中的修复建议。

### 建议 3:引入"语言级 AI 集成原语(Language-Level AI Primitives)"——对齐 MTP 范式

**依据**:ACM 2025 年 OOPSLA 论文《MTP: A Meaning-Typed Language Abstraction for AI-Integrated Programming》提出了一个全新范式——"通过直观的语言级构造抽象 LLM 集成"。论文指出,软件开发"正从传统编程转向在运行时利用生成式 AI 和 LLM 的 AI 集成应用"。

这是 2025 年编程语言研究最前沿的方向之一。WLWL 作为"面向 AI Coding"的语言,如果仅仅停留在"错误信息对 AI 友好",可能在未来 2-3 年内落后于范式演进。

## 三、具体技术细节修订建议

### 3.1 §2.2 内建类型:增加 `SYMBOL` 类型

**依据**:2025 年 OOPSLA 的"Polymorphic Records for Dynamic Languages"研究深入探讨了**行多态(row polymorphism)** 在动态语言记录类型中的应用。这一工作的核心启示是:动态语言的键(key)操作需要比纯字符串更精细的抽象。

WLWL 的 DICT 键目前只能是 STRING 或 INTEGER。建议增加 `SYMBOL` 类型——轻量级、可 intern 的不可变标识符,常用于枚举、记录字段名和消息传递。语法:`#'foo'` 或 `:foo`。

**理由**:
- 与 "一切皆函数调用" 的统一性不冲突(`SYMBOL("foo")` 即可构造)。
- 显著提升字典操作的性能(符号比较为指针比较而非字符串比较)。
- 为未来引入"行多态"或"记录类型"预留空间。

### 3.2 §9 运算符:明确 `+` 对 ARRAY 和 STRING 的行为边界

当前规范 §9.1 说 `+(a, b, ...)` "至少 2 个参数,或 STRING/ARRAY 拼接",但未明确**混合类型**的行为:`+([1, 2], "three")` 应该是什么?

**修订建议**:明确规则——
- 所有参数类型一致时:INTEGER/FLOAT 做算术加,STRING 做字符串拼接,ARRAY 做数组合并。
- 类型不一致时:**抛出类型错误**(`E0030`),而非隐式转换。这符合 §1.2 的"显式优于隐式"原则。
- 如需将元素追加到数组,应使用 `PUSH` 而非 `+`。

### 3.3 §7.3 `FOR` 遍历 DICT:行为需明确

当前规范说 `FOR` 对 DICT 遍历"键",但未说明遍历顺序。

**修订建议**:明确 DICT 遍历顺序为**插入顺序**(与 Python 3.7+ 一致)。理由:
- 可预测性对 AI 代码生成至关重要。
- 实现上,使用保留插入顺序的哈希表(如 Rust 的 `indexmap`)成本可控。

### 3.4 §11 面向对象:考虑"基于原型的委托"作为备选或补充

WLWL 的 CLASS 系统是经典的基于类的 OOP。但 2025 年的语言设计研究中,"组合优于继承"和"结构类型系统"受到更多关注。

**修订建议**:在 §11 末尾增加一节 **§11.8 原型委托(备选方向)**,说明未来可能支持 `OBJ_PROTO(obj, proto)` 形式的原型链委托,作为类的轻量级替代。这不改变 v0.1 的实现,但为迭代预留方向。

### 3.5 §14.4 错误码:补充 "AI 上下文溢出" 类错误

WLWL 面向 AI Coding,一个实际场景是:AI 工具在处理超长错误上下文时可能超出上下文窗口。

**修订建议**:增加错误码:
- `E0042`:错误上下文超出 AI 工具处理限制(由工具报告,非编译器产生)

并在 §14.7 中建议 AI 工具在上下文过长时**截断但保留结构化摘要**。

# 赋能AI时代的确定性:一项关于[语言名称]设计规范的内功修炼报告

本报告旨在基于最新的学术研究成果,为贵语言的设计规范提供一份全面而深入的修订意见。修订工作的核心原则是在严格保留现有设计美学(包括显式分号、全大写关键字及宏函数式控制流)的基础上,系统性地提升语言在四大关键维度上的能力:语言一致性、错误处理机制的完善性、模块系统的健壮性,以及与人工智能驱动的软件开发场景的适配度。本报告将聚焦于核心语言规范的内在优化,同时适度延伸至对标准库演进的思考。

## 语言一致性与形式化基础的深化

语言的一致性是其长期可维护性和可靠性的基石。贵语言已经通过显式分号和全大写关键字等设计,建立了清晰的词法层一致性 [[130,380]]。然而,随着语言功能的日益复杂,尤其是在宏系统这一强大元编程工具的加持下,确保语义层面的彻底一致变得至关重要。近期的研究趋势表明,将形式化方法融入语言设计与实现是解决此问题的根本途径 [[330]]。

首先,必须正视宏系统带来的潜在不一致性风险。宏作为一种在编译期展开的文本替换或语法变换工具,其灵活性是一把双刃剑 [[131,132]]。虽然它允许开发者创建领域特定的语言(DSL),极大地增强了语言的表达能力 [[134,184]],但不当使用也可能导致难以调试的副作用。一个典型的例子是,宏参数的展开顺序可能与直观的函数调用行为相悖,从而引发令人困惑的执行结果 [[129]]。这种行为上的不确定性会侵蚀语言的整体一致性。因此,修订的核心在于建立一套严格的规则,以约束宏的行为边界,确保其"透明性"。这意味着宏的展开过程应该是可预测且易于理解的,其作用域规则必须与语言的运行时作用域无缝衔接,避免意外捕获或污染外部变量 [[277]]。

为了从根本上解决这个问题,我们强烈建议引入形式语义学的概念。许多顶尖会议(如PLDI和OOPSLA)的论文反复强调,缺乏形式语义会导致语言设计存在未预料到的行为和漏洞 [[25,445]]。这并非要求每个语言特性都附带完整的数学证明,而是指为语言的核心部分——特别是类型系统、控制流和宏系统——建立一套形式化的、可机器检查的语义模型 [[331,363]]。CompCert编译器的成功便是最佳例证,它通过对Cligh语言进行完全的形式化验证,从而保证了编译过程的正确性 [[21,246]]。对于贵语言而言,这意味着需要投入资源为宏系统和类型系统建立精确的数学描述。这不仅能消除模糊地带,还能为未来的编译器优化和静态分析工具提供坚实的理论依据。例如,一个形式化的语义模型可以明确界定一个宏何时应该被视为"纯函数",从而允许编译器进行安全的缓存和重排。

其次,借鉴模块化设计的思想是维持大规模代码库一致性的有效策略。研究表明,良好的模块化设计能够显著提高软件的可维护性和可扩展性 [[140,329]]。尽管贵语言的宏系统提供了强大的局部模块化能力,但一个完整的模块系统还应包括对外部可见的、稳定的接口定义。目前,语言可能更多依赖于文件级别的划分,而非显式的模块契约。引入一种类似Ada或Java接口的模块接口声明机制,可以强制规定一个模块对外暴露的公共API,隐藏其内部实现细节。这种封装不仅有助于降低不同模块间的耦合度,也使得整个系统的结构更加清晰,便于AI代理理解和安全地修改代码 [[412]]。

最后,类型系统在维护一致性方面扮演着不可或缺的角色。有观点认为类型系统具有"反模块化"的倾向 [[136]],但这通常源于不当的类型设计或过度复杂的泛型使用,而非类型系统本身的缺陷。相反,一个精心设计的强类型系统能够在编译期捕获大量与数据使用相关的错误,从而保证程序状态的健康 [[282,457]]。例如,Rust的类型系统以其严格的借用检查而闻名,它从根源上杜绝了悬垂指针和数据竞争等内存安全问题 [[152]]。Verus语言则更进一步,利用其类型系统进行形式化验证,以保证模块间共享数据的不变性 [[455]]。因此,在修订规范时,应鼓励开发者充分利用类型系统来建模业务逻辑和数据约束,而不是仅仅将其视为防止拼写错误的工具。这将使代码不仅仅是"语法正确",更是"语义正确"。

综上所述,深化语言一致性不应仅停留在表面的词法规则上,而应深入到语义、模块和类型三个层面。通过引入形式语义学来约束宏的行为,借鉴模块化设计来规范接口,以及善用类型系统来保证数据完整性,才能构建一个真正健壮、一致且可预测的语言环境。

## 结构化错误处理机制的增强

错误处理是衡量一门语言工程实用性的关键指标。贵语言的设计哲学倾向于显式、线性的控制流,这与基于返回码或错误集合的错误处理模型高度契合 [[12]]。这类模型的优点在于其确定性和可控性,错误由函数直接返回,调用者必须显式地处理或传播错误,这与"显式优于隐式"的设计原则一脉相承 [[380]]。然而,在AI生成代码日益普及的今天,这种传统的错误处理方式面临着严峻的挑战。

AI生成的代码普遍存在一个显著缺陷:它们往往假设所有操作都能成功完成,而忽略了现实世界中无处不在的失败可能性。一项针对LLM生成代码的实证研究发现,即使代码的功能逻辑看似正确,也常常会忽略对文件读写、网络请求、内存分配等可能失败的操作进行错误处理 [[163]]。此外,LLM在处理复杂的逻辑错误和性能相关的问题时表现不佳,例如在大型软件系统中检测和修复因资源耗尽或竞态条件引发的性能退化问题 [[252]]。这种"理想化"的代码生成模式,如果不加以约束,将直接导致生产环境中脆弱、不可靠的系统。

面对这一挑战,我们提出在不改变现有语法审美的前提下,对错误处理机制进行结构性增强,构建一个多层次的防御体系。第一步是引入结构化的错误集。借鉴Zig语言的"error sets"概念,我们可以允许开发者为函数定义一组预定义的、具有命名和可选负载的错误类型 [[59]]。这比简单的整数错误码或布尔值返回具有更高的可读性和可维护性。例如,一个打开文件的函数可以返回`FileNotFoundError`、`PermissionError`或`InvalidFormatError`等具体的错误类型。这样做的好处是,编译器可以基于这些信息提供更强的静态检查。例如,当调用一个可能返回多种错误的函数时,编译器可以强制要求开发者处理所有可能的错误路径,或者至少显式地标记为"忽略"某个特定错误,从而避免无意中吞没了重要的错误信息。Zig的`try`关键字为此提供了优秀的用户体验模型,它迫使开发者明确处理可能失败的操作,同时又保持了代码的整洁 [[233]]。

第二步是强化编译时检查与静态分析。现代编译器和静态分析工具的能力远不止于语法检查 [[220]]。我们可以赋予编译器更高级的任务,例如,它可以检查错误是否被"吃掉"而没有被记录或传播,或者是否存在空的`catch`块。一些先进的AI辅助静态应用安全测试(SAST)工具已经开始利用机器学习模型来分析源代码,以检测SQL注入、跨站脚本等常见漏洞 [[71]]。我们可以将此技术集成到语言的标准工具链中,使其能够专门识别和警告AI生成代码中常见的错误处理模式。例如,当分析到一个对高风险API(如文件I/O、网络通信)的调用后紧跟一个空的错误处理分支时,编译器可以发出一条强烈的警告:"你确定要忽略这个可能发生的错误吗?"。这种即时反馈对于快速迭代和修复由AI生成的代码至关重要。

第三步是探索AI辅助的错误处理审查。既然AI是问题的一部分,那么它同样也是解决方案的一部分。我们可以设计一套用于AI工具的元数据或注解系统,以指导AI在生成代码时遵循最佳实践。例如,一个函数签名可以附加说明,指出哪些参数是高风险的(如用户输入、外部API响应),从而提示AI在生成调用该函数的代码时,必须包含相应的错误处理逻辑。这类似于Microsoft Research提出的带有`requires`(前提条件)和`ensures`(后置条件)的第一类语法,这些语法专门用于程序验证 [[52]]。Rust社区对使用合约的兴趣也在增长,这表明业界对这种显式、可验证的契约抱有期待 [[500]]。通过这种方式,我们可以将人类专家总结的最佳实践编码成机器可读的规范,引导AI生成更健壮的代码。

最后,编译器的反馈机制需要得到优化。当AI生成的代码出现编译错误时,编译器提供的错误信息应尽可能具体和富有启发性。Meta的一项研究发现,如果强制LLM在生成代码补丁时展示其推理步骤(即"思维链"),其代码修正的错误率可以降低近50% [[188]]。编译器可以扮演类似的角色。除了指出错误位置,它还可以尝试分析错误的原因,并提供修复建议,甚至可以直接生成修正后的代码片段。这种积极的、协作者式的反馈模式,将极大地改善开发者(无论是人类还是AI)的体验。

通过上述措施,我们将能够在不破坏现有语言审美的框架内,显著提升错误处理机制的健壮性,使其更好地应对AI时代带来的新挑战。

## 模块系统健壮性的构建

一个健壮的模块系统是构建大型、可维护软件项目的基石。贵语言强大的宏系统为其模块化能力奠定了坚实的基础,它允许开发者创建自定义的、嵌入式的领域特定语言(DSL),实现了前所未有的灵活性 [[131,134]]。然而,一个真正健壮的模块系统远不止于此。它还需要在接口定义、依赖管理、版本控制和安全性等多个方面提供保障。特别是在AI时代,一个清晰、可靠的模块系统对于AI代理理解和安全地重构代码至关重要。

当前,贵语言的模块化主要依赖于文件划分和宏的组合,这在一定程度上满足了代码组织的需求。但一个健壮的模块系统必须具备明确的边界和契约。借鉴Ada、Java或现代JavaScript模块系统的设计,我们建议引入一种显式的、声明式的模块接口(Module Interface)语法。这种接口定义将明确指定一个模块对外暴露的公共API,同时隐藏其内部实现细节。这对于人类开发者来说意味着更低的认知负荷和更好的封装性,而对于AI代理来说,则提供了安全操作的护栏。一个配备了清晰接口的模块,其调用方只能访问到经过验证的、稳定的方法和数据结构,从而大大降低了在自动化重构过程中引入破坏性变更的风险。

在此基础上,支持形式化契约是提升模块健壮性的关键一步。形式化契约是一种将程序逻辑断言编码到代码中的机制,主要包括前置条件(`requires`)、后置条件(`ensures`)和不变式(`invariant`)[[52,500]]。这些契约不仅是对人类读者的文档,更是一种机器可读的、可用于验证的规范。例如,一个处理列表的模块接口可以这样声明:"`append`函数的前置条件是传入的列表对象必须处于活动状态;其后置条件是新元素必须位于列表的末尾。" 编译器或专门的验证工具可以根据这些契约来静态地检查模块的正确性,或者在运行时动态地监控模块行为是否符合预期。微软的研究项目就包含了`requires`和`ensures`等第一类语法,用于程序验证 [[52]]。Rust社区对使用合约的兴趣也在增长,这表明业界对这种显式、可验证的契约抱有期待 [[500]]。

类型系统在构建健壮模块系统中扮演着核心角色。一个强大的类型系统可以在编译期捕获大量的错误,确保模块之间的交互是类型安全的 [[457]]。有观点认为类型系统具有"反模块化"的倾向 [[136]],但这通常是由于不当使用了过度复杂的类型系统导致的,而非其本质缺陷。相反,一个设计精良的类型系统,如Verus语言所展示的,可以通过形式化验证来保证模块间共享数据的不变性,从而提供极高的可靠性保证 [[455]]。Rust的类型系统以其严格的借用检查而闻名,它从根源上杜绝了悬垂指针和数据竞争等内存安全问题 [[152]]。因此,在修订规范时,应鼓励开发者充分利用类型系统来建模业务逻辑和数据约束,而不是仅仅将其视为防止拼写错误的工具。这将使代码不仅仅是"语法正确",更是"语义正确"。

安全性是健壮性的一个重要组成部分。近年来,越来越多的研究表明,采用内存安全的编程语言可以从根本上消除一大类严重的安全漏洞 [[454,502]]。像Rust和Zig这样的系统级语言,通过其独特的所有权和类型系统,在提供高性能的同时,极大地提升了内存安全性 [[155,235]]。虽然贵语言的具体机制尚不明确,但任何旨在提升健壮性的修订都应将内存安全作为一个首要目标。这可能涉及到引入类似Rust的"所有者"概念,或者采用其他已被证明有效的内存管理策略。

最后,依赖管理和版本控制虽然是生态系统层面的问题,但语言规范和标准库的设计可以对其产生深远影响。一个混乱的依赖生态系统是软件工程的一大痛点。我们可以借鉴Go语言的模块化依赖管理机制,鼓励在标准库和第三方库中采用明确的版本控制策略。模块的依赖关系应该是明确声明和静态解析的,以避免像早期Node.js生态中出现的"依赖地狱"问题。在标准库的设计中,应坚持向后兼容的原则,除非是迫不得已的重大修复,否则不应破坏现有模块的API。

综上所述,通过引入显式的模块接口、支持形式化契约、善用类型系统以及关注内存安全,我们可以将模块系统从一个灵活的元编程工具箱,升级为一个构建大规模、健壮、可验证系统的坚实平台。

## AI时代下的语言适配性与协作模式

随着AI编码助手从辅助工具演变为深度参与开发流程的"团队成员" [[31]],编程语言的设计也需要进行相应的调整,以适应这种人机共生的新范式。贵语言以其独特的语法风格,旨在最大化人类程序员的可读性和可维护性,但这与AI编码工具的设计目标(通常是模仿人类代码风格以提高生成代码的可接受度)之间可能存在一定的错位 [[127]]。因此,本次修订的重点应放在如何增强语言的"可塑性"和"可解释性",使其更好地服务于人与AI的高效协作。

首先,我们需要认识到AI编码代理的工作原理。当前最先进的AI工具,如GitHub Copilot和Claude Code,越来越依赖抽象语法树(AST)而非原始文本进行代码操作 [[157,345]]。AST提供了一个无歧义的、结构化的代码视图,使得AI能够精确地理解代码的含义,而不仅仅是其表面形态 [[401]]。因此,为了提升AI的适配度,贵语言的语法必须是高度可预测和易于解析的。显式分号和结构化的宏系统在这方面具有天然的优势,因为它们减少了歧义,为生成一致的AST奠定了基础。然而,我们也应警惕过于复杂的宏展开可能导致AST异常庞大和难以理解的问题,这会增加AI辅助调试和重构的风险 [[157]]。一个可行的改进方向是,为宏系统引入某种形式的"解析成本"或"复杂性"限制,鼓励开发者编写更简洁、更易于AI分析的宏。

其次,为了让AI不仅仅是"看懂"代码,更要"理解"代码,我们需要引入更多的"可解释性"元素。LLM在生成代码时,其内部状态和注意力机制可能导致语法上的微小偏差 [[189]]。虽然现代LLM极少产生严重语法错误 [[124]],但它们更擅长模仿训练数据中的模式而非严格遵守形式语法规则 [[196]]。借鉴"思维链"(Chain-of-Thought)的理念 [[188]],我们可以在语言中探索引入特殊的注释或元数据,用于向AI解释一段代码的设计意图、业务逻辑或错误处理策略。例如,一个复杂的算法函数可以附带一段注释,详细说明其时间复杂度、适用场景和边界条件。这使得AI不仅能生成语法正确的代码,还能生成更高质量、更符合上下文的代码。

再者,编译器的角色需要重新定位。在AI时代,编译器不应仅仅是报错的工具,而应成为一个积极的协作者。当检测到AI生成代码中常见的模式时,例如对错误的忽略、不安全的指针操作或潜在的数据竞争,编译器应主动发出警告,并附带最佳实践链接或修复建议 [[220,221]]。Meta的研究表明,提供推理步骤的提示可以显著降低代码补丁的错误率 [[188]],编译器也可以扮演类似的角色。此外,当AI生成的代码出现编译错误时,错误信息应尽可能具体和富有启发性。与其只给出一行行号,不如提供关于错误原因的简短解释,甚至直接生成修正后的代码片段。这种积极的、协作者式的反馈模式,将极大地改善开发者(无论是人类还是AI)的体验。

最后,我们可以探索定义语言的"AI感知"子集。考虑到AI在生成代码时的能力边界,可以考虑定义一个语言的核心子集,这个子集是AI最容易理解和生成的。这个子集可以包含语言中最常用、最稳定的特性,排除那些过于复杂或容易引起歧义的部分。这有助于在项目初期快速搭建原型,然后再逐步引入更复杂的、由人类专家编写的语言特性。这种分层 approach 符合渐进式采纳的原则,使得AI工具可以在不同阶段发挥不同的作用。

综上所述,为了提升AI适配度,修订工作应聚焦于以下几个方面:
1.  **巩固语法的解析性**:确保语言的语法足够清晰、一致,以便AI能够生成稳定、可靠的AST。
2.  **引入可解释性元素**:通过特殊的注释或元数据,向AI传递代码的更高层次的意图和约束。
3.  **重塑编译器角色**:将编译器从一个被动的错误报告者,转变为一个主动的、智能的协作者,提供高质量的反馈和修复建议。
4.  **定义AI友好的子集**:为AI生成代码提供一个简单、安全的"沙盒",促进人机协作的平稳过渡。

通过这些调整,贵语言将能够更好地拥抱AI时代,成为一个既能满足严谨的人类程序员需求,又能高效赋能新一代AI编码工具的强大平台。

## 综合修订策略与标准库演进规划

基于前述四个维度的深入分析,本节将提出一套综合性、分优先级的修订策略,并规划未来标准库的演进方向。我们的目标是在坚守语言核心美学与设计哲学的前提下,通过一系列"内功修炼",显著提升语言的健壮性、可用性和未来适应性。

**核心修订策略:分阶段、递归式演进**

我们建议将修订工作分为两个阶段,形成一个持续演进的良性循环。

**第一阶段:奠定坚实基础(近期目标)**

此阶段的目标是解决最根本、最紧迫的问题,为后续的高级功能打下坚实的基础。

1.  **深化形式化基础**:这是所有修订工作的重中之重。应立即成立专项小组,为语言的核心机制——特别是宏系统和类型系统——建立一套形式化的语义模型 [[25,330]]。这项工作虽然艰巨,但其产出将是长期受益的,它将消除语言设计中的模糊地带,为编译器验证、静态分析和未来的新特性提供理论保障。
2.  **引入结构化的错误集**:借鉴Zig的"error sets"模型 [[59]],对错误处理机制进行首次重大升级。这将使错误处理从简单的返回码提升到结构化的、可枚举的类型级别,极大增强代码的可读性和可维护性。编译器应随之增强对错误处理路径的静态检查能力,强制要求开发者处理或显式忽略可能的错误。
3.  **标准化模块接口**:引入显式的模块接口声明语法,取代当前可能存在的隐式或基于文件的模块划分方式。这将为大型项目提供清晰的模块边界和稳定的契约,是构建健壮系统的必要条件。

**第二阶段:构建高级协作能力(中长期目标)**

在坚实的基础之上,此阶段将重点发展与AI时代的深度协作能力。

1.  **探索形式化契约与AI辅助验证**:在模块接口层面引入形式化契约(`requires`, `ensures`, `invariant`)[[52,500]]。这些契约将成为机器可读的规范,供AI工具在生成和审查代码时使用,以确保生成的代码满足预设的逻辑要求。
2.  **重塑编译器的反馈机制**:将编译器定位为AI的协作者。开发高级的静态分析能力,使其能够识别AI生成代码中的常见模式(如错误处理遗漏、资源泄漏等),并提供具体、可操作的修复建议。这将构成一个高效的"生成-验证-反馈"闭环。
3.  **定义语言的"AI感知"子集**:研究并定义一个对AI最友好的语言核心子集。该子集应包含语言中最稳定、最易理解的特性,为AI在项目初期快速原型设计提供一个安全、高效的环境。

**标准库演进规划**

核心语言规范的修订将直接影响标准库的设计与演进。标准库不应仅仅是核心特性的被动使用者,而应成为推广和示范新特性的先行者。

1.  **内置模块 (`std.builtins`) 的扩展**:随着结构化错误集和模块接口的引入,标准库应提供一套统一的、用于定义和操作这些新特性的内置模块。例如,`std.error`模块可以提供创建和匹配错误集的通用函数,`std.interface`模块可以定义接口的语法糖。
2.  **增强标准库的健壮性**:所有标准库模块都应遵循新引入的健壮性原则。这意味着它们必须拥有清晰的接口定义,广泛使用类型系统来保证数据安全,并且自身的错误处理必须做到全面和结构化。这将为用户提供一个高质量的编程范例。
3.  **新增领域专用模块**:为了支撑新特性,可以酌情扩展标准库。例如:
    *   **`std.contracts`**:提供实现形式化契约的宏和函数。
    *   **`std.ai_assist`**:提供用于与AI工具交互的元数据注解,以及获取编译器反馈的API。
    *   **`std.test`**:扩展单元测试框架,使其能够验证形式化契约的满足情况,从而实现更高级别的自动化测试。

**结论**

总而言之,本次修订的核心思想不是颠覆性的语法革命,而是在坚守语言独特魅力的基础上,进行一次深刻的"内功修炼"。通过深化形式化基础、结构化错误处理、规范化模块契约以及拥抱人机共生的协作模式,我们有望将贵语言从一个优雅的、面向人类的编程工具,提升为一个强大、健壮且能与AI时代无缝对接的现代化编程平台。这份修订路线图提供了一个清晰的、分阶段的实施路径,旨在确保每一次演进都建立在坚实的基础之上,最终实现语言长期的可持续发展和竞争力。

## 1. 设计目标与原则

### 1.1 一句话定位

**WLWL 是一门"一切皆统一函数调用"的纯动态类型通用编程语言,以 Rust 级别的结构化错误信息为核心,优先面向 AI Coding 场景。**

### 1.2 设计原则(按优先级排序)

1. **统一性(Unification)**:语言里的所有"动作"——变量赋值、运算、控制流、类定义、HTML 标签、SQL 语句——都是**对函数的调用**。这是最高原则。
2. **表达性(Expression-oriented)**:一切都是表达式,任何表达式都有值,包括 `IF`、`WHILE`、`LET`、`TRY`。
3. **显式优于隐式(Explicit over Implicit)**:必须用 `;` 结束语句;不依赖缩进;不依赖上下文推断;不引入隐式转换。
4. **错误前置(Error-first)**:错误必须尽早暴露、必须位置精确、必须给出可操作的修复建议。这是面向 AI Coding 的硬要求。
5. **函数式核心 + OOP 上层(FP core, OOP surface)**:函数是一等公民;类、继承、封装作为组织大型代码的上层建筑。
6. **可读性优于简洁(Readability over Brevity)**:`+(a, b, c)` 比 `a+b+c` 啰嗦,但统一;真要简洁,语法糖永远可以后加。

### 1.3 非目标(Non-goals)

- WLWL **不追求**静态类型保证。
- WLWL **不追求**极致运行性能(初版用 tree-walking 解释器,见 §17)。
- WLWL **不追求**成为系统编程语言(不需要替代 C/Rust 做底层)。
- WLWL **不追求**最短代码行数。

### 1.4 长期愿景(可分阶段实现)

- 同一份 WLWL 源码编译到 HTML/CSS/JS、SQL、华为/思科交换机配置、Nginx/Apache 配置(来自原始草稿)。
- 上述目标**不进入 v0.1 规范**,仅作为方向保留。

## 2. 类型系统

### 2.1 纯动态类型

- WLWL **不**做编译期类型检查。
- 任何变量可以持有任何类型的值。
- 类型错误在运行时被捕获并以结构化错误抛出(见 §12、§14)。

### 2.2 内建类型(初版,共 8 种)

| 类型 | 字面量示例 | 备注 |
|------|------------|------|
| `INTEGER` | `1`, `-42`, `0` | 64 位有符号整数(实现可调整) |
| `FLOAT` | `1.5`, `-3.14`, `0.0` | 64 位 IEEE 754 双精度 |
| `STRING` | `"hello"`, `""` | UTF-8 不可变字符串 |
| `BOOLEAN` | `TRUE`, `FALSE` | 关键字,大小写敏感 |
| `NULL` | `NULL` | 表示"无值",关键字 |
| `ARRAY` | `[1, 2, 3]` | 有序、可变、可嵌套 |
| `DICT` | `["k": 1, "k2": "v"]` | 键值映射,键必须为 STRING 或 INTEGER |
| `FUNCTION` | `FUN(...)` | 一等公民,可作为参数、返回值 |

> 复合类型(类实例)是 v0.1 中 `DICT` 的一个特化形式,见 §11。

### 2.3 类型查询

通过 `TYPE(x)` 表达式获取值的类型名称(返回 STRING):

```wlwl
LET(t, TYPE(1));        // "INTEGER"
LET(t, TYPE("hi"));     // "STRING"
LET(t, TYPE([1, 2]));   // "ARRAY"
```

## 3. 词法

### 3.1 字符集

- 源文件为 UTF-8。
- 标识符允许字母、数字、下划线,首字符不能是数字。**允许中文标识符**(为符合草稿作者"事屑""事true"这类命名习惯),但建议在生产代码中使用 ASCII 标识符以提升 AI 编码效率。
- 区分大小写。

### 3.2 关键字(初版,共 16 个)

```
TRUE  FALSE  NULL
LET   FUN    RETURN
IF    WHILE  FOR
BREAK CONTINUE
CLASS NEW    THIS
```

### 3.3 分隔符

| 符号 | 用途 |
|------|------|
| `(` `)` | 函数调用 / 表达式分组 |
| `,` | 参数分隔 |
| `;` | **语句结束符,必须** |
| `[` `]` | 数组、字典、下标访问 |
| `:` | 字典键值对分隔 |
| `.` | 成员访问(对象属性 / 方法 / 链式调用) |
| `"` | 字符串字面量边界 |
| `//` | 单行注释起始,直到行尾 |
| `/*` `*/` | 块注释边界,可嵌套 |

### 3.4 注释

- 单行:`//` 到行尾。
- 块注释:`/* ... */`,**支持嵌套**(便于注释掉大段已经包含块注释的代码)。

```wlwl
// 这是单行注释
LET(x, 1);

/*
   这是块注释
   /* 可以嵌套 */
   结束 */
LET(y, 2);
```

> AI 友好约束:注释中以 `TODO(agent):` 开头的行,WLWL 编译器在严格模式下会输出结构化警告(见 §14)。

### 3.5 空白

- 缩进不影响语义。
- 多个连续空白等同于一个空白。
- **换行不影响语义**;语句必须用 `;` 显式结束。

```wlwl
LET(x, 1); LET(y, 2);  // 合法的同行多语句
LET(z,
    3);                  // 换行不影响
```

## 4. 字面量

### 4.1 数值

```wlwl
LET(i, 42);
LET(f, 3.14);
LET(n, -1);
```

### 4.2 字符串

使用双引号。支持转义序列:`\n` `\t` `\r` `\\` `\"` `\0`。**v0.1 不支持字符串模板**(插值);需要拼接请用 `+(...)`。

```wlwl
LET(s, "事屑");
LET(greet, +("hello, ", "world"));
```

### 4.3 布尔与空

```wlwl
LET(b, TRUE);
LET(n, NULL);
```

### 4.4 数组

用 `[` `]` 包裹,逗号分隔:

```wlwl
LET(i, [1, 1, 4, 5, 1, 4]);
LET(empty, []);
LET(mixed, [1, "two", TRUE, NULL]);
```

### 4.5 字典

用 `[` `]` 包裹,键值对用 `:` 分隔,各对之间用 `,` 分隔。键必须为 STRING 或 INTEGER:

```wlwl
LET(j, ["cat": "nya", "dog": 2]);
LET(empty, []);
LET(mixed, [1: "one", "two": 2]);
```

> 注:数组和字典语法相同,根据内容(纯值 vs `键:值` 对)消歧。**不允许**一个数组字面量中混用两种形式。

### 4.6 函数字面量

见 §8.2。

## 5. 表达式

### 5.1 一切都是表达式

WLWL 中所有"语句"在求值后都产生一个值。下列形式都是表达式:

- 字面量(§4)
- 函数调用(§5.2)
- 变量引用(§6)
- 控制流(§7):`IF`、`WHILE`、`FOR`、`TRY`
- 块表达式(§5.3)

### 5.2 函数调用

**调用形式**:`NAME(arg1, arg2, ..., argN)`

```wlwl
LET(x, +(1, 2));          // 1 + 2 = 3
LET(y, PRINT("hi"));      // 表达式有值,PRINT 返回 NULL
```

**方法调用**(对对象的链式访问):

```wlwl
LET(t, HTML(HEAD(TITLE("x")), BODY()));
LET(j, t.DOM.ID("j"));
j.APPEND(IMG("./1.jpg"));
```

> 解析规则:`a.b.c.d(args)` 等价于 `CALL_METHOD(CALL_METHOD(CALL_METHOD(a, "b"), "c"), "d", args)`,见 §11.4。

### 5.3 块表达式

用 `(` `)` 包裹的语句序列,值为最后一条表达式的值:

```wlwl
LET(x, (
    LET(a, 1);
    LET(b, +(a, 2));
    +(a, b)
));  // x = 4
```

空块 `()` 的值为 `NULL`。

### 5.4 求值顺序

- 函数实参在传入前**完全求值**(无惰性求值)。
- 自左向右。
- 如需短路行为,使用 `AND`/`OR`(§9.3),它们是**宏函数**,提供短路语义。

## 6. 变量与作用域

### 6.1 变量绑定

**唯一方式**:`LET(name, value)` 表达式。**没有**`var`、`x = 1`、自增自减等语法。

```wlwl
LET(x, 1);
LET(y, +(x, 1));
LET(z, !(FALSE));
```

> `LET` 表达式本身返回 `NULL`;它的"作用"是副作用(命名绑定)。

### 6.2 重新绑定

- 同一作用域内对同一名字再次 `LET`,**默认报错**(`W0012: name 'x' already bound in this scope`)。
- 如需"重赋值"语义,使用 `SET(name, value)` 表达式(等价的宏函数,会编译为读写 `name` 的代码):

```wlwl
LET(x, 1);
SET(x, +(x, 1));  // x = 2
```

> 初版规范明确:WLWL **没有**单独的"赋值语句",`SET` 是函数。这避免"赋值是表达式还是语句"的歧义。

### 6.3 作用域规则

- **词法作用域(lexical scoping)**。
- 引入新作用域的构造:函数体、块表达式、类体、模块顶层。
- 子作用域可读父作用域的绑定,**不可**写(无 `nonlocal`/`global` 关键字)。
- 读未定义名字 → `W0001: undefined name 'x'(你是否想引用 'y'?列出最近似的候选)`。

### 6.4 提升(hoisting)

- WLWL **不做**变量提升。
- 在 `LET` 之前引用一个名字 → `W0001` 错误,带行号。

## 7. 控制流

### 7.1 条件:`IF`

`IF(cond, then, else)` —— **三元表达式**。`else` 分支可省略,默认值为 `NULL`。

```wlwl
IF(=(x, TRUE),
    (PRINT("x是true")),
    (PRINT("x是false"))
);

LET(msg, IF(>(x, 0), "positive", "non-positive"));
```

> `IF` **不是**特殊语法,是宏函数。条件真假规则见 §9.4。

### 7.2 循环:`WHILE`

`WHILE(cond, body)` —— 条件为真时反复执行 body。`WHILE` 表达式的值是**最后依次循环体的值**,若从未执行则为 `NULL`。

```wlwl
LET(x, 2);
WHILE(>(x, 0),
    (PRINT(x), SET(x, -(x, 1)))
);
```

### 7.3 循环:`FOR`(遍历)

`FOR(var, iterable, body)` —— 对 iterable(ARRAY 或 DICT 的键)逐项执行 body,var 在每次迭代中绑定当前项。

```wlwl
FOR(item, [1, 2, 3],
    (PRINT(item))
);

FOR(key, ["a": 1, "b": 2],
    (PRINT(key))
);
```

`FOR` 表达式的值是 `NULL`。

### 7.4 提前退出

- `RETURN(value)` —— 立即从当前函数返回,值为 `value`(若省略则 `NULL`)。
- `BREAK()` —— 立即终止最近的 `WHILE`/`FOR` 循环。
- `CONTINUE()` —— 立即跳到最近的 `WHILE`/`FOR` 循环的下一次迭代。

```wlwl
FUN(first_positive(nums),
    FOR(n, nums,
        IF(>(n, 0), RETURN(n))
    );
    NULL
);
```

> `RETURN`/`BREAK`/`CONTINUE` 是宏函数,只能出现在 `FUN`/`WHILE`/`FOR` 体内,否则报错(见 §14.4)。

## 8. 函数

### 8.1 函数是一等公民

- 函数可作为参数传递、作为返回值、存放在变量/数组/字典中。
- 函数没有"方法重载",靠参数模式匹配区分(§8.4)。

### 8.2 函数定义

`FUN(name(params), body)`:

```wlwl
FUN(hello(str),
    (PRINT(+(+("hello ", str), "!")))
);
```

- `name` 可省略,产生**匿名函数**:`FUN((x), (*(x, x)))`。
- `params` 是**参数列表**,每个参数用 `LET`-风格声明类型/默认值(初版仅支持默认值)或仅给名字。

**参数声明语法**(v0.1):
- `name` —— 必填参数
- `name = default` —— 默认参数
- `*rest` —— 剩余参数(收集为数组)

```wlwl
FUN(greet(name, greeting = "hi"),
    (PRINT(+(+(greeting, ", "), name)))
);

greet("alice");                  // "hi, alice"
greet("alice", "hello");         // "hello, alice"
```

> 初版**不支持**类型注解(因动态类型)。未来如需,语法形如 `name: Type`,不影响现有代码。

### 8.3 函数调用

直接用 `name(args...)`,不区分"方法调用"和"普通调用"——但 `a.b(args)` 是对 `a` 的 `"b"` 方法的语法糖,见 §11.4。

### 8.4 函数应用与元数

- 函数对**元数(arity)**敏感:`FUN((x, y), ...)` 与 `FUN((x), ...)` 是不同函数。
- 传入参数数量与声明不符 → `W0003: function 'foo' expects 2 args, got 1`(带签名、行号、调用点)。

### 8.5 闭包

函数捕获其定义时的词法环境:

```wlwl
FUN(make_counter(),
    LET(count, 0);
    FUN((),
        SET(count, +(count, 1));
        count
    )
);

LET(c, make_counter());
CALL(c);  // 1
CALL(c);  // 2
```

> 闭包变量存放在堆上,由 GC 管理(实现细节见 §17)。

## 9. 运算符

**核心原则**:一切运算符都是函数,大写命名,中缀仅在语法糖中后加。

### 9.1 算术

| 函数 | 等价中缀(规划) | 说明 |
|------|----------------|------|
| `+(a, b, ...)` | `a + b` | 至少 2 个参数,或 STRING/ARRAY 拼接 |
| `-(a, b)` | `a - b` | 二元 |
| `*(a, b, ...)` | `a * b` | 至少 2 个参数 |
| `/(a, b)` | `a / b` | 整数除法按 C 语义(向零截断) |
| `%(a, b)` | `a % b` | 整数取模 |
| `NEG(a)` | `-a` | 一元取负 |

### 9.2 比较

| 函数 | 含义 |
|------|------|
| `=(a, b)` | 等于 |
| `!=(a, b)` | 不等于 |
| `>(a, b)` | 大于 |
| `<(a, b)` | 小于 |
| `>=(a, b)` | 大于等于 |
| `<=(a, b)` | 小于等于 |

> 比较运算符的返回类型**总是** `BOOLEAN`,**不**是数字。

### 9.3 逻辑

| 函数 | 短路 | 说明 |
|------|------|------|
| `AND(a, b)` | 是 | 仅当 a 真才求值 b |
| `OR(a, b)` | 是 | 仅当 a 假才求值 b |
| `!(a)` | 否 | 逻辑非,可接受多个参数(全部真才真) |

### 9.4 真值规则

- `FALSE`、`NULL`、`0`、`""`、`[]`、`[]`(空字典) 视为**假**。
- 其他视为**真**。
- 这条规则由 `BOOL(x)` 函数显式化(将任意值转为 BOOLEAN)。

### 9.5 下标

`AT(collection, key)` 替代中缀 `[]`:

```wlwl
LET(arr, [10, 20, 30]);
LET(v, AT(arr, 1));     // 20(0-based 索引)
LET(d, AT(["a": 1], "a"));  // 1
```

> `array[1]` 形式的字面量下标**不在** v0.1 中(`[` `]` 已用于数组/字典字面量)。如要字面量下标,使用 `AT`。

### 9.6 中缀语法糖(可选,实现可选)

为了写起来不那么累,实现可选择支持中缀语法糖:

```wlwl
LET(x, 1 + 2);  // 语法糖:+(1, 2)
```

若启用,必须保证解析无歧义,且**生成的 AST 节点**与函数调用一致(便于 AST 元数据被 AI 工具消费,见 §14)。

## 10. 数据结构

### 10.1 数组(ARRAY)

| 操作 | 函数 | 说明 |
|------|------|------|
| 取长度 | `LEN(arr)` | 嵌套数组不递归 |
| 追加 | `PUSH(arr, val)` | 原地,返回 arr |
| 弹出 | `POP(arr)` | 移除末尾,返回该值 |
| 头部插入 | `UNSHIFT(arr, val)` | 原地,返回 arr |
| 头部删除 | `SHIFT(arr)` | 移除首位,返回该值 |
| 切片 | `SLICE(arr, start, end = -1)` | 返回新数组,负数从末尾数 |
| 连接 | `CONCAT(a, b, ...)` | 返回新数组,非破坏性 |
| 包含 | `CONTAINS(arr, val)` | 返回 BOOLEAN |
| 索引 | `INDEX(arr, val)` | 返回第一次出现的索引,无则 -1 |
| 反转 | `REVERSE(arr)` | 原地,返回 arr |

### 10.2 字典(DICT)

| 操作 | 函数 | 说明 |
|------|------|------|
| 取键 | `KEYS(d)` | 返回 ARRAY |
| 取值 | `VALUES(d)` | 返回 ARRAY |
| 包含键 | `HAS(d, key)` | 返回 BOOLEAN |
| 删除键 | `DEL(d, key)` | 原地,返回 d |
| 合并 | `MERGE(a, b, ...)` | b 覆盖 a,返回新字典 |

### 10.3 字符串(STRING)

| 操作 | 函数 | 说明 |
|------|------|------|
| 长度 | `LEN(s)` | 字符数(按 Unicode 码点) |
| 拼接 | `+(s1, s2, ...)` | 与算术 `+` 共用,过载 |
| 子串 | `SUB(s, start, len = -1)` | 负数从末尾 |
| 包含 | `CONTAINS(s, substr)` | 字符串版本 |
| 分割 | `SPLIT(s, sep)` | 返回 ARRAY |
| 替换 | `REPLACE(s, old, new)` | 全部替换,返回新串 |
| 大小写 | `UPPER(s)`, `LOWER(s)` | ASCII;非 ASCII 行为由实现定义 |
| 整数/字符串转换 | `STR(n)`, `INT(s)` | INT 失败抛 `ERR` |

> 字符串**不可变**;任何"修改"返回新串。

### 10.4 相等性

- `=(a, b)`:对 INTEGER/FLOAT/STRING/BOOLEAN/NULL 按值比较;对 ARRAY/DICT 递归比较;对 FUNCTION 按引用比较(同一闭包实例)。

## 11. 面向对象

### 11.1 设计取向

OOP 是函数式之上的"组织代码"机制,**不是**核心。类的内部表示就是 DICT + 函数。

### 11.2 类定义

`CLASS(name, parent, members)`:

- `name`:STRING,类名(可省略,产生匿名类)
- `parent`:父类(可为 `NULL` 表示无父类)
- `members`:DICT,键为属性/方法名,值为:
  - 默认值(属性)
  - `FUN(...)` 函数字面量(方法)

```wlwl
CLASS("Rectangle", NULL, [
    "width": 0,
    "height": 0,
    "getArea": FUN((self),
        *(GET_PROP(self, "width"), GET_PROP(self, "height"))
    ),
    "scale": FUN((self, factor),
        SET_PROP(self, "width", *(GET_PROP(self, "width"), factor));
        SET_PROP(self, "height", *(GET_PROP(self, "height"), factor))
    )
]);
```

> `self` 不是关键字,只是约定为方法第一个参数的名字;`NEW(ClassName, args...)` 会把新对象作为第一参数传入。

### 11.3 实例化与属性

```wlwl
LET(rect, NEW("Rectangle"));
SET_PROP(rect, "width", 10);
SET_PROP(rect, "height", 20);
LET(area, CALL_METHOD(rect, "getArea"));  // 200
```

### 11.4 方法调用的链式语法糖

`a.b.c(args)` 在词法上等价于:

```
CALL_METHOD(CALL_METHOD(GET_PROP(a, "b"), "c"), ???, args)
```

但 `a.b` 应当是属性访问;只有当末尾带 `(args)` 时才触发方法调用。具体规则:

- `a.b` —— 属性访问,等价 `GET_PROP(a, "b")`
- `a.b(args)` —— 方法调用,等价 `CALL_METHOD(a, "b", args...)`
- `a.b.c(args)` —— 链式:先 `a.b`,再对结果做 `.c(args)`,等价:
  ```
  LET(_tmp, a.b);
  CALL_METHOD(_tmp, "c", args...)
  ```
- `a.b.c.d(args)` —— 同理递归。

> **初版实现细节**:`a.b(args)` 的中间产物是临时的"self + method"绑定,见 §17。

### 11.5 继承

- `CLASS(name, parent, members)` 中 `parent` 可以是父类的类名字符串,或父类对象本身。
- 方法解析顺序(MRO):v0.1 用**单链**:子类 → 父类 → NULL。
- 多继承**不支持**。

### 11.6 封装

- v0.1 **不**做访问控制。所有属性公开。
- 命名约定:以下划线 `_` 开头的属性/方法视为"私有",由文档和工具约定,语言层不强制。

### 11.7 静态属性/方法

v0.1 不做。`CLASS` 体里只能是属性默认值和方法。需要在类层面共享数据,使用一个外部 DICT。

## 12. 错误处理

### 12.1 范式

参考 Rust 的 `Result<T, E>`,但在动态类型下表示为两个构造器函数:

- `OK(value)` —— 成功,值可以是任意类型
- `ERR(error)` —— 失败,值必须是 STRING 或 DICT(描述错误的结构化信息)

### 12.2 触发与传播

| 操作 | 函数 | 说明 |
|------|------|------|
| 不可恢复错误 | `PANIC(msg)` | 立即终止执行,msg 必须是 STRING 或 DICT |
| 错误传播 | `TRY(expr)` | 若 expr 求值为 `ERR(...)`,提前从当前函数返回该 ERR;否则取其值 |
| 默认值兜底 | `OR_DIE(expr, default)` | 若 expr 是 `ERR`,返回 default;否则取 expr 的值 |
| 主动判断 | `IS_OK(x)`, `IS_ERR(x)` | BOOLEAN |

```wlwl
FUN(parse_int(s),
    LET(n, INT(s));
    IF(IS_ERR(n), RETURN(ERR(["kind": "ParseError", "input": s])));
    OK(GET_PROP(n, "value"))  // 视 INT 失败行为而定
);
```

### 12.3 `TRY` 的关键语义

`TRY(expr)` 在语义上等价于:

```
LET(_tmp, expr);
IF(IS_ERR(_tmp), RETURN(_tmp));
UNWRAP(_tmp)  // 取出 OK 里的值
```

因此它**只能**出现在期望"接收一个值"的位置,比如赋值、函数实参、另一层 `TRY` 的内部。

```wlwl
LET(x, TRY(some_risky_op()));  // 若失败,x = ERR,函数继续
LET(y, TRY(other_op()));         // 多个 TRY 可以链式
```

### 12.4 `PANIC` vs `ERR`

- `ERR`:**可恢复**,沿调用栈向上传播,通过 `TRY` 或调用方处理。
- `PANIC`:**不可恢复**,打印结构化错误后立即终止(默认 exit code 1)。用于真正不可处理的内部错误(如 `NEW("Foo")` 时找不到类)。

> AI 友好:任何 `PANIC` 都附带源码位置、栈、修复建议;任何 `ERR` 在未被 `TRY`/`OR_DIE` 捕获时,最终在顶层被 `PANIC`,**且**把"未被处理的错误"作为单独的错误码(便于 AI 工具检测)。

### 12.5 错误信息结构(必读,见 §14)

所有 `ERR` / `PANIC` 的 `error` 字段必须是 STRING 或 DICT。DICT 形式推荐字段:

```wlwl
ERR([
    "code": "E1003",                     // 错误码,见 §14.5
    "message": "division by zero",      // 人类可读
    "location": ["file.wl", 42, 5],     // [file, line, col]
    "hint": "检查除数是否可能为 0"      // 修复建议,中文 OK
]);
```

## 13. 模块系统

### 13.1 文件即模块

- 每个 `.wl` 源文件是一个模块,模块名默认为**文件名**(不含扩展名),可通过 §13.4 显式命名。
- 同一目录下的 `foo.wl` 可被 `IMPORT("foo", [...])` 引用。

### 13.2 显式 `EXPORT` 名单

模块必须通过 `EXPORT(names)` 显式声明哪些名字对外可见,否则一律私有。

```wlwl
// file: math.wl
FUN(add(a, b), +(a, b));
FUN(sub(a, b), -(a, b));
LET(PI, 3.14159);

EXPORT(["add", "PI"]);
```

- `EXPORT` 必须出现在文件**顶层**的末尾(实现可放宽为任意位置,但 v0.1 规范规定为末尾)。
- `EXPORT` 可多次出现,实现应取并集(便于条件导出)。
- 引用一个**未导出**的名字 → `W0004: 'sub' is not exported by module 'math'`。

### 13.3 显式 `IMPORT`

```wlwl
// file: main.wl
IMPORT("math", ["add", "PI"]);   // 引入名字到当前作用域

LET(x, add(1, 2));
LET(y, *(PI, 2));
```

- `IMPORT("mod", [names])` 把 names 中的每个名字作为**当前作用域的绑定**。
- `IMPORT` 必须出现在文件顶层,不允许在函数体内部动态 `IMPORT`(避免作用域污染)。

### 13.4 模块命名空间(可选,语法保留)

若两个被导入的名字冲突,使用 `AS(name, alias)` 重命名:

```wlwl
IMPORT("math", ["add"]);
IMPORT("more_math", ["add"]);
AS("add", "math_add");           // math 版本的 add 改名为 math_add
// 现在 add 仍指向 more_math 版本(后导入的覆盖)
```

### 13.5 入口文件

```bash
wlwl run main.wl
```

- `main.wl` 是入口;`IMPORT` 链式解析。

### 13.6 包管理(远期,本规范不定义)

未来可能引入 `wlwl.toml` 清单和中央仓库。**v0.1 不规定**。

## 14. 错误信息格式(AI 友好核心)

### 14.1 总则

**所有** WLWL 错误,无论来自词法、语法、运行时还是用户主动 `ERR`/`PANIC`,**必须**符合以下结构化格式。实现**不得**只输出不可解析的自由文本。

### 14.2 标准错误对象

```wlwl
ERR([
    "code": "E1003",                                  // 错误码
    "severity": "error",                              // "error" | "warning" | "note"
    "message": "division by zero",                    // 一句话人类描述
    "location": ["main.wl", 42, 5, 42, 12],           // [file, line, col_start, line_end, col_end]
    "source_line": "LET(x, /(y, z));",                // 出错行的源码(便于 AI 上下文)
    "hint": "检查除数 z 是否可能为 0",                // 修复建议
    "related": [                                       // 相关位置(可选)
        ["note", "y 在此声明", "main.wl", 41, 5, 41, 8]
    ]
]);
```

### 14.3 顶层输出格式(CLI)

默认 CLI 输出人类可读形式:

\`\`\`
error[E1003]: division by zero
 --> main.wl:42:5
  |
42 | LET(x, /(y, z));
  |          ^^^^^^^
  |
  = hint: 检查除数 z 是否可能为 0
  = note: y 在此声明
   --> main.wl:41:5
\`\`\`

通过 \`--format=json\` 输出机器可解析的 JSON,AI 工具必须使用此格式:

\`\`\`json
{
  "code": "E1003",
  "severity": "error",
  "message": "division by zero",
  "location": {"file": "main.wl", "line": 42, "col": 5, "line_end": 42, "col_end": 12},
  "source_line": "LET(x, /(y, z));",
  "hint": "检查除数 z 是否可能为 0",
  "related": []
}
\`\`\`

### 14.4 错误码(初版预定)

| 码 | 类别 | 含义 |
|----|------|------|
| \`E0001\` | 词法 | 非法字符 |
| \`E0002\` | 词法 | 未闭合的字符串 |
| \`E0003\` | 词法 | 未闭合的块注释 |
| \`E0010\` | 语法 | 期望表达式 |
| \`E0011\` | 语法 | 期望 \`)\` |
| \`E0012\` | 语法 | 期望 \`,\` |
| \`E0013\` | 语法 | 期望 \`;\` |
| \`E0014\` | 语法 | \`RETURN\`/\`BREAK\`/\`CONTINUE\` 出现在非法位置 |
| \`E0020\` | 名字 | 未定义名字 |
| \`E0021\` | 名字 | 重复定义 |
| \`E0022\` | 名字 | 函数元数不匹配 |
| \`E0023\` | 名字 | 未导出的模块成员 |
| \`E0030\` | 类型 | 算术运算类型错误 |
| \`E0031\` | 类型 | 下标类型错误 |
| \`E0032\` | 类型 | 属性/方法不存在 |
| \`E0040\` | 模块 | 找不到模块 |
| \`E0041\` | 模块 | 循环导入 |
| \`E0050\` | OOP | 类继承链错误 |
| \`E0051\` | OOP | \`NEW\` 元数与 \`INIT\` 不匹配 |
| \`E0099\` | 用户 | 用户抛出的 \`ERR\`/\`PANIC\` |
| \`E0100\` | 内部 | 实现内部错误(\`PANIC\` 默认值) |
| \`E0101\` | 内部 | 栈溢出 |
| \`E0102\` | 内部 | 未处理的 \`ERR\` 逃逸到顶层 |

> 错误码**必须稳定**。任何变更都需在规范更新中说明。

### 14.5 警告(W 开头,不影响运行但建议修复)

| 码 | 含义 |
|----|------|
| \`W0001\` | 名字未定义 |
| \`W0010\` | 未使用的 \`LET\` 绑定 |
| \`W0011\` | 未使用的函数参数(标注 \`_\` 前缀忽略) |
| \`W0012\` | 同名重复 \`LET\` |
| \`W0013\` | \`IF\` 的 then/else 分支类型不一致(可能 bug) |
| \`W0020\` | 数组/字典字面量中混用裸值和键值对 |
| \`W0030\` | \`IMPORT\` 了一个名字但未使用 |

## 1. 设计目标与原则

### 1.1 一句话定位

**WLWL 是一门"一切皆统一函数调用"的纯动态类型通用编程语言,以 Rust 级别的结构化错误信息为核心,优先面向 AI Coding 场景。**

### 1.2 设计原则(按优先级排序)

1. **统一性(Unification)**:语言里的所有"动作"——变量赋值、运算、控制流、类定义、HTML 标签、SQL 语句——都是**对函数的调用**。这是最高原则。
2. **表达性(Expression-oriented)**:一切都是表达式,任何表达式都有值,包括 `IF`、`WHILE`、`LET`、`TRY`。
3. **显式优于隐式(Explicit over Implicit)**:必须用 `;` 结束语句;不依赖缩进;不依赖上下文推断;不引入隐式转换;不引入隐式覆盖。
4. **错误前置(Error-first)**:错误必须尽早暴露、必须位置精确、必须给出可操作的修复建议;ERR 默认透明传播,必须显式消费。这是面向 AI Coding 的硬要求。
5. **函数式核心 + OOP 上层(FP core, OOP surface)**:函数是一等公民;类、继承、封装作为组织大型代码的上层建筑。
6. **可读性优于简洁(Readability over Brevity)**:`+(a, b, c)` 比 `a+b+c` 啰嗦,但统一;真要简洁,语法糖永远可以后加。
7. **语法可预测性(Predictability)**[v0.2 新增]:同一语义**仅**保留一种标准写法,不提供多种等价语法糖。语法糖仅作为**实现层**的可选扩展,**不得**进入核心规范。

### 1.3 非目标(Non-goals)

- WLWL **不强制**静态类型检查(注:可**可选**地声明类型注解供文档/AI 工具消费,见 §2.4)。
- WLWL **不追求**极致运行性能(本规范不规定实现模型)。
- WLWL **不追求**成为系统编程语言(不需要替代 C/Rust 做底层)。
- WLWL **不追求**最短代码行数。
- **Web 子集技术边界**[v0.2 新增]:Web 子集是**语义子集**,**不**承诺 Web 端运行时与原生运行时性能一致;**不**包含文件 IO、原生扩展、系统调用等能力。多目标编译时,目标间共享核心语义,平台相关能力显式标注。

### 1.4 长期愿景(可分阶段实现)

- 同一份 WLWL 源码编译到 HTML/CSS/JS、SQL、华为/思科交换机配置、Nginx/Apache 配置(来自原始草稿)。
- **语言级 AI 原语**[v0.2 新增]:在标准库提供 `ASK(model, prompt)`、`EMBED(text)`、`COMPLETE(code_context)` 等内置函数,使 WLWL 程序能在运行时调用 LLM。这些函数遵循"一切皆函数调用"的统一性原则。**v0.2 仅占位,签名待定**。
- 上述目标**不进入 v0.2 规范**的强制性条款,仅作为方向保留。

## 2. 类型系统

### 2.1 动态优先,渐进可选(Dynamic-first, Optionally Gradual)

v0.2 起,WLWL 的类型立场从"**纯动态**"调整为"**动态优先,渐进可选**":

- **默认行为**:纯动态类型。运行时不做类型检查(除显式的 `TYPE(x)` 查询)。
- **可选能力**:v0.2 预留类型注解语法槽 `name: Type`(见 §2.4),**仅供文档、IDE、静态分析工具、AI 工具消费**。v0.2 运行时**完全忽略**类型注解。
- **未来兼容性**:此预留保证未来如需引入渐进类型检查时,无需破坏性变更现有代码。

### 2.2 内建类型(共 8 种)

| 类型 | 字面量示例 | 备注 |
|------|------------|------|
| `INTEGER` | `1`, `-42`, `0` | 64 位有符号整数 |
| `FLOAT` | `1.5`, `-3.14`, `0.0` | 64 位 IEEE 754 双精度 |
| `STRING` | `"hello"`, `""` | UTF-8 不可变字符串 |
| `BOOLEAN` | `TRUE`, `FALSE` | 关键字,大小写敏感 |
| `NULL` | `NULL` | 表示"无值",关键字 |
| `ARRAY` | `[1, 2, 3]` | 有序、可变、可嵌套 |
| `DICT` | `["k": 1, "k2": "v"]` | 键值映射 |
| `FUNCTION` | `FUN(...)` | 一等公民 |

> 复合类型(类实例)是 v0.2 中 `DICT` 的一个特化形式,见 §11。

### 2.3 DICT 键的相等性规则[v0.2 补全]

- DICT 键使用**严格相等**比较。
- **不**做隐式类型转换:整数键 `1` 与字符串键 `"1"` 是不同的键。
- 仅以下类型可作为 DICT 键:`STRING`、`INTEGER`、以及实现了相等语义的不可变类型(初版仅前两种)。
- 违反(如以 ARRAY/DICT/FUNCTION 作键)→ `E0031`。

### 2.4 类型注解(预留,v0.2 不做检查)[v0.2 新增]

- 函数参数、形参、变量绑定**可以**携带类型注解:`name: Type`。
- `Type` 可以是内建类型名(`INTEGER`、`STRING` 等)、自定义类名,或数组/字典的容器类型(具体语法待定)。
- **v0.2 运行时完全忽略注解**;不存在的类型注解不报错。
- 工具/AI 可以读取注解生成文档、提示、或(未来)进行静态检查。
- 任何具体类型注解的语义、形式化定义、模块契约集成,均在 v0.3 及之后讨论。

### 2.5 类型查询

通过 `TYPE(x)` 表达式获取值的类型名称(返回 STRING):

```wlwl
LET(t, TYPE(1));        // "INTEGER"
LET(t, TYPE("hi"));     // "STRING"
LET(t, TYPE([1, 2]));   // "ARRAY"
```

- 源文件为 UTF-8。
- 标识符允许字母、数字、下划线,首字符不能是数字。**允许中文标识符**(为符合草稿作者"事屑""事true"这类命名习惯),但建议在生产代码中使用 ASCII 标识符以提升 AI 编码效率。
- 区分大小写。

### 3.2 关键字(共 16 个)

```
TRUE  FALSE  NULL
LET   FUN    RETURN
IF    WHILE  FOR
BREAK CONTINUE
CLASS NEW    THIS
```

### 3.3 分隔符

| 符号 | 用途 |
|------|------|
| `(` `)` | 函数调用 / 表达式分组 |
| `,` | 参数分隔 |
| `;` | **语句结束符,必须** |
| `[` `]` | 数组、字典、下标访问 |
| `:` | 字典键值对分隔;**类型注解分隔(预留,见 §2.4)** |
| `.` | 成员访问(对象属性 / 方法 / 链式调用) |
| `"` | 字符串字面量边界 |
| `//` | 单行注释起始 |
| `/*` `*/` | 块注释边界,**可嵌套** |

### 3.4 注释

- 单行:`//` 到行尾。
- 块注释:`/* ... */`,**支持嵌套**。

```wlwl
// 这是单行注释
LET(x, 1);

/*
   这是块注释
   /* 可以嵌套 */
   结束 */
LET(y, 2);
```

> AI 友好约束:注释中以 `TODO(agent):` 开头的行,在严格模式下输出结构化警告(见 §14.5)。

### 3.5 空白

- 缩进不影响语义。
- 多个连续空白等同于一个空白。
- 换行不影响语义;语句必须用 `;` 显式结束。

## 4. 字面量

### 4.1 数值

```wlwl
LET(i, 42);
LET(f, 3.14);
LET(n, -1);
```

### 4.2 字符串

使用双引号。支持转义序列:`\n` `\t` `\r` `\\` `\"` `\0`。**v0.2 不支持字符串模板**;需要拼接请用 `+(...)`。

```wlwl
LET(s, "事屑");
LET(greet, +("hello, ", "world"));
```

### 4.3 布尔与空

```wlwl
LET(b, TRUE);
LET(n, NULL);
```

### 4.4 数组

用 `[` `]` 包裹,逗号分隔:

```wlwl
LET(i, [1, 1, 4, 5, 1, 4]);
LET(empty, []);
LET(mixed, [1, "two", TRUE, NULL]);
```

### 4.5 字典

用 `[` `]` 包裹,键值对用 `:` 分隔,各对之间用 `,` 分隔:

```wlwl
LET(j, ["cat": "nya", "dog": 2]);
LET(empty, []);
LET(mixed, [1: "one", "two": 2]);
```

> 注:数组和字典语法相同,根据内容消歧。**不允许**一个数组字面量中混用两种形式(违反 → `W0020`)。

### 4.6 函数字面量

见 §8.2。

## 5. 表达式

### 5.1 一切都是表达式

WLWL 中所有"语句"在求值后都产生一个值。下列形式都是表达式:

- 字面量(§4)
- 函数调用(§5.2)
- 变量引用(§6)
- 控制流(§7):`IF`、`WHILE`、`FOR`、`TRY`
- 块表达式(§5.3)

### 5.2 函数调用

**调用形式**:`NAME(arg1, arg2, ..., argN)`

```wlwl
LET(x, +(1, 2));          // 3
LET(y, PRINT("hi"));      // PRINT 返回 NULL
```

**方法调用**(对对象的链式访问):

```wlwl
LET(t, HTML(HEAD(TITLE("x")), BODY()));
LET(j, t.DOM.ID("j"));
j.APPEND(IMG("./1.jpg"));
```

### 5.3 块表达式

用 `(` `)` 包裹的语句序列,值为最后一条表达式的值:

```wlwl
LET(x, (
    LET(a, 1);
    LET(b, +(a, 2));
    +(a, b)
));  // x = 4
```

空块 `()` 的值为 `NULL`。

### 5.4 求值顺序

- 函数实参在传入前**完全求值**(无惰性求值)。
- 自左向右。
- 如需短路行为,使用 `AND`/`OR`(§9.3),它们是**宏函数**,提供短路语义。

## 6. 变量与作用域

### 6.1 变量绑定

**唯一方式**:`LET(name, value)` 表达式。**没有**`var`、`x = 1`、自增自减等语法。

```wlwl
LET(x, 1);
LET(y, +(x, 1));
LET(z, !(FALSE));
```

> `LET` 表达式本身返回 `NULL`;它的"作用"是副作用(命名绑定)。

### 6.2 重新绑定

- 同一作用域内对同一名字再次 `LET`,**默认报错**(`W0012: name 'x' already bound in this scope`)。
- 如需"重赋值"语义,使用 `SET(name, value)` 表达式:

```wlwl
LET(x, 1);
SET(x, +(x, 1));  // x = 2
```

> 初版规范明确:WLWL **没有**单独的"赋值语句",`SET` 是函数。

### 6.3 作用域规则

- **词法作用域(lexical scoping)**。
- 引入新作用域的构造:函数体、块表达式、类体、模块顶层。
- 子作用域可读父作用域的绑定,**不可**写(无 `nonlocal`/`global` 关键字)。
- 读未定义名字 → `W0001: undefined name 'x'(附最近似候选)`。

### 6.4 提升(hoisting)

- WLWL **不做**变量提升。
- 在 `LET` 之前引用一个名字 → `W0001` 错误,带行号。

## 7. 控制流

### 7.1 条件:`IF`

`IF(cond, then, else)` —— **三元表达式**。`else` 分支可省略,默认值为 `NULL`。

```wlwl
IF(=(x, TRUE),
    (PRINT("x是true")),
    (PRINT("x是false"))
);
```

> `IF` **不是**特殊语法,是宏函数。条件真假规则见 §9.4。

### 7.2 循环:`WHILE`

`WHILE(cond, body)` —— 条件为真时反复执行 body。`WHILE` 表达式的值是**最后依次循环体的值**,若从未执行则为 `NULL`。

```wlwl
LET(x, 2);
WHILE(>(x, 0),
    (PRINT(x), SET(x, -(x, 1)))
);
```

### 7.3 循环:`FOR`(遍历)

`FOR(var, iterable, body)` —— 对 iterable(ARRAY 或 DICT 的键)逐项执行 body,var 在每次迭代中绑定当前项。

```wlwl
FOR(item, [1, 2, 3],
    (PRINT(item))
);

FOR(key, ["a": 1, "b": 2],
    (PRINT(key))
);
```

**DICT 遍历顺序保证[v0.2 明确]**:`FOR` 遍历 DICT 时,键的出现顺序为**插入顺序**(与 Python 3.7+ 语义一致),不依赖实现细节。

`FOR` 表达式的值是 `NULL`。

### 7.4 提前退出

- `RETURN(value)` —— 立即从当前函数返回,值为 `value`(若省略则 `NULL`)。
- `BREAK()` —— 立即终止最近的 `WHILE`/`FOR` 循环。
- `CONTINUE()` —— 立即跳到最近的 `WHILE`/`FOR` 循环的下一次迭代。

```wlwl
FUN(first_positive(nums),
    FOR(n, nums,
        IF(>(n, 0), RETURN(n))
    );
    NULL
);
```

> `RETURN`/`BREAK`/`CONTINUE` 是宏函数,只能出现在 `FUN`/`WHILE`/`FOR` 体内,否则报错(见 §14.4)。

## 8. 函数

### 8.1 函数是一等公民

- 函数可作为参数传递、作为返回值、存放在变量/数组/字典中。
- 函数没有"方法重载",靠参数模式匹配区分(§8.4)。

### 8.2 函数定义

`FUN(name(params), body)`:

```wlwl
FUN(hello(str),
    (PRINT(+(+("hello ", str), "!")))
);
```

- `name` 可省略,产生**匿名函数**:`FUN((x), (*(x, x)))`。
- `params` 是参数列表,每个参数:
  - `name` —— 必填参数
  - `name = default` —— 默认参数
  - `name: Type` —— **类型注解(v0.2 起预留,运行时忽略,见 §2.4)**
  - `*rest` —— 剩余参数(收集为数组)
  - 三者可组合,形如 `name: Type = default`

```wlwl
FUN(greet(name, greeting = "hi"),
    (PRINT(+(+(greeting, ", "), name)))
);

greet("alice");                  // "hi, alice"
greet("alice", "hello");         // "hello, alice"
```

> 类型注解在 v0.2 仅为**元数据**,不参与运行时检查;任何语法上合法的注解都不报错。

### 8.3 函数调用

直接用 `name(args...)`,不区分"方法调用"和"普通调用"——但 `a.b(args)` 是对 `a` 的 `"b"` 方法的语法糖,见 §11.4。

### 8.4 函数应用与元数[v0.2 补全]

- 函数对**元数(arity)**敏感:`FUN((x, y), ...)` 与 `FUN((x), ...)` 是不同函数。
- **元数检查规则**[v0.2 明确]:
  - 剩余参数 `*rest` **不计入**必填参数数量。
  - 带有默认值的参数,若调用方未提供,则使用默认值;若调用方提供了,则按位置/名字覆盖。
  - 调用参数数量必须满足:**`必填参数数量 ≤ 实际参数数量 ≤ 必填参数数量 + 1`(若存在剩余参数)**。
  - 违反 → `E0022: function 'foo' expects N..M args, got K`(带签名、行号、调用点)。

### 8.5 闭包

函数捕获其定义时的词法环境:

```wlwl
FUN(make_counter(),
    LET(count, 0);
    FUN((),
        SET(count, +(count, 1));
        count
    )
);

LET(c, make_counter());
CALL(c);  // 1
CALL(c);  // 2
```

> 闭包变量存放在堆上;具体 GC 策略由实现决定,**不在本规范范围**。

## 9. 运算符

**核心原则**:一切运算符都是函数,大写命名,中缀仅在语法糖中后加(且**不进入核心规范**,见 §1.2 第 7 条)。

### 9.1 算术

| 函数 | 说明 |
|------|------|
| `+(a, b, ...)` | 至少 2 个参数 |
| `-(a, b)` | 二元 |
| `*(a, b, ...)` | 至少 2 个参数 |
| `/(a, b)` | 二元 |
| `%(a, b)` | 二元 |
| `NEG(a)` | 一元取负 |

#### `+` 的混合类型规则[v0.2 明确]

- 所有参数类型一致时:
  - `INTEGER` / `FLOAT` 做算术加。
  - `STRING` 做字符串拼接。
  - `ARRAY` 做数组合并(返回新数组,非破坏性)。
- **类型不一致时**:**抛出 `E0030` 类型错误**,**不**做隐式转换。
- 如需将元素追加到数组,使用 `PUSH` 而非 `+`(语义清晰、避免歧义)。
- 例外:`INTEGER` 与 `FLOAT` 混合时,允许结果提升为 `FLOAT`,不视为类型不一致(算术常规)。

### 9.2 比较

| 函数 | 含义 |
|------|------|
| `=(a, b)` | 等于 |
| `!=(a, b)` | 不等于 |
| `>(a, b)` | 大于 |
| `<(a, b)` | 小于 |
| `>=(a, b)` | 大于等于 |
| `<=(a, b)` | 小于等于 |

> 比较运算符的返回类型**总是** `BOOLEAN`。

### 9.3 逻辑

| 函数 | 短路 | 说明 |
|------|------|------|
| `AND(a, b)` | 是 | 仅当 a 真才求值 b |
| `OR(a, b)` | 是 | 仅当 a 假才求值 b |
| `!(a)` | 否 | 逻辑非,可接受多个参数(全部真才真) |

### 9.4 真值规则[v0.2 明确]

以下值视为**假**:

- `FALSE`
- `NULL`
- `INTEGER` 值 `0`
- `FLOAT` 值 `0.0`
- `STRING` 值 `""`(空字符串)
- `ARRAY` 值 `[]`(空数组)
- `DICT` 值 `[]`(空字典)

**非空**的 `ARRAY` / `DICT` **无论内部元素值是什么,一律视为真**(空数组 `[]` 和非空数组 `[NULL]` 是不同的真值)。

其他值视为**真**。`BOOL(x)` 函数显式化转换规则。

## 10. 数据结构

### 10.1 数组(ARRAY)

| 操作 | 函数 | 说明 |
|------|------|------|
| 取长度 | `LEN(arr)` | 嵌套数组不递归 |
| 追加 | `PUSH(arr, val)` | 原地,返回 arr |
| 弹出 | `POP(arr)` | 移除末尾,返回该值 |
| 头部插入 | `UNSHIFT(arr, val)` | 原地,返回 arr |
| 头部删除 | `SHIFT(arr)` | 移除首位,返回该值 |
| 切片 | `SLICE(arr, start, end = -1)` | 返回新数组,负数从末尾数 |
| 连接 | `CONCAT(a, b, ...)` | 返回新数组,非破坏性 |
| 包含 | `CONTAINS(arr, val)` | 返回 BOOLEAN |
| 索引 | `INDEX(arr, val)` | 返回第一次出现的索引,无则 -1 |
| 反转 | `REVERSE(arr)` | 原地,返回 arr |

### 10.2 字典(DICT)

| 操作 | 函数 | 说明 |
|------|------|------|
| 取长度 | `LEN(d)` | 键的数量 |
| 取键 | `KEYS(d)` | 返回 ARRAY(键列表,按插入顺序) |
| 取值 | `VALUES(d)` | 返回 ARRAY(值列表,按插入顺序) |
| 包含键 | `HAS(d, key)` | 返回 BOOLEAN |
| 删除键 | `DEL(d, key)` | 原地,返回 d |
| 合并 | `MERGE(a, b, ...)` | b 覆盖 a,返回新字典 |
| 遍历顺序 | `FOR(k, d, ...)` | 按**插入顺序**遍历键(见 §7.3) |

### 10.3 字符串(STRING)

| 操作 | 函数 | 说明 |
|------|------|------|
| 长度 | `LEN(s)` | 字符数(按 Unicode 码点) |
| 拼接 | `+(s1, s2, ...)` | 与算术 `+` 共用,过载 |
| 子串 | `SUB(s, start, len = -1)` | 负数从末尾 |
| 包含 | `CONTAINS(s, substr)` | 字符串版本 |
| 分割 | `SPLIT(s, sep)` | 返回 ARRAY |
| 替换 | `REPLACE(s, old, new)` | 全部替换,返回新串 |
| 大小写 | `UPPER(s)`, `LOWER(s)` | ASCII;非 ASCII 行为由实现定义 |
| 整数/字符串转换 | `STR(n)`, `INT(s)` | INT 失败抛 `ERR` |

> 字符串**不可变**;任何"修改"返回新串。

### 10.4 相等性

- `=(a, b)`:对 INTEGER/FLOAT/STRING/BOOLEAN/NULL 按值比较;对 ARRAY/DICT 递归比较;对 FUNCTION 按引用比较(同一闭包实例)。
- DICT 键的相等性遵循 §2.3 严格相等规则。

## 11. 面向对象

### 11.1 设计取向

OOP 是函数式之上的"组织代码"机制,**不是**核心。类的内部表示就是 DICT + 函数。

### 11.2 类定义

`CLASS(name, parent, members)`:

- `name`:STRING,类名(可省略,产生匿名类)
- `parent`:父类(可为 `NULL` 表示无父类)
- `members`:DICT,键为属性/方法名,值为:
  - 默认值(属性)
  - `FUN(...)` 函数字面量(方法)

```wlwl
CLASS("Rectangle", NULL, [
    "width": 0,
    "height": 0,
    "getArea": FUN((self),
        *(GET_PROP(self, "width"), GET_PROP(self, "height"))
    ),
    "scale": FUN((self, factor),
        SET_PROP(self, "width", *(GET_PROP(self, "width"), factor));
        SET_PROP(self, "height", *(GET_PROP(self, "height"), factor))
    )
]);
```

### 11.3 实例化与属性

```wlwl
LET(rect, NEW("Rectangle"));
SET_PROP(rect, "width", 10);
SET_PROP(rect, "height", 20);
LET(area, CALL_METHOD(rect, "getArea"));  // 200
```

### 11.4 方法调用的链式语法糖

`a.b.c(args)` 在词法上等价于:

```
CALL_METHOD(CALL_METHOD(GET_PROP(a, "b"), "c"), ???, args)
```

但 `a.b` 应当是属性访问;只有当末尾带 `(args)` 时才触发方法调用。具体规则:

- `a.b` —— 属性访问,等价 `GET_PROP(a, "b")`
- `a.b(args)` —— 方法调用,等价 `CALL_METHOD(a, "b", args...)`
- `a.b.c(args)` —— 链式:先 `a.b`,再对结果做 `.c(args)`。
- `a.b.c.d(args)` —— 同理递归。

### 11.5 继承

- `CLASS(name, parent, members)` 中 `parent` 可以是父类的类名字符串,或父类对象本身。
- 方法解析顺序(MRO):v0.2 用**单链**:子类 → 父类 → NULL。
- 多继承**不支持**。

### 11.6 封装

- v0.2 **不**做访问控制。所有属性公开。
- 命名约定:以下划线 `_` 开头的属性/方法视为"私有",由文档和工具约定,语言层不强制。

### 11.7 静态属性/方法

v0.2 不做。`CLASS` 体里只能是属性默认值和方法。需要在类层面共享数据,使用一个外部 DICT。

## 12. 错误处理

### 12.1 范式

参考 Rust 的 `Result<T, E>`,但在动态类型下表示为两个构造器函数:

- `OK(value)` —— 成功,值可以是任意类型
- `ERR(error)` —— 失败,值必须是 STRING 或 DICT(描述错误的结构化信息)

### 12.2 触发与传播

| 操作 | 函数 | 说明 |
|------|------|------|
| 不可恢复错误 | `PANIC(msg)` | 立即终止执行,msg 必须是 STRING 或 DICT |
| 错误传播 | `TRY(expr)` | 若 expr 求值为 `ERR(...)`,提前从当前函数返回该 ERR;否则取其值 |
| 默认值兜底 | `OR_DIE(expr, default)` | 若 expr 是 `ERR`,返回 default;否则取 expr 的值 |
| 主动判断 | `IS_OK(x)`, `IS_ERR(x)` | BOOLEAN |

```wlwl
FUN(parse_int(s),
    LET(n, INT(s));
    IF(IS_ERR(n), RETURN(ERR(["kind": "ParseError", "input": s])));
    OK(GET_PROP(n, "value"))
);
```

### 12.3 `TRY` 的关键语义

`TRY(expr)` 在语义上等价于:

```
LET(_tmp, expr);
IF(IS_ERR(_tmp), RETURN(_tmp));
UNWRAP(_tmp)  // 取出 OK 里的值
```

因此它**只能**出现在期望"接收一个值"的位置,比如赋值、函数实参、另一层 `TRY` 的内部。

```wlwl
LET(x, TRY(some_risky_op()));
LET(y, TRY(other_op()));
```

### 12.4 `PANIC` vs `ERR`

- `ERR`:**可恢复**,沿调用栈向上传播,通过 `TRY` 或调用方处理。
- `PANIC`:**不可恢复**,打印结构化错误后立即终止(默认 exit code 1)。用于真正不可处理的内部错误。

### 12.5 错误信息结构

所有 `ERR` / `PANIC` 的 `error` 字段必须是 STRING 或 DICT。DICT 形式推荐字段见 §14.2。

### 12.6 ERR 透明传播规则[v0.2 新增,核心语义]

> 这是 v0.2 对错误处理的关键语义补全。**缺失此规则会导致错误被意外吞掉,是最严重的语义漏洞之一。**

**规则**:`ERR` 值在所有普通函数调用中**透明传播**。

- 任何**普通函数**(白名单外的函数)接收到 `ERR` 类型的实参时,**必须**直接返回该 `ERR`,**不**执行函数体,亦不报"参数类型错误"。
- 传播过程**不消耗** `ERR`;原 `ERR` 值原封不动地向上冒泡。
- 仅以下 4 个函数**可以消费** `ERR` 值:
  - `IS_OK(x)` / `IS_ERR(x)` —— 显式判断
  - `OR_DIE(expr, default)` —— 提供默认值
  - `TRY(expr)` —— 显式传播
- 其他函数(算术、字符串、数据结构、I/O 等)对 `ERR` 输入一律透明传播。

**示例**:

```wlwl
LET(r, +(1, ERR("oops")));     // r = ERR("oops"),+ 本身不被调用
LET(r, LEN(ERR("oops")));      // r = ERR("oops")
LET(r, IF(TRUE, ERR("e"), 2)); // r = ERR("e")
LET(r, OK(+(1, 2)));           // r = OK(3)
LET(r, IS_OK(OK(1)));          // r = TRUE
LET(r, OR_DIE(ERR("e"), 0));   // r = 0
LET(r, TRY(ERR("e")));         // r = ERR("e")(传播到当前函数)
```

**为何如此设计**:
- 默认传播、显式处理,杜绝错误被静默吞掉。
- 调用方不显式 `TRY`/`OR_DIE`,错误就一直往上冒,直到最外层被 `PANIC` 兜底。
- 强制 AI 生成代码时考虑错误路径(否则测试会立即暴露)。

**与 `PANIC` 的区别**:`ERR` 透明传播是**软失败**;`PANIC` 是**硬终止**。`PANIC` 不参与透明传播规则。

## 13. 模块系统

### 13.1 文件即模块

- 每个 `.wl` 源文件是一个模块,模块名默认为**文件名**(不含扩展名),可通过 §13.4 显式命名。
- 同一目录下的 `foo.wl` 可被 `IMPORT("foo", [...])` 引用。
- 跨目录引用、`wlwl.toml` 等包管理**不在 v0.2 范围**(见 §18)。

### 13.2 显式 `EXPORT` 名单

模块必须通过 `EXPORT(names)` 显式声明哪些名字对外可见,否则一律私有。

```wlwl
// file: math.wl
FUN(add(a, b), +(a, b));
FUN(sub(a, b), -(a, b));
LET(PI, 3.14159);

EXPORT(["add", "PI"]);
```

- `EXPORT` 必须出现在文件**顶层**。
- `EXPORT` 可多次出现,实现应取并集(便于条件导出)。
- 引用一个**未导出**的名字 → `E0023: 'sub' is not exported by module 'math'`。

### 13.3 显式 `IMPORT`

```wlwl
// file: main.wl
IMPORT("math", ["add", "PI"]);   // 引入名字到当前作用域

LET(x, add(1, 2));
LET(y, *(PI, 2));
```

- `IMPORT("mod", [names])` 把 names 中的每个名字作为**当前作用域的绑定**。
- `IMPORT` 必须出现在文件顶层,不允许在函数体内部动态 `IMPORT`。

#### 重复导入规则[v0.2 修订,核心防御]

> **v0.1 中"后导入的覆盖"语义已删除**。隐式覆盖会让 AI 无法预判符号绑定结果,是高频 bug 来源。

- 同一作用域内,**重复导入同名符号** → `E0021: name 'x' already bound by previous IMPORT`。
- **不**允许隐式覆盖(无论两次 `IMPORT` 的是同一模块还是不同模块)。
- 如需重命名,使用 `AS(name, alias)`(§13.4)。

```wlwl
IMPORT("math", ["add"]);
IMPORT("more_math", ["add"]);   // 错误:E0021
AS("add", "math_add");           // 正确做法:重命名
```

### 13.4 模块命名空间(可选)

使用 `AS(name, alias)` 重命名:

```wlwl
IMPORT("math", ["add"]);
IMPORT("more_math", ["add"]);
AS("add", "math_add");           // math 版本的 add 改名为 math_add
// 现在 add 仍指向 more_math 版本(后导入的),math 版本通过 math_add 访问
```

> 上述示例在 v0.2 中**非法**——重复导入直接 `E0021`。`AS` 应在 `IMPORT` 的**同一位置**使用:

```wlwl
IMPORT("math", ["add": "math_add"]);     // 推荐:导入时直接重命名
IMPORT("more_math", ["add"]);             // 现在的 add 是 more_math 版本
```

具体语法在 v0.3 讨论;v0.2 仅承诺"必须重命名,不允覆盖"。

### 13.5 入口文件

```bash
wlwl run main.wl
```

`main.wl` 是入口;`IMPORT` 链式解析。具体命令行形式**不在本规范范围**(由实现/工具决定)。

### 13.6 循环导入[v0.2 新增]

- 检测到循环导入(`A` 导入 `B`,`B` 导入 `A`,形成环)时,抛出 `E0041: circular import detected: A -> B -> A`,**终止加载**。
- v0.2 **不**支持部分加载或延迟加载解决循环依赖。
- 设计动机:循环导入在 AI 生成代码中常见,显式失败比"运行时找不到名字"更易诊断。

### 13.7 模块接口契约(预留,v0.2 不实现)[v0.2 新增]

未来版本可在 `EXPORT` 中增加函数签名契约,用于模块间的动态参数校验。**v0.2 仅预留语法位置,不做检查**。

```wlwl
EXPORT([
    "add": ["params": ["INTEGER", "INTEGER"], "returns": "INTEGER"]
]);
```

> 实现细节、契约执行时点(运行时/构建时)、违反时的错误码,在 v0.3 讨论。

## 14. 错误信息格式(AI 友好核心)

### 14.1 总则

**所有** WLWL 错误,无论来自词法、语法、运行时还是用户主动 `ERR`/`PANIC`,**必须**符合以下结构化格式。实现**不得**只输出不可解析的自由文本。

### 14.2 标准错误对象[v0.2 增强]

```wlwl
ERR([
    "code": "E1003",                                  // 错误码
    "severity": "error",                              // "error" | "warning" | "note"
    "message": "division by zero",                    // 一句话人类描述
    "location": ["main.wl", 42, 5, 42, 12],           // [file, line, col_start, line_end, col_end]
    "source_line": "LET(x, /(y, z));",                // 出错行的源码
    "hint": "检查除数 z 是否可能为 0",                // 修复建议(自然语言)
    "suggestion_code": [                              // [v0.2 新增]机器可执行的修复
        "kind": "patch",                              // patch | ast_rewrite | note
        "description": "在除法前增加零值守卫",
        "patch": [
            ["replace", 42, 5, 42, 18,
             "IF(=(z, 0), RETURN(ERR(\"zero divisor\")), /(y, z))"]
        ]
    ],
    "related": []                                     // 相关位置
]);
```

#### `suggestion_code` 字段规范[v0.2 新增]

- **类型**:ARRAY(可包含多条建议,按置信度排序);也允许为 `NULL` 表示无可执行建议。
- **每条建议**是一个 DICT,字段:
  - `kind`:`"patch"`(基于源码位置替换)/`"ast_rewrite"`(基于 AST 节点重写,语法待定)/`"note"`(仅文字说明)
  - `description`:人类可读的修复描述
  - `patch`(仅 `kind="patch"`):ARRAY of `[op, line, col_start, line_end, col_end, text]`,op 目前仅支持 `"replace"`
  - `ast_rewrite`(仅 `kind="ast_rewrite"`):DICT,具体 schema 在 v0.3 讨论
- AI 工具**应优先执行** `suggestion_code` 而非仅依赖 `hint` 自然语言。
- `hint` 仍然保留,因为它对人类开发者更有用;`suggestion_code` 主要服务于 AI 自动修复。

### 14.3 顶层输出格式(CLI)

默认 CLI 输出人类可读形式:

```
error[E1003]: division by zero
 --> main.wl:42:5
  |
42 | LET(x, /(y, z));
  |          ^^^^^^^
  |
  = hint: 检查除数 z 是否可能为 0
  = fix: 在除法前增加零值守卫(可自动应用)
  = note: y 在此声明
   --> main.wl:41:5
```

通过 `--format=json` 输出机器可解析的 JSON,AI 工具**应总是**使用此格式:

```json
{
  "code": "E1003",
  "severity": "error",
  "message": "division by zero",
  "location": {"file": "main.wl", "line": 42, "col": 5, "line_end": 42, "col_end": 12},
  "source_line": "LET(x, /(y, z));",
  "hint": "检查除数 z 是否可能为 0",
  "suggestion_code": [
    {
      "kind": "patch",
      "description": "在除法前增加零值守卫",
      "patch": [["replace", 42, 5, 42, 18, "IF(=(z, 0), RETURN(ERR(\"zero divisor\")), /(y, z))"]]
    }
  ],
  "related": []
}
```

### 14.4 错误码(初版预定)

| 码 | 类别 | 含义 |
|----|------|------|
| `E0001` | 词法 | 非法字符 |
| `E0002` | 词法 | 未闭合的字符串 |
| `E0003` | 词法 | 未闭合的块注释 |
| `E0010` | 语法 | 期望表达式 |
| `E0011` | 语法 | 期望 `)` |
| `E0012` | 语法 | 期望 `,` |
| `E0013` | 语法 | 期望 `;` |
| `E0014` | 语法 | `RETURN`/`BREAK`/`CONTINUE` 出现在非法位置 |
| `E0020` | 名字 | 未定义名字 |
| `E0021` | 名字 | 重复定义 / 重复 IMPORT |
| `E0022` | 名字 | 函数元数不匹配 |
| `E0023` | 名字 | 未导出的模块成员 |
| `E0030` | 类型 | 算术运算类型错误(含 `+` 混合类型) |
| `E0031` | 类型 | 下标/键类型错误 |
| `E0032` | 类型 | 属性/方法不存在 |
| `E0040` | 模块 | 找不到模块 |
| `E0041` | 模块 | 循环导入 |
| `E0050` | OOP | 类继承链错误 |
| `E0051` | OOP | `NEW` 元数与 `INIT` 不匹配 |
| `E0099` | 用户 | 用户抛出的 `ERR`/`PANIC` |
| `E0100` | 内部 | 实现内部错误(`PANIC` 默认值) |
| `E0101` | 内部 | 栈溢出 |
| `E0102` | 内部 | 未处理的 `ERR` 逃逸到顶层 |

> 错误码**必须稳定**。任何变更都需在规范更新中说明。

### 14.5 警告(W 开头)

| 码 | 含义 |
|----|------|
| `W0001` | 名字未定义 |
| `W0010` | 未使用的 `LET` 绑定 |
| `W0011` | 未使用的函数参数(标注 `_` 前缀忽略) |
| `W0012` | 同名重复 `LET` |
| `W0013` | `IF` 的 then/else 分支类型不一致(可能 bug) |
| `W0020` | 数组/字典字面量中混用裸值和键值对 |
| `W0030` | `IMPORT` 了一个名字但未使用 |
| `W0040` | `TODO(agent):` 注释未处理 |

#### 未使用警告的 AI 语义约定[v0.2 新增]

- AI 工具在严格模式下,**应将**未使用变量/参数视为高概率 bug,优先检查是否存在拼写错误或遗漏逻辑。
- 这是因为统计上未使用绑定是 LLM 生成代码中常见的低级错误(占比最高的一类);显式警告语义约定可显著提升 AI 工具的问题识别率。
- 人类开发者可通过 `_` 前缀显式忽略(如 `LET(_unused, expr)`);AI 工具也应把这一约定作为"安全忽略"信号。

### 14.6 严重程度与退出码

| 严重度 | CLI 退出码 |
|--------|------------|
| error | 1 |
| warning | 0(在 `strict` 模式下变 1) |
| note | 0 |

### 14.7 AI 工具约定

- AI 编码工具**应总是**用 `--format=json` 调用 WLWL 编译器。
- AI 工具**应优先执行** `suggestion_code` 字段的修复,而非仅依赖 `hint` 自然语言。
- AI 工具**应**根据 `hint` 字段生成自然语言建议,作为 `suggestion_code` 不可用时的兜底。
- AI 工具**应**把 `related` 字段内的所有位置都纳入上下文,而不是只看主错误位置。
- AI 工具**应**尊重 `severity`:`warning` 在常规模式下不应阻塞,但在 `strict` 模式下应阻塞。

### 14.8 语法错误恢复策略[v0.2 新增]

- 词法/语法错误采用**单错误终止模式**:检测到**第一个**错误后,输出错误信息并终止解析,**不**进行级联错误报告。
- 错误的 `suggestion_code` 字段可提供最多 3 个按置信度排序的修复方案(实现可选,推荐提供)。
- 设计动机:级联错误会掩盖真实错误,单错误模式 + 多候选修复的组合对 AI 工具的修复效率提升最明显;同时大幅降低解释器实现复杂度。
- 运行时错误(非词法/语法)**不**受单错误终止约束,可继续报告(如"未处理 ERR 逃逸" + "原始抛出点"两条)。

- v0.2 仅占位,具体签名、错误处理、超时、并发、流式响应等规范在 v0.3 讨论。
- 这些函数遵循"一切皆函数调用"的统一性原则——LLM 调用与本地函数调用语法一致。

## 16. 工具设计原则(非实现)

> **本章不规定具体命令、具体实现技术栈,只规定 WLWL 工具链必须遵守的设计契约。** 工具链是工程实现层,超出本规范范围;但 AI 工具如何使用 WLWL 是设计层问题,故在此约束。

### 16.1 工具的 AI 契约(必读)

任何与 WLWL 交互的工具(AI 代理、LSP 客户端、CI、IDE 插件)若要"AI 友好",**必须**:

1. **总是用 `--format=json`** 获取错误信息(若工具支持该 flag)。
2. **总是读取 `suggestion_code` 字段**并尝试自动应用。
3. **总是把 `related` 字段全部纳入上下文**。
4. **总是尊重 `severity` 字段**(`strict` 模式下 warning 视为 error)。
5. **总是优先使用 §14.4 错误码表**做错误分类(而非自然语言正则匹配)。
6. **永远不要**自由发挥修复方案,而应忠实执行 `suggestion_code` 或在缺失时明确告知用户。

### 16.2 工具不应做的事

- 不应在用户未授权时自动修改源码——`suggestion_code` 是**建议**,不是**自动应用**。
- 不应忽略 `code` 字段而用自然语言推断错误类型。
- 不应假设错误信息是自然语言——必须按结构化字段解析。
- 不应同时输出多个 `severity="error"` 级别的错误(由 §14.8 单错误终止保证)。

### 16.3 不在本规范范围的内容

- 具体命令(`wlwl run`、`wlwl check`、`wlwl fmt` 等)。
- 具体实现技术栈(Rust、C、字节码、AOT 等)。
- REPL、调试器、性能分析器的具体形式。
- LSP、formatter、syntax highlighting 的具体协议。
- 包管理、版本约束、中央仓库协议。

> 实现者可以自由设计这些,只要符合 §16.1 的 AI 契约。

## 18. 未决问题(留给后续迭代)

下列问题**v0.2 不决**,在迭代中讨论:

### 18.1 短期(可能在 v0.3 决定)

1. **`AS` 语法的最终形式**:`AS("add", "math_add")` vs `IMPORT("math", ["add": "math_add"])`?
2. **跨目录模块引用**:`IMPORT("../other/foo", ...)` 还是只允许包管理器?
3. **类构造函数 `init` 与 `NEW` 元数检查**:是否与函数元数统一(§8.4)?
4. **字符串模板**:要不要 `\`hello, ${name}\``?对 `+` 字符串拼接是补充还是取代?
5. **数字字面量扩展**:十六进制、八进制、二进制、`1_000_000` 下划线分隔?
6. **`std.ai` 的具体签名**:同步 vs 异步,流式 vs 一次性,超时,错误传播?

### 18.2 中期(可能在 v0.4+ 讨论)

7. **SYMBOL 类型**:4.txt 审计建议新增 `SYMBOL` 类型(`#'foo'` 或 `:foo`)。**v0.2 不采纳**,因为:
   - 与现有 STRING 边界模糊,可能成为过度设计的根源。
   - 性能优势在通用语言场景下不显著。
   - 未来若真的需要,可以独立引入,不影响现有规范。
8. **原型委托作为类的备选**:4.txt 审计建议增加 `OBJ_PROTO(obj, proto)`。**v0.2 不采纳**:
   - WLWL 的 OOP 已选择基于类(§11),引入原型是双范式负担。
   - JS 的经验表明双范式会增加教学和推理成本。
9. **`error sets` 借鉴 Zig**:5.txt 审计建议引入命名错误集。**v0.2 不采纳**:
   - 当前 `OK`/`ERR` 模式已能表达"成功/失败",`error sets` 主要价值在于编译器静态检查,与 WLWL 的"动态优先"立场冲突。
   - 未来若引入渐进类型,`error sets` 可能作为"可选的静态检查层"出现,**不**进入核心。
10. **形式化语义 / 形式化契约 (`requires`/`ensures`/`invariant`)**:5.txt 审计建议。**v0.2 不采纳**:
    - 形式化验证是重型特性,会显著增加语言复杂度。
    - WLWL 的"显式 + 简单 + 统一函数调用"美学与形式化契约的语言学风格(Ada/Eiffel)有冲突。
    - 未来若要,可以作为**外部工具**(类似 Dafny)而非核心特性引入。

### 18.3 长期愿景

11. **元编程 / 宏**:是否提供 WLWL 自身的"读取自身 AST"接口?**v0.2 仅承诺 `wlwl ast` 类工具输出 JSON AST**(见 §16 不在本规范范围);**不**承诺语言级宏。
12. **async/await**:通用语言早晚要有,但初版不做。
13. **并发原语**:协程?actor?Promise?channel?留待讨论。
14. **多目标编译**:HTML/SQL/交换机配置编译器的目标 AST 形状、共享核心语义的边界。`std.web.*` 的"Web 子集"是这一愿景的起点。
15. **包管理**:`wlwl.toml` 格式、版本约束、中央仓库协议。
16. **AI 上下文溢出处理**:4.txt 审计建议的 `E0042` 错误码**不在 v0.2 中**,因为该错误由 AI 工具本身报告,不是 WLWL 编译器产物。AI 工具可自行决定如何处理超长上下文。
17. **错误码扩充**:v0.2 错误码 23 个,稳定不变;后续扩展须严格按"先提案、后实现、再进规范"流程。

CLASS("Rectangle", NULL, [
    "width": 0,
    "height": 0,
    "init": FUN((self, w, h),
        SET_PROP(self, "width", w);
        SET_PROP(self, "height", h)
    ),
    "getArea": FUN((self),
        *(GET_PROP(self, "width"), GET_PROP(self, "height"))
    )
]);

EXPORT(["Rectangle"]);

// main.wl
IMPORT("rectangle", ["Rectangle"]);

LET(rect, NEW("Rectangle", 10, 20));
PRINT(GET_PROP(rect, "getArea")());  // 200
