## 范围 (spec v0.4 §12.2 + §12.8 + §14.2)

| 项 | 行为 |
|----|------|
| `UNWRAP(OK(v))` | → `v` |
| `UNWRAP(ERR(e))` | → PANIC `E0100` with `cause = e`（ErrorCause::String 或 ErrorCause::Dict）|
| `UNWRAP(non-RESULT)` | → `E0030` type error |
| `ERR_PAYLOAD(ERR(e))` | → `e` |
| `ERR_PAYLOAD(OK(_))` | → `E0030` "expected ERR, got OK" |
| `ERR_PAYLOAD(non-RESULT)` | → `E0030` |
| `WRAP(ERR(e), ctx)` | → `Err({"original": e, "context": ctx})` |
| `WRAP(OK(v), _)` | → `OK(v)` pass-through（ctx 被忽略）|
| `WRAP(non-RESULT, _)` | → `E0030` |
| `WRAP(WRAP(...))` | 嵌套 dict（**不**做 flatten）—— `original` 始终是上一层的 whole ERR value |
| `cause` 字段 | 通过 WRAP 链构建；UNWRAP 时填入 E0100 diagnostic 的 `cause` slot |

- `UNWRAP` / `ERR_PAYLOAD` / `WRAP` 的 v0.3 alias + W0051 → **本批不做**。这些是 v0.4 §12.7 canonical names，不是 v0.3 别名（v0.3 时代根本没有 UNWRAP 原语）。W0051 路径只在 B2 DEL / B3 OR_DIE 这类有 v0.3 字面映射的别名上。
- A1e `cause` 的 AI 工具链消费方（auto-apply fix）→ 等 Phase G 质量门禁 CI 强制 jsonl schema 后再说
- 例外传播（exception propagation）→ 不在 v0.4 scope

## 关键设计决策

### 1. `WlwlDiagnostic.cause` 早就在 A1d 准备就位，B4 只是填值

A1d (commit `e1531fc`) 把 `cause: Option<Box<ErrorCause>>` 字段加到 `WlwlDiagnostic`（A1d history §关键字段 1.1.0），`ErrorCause` 是 `#[serde(untagged)]` enum `String(String) | Dict(serde_json::Map)`。A1d 把字段放在那但所有 diagnostic 都填 `None`；A1e deferred "待 B4 WRAP 链填入"。

B4 把 `UNWRAP(ERR(e))` 路径上的 E0100 填充 `cause = value_to_error_cause(e)`。`with_cause(ErrorCause)` builder 自带 replace 语义（如有第二次 with_cause 覆盖前值）。

### 2. `Evaluator.current_span` 字段 + eval_call save/restore

内置函数签名是 `fn(&mut Evaluator, Vec<Value>) -> WlwlResult<Outcome>`——不接收 span 参数。要让 `builtin_unwrap` 构造 span-aware 的 E0100（`location.file/line/col` 是 UNWRAP **call site**，不是 `<runtime>`），需要把 span 临时存到 Evaluator 上。

`eval_call` 在 `b(self, arg_values)` 调用前后 save/restore `self.current_span`：
```rust
let prev_span = self.current_span.take();
self.current_span = Some(span.clone());
let result = b(self, arg_values);
self.current_span = prev_span;
return result;
```

save/restore 是为防止 builtin 内部递归触发 `eval_call`（理论上大多数 builtin 不会，但 native fn / std 包装器可能）覆盖外层 span。绝大多数 builtin 不读 `current_span`——只有 `builtin_unwrap` 用。

### 3. `WRAP` 不做 flatten，保留嵌套 dict 链

`WRAP(WRAP(ERR("e"), "c1"), "c2")` 产生 `ERR({"original": <previous-ERR>, "context": "c2"})` 而不是 `ERR({"original": "e", "context": "c2"})`。

理由：
- 不丢失信息：每次 WRAP 都看到完整的上一层结构（如果未来想加"链长度"统计，flat 化后拿不到）
- 用户可决定何时/是否 flatten：`WRAP(WRAP(ERR("e"), "c1"), "c2").original.original` 拿最深层 original，`WRAP(...).context` 是最近一层 context
- 跟 Rust `?` operator 的 `From::from` 链类比——每层 source 都包一个 context

错误消息（含顶层）原样展示嵌套结构：`"original: {original: e, context: c1}, context: c2"`。

### 4. `value_to_error_cause` 仅在 STRING / DICT payload 返回 `Some`

ERR(payload) 在构造阶段（`ERR(e)` eval）就校验过 `e` 必须是 STRING 或 DICT（spec §2.2.1 + A1 已有测试 `err_payload_integer_errors_with_e0030` 等覆盖）。所以 B4 的 `value_to_error_cause` 在 well-formed 程序里**总是**返回 `Some`，`None` 分支只在 legacy 异常数据上才触发（panic-safe，不爆）。

转换规则：
- `Value::String(s)` → `ErrorCause::String(s)`
- `Value::Dict(entries)` → 递归转 `serde_json::Value` → `ErrorCause::Dict(map)`
- `Value::Err(inner)` → 递归 unwrap（防御性，正常 WRAP 链不会产生 ERR-in-ERR）
- 其他（Integer / Float / Array / Boolean / Null / Closure / NativeFn）→ `None`

### 5. `value_to_json_value` 是 `value_to_std_value` 的简化版

`wlwl-std` 已有 `value_to_std_value` 把 `Value` 转 `StdValue`（带 Result error）。B4 需要 infallible 转换（`cause` 字段塞值不抛错），所以新加 `value_to_json_value`：
- 闭包 / native fn / NaN / Inf → `None`
- 其他 → 对应 `serde_json::Value`

Array / Dict 元素递归处理；OK 透传 unwrap；ERR 跳过（不会无限递归，因为 WRAP 不会产生 ERR-in-ERR）。

### 6. ERR consumer registry 注释统一更新

A6 在注册表给 UNWRAP / ERR_PAYLOAD / WRAP 留了 "**not yet implemented** (Phase B4)" 标注。本批改为反映 B4 完成状态：

```
/// | `UNWRAP`      | `PANIC` E0100 with `cause` = payload — spec §12.2 (Phase B4) |
/// | `ERR_PAYLOAD` | extracts payload — spec §12.2 (Phase B4)              |
/// | `WRAP`        | re-wraps with `{original, context}` dict — spec §12.2 (Phase B4) |
```

### 7. `registry_unwrap_not_yet_implemented` → 重写为 B4 contract

原测试（line 4509）的注释明确说："will start failing once Phase B4 lands, which is the intended behavior (a follow-up commit then updates this test to assert the new B4 contract)"。本批就是那个 follow-up：

```rust

    // (`registry_unwrap_not_yet_implemented`) is closed: E0020
    // no longer fires for UNWRAP.

```

### 8. 不发 W0051 — 这些是 v0.4 canonical 名（不是 v0.3 alias）

B2 DEL / B3 OR_DIE 是 v0.3 字面名 → v0.4 canonical 的别名，每次用触发 W0051 弃用警告。

`UNWRAP` / `ERR_PAYLOAD` / `WRAP` 在 v0.3 **没有**任何等价字面（v0.3 只有 `OR_DIE` / `UNWRAP_OR` 是 OK/ERR consumer；UNWRAP 是 v0.4 新原语）。所以零 W0051 路径——这是有意差异，不是疏漏。`b4_does_not_register_or_die_alias_path` 测试锁定。

### 9. `WlwlDiagnostic::with_cause` builder

跟现有 `with_hint` / `with_suggestion` / `with_related` 风格一致：
```rust
pub fn with_cause(mut self, cause: ErrorCause) -> Self {
    self.cause = Some(Box::new(cause));
    self
}
```

命名风格选择 `with_X` 而不是 `set_X`，因为 `set_cause` 听起来像 mutable 引用方法（这其实是 `&mut self` consuming builder）。`with_X` 是 Rust 惯例。

## 反思（本次踩到的坑）

1. **顶层 WRAP(ERR, ctx) 触发 E0102 截断**：跟 B3 `b3_doc_style_unwrap_or_chains_are_silent` 同款陷阱——顶层 expression 评估完检查 ERR 是否被消费，没被消费就 E0102。WRAP 本身合法，但返回 ERR([...]) 到顶层就是 ERR value，被截断。修复用 `ERR_PAYLOAD(WRAP(...))` 把 WRAP 结果取出来再 assert。
2. **user function 不是 ERR consumer：`f(ERR_value)` 被 §12.6 截断不进入 f body**：第一次写测试 `LET(f, FUN((x), UNWRAP(x))); f(ERR(...))` 期望 UNWRAP 触发 panic，结果 E0102 "ERR escaped to top level"。f 不在 §12.7 registry，ERR 参数在 arg eval 阶段就被截断。修复：ERR 必须在 f body 内部构造（LET 绑定），不能从参数传入。
3. **ErrorCause 没在 wlwl-eval scope**：第一次编译报 `cannot find type ErrorCause`，加 `use wlwl_error::{..., ErrorCause, ...}` 修。
