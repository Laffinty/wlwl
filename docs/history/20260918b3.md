## 关键设计决策

### 1. W0051 触发点只在 `Expr::OrDie` AST eval 分支

`OR_DIE` 是无条件 lexer keyword（`TokenKind::OrDie`），parser 的 `parse_or_die`
严格把它降为 `Expr::OrDie` AST 节点；运行时永远不进 `resolve_builtin("OR_DIE")`。
所以 W0051 只在 `eval_expr` 的 `Expr::OrDie { ... }` arm 顶部 emit 一次。

`builtin_unwrap_or_compat` wrapper（指向 `OR_DIE` 的 dispatch alias entry）保留
作为**防御性 alias entry**——当前 unreachable，但未来 `OR_DIE` 改成 identifier
时立刻 work，零额外代码。注释明确说明这一事实，避免下一个读代码的人疑惑
"这个 wrapper 是干嘛的"。

### 2. OR_DIE 触发 W0051 不分 OK / ERR / short-circuit

与 B2 `DEL` 行为有意差异。`DEL` 在 ERR 流上不发警告，因为 `DEL` 不是 §12.7
ERR consumer，ERR 透传给 legacy 调用方是透明的；ERR short-circuit 跳过 alias
wrapper 防止 spam。`OR_DIE` 是合法 ERR consumer——用户写 `OR_DIE` 是有意的
ERR 处理——所以无论 value 是 OK / ERR / non-RESULT / arity 错误，每次 source
occurrence 都发 `W0051`。spec §14.5 文字"使用 v0.3 已弃用别名"是按 source
occurrence 算的。

### 3. OR_DIE arity 是 parse-time 错误，不是 runtime E0022

`OR_DIE` 是 lexer keyword，parser 的 `parse_or_die`（line ~1072）严格语法
`OR_DIE '(' expr ',' expr ')'`。少 / 多参数触发 `E0012` "expected ','" /
`E0011` "expected ')'"，是 parse-time 错误，不进 eval。
`UNWRAP_OR` 是 builtin call，arity 错误在 runtime 走 `E0022`。两种名字两种
路径，测试分别锁定（B3 子组 §`b3_or_die_arity_*_is_parse_time_error` +
`b3_unwrap_or_arity_*_saying_unwrap_or`）。

### 4. `builtin_unwrap_or` 函数重命名 + 错误消息统一

- `builtin_or_die(_ev, args)` → `builtin_unwrap_or(_ev, args)`（line ~1797）
- 函数体内 3 处字符串 `"OR_DIE"` → `"UNWRAP_OR"`：
  - `arity_error("UNWRAP_OR", args.len(), 2)`
  - `type_error("UNWRAP_OR", ...)`
  - `format!("expected OK/ERR, got {}", ...)`
- 文档注释更新：canonical name 说明 + 指向 `compat` wrapper

`_ev` 仍保留下划线前缀（ev 在函数体内不使用，与 B2 `builtin_remove_key` 同款）。

### 5. `Expr::OrDie` arm 的 E0030 错误消息统一

`Expr::OrDie` eval 分支的 `other` 分支（non-OK/ERR）错误消息从
`"OR_DIE expects OK/ERR, got X"` 改成 `"UNWRAP_OR expects OK/ERR, got X"`。
理由：项目内部错误消息层级用 canonical name（B2 `REMOVE_KEY` 也是这模式），
避免让工具链（grep / AI 自动 apply）误以为需要 rename `UNWRAP_OR` → `OR_DIE`。

`Expr::OrDie` arm 顶部 emit W0051 之后才 `eval_expr(value)`——确保
short-circuit（`o.signal != Signal::None`）不会跳过警告：TRY 提前 RETURN 时
仍然 emit（用户写了 `OR_DIE` 这个 alias 是事实，是否真消费 ERR 不重要）。

### 6. `builtin_unwrap_or_compat` wrapper 名字选择

用 `_compat` 后缀跟 B2 `builtin_remove_key_compat` 对称。函数体内 emit W0051
后直接 delegate `builtin_unwrap_or(ev, args)`，无新逻辑 path。
`builtin_unwrap_or` 签名保持 `_ev: &mut Evaluator`（实际不需要 ev），但
compat wrapper 需要 `ev` 来 emit warning，所以 compat 用 `ev`（无下划线）。

### 7. dispatch 表 4 处注释更新

`resolve_builtin` 段（line ~1318-1327）把旧的 "UNWRAP_OR is the main name;
error messages still surface as OR_DIE until Phase B3 unifies..." 改成反映
B3 完成状态；`ERR_CONSUMER_REGISTRY` 表格 UNWRAP_OR 行说明（line ~1346）
改成 "canonical (v0.4 §12.7); OR_DIE is the v0.3 alias that emits W0051"。
`ERR_CONSUMER_REGISTRY` 字符串列表保留 `OR_DIE` / `UNWRAP_OR` 两条
（注册表语义是 spec 字面名；A6 注释已说明 lexer-keyword 路径不进 registry）。

### 8. `wlwl-error` 3 处状态注释

W0051 enum 定义 / `category()` 路由 / `snap_name` fixture 三处的
"Added in Phase B2 / wired in Phase B3" 注释统一更新为
"Added in Phase B2 (DEL alias) + Phase B3 (OR_DIE alias)"。无新增 W-code /
新增 W-category / 新增 fixture（W0051 + `deprecated_alias` 不变）。

- `builtin_or_die(_ev, args)` → `builtin_unwrap_or(_ev, args)`（line ~1797）

- 新增 `builtin_unwrap_or_compat(ev, args)`（line ~1822）：

  ```rust
  /// v0.4 §12.7 + §14.5 — `OR_DIE(value, default)` is the v0.3-compat
  /// alias for `UNWRAP_OR`. Per spec §14.5, every call emits `W0051`.
  /// v0.5 will drop this alias entirely.
  ///
  /// This wrapper handles the **runtime-call** path:
  ///   `OR_DIE` reaches `eval_call` only when called as an ordinary
  ///   function reference (e.g. via `f = OR_DIE; f(ERR, 0)` after a
  ///   normal `resolve_builtin` lookup). The **lexer-keyword** path
  ///   (`OR_DIE(...)` literal at parse time) is handled separately in
  ///   `eval_expr`'s `Expr::OrDie` arm — both paths emit exactly one
  ///   `W0051` per user-visible `OR_DIE(...)` source occurrence.
  fn builtin_unwrap_or_compat(ev: &mut Evaluator, args: Vec<Value>) -> WlwlResult<Outcome> {
      ev.emit_warning(
          ErrorCode::W0051,
          "`OR_DIE` is a v0.3-compat alias; use `UNWRAP_OR` instead (will be removed in v0.5)",
      );
      builtin_unwrap_or(ev, args)
  }
  ```

## 反思（本次踩到的坑）

1. **OR_DIE arity 是 parse-time 不是 runtime**：第一版测试写 `OR_DIE(OK(1))`
   期望 runtime E0022，但 parser 严格 `parse_or_die` 直接报 E0012。改测
   parse-time 错误。教训：lexer-keyword 类内建（`OR_DIE` / `IS_OK` / `IS_ERR` /
   `TRY`）的 arity 都在 parse 时校验，runtime arity 只对 builtin-call 路径有效。

2. **`OR_DIE(OR_DIE(OK(1), 0), 0)` 不是合法 nested**：内层返回 integer，
   外层收到非 RESULT → E0030。合法 nested 只能发生在 default arg 位置（外层
   走 ERR branch 才 eval default）或 user function 调用栈。第一版测试错把
   "nested" 写成"outer wraps inner"，改为"inner 在 default arg 位置"，且补
   `b3_or_die_outer_wraps_inner_returns_e0030` 锁定"非法 nested"被拒绝。

3. **`INDEX_GET` missing key 不返回 ERR 而是 E0037**：doc-style 测试想构造
   "IF EXISTS then OK else ERR" pattern，但 `INDEX_GET(d, k)` 在 missing key
   时抛 E0037 type error，不返回 ERR value。改用最简 `UNWRAP_OR(OK/ERR,
   default)` 直接消费 RESULT 锁定 silent-canonical 契约。

### 为什么不直接删 `builtin_unwrap_or_compat`？

A6 在 dispatch 表给 `OR_DIE` 加了 `Some(builtin_or_die)` entry，但 `OR_DIE`
永远走 lexer-keyword 路径——wrapper 实际 unreachable。但 plan v0.2 §3 Phase
B3 明确说 "`OR_DIE` 保留为 v0.3 兼容别名"，所以保留 wrapper + dispatch
entry 作为防御性 alias。未来 OR_DIE 改回 identifier 时立刻 work，零额外代码
路径。注释明确说明这一事实。
