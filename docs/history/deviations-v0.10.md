## D10-005 · `FUN(...) -> U` 箭头形式不可达且**不报错**

- **状态**:接受保留(D-5 已定「最小显式约束」,本版不解决;等 `->` 终结符落地)
- **发现时机**:Step 3 实测 `Ty::Fun` 的可达性时
- **影响范围**:类型注解文法
- **现象**:`parse_type_expr_from_pieces` 把类型区采集成平铺 token 列,解析完
  `FUN` 头后把剩余 pieces 拼成一个 `Named`。于是 `FUN(INTEGER) -> STRING`
  **不报错**,而是落成 `Named { name: "( INTEGER ) - > STRING" }` —— 用户看不到
  任何错误,却也得不到任何检查。同理,尖括号形式
  `DICT<STRING, INTEGER>` 也**不可达**(被吸收成单个不透明类型)。
- **处置选项**:(a) 补 `->` 终结符(语法面扩张);(b) 检出残余记号并报错;
  (c) 写进规范
- **裁决**:本版 **(c)** —— spec §2.6 与附录 A **如实写明**「箭头形式与尖括号形式
  都不可达,本规范不承认」,并把 (b) 留作后续项(比 (a) 小:只加一条诊断,不动词法)。
  Step 12 顺带在 `parse_type_expr_from_pieces` 加了兜底:残余 pieces 里出现 `:` 时
  报 `E0010` 而不是静默吸收(那只覆盖「给容器加约束」一种形态,不含箭头)。
- **与 v0.9 兼容性**:无(新增语法,不改既有解析)

## D10-006 · 数组 / 字典的穷尽性不判定

- **状态**:接受保留(推 v0.10.1)
- **发现时机**:Step 8 设计 usefulness 算法时
- **影响范围**:`MATCH` 静态诊断的覆盖面
- **现象**:数组构造子按元数无限展开(`[]` / `[x]` / `[x, y]` / …,带 `*rest`
  又是 `[n..∞)`),字典是**键子集**匹配。`[1, _]` 与 `[_ , 2]` 的**并集**能盖住
  `[_, _]`,而**任何一行单独都盖不住** —— 只做单行句法判定必然误报。
- **处置**:闭空间走精确并集递归;数组 / 字典 / 未知列走**保守句法**,判不准就
  `Unknown` 不报
- **代价**:漏报(例如 `[1, _]` 之后的 `[_, 2]` 不会被报成不可达)
- **与 v0.9 兼容性**:无(漏报方向)

## D10-007 · `OPTION` 是注解糖,但 `strict_types` 默认关

- **状态**:接受保留(设计上就该如此)
- **发现时机**:Step 8 决定构造子空间时
- **影响范围**:`Ty::Option` 的静态判定
- **现象**:`OPTION[T]` 在运行期**没有**对应类型(spec §2.1 的 13 个值域里没有它),
  它的两个见证是 `NULL` 与 `RESULT[T, ·]`。但 `strict_types` 默认关,**注解
  并未被运行时强制** —— 于是把 `Ty::Option` 枚举成 `{NULL, OK(_), ERR(_)}`
  是不成立的:被注解为 `OPTION` 的变量在运行期可能装着任何东西。
- **裁决**:静态层**不枚举** `OPTION` 的构造子空间(宁可漏报);`satisfies_annotation`
  仍承认它的两个见证(那是**注解边界**判定,与构造子枚举是两件事,见 spec §5.2.1)
- **与 v0.9 兼容性**:无

## D10-008 · 泛型没有量词语法,同一变量每处都要重写约束

- **状态**:接受保留(D-5 的直接推论;后续版本再议)
- **发现时机**:Step 9
- **影响范围**:`T: Bound` 的书写
- **现象**:本版泛型**只能**写成「裸标识符 + 显式约束」,且**没有**量词语法
  (`FUN[T](…)` 不存在)。于是
  `FUN((a: T: Comparable, b: T: Comparable) : T: Comparable, …)` 里
  `T: Comparable` 要写三遍。
- **为什么不用裸 `T` 当变量**:裸的未知类型名(`x: Foo`)在语言里**只能**是不透明
  类型 —— 没有声明名义类型的语法,没人认识的名字要么是拼错了、要么是某个
  运行期类型。让它当变量会**悄悄废掉** `LET(x: Foo, 1)` 的 `E0110` 拼错诊断。
  保住这条诊断比少写两遍约束更值(锁测试
  `a_bare_unknown_name_is_still_an_opaque_type`)。
- **与 v0.9 兼容性**:无(新增语法)

### D10-013 · `ARRAY(items...)` / `DICT(pairs...)` 是三份副本**共同**虚报的幻影 API

- **状态**:**已修复(2026-09-29)** —— 裁决:三处全删,只留零参形式
- **发现时机**:Step 10 / R10-064,核实 `ARRAY` / `DICT` 时顺带撞上
- **影响范围**:spec §10.9、spec 附录 G、`BUILTIN_REGISTRY`、`docs/appendix_G.md`
- **现象**:三份副本**都**写着 `ARRAY(items...)` / `DICT(pairs...)`。实测
  `ARRAY(1, 2)` 与 `DICT("a", 1)` 都报 `E0020: undefined name`。零参形式
  `ARRAY()` / `DICT()` 由 `wlwl-eval` 的 `eval_call` **直接拦截**并返回空容器,
  根本不走 `resolve_builtin`;带参形式则落到未定义名分支。
- **为什么一直没被发现**:这正是「多份副本 + 只锁数目」的典型失效 —— 三份
  **同样错**,于是彼此"一致",谁也没被锁住。条目数锁(110 == 110)照样绿。
- **裁决(2026-09-29,用户拍板)**:三处全删,只留 `ARRAY() -> ARRAY` /
  `DICT() -> DICT`,并顺带核对 §4.8 与 §10.9 正文。§4.8 原本已经写对
  (「空字典只有一种写法:`DICT()`」),§10.9 此前写的是

## D10-NNN 行为变更汇总(v0.10.1)

> 下面四条是 v0.10.1 里**真正改变既有程序可观察行为**的修复,按计划书附录 A
> 的要求登记,并同步进 `CHANGELOG.md` 的 §0.4 兼容性承诺表。
> 纯文档 / 纯测试的改动不登记 —— 偏差台账记的是行为与承诺,不是工作量。

### D10-014 · `CLASS` / `INSTANCE` 的相等按**对象身份**判(R10-012)

- **状态**:**已修复(2026-09-29)**
- **发现时机**:v0.10.1 动态 REVIEW 的 P0-4
- **影响范围**:`wlwl-eval` 的 `==` / `!=` 派发;spec §2.4
- **现象**:`==` 作用在 `CLASS` 或 `INSTANCE` 上**恒为 `FALSE`** —— 包括
  拿一个对象和它自己比。这**破坏自反律**:`x == x` 对任何值都应当为真。
- **修法**:按对象身份比较 —— `CLASS` 比类身份,`INSTANCE` 比对象身份
  (即「是不是同一个东西」),而不是比值。
- **行为变更**:这批修复里**唯一一个让更多程序通过**的。原先恒假的
  `a == a` 现在为真;原先恒真的两处**不同**对象比较不受影响。
  依赖「实例比较恒为 FALSE」这一错误行为的程序不存在合理动机,但如果有,
  它现在会开始为真。
- **必须进 §0.4**:它改变既有程序的可观察结果。
- **锁测试**:`impl/tests/conformance/oop/` 身份夹具 + 自反 / 对称 / 传递三律。

### D10-015 · 无缓冲通道的 rendezvous 不再顺序敏感 + 新错误码 `E0064`(R10-014)

- **状态**:**已修复(2026-09-29)**
- **发现时机**:v0.10.1 动态 REVIEW 的 P0-3
- **影响范围**:`wlwl-runtime` 的通道等待表;spec §17.7;**新增错误码 `E0064`**
- **现象**:阻塞型 `CHANNEL_SEND` / `CHANNEL_RECV` 的唤醒判定先于「唤醒对端」
  执行,于是**生产者先 `SPAWN` 必假死锁** —— 这与 §17.7 的明文冲突。
  文档里没有任何地方提示这一点。
- **根因**(与计划书的描述不同):不是「唤醒顺序」,是 `CHANNEL_RECV` 缺
  `try_pair_recv` 的**对偶调用** —— 配对逻辑只在一侧存在。
- **修法**:唤醒等待对端**之后**再做 L1 死锁判定。
- **新增错误码 `E0064`**(此前完全未占用):**活锁护栏**。同一对任务在同一条
  **无缓冲**通道上**第二次** rendezvous 时报出。护栏按**任务对**计数(不是按
  通道),阈值 2,**只对 `capacity == 0` 生效**。真死锁仍分别报 `E0065` /
  `E0053`。
- **行为变更**:一批原本假死锁的程序会**开始正常完成**。这是修 bug,但
  可观察结果变了。
- **已登记的限制**:无缓冲通道上同一对任务**只能交接一次**(`E0064` 护栏);
  **缓冲通道**上的「发 N 条收 N 条」循环**挂死** —— 段重跑模型限制,
  **修之前就挂**,非本轮引入,护栏刻意不覆盖它。需段内恢复才能根治,属 v0.11。
- **必须进 §0.4**:新增了码号,且改变既有程序的可观察结果。
- **错误码计数**:E 码 74 → **75**。

### D10-016 · `IMPORT` 的签名类型进入类型检查(R10-023)

- **状态**:**已修复(2026-09-29)** —— 用户已确认接受这项行为变更

### D10-018 · `wlwl fmt --check` 把 CRLF 判成规范偏离(Windows CI 抓出来)

- **状态**:**已修复(2026-09-29)** —— 用户裁决:比较前归一化行尾
- **发现时机**:v0.10.1 推送后 CI **run #156** 的 Windows job 在 `cargo test`
  红了(ubuntu / macOS 同一步都过)。日志需鉴权取不到,改用「把夹具强制转成
  CRLF 再跑」在本地精确复现。
- **影响范围**:`wlwl fmt --check` 的判定口径(`wlwl-cli/src/main.rs`)
- **现象**:规范形式由 `wlwl_formatter::format` 生成,行尾恒为 `\n`;源码那一侧
  原样保留磁盘上的 `\r\n`,于是逐字节不等:

  | 输入 | 修之前 |
  |---|---|
  | `PRINT("x")\n` | rc=0 |
  | `PRINT("x")\r\n` | **rc=1 + `W0053`** |

- **为什么会漏到发布**:仓库的 `.gitattributes` **只给 `*.rs` 定了 `eol=lf`**,
  `.wll` 夹具没有任何规则。Linux 检出恒为 LF,Windows 检出(`core.autocrlf`
  生效)恒为 CRLF ⇒ **同一个 commit 在两台机器上结论相反**。格式化器从来没
  考虑过行尾,这个洞一直开着;是 D-5(97 个 probe 进 CI)把它**暴露**出来的 ——
  `G3_fmt_check_clean` / `G4_fmt_idempotent` 两条正是干这件事的。
- **定性**:「CRLF 文件偏离 §16.3 规范形式」这句话**本身是错的**。规范规定的
  是 token 之间的空白与换行**布局**(一条语句一行、无缩进、无句末分号),
  **没有规定换行用哪个字节表示**。所以要改的是判据,不是文件。
- **修法**:比较前把两侧的 EOL 统一成 LF(`normalize_eol`),顺序上**先归一化
  再剥注释**,这样 `strip_comments` 看到的是干净的 `\n`。裸 CR 一并归一 ——
  它在 lexer 能过、在 formatter 不该过,留着就是另一个同类洞。
- **行为变更**:`--check` 从「拒绝 CRLF」变成「接受 LF 与 CRLF」。

  | 场景 | 之前 | 现在 |
  |---|---|---|
  | 规范源码 + LF | rc=0 | rc=0 |
  | 规范源码 + CRLF | rc=1 `W0053` | **rc=0** |
  | 规范源码 + 裸 CR | rc=1 `W0053` | **rc=0** |
  | **真**偏离(多余空格)+ CRLF | rc=1 | **rc=1**(不变) |

  最后一行是反向守卫:归一化**不能**把真正的偏离一起放过去。
- **不在本次范围**:`wlwl fmt <file>` 的 **stdout 输出仍恒为 LF** —— 那是
  `wlwl-formatter` 的渲染结果,改动面在那个 crate。
- **未处理(已与用户确认本轮不动)**:`impl/examples/showcase.wll`、
  `impl/examples/phase2_demo.wll`、`wlwl-skill/interp.wll` 这 **3 个文件的
  blob 本身就是 CRLF**,而其余 178 个 `.wll` / `.sig` 全是 LF。恰好前两个是
  R10-070 刚接进 CI 的示例。归一化它们会在下一次 checkout 时产生一次真实
  diff,本轮不扩大。
