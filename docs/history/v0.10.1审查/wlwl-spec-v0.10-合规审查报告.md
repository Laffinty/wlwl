# WLWL v0.10 规范符合性独立审查报告

- **被审对象**:`wlwl.exe`(`--version` → `wlwl 0.10.0`,Windows x64,3,463,680 字节)
- **基准文档**:`docs/standard/wlwl-spec-v0.10.md`(2,432 行 / 150,246 字节)
- **辅助文档**:`wlwl-skill/SKILL.md`、`wlwl-skill/reference.md`、`CHANGELOG.md`
- **审查方式**:黑盒。全部结论来自**在本工作文件夹内**编写 `.wll` 程序并观测 `wlwl.exe` 的可观察行为(退出码 / stdout / stderr / JSON 诊断)。
- **审查边界**:未读取任何 WLWL 源码(Rust 实现);未访问本工作文件夹以外的任何文件;所有临时用例、清单、签名文件均写在 `_audit/cases/` 下。

---

## 一、结论摘要

**不是 100% 完整实现。** 核心语言、类型系统、OOP、会话类型协议、线性 `THIS`、并发、静态契约层、CLI 工具链整体质量很高 —— 30 个随包示例全部通过,108 个附录 G 内建里 104 个行为完全正确。但存在 **13 项确认缺陷**,其中 **4 项为 P0**(会让按规范写出的正确程序直接无法解析或静默算错)。

| 等级 | 数量 | 说明 |
|---|---|---|
| **P0** | 4 | 规范明确要求的能力完全缺失,或错误被静默吞掉 |
| **P1** | 5 | 规范条款与实现行为不一致,产生错误诊断码或错误分类 |
| **P2** | 4 | 规范声明的警告/特性未实现,文档与实现脱节 |
| **P3** | 0 | — |

**关键风险**:P0-1(具名 `FUN`)使规范 §5.1 的整条语法分支不可用;P0-2/P0-3(`WHILE`/`FOR` 体吞 `ERR`)是**静默错误** —— 程序不报错、不中止,继续跑出错误结果,这是最危险的一类。

## 二、P0 缺陷(严重)

### P0-1 具名函数定义 `FUN name(params) body` 完全没有实现

**规范依据**:§5.1 明文规定两种形式等价 ——
> `FUN(name(params), body)` 产生同样的函数值,**并**在当前作用域将 `name` 绑定到它——与 `LET(name, FUN(...))` 等价。

附录 A.2 文法同样定义:`FunExpr = "FUN" [ identifier ] "(" [ Param { "," Param } ] ")" [ ":" TypePos ] Expression .`
`identifier` 在方括号内表示**可选** —— 该分支是规范的一部分。

**实测**(6 种写法全部失败):

| 写法 | 退出码 | 实际诊断 |
|---|---|---|
| `FUN f(x) x;` | 3 | `E0011: expected '(', got Ident("f")` |
| `FUN f(x) (x);` | 3 | 同上 |
| `FUN f((x)) x;` | 3 | 同上 |
| `FUN f() 1;` | 3 | 同上 |
| `FUN f((x), x);` | 3 | 同上 |
| `FUN f(x) (x + 1);` | 3 | 同上 |
| `LET(f, FUN((x), x));` | 0 | ✅ 正常 |

**影响**:解析器在 `FUN` 后只接受 `(`。规范 §5.1 的整个「函数定义即绑定」语义不可达。注意 `RETURN`/`BREAK` 的检查也依赖函数体识别,这一缺陷会连带影响调用栈判定。

**对照**:附录 B 第 11 条「命名函数定义绑定名字;`LET` 与命名定义可并存」同样落空。

---

### P0-2 `WHILE` / `FOR` 循环体内的 `ERR` 被完全吞掉 —— 不传播、不中止

**规范依据**:§6.2 —— 「体产生的 `ERR` 终止循环并传播」;§6.3 `FOR` 同理。

**实测**:

```wlwl
LET MUT(i, 0);
LET MUT(n, 0);
LET(r, WHILE(<(i, 100), (SET(i, +(i, 1)); SET(n, +(n, 1)); IF(==(i, 3), ERR("stop"), 1))));
PRINT(n);        // 实测 100
PRINT(IS_ERR(r));// 实测 FALSE
```

- 规范要求:第 3 轮中止,`n == 3`,`r` 为 `ERR`
- 实测:循环**跑满 100 轮**,`n == 100`,`r` 不含 `ERR`,退出码 `0`

`FOR` 同样:体在第 2 个元素产生 `ERR`,实测仍跑满 3 轮,`IS_ERR(r)` 为 `FALSE`。

**对照实验**:`(1; ERR("stop"))` 块序列、`IF(TRUE, ERR("b"), 1)` 均正确传播 → 问题**特定于循环构造**,不是 `ERR` 机制本身的问题。

**影响**:这是**静默错误**。程序不报任何诊断、退出码 0,却跳过了错误处理并继续执行后续逻辑。任何「循环里逐项校验、遇错即停」的模式都会失效。§10.1 也明确要求「集合套件回调抛出的 `ERR` 使整个调用传播」,同类问题需一并复核。

---

### P0-3 `RETURN` 出现在函数体外不报 `E0014`,而是静默终止整个程序

**规范依据**:§6.4 —— 「三者出现在函数或循环体之外时产生 `E0014`」;§11.2 `E0014` 行同义;附录 B 第 6 条、SKILL 反模式 #6。

**实测**:

| 写法 | 规范 | 实测 |
|---|---|---|
| `PRINT("before"); RETURN(1)` | `E0014`,rc=1 | **rc=0**,只输出 `before`,程序静默结束 |
| `RETURN(1)` | `E0014`,rc=1 | **rc=0**,无任何输出 |
| `RETURN()` | `E0014`,rc=1 | **rc=0** |
| `(RETURN(1))` 块内 | `E0014`,rc=1 | **rc=0** |
| 循环体内 `RETURN(99)` | `E0014`,rc=1 | **rc=0**,循环中止但无诊断 |
| `BREAK()` 顶层 | `E0014`,rc=1 | ✅ rc=1 `E0014` |
| `CONTINUE()` 顶层 | `E0014`,rc=1 | ✅ rc=1 `E0014` |

`BREAK` / `CONTINUE` 正确,唯独 `RETURN` 漏检。

**影响**:顶层误写 `RETURN` 会让程序**无声地少跑一半**,退出码 0。CI 门禁无法发现。

---

### P0-4 `CALL(fn, args...)` 动态调用在任何实参组合下都失败

**规范依据**:§10.3 —— 「`CALL(fn, args...)` 动态调用 `fn` 并传递 `args...`;`fn` 不是函数值产生 `E0020`」;附录 G 登记 `CALL | CALL(fn, args...) -> v | ✔ 可调用 | 已定义`。

**实测**:

| 写法 | 实测 |
|---|---|
| `CALL(f, 1)`(f 为一元闭包) | rc=1 `E0030: CALL: CALL(closure, ...) is dispatched via eval_call already; this path is reserved for dynamic dispatch` |
| `CALL(f)` | 同上 `E0030` |
| `CALL(f, 1, 2)` | 同上 `E0030` |
| `CALL(5, 1)` | `E0030: CALL first arg must be closure...`(规范要求 `E0020`) |
| `f(1)` 直接调用 | ✅ rc=0 |

诊断文本自陈「this path is reserved for dynamic dispatch」—— **该路径未实现**,是留白而非设计。

**影响**:§10.3 与附录 G 承诺的动态分发能力完全不可用。附录 G 的「可调用 ✔」列对该条目不成立(这正是 v0.10.1 新增「可调用」列本应防住的那类漂移)。

## 三、P1 缺陷(中度)

### P1-1 `native_channel_close = true` 对 `CHANNEL_TRY_RECV` 无效

**规范依据**:§9.4 —— 「为 `true` 时,关闭后 `RECV` / `TRY_RECV` 在缓冲读空后改抛硬诊断 `E0054`」;§17.2.3 同。

**实测**:

| 场景 | `false`(缺省) | `true` |
|---|---|---|
| 阻塞 `CHANNEL_RECV` | ✅ `ERR(ChannelClosed)` | ✅ `E0054` |
| `CHANNEL_TRY_RECV` | ✅ `ERR(ChannelClosed)` | ❌ 仍返回 `ERR(ChannelClosed)` |

特性开关**只对阻塞路径生效**,`TRY_*` 路径漏实现。

---

### P1-2 `E0065` 的 `error_category` 为 `"concurrent"`,规范要求 `"deadlock"`

**规范依据**:§11.1 —— 「死锁检测产生的 `E0065` 的 `error_category` 字段值为 `"deadlock"`」;参考文档 §18 重复了同一约束。

**实测**(`--format json` 与 `jsonl` 一致):
```json
{"code": "E0065", "error_category": "concurrent", ...}
```

**影响**:编辑器 / CI 按 `error_category == "deadlock"` 分类死锁的工具会漏判。其余诊断码的 `error_category` 分类正常(`name` / `runtime` / `syntax` / `type`)。

---

### P1-3 `W0051` 弃用别名警告完全未实现

**规范依据**:§10.4 表格 `POP` / `DEL` 标注「弃用别名」、`OR_DIE` 标注「deprecated」;§11.3 `W0051` = 「使用弃用别名(`OR_DIE`、`DEL` 等)」;附录 G 三处均标「弃用别名 (W0051)」。

**实测**(`run` 与 `check` 双模式均无输出):

| 用法 | 语义 | `W0051` |
|---|---|---|
| `POP(["a":1], "a", 0)` | ✅ 正确返回 1 | ❌ 无 |
| `DEL(["a":1], "a")` | ✅ 正确 | ❌ 无 |
| `OR_DIE(OK(1), 0)` | ✅ 正确 | ❌ 无 |

**影响**:迁移引导失效。规范反复强调「`AT_K` 优于 `POP`」「`REMOVE_KEY` 优于 `DEL`」,但用户写旧名得不到任何提示。

---

### P1-4 `EXPORT` 必须在所有绑定**之后**,否则报 `E0020`

**规范依据**:§9.1 —— 「模块顶层可以有 `EXPORT(name_array)`」;附录 A.2 `Program = { ExprStmt | ModuleDecl } [ Expression ]`,`ModuleDecl` 与 `ExprStmt` **无先后约束**。

**实测**:

| 写法 | 结果 |
|---|---|
| `EXPORT(["add"]); LET(add, ...)` | ❌ rc=1 `E0020: EXPORT: name 'add' is not bound in this module` |
| `LET(add, ...); EXPORT(["add"])` | ✅ |
| `LET(a,1); EXPORT(["a"]); LET(b,2)` | ✅(放中间可以) |

实现按执行序求值 `EXPORT`,而规范未规定顺序约束。**注意**:这与 §9.2 / §9.1 的模块契约检查(`E0113`/`E0114`)相冲突 —— 那套检查需要「先知道导出面,再比对实现」,本实现做不到。放在前面的 `EXPORT` 直接崩溃,放在后面才能被 `check` 正确校验。

---

### P1-5 顶层 `LET` 绑定 `ERR` 时,§8.5 逃逸检查不生效(超出 D-19 已申报范围)

**规范依据**:§8.5 + 附录 D-19。规范**已申报**的已知限制是:顶层**非末条**语句的 `ERR` 被静默丢弃(D-19 / R10-019),并明确说明「这是已知限制」。

**实测**:该限制的**实际范围比申报的更宽** ——

| 末条语句 | 规范 | 实测 |
|---|---|---|
| `ERR("x")` | `E0102` rc=1 | ✅ rc=1 |
| `LEN(ERR("x"))`(非消费者) | `E0102` rc=1 | ✅ rc=1 |
| `IF(TRUE, ERR("x"), 1)` | `E0102` rc=1 | ✅ rc=1 |
| `MATCH(...)` 产出 `ERR` | `E0102` rc=1 | ✅ rc=1 |
| **`LET(r, ERR("x"))`** | `E0102` rc=1 | ❌ **rc=0,静默丢弃** |
| **`SET(z, ERR("x"))`**(末条) | `E0102` rc=1 | ❌ **rc=0,静默丢弃** |
| **`LET MUT(i,0); WHILE(...)` 体产 `ERR`** | `E0102` rc=1 | ❌ **rc=0** |
| **`FOR(...)` 体产 `ERR`** | `E0102` rc=1 | ❌ **rc=0** |

D-19 只申报了「非末条 `ExprStmt`」,但实测**末条的 `LET` / `SET` 绑定同样丢失**。根因与 D-19 描述一致(`eval_block` 只保留最后一个 `ExprStmt` 的 `Outcome`,`LET` / `SET` 自身值为 `NULL` 且其内部 `ERR` 无检查点),但**规范申报的边界不准确**,会误导修复范围。

## 四、P2 缺陷(轻度 / 文档漂移)

### P2-1 `W0066` 大缓冲警告未实现,且 `channel_large_buf_threshold` 无效

**规范依据**:§9.4 / §11.3 / §17.2.4 —— `CHANNEL_NEW(buf)` 超软阈值(默认 1024)产生 `W0066`;取 `0` 关闭。

**实测**(`run` 与 `check` 双模式):

| 配置 | buf | 期望 | 实测 |
|---|---|---|---|
| 缺省阈值 1024 | 2000 | `W0066` | ❌ 无 |
| 缺省阈值 1024 | 5000 | `W0066` | ❌ 无 |
| `threshold = 10` | 11 | `W0066` | ❌ 无 |
| `threshold = 10` | 100 | `W0066` | ❌ 无 |
| `threshold = 0` | 2000 | 静默 | ✅ 静默 |
| 缺省 | 1024 | 静默 | ✅ 静默 |

`CHANNEL_NEW` 本身工作正常(容量正确、无内存问题),仅警告与阈值开关缺失。

---

### P2-2 `W0013`(IF 两支类型不一致)未实现

规范 §11.3 登记 `W0013` = 「`IF` 两支类型不一致」。实测 `IF(TRUE, 1, "s")` 在 `check` 下无任何诊断。

---

### P2-3 栈溢出不是 `E0101`,而是宿主崩溃(退出码 `0xC00000FD`)

**规范依据**:§11.2 `E0101` = 栈溢出;§11.4 退出码表:`0` 成功 / `1` 程序不对 / `3` 解析失败 / `101` 实现内部崩溃。

**实测**:深递归(如 `f(100000)`)导致进程栈溢出:

```
thread 'main' (5728) has overflowed its stack
```

退出码 `3221225725` = `0xC00000FD`(`STATUS_STACK_OVERFLOW`)。
既不是 `E0101` + rc=1,也不是规范定义的 `101`。宿主直接崩溃,无诊断 trace,也无 §17.1「`AWAIT` 重抛宿主诊断」的处理。

---

### P2-4 `wlwl:std.ai` 导出面与 §10.11 完全不符

**规范依据**:§10.11 表格声明 `wlwl:std.ai` 导出 `TASK` / `MODEL` / `TOOL` / `CALL_TOOL` / `CONTEXT`,并给出示例:
```wlwl
IMPORT("wlwl:std.ai", ["TASK", "MODEL"]);
```

**实测**:
- 实际导出:`ASK`、`ASK_ALL`、`ASK_STREAM`、`COMPLETE`、`EMBED`(5 个,均可用)
- 规范列出的 5 个名字**全部报 `E0023: not exported`**,包括规范自己的示例代码
- `wlwl:std.agent` 反而**完全符合** §10.11(`TASK`/`MODEL`/`TOOL`/`CALL_TOOL`/`CONTEXT` 全部可导入)

推测:实现把 §10.11 的两张表对调了(`ai` ↔ `agent`),或 `ai` 命名空间实为 LLM 推理接口而规范未跟上。

## 八、建议修复顺序

1. **P0-2 / P0-3** —— 静默错误,危害最大且修复面小(循环体与 `RETURN` 的求值结果检查)。
2. **P0-1** —— 解析器在 `FUN` 后接受可选 `identifier`,工作量集中在 parser。
3. **P0-4** —— 补 `CALL` 的动态分发路径。
4. **P1-4** —— `EXPORT` 改为两趟(先收集绑定再校验导出面),顺带打通 `E0113`/`E0114` 的完整语义。
5. **P1-1 / P1-3 / P2-1 / P2-2** —— 局部补齐,风险低。
6. **P1-5** —— 要么把 D-19 的申报范围改准确(覆盖 `LET`/`SET`/循环体),要么在求值器加检查点;后者可一并消除整类静默失败。
7. **P2-3** —— 加递归深度保护,转成 `E0101` + rc=1。
8. **P2-4** —— 二选一:修实现导出面,或修规范 §10.11 使其与实现一致(并同步 `SKILL.md` 的 stdlib 清单)。
