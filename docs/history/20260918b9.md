## 范围 (spec v0.4 §3.4 / §14.5)

| 输入 | dispatch | 行为 |
|------|---------|------|
| `NOT(x)` | lexer `Not` → parser name `"NOT"` → eval `builtin_not` | clean — §9.4 truthiness 反向；返回 BOOLEAN |
| `!x` | lexer `Bang` → parser name `"!"` → eval `builtin_not_bang_compat` | 先 emit **W0054**（"deprecated_op_form"），再调 `builtin_not` |
| `!(x)` | 同 `!` | 同 `!`（call syntax 是 token-level 同 token） |

**§9.4 truthiness**：`Boolean(b)=b` / `Null=false` / **其他（Integer / Float / String / Array / Dict / Closure / NativeFn / Ok / Err）= true` —— 包括 `0` 和 `""` 都是 truthy。**

锁测试：`b9_not_truthiness_matches_negation_table`（10 个 case 锁定 truthiness 表）。

## 关键设计决策

### 1. 双 dispatch 入口（不是单 builtin + 内部判别）

在 eval `resolve_builtin` 表里：
```rust
"NOT" => Some(builtin_not),
"!"   => Some(builtin_not_bang_compat),  // ← 包装器：emit W0054 + 委托
```

不是单 builtin 内 `if name == "!"` 判别 —— 因为:
- **每次 dispatch 都重新检查**（函数不缓存"我是从哪来的"）
- 单 entry 方案会让 `NOT(x)` 路径**理论上**也可能 emit W0054（如果未来某次 dispatch 走 name 重映射），双 entry 物理上保证 `NOT(x)` 永远不进 W0054 emit
- 锁测试 `b9_not_clean_path_emits_no_warnings` 直接 verify `NOT(...)` 不进 warnings 列表

`builtin_not_bang_compat` 是 3 行 wrapper：emit warning + 委托 `builtin_not(ev, args)`。维护成本忽略不计。

### 2. 警告 emit 时机：dispatch 边界而非 inner fn

W0054 emit 在 `builtin_not_bang_compat`（dispatch 包装），**不**在 `builtin_not` 内部。这样:
- 同一 `!x` 表达式**不会**因 retry / 多次 eval emit 多次 W0054
- `NOT(x)` 永远**不**进入这个 wrapper
- 内部 `builtin_not` 保持纯语义表达式

### 3. 修了一个先前没发现的 parser bug：unary `!x` 解析

旧 parser 在 `parse_call_or_ident` 里把 `Bang` token 当成 var 处理：
- `!TRUE` → `parse_call_or_ident` advance `!` → name="!" → peek=`TRUE`（**不是 `LParen`**） → 进入 var 分支 → 返回 `Var("!")`，**没有 parse TRUE 作为参数** → TRUE 落到下一个 expr 解析 → `;` 不在期望位置 → **E0013 "expected ';' after expression"**

这个 bug 自从 v0.1 就在（plan §5.1 「运算符既作 token 又作函数名」路径只覆盖了 `!(x)` call syntax，没考虑 prefix-unary）。B9 第一次写了 `!TRUE;` 的测试就撞到了。

修复：在 `parse_expr` 主循环加类似 `Minus` 已有的 unary-prefix 分支：
```rust
if matches!(kind, TokenKind::Bang) && !matches!(self.peek_at(1), TokenKind::LParen) {
    let (l2, c2, _, _) = self.span_here();
    self.advance(); // '!'
    let inner = self.parse_expr()?;
    return Ok(Expr::Call { name: "!".into(), args: vec![inner], ... });
}
```

`!(x)` 走原有 `parse_call_or_ident` 路径（LParen 触发 call syntax），不影响。

锁测试：`b9_bang_emits_w0054_once_per_call`（直接证明 `!TRUE; !FALSE;` 能 parse + emit 2 次 W0054）+ `b9_bang_call_form_emits_w0054`（`!(TRUE)` 同样 emit 1 次）。

### 4. W0054 bucket = Name（与 W0051 一致）

W0051 = "v0.3 deprecated alias"（`DEL` / `OR_DIE`），W0054 = "v0.3 deprecated operator form"（`!`）。两者都是「source 里有 deprecated thing」，语义同类，**bucket 都放 `Name` bucket**。这样 user tool / lint / router 可以一并过滤 "deprecated thing in source" 类警告，不需要为两种语义不同的 W 维护多份代码。

`ErrorCode::W0054 => ErrorCategory::Name`（deviations 记录）。

### 5. NOT 关键字设计：与 IF / WHILE / MATCH / TRY 对齐

`NOT` 在 lexer 里与 `MATCH`（§7.6 macro-function 关键字）走同一条路径：
- lexer 关键字表加 `"NOT" => TokenKind::Not`
- parser dispatch（parse_call_or_ident）处理 `TokenKind::Not` → name "NOT"

`Not` 不走 IF/WHILE/TRY 的 `parse_expr` 关键字 arm（MATCH 是这样做的），因为 `NOT(x)` 是函数调用形式，不是 control-flow form。这与 spec §3.4 macro-function 列表一致。

### 6. §9.4 truthiness 锁定（B9 测试核心）

`NOT(0) = FALSE` / `NOT("") = FALSE` / `NOT(NULL) = TRUE` —— **0 和 "" 都是 truthy**（按 §9.4 row 5 「其他」规则）。

这与 Python `bool(0) = False` / JS `Boolean(0) = false` 不一致。spec v0.4 §9.4 明确选定"非 Boolean / 非 Null 都是 truthy"。

锁测试 `b9_not_truthiness_matches_negation_table` 把 10 个 case 钉死，防止未来 refactor 时漂移。
