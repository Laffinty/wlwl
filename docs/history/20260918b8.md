| `TRIM_END(s)` | | 仅后缀 |
| `STARTS_WITH(s, pre)` | `s, pre: STRING` | `TRUE` / `FALSE` |
| `ENDS_WITH(s, suf)` | | |

## 关键设计决策

### 1. Global builtin（不走 std 模块）

11 个 builtin 都放在 `resolve_builtin` 全局表，**不**走 std 路径。原因：
- 都是纯函数无 callback → 不需要 B6 collection / B7 test 的「name catalog」架构
- 附录 G 把它们列为 global（与 `STR` / `INT` 同位）

未走 std 模块，所以没有 std 边界 callback 问题；这是「global 比 std 简单」的典型情况。

### 2. `FLOAT` ParseError 与 `INT` 同形

```rust
Value::String(s) => match s.parse::<f64>() {
    Ok(f) if f.is_finite() => Ok(Outcome::normal(Value::Float(f))),
    Ok(f) => /* non-finite (NaN/Inf) → ParseError */,
    Err(e) => /* parse fail → ParseError */,
},
```

`{kind: "ParseError", input, reason}` schema 与 `INT` 一致（plan §9.5 + spec §10.3）。`FLOAT` 与 `INT` 的 ParseError 是同一个 ERR 形状 —— 调用方可用同一个 `IS_ERR` / `UNWRAP` 路径处理。锁测试：`b8_float_parse_error_returns_err_value`。

NaN / ±Inf（从 "nan" / "inf" 字符串解析）也走 ParseError —— §10.3 没有钉死，我们保持与 INT 一致。Plan §0.1 不允许「同一模块不同 ERR 形状」的分裂。

### 3. `REPEAT(s, n)` 饱和处理

`String::repeat(usize)` 在 usize 溢出时 panic。spec §9.5 一致要求 saturation（`+/INT64_MAX + 1 → INT64_MAX` + `W0015`）。我们选择：
- n < 0 → E0030（type，不是 type-bucket runtime err —— §10.3 row 11 明确 ≥ 0）
- n 超出 `usize::MAX` → 饱和到 `usize::MAX`（`isize::MAX` on 64-bit ≈ 9.2 EB）

无 W0015 emit —— spec §9.5 的 overflow 警告通道是为算术（+/-/etc）设计的，迭代计数不该污染警告流。

### 4. `CODEPOINTS` 用 Rust 的 `char`（Unicode scalar），不是 UTF-16 units

```rust
s.chars().map(|c| Value::Integer(c as i64)).collect()
```

`char::from_u32` + 范围 `(0..=0x10FFFF)` 锁定 Unicode scalar 范围。spec §10.3 row 13/14：「Unicode 码点 INTEGER」—— 不是 UTF-16 code units。

锁测试：
- `b8_codepoints_unicode_basic_multilingual_plane` —— U+00E9 `é`（BMP）
- `b8_codepoints_unicode_supplementary_plane` —— U+1D11E `𝄞`（supplementary plane，需要 UTF-16 surrogate pair，但 Rust `char` 是单值）
- `b8_from_codepoints_surrogate_half_is_e0031` —— U+D800 / U+DFFF surrogate halves → E0031
- `b8_from_codepoints_above_max_is_e0031` —— U+110000+ → E0031

### 5. `FROM_CODEPOINTS` 用 E0031（Type bucket，越界）

`E0031` 在 spec §14.4 row 10 是 "type bucket — 越界 / 数值溢出" 类。FLOAT 的 `INT(F)` 溢出也用 E0035（也是 type bucket），所以 `FROM_CODEPOINTS` 越界用 E0031 是一致的语义。**非整数 element** 用 E0030（类型错），保持 `value_type` 边界清晰。

### 6. `PAD_START` / `PAD_END` 共享 `pad_with` helper

```rust
fn pad_with(s: &str, n: usize, c: char, side: &str) -> String {
    let len = s.chars().count();  // codepoint 长度，不是 byte 长度
    if len >= n { return s.to_string(); }
    let pad: String = std::iter::repeat(c).take(pad_count).collect();
    if side == "start" { /* pad + s */ } else { /* s + pad */ }
}
```

`n` 是**码点长度**（与 `LEN(s)` 一致 —— `LEN` 用 `chars().count()`，见 §10.3 row 1），不是字节数。这避免了「len(s) 是字节数 vs 码点数」的常见混淆。

### 7. ASCII vs Unicode：W0014 deferred

plan §5.8 列了「非 ASCII `UPPER` / `LOWER` 行为实现定义，缺实现时 emit `W0014`」。本批**不**实施 W0014 emit point —— 当前 `UPPER` / `LOWER` builtin 已在 Phase B5 之前实现（用 Rust 默认 `to_lowercase` / `to_uppercase`）。W0014 的 emit 位置在 §14.4 row 5「impl-defined behavior 警告」，是 unicode 表加进来后才有意义 —— **推迟到 Phase C（unicode 表批）**。deviations P4-B8-006 记录。

### 8. TRIM ASCII-only

`TRIM` / `TRIM_START` / `TRIM_END` 用 `is_ascii_whitespace()`（spec §10.3 row 9：「ASCII 行为确定」）。非 ASCII 空白字符（NBSP `\u{00A0}`、ideographic space `\u{3000}` 等）**不**被 trim —— 与 `String::trim_matches(char::is_whitespace)` 行为不同。这是有意限制：spec 只承诺 ASCII 行为，扩展到 unicode 空白需要 char::is_whitespace，需要时再开 Phase C。
