# WLWL 语言规范 v0.4

> **状态**:正式修订版
> **基于**:v0.3(MD5 `4308b3d2071ebed5cb52eba61272b1ea`)
> **核心约束**:保留 WLWL 原有审美风格——一切皆统一函数调用、显式分号、全大写关键字、宏函数式控制流。v0.4 的工作重心是"**变硬而非变胖**":修复 v0.3 留下的语义矛盾、补齐工业级语言必须的最小特性集、把规范自身从"设计稿"推进为"可被编译器作者、Agent、企业同时采信的封闭规范"。

### 0.4 符合性(Conformance)

**符合规范实现(conforming implementation)**必须满足以下全部条件:

1. **接受性**:必须接受本规范词法、句法(附录 F)定义的每一个合法 WLWL 程序。
2. **拒绝性**:必须拒绝附录 F 之外的非法程序,或在 §X.Y 明确允许"实现定义行为(implementation-defined behavior)"处提供一致的扩展。
3. **可观察行为**:对任何被接受的程序,其可观察行为必须符合 §2 - §14 的语义规定,以及附录 E 的形式化定义(自然语言与形式化冲突时,**以自然语言为准**;详见 §0.5)。
4. **诊断行为**:对任何 §14 列出的错误,必须输出符合 §14 schema 的结构化对象。诊断输出流(详见 §14.3)与程序的常规输出流隔离。
5. **实现定义行为**:凡本规范明确标注"由实现定义(implementation-defined)"的,实现**必须**在文档中列出所有此类行为点及取值。
6. **可扩展性**:实现**不得**破坏本规范的语义,但可以提供额外能力(额外的标准库模块、额外的优化、额外的输入格式)——前提是不影响符合性程序的可观察行为。
7. **诊断契约**:必须实现 §14.3 的 JSONL 与 JSON 输出;CLI 退出码必须符合 §14.6。

**不符合规范实现**包括但不限于:
- 引入 §1.2 第 7 条禁止的"等价语法糖"并对外暴露(允许实现层内部提供)
- 改变 §6.4 的捕获变量 cell 语义
- 改变 §12.6 的 ERR 透明传播默认行为(除 §12.7 注册表显式声明)
- 改变 §9.4 的真值规则
- 改变 §4.4 / §4.5 的字面量消歧规则

### 0.5 规范性语言(Normative language)

本规范采用 RFC 2119 定义的层级化规范性语言,并使用其中文化对应词:

| 英文 | 中文 | 含义 |
|------|------|------|
| **MUST** | **必须** | 绝对要求 |
| **MUST NOT** | **不得** | 绝对禁止 |
| **SHOULD** | **应当** | 在例外情形下可有正当理由偏离,但偏离时需在文档中说明 |
| **SHOULD NOT** | **不应当** | 不推荐,但可在例外情形偏离 |
| **MAY** | **可以** | 完全可选 |

凡本规范未使用上述关键词的陈述,均视为说明性(资料性)描述。

### 0.7 形式化与自然语言冲突时的优先级

本规范包含一份**形式化附录**(附录 E,small-step CEK 风格),**冲突时以自然语言主体为准**。理由:

1. 形式化覆盖范围有限(核心子集),仅作为"无歧义参考"而非"完备证明";
2. 形式化本身的非形式化证明状态(附录 E 末尾声明)使其不能与自然语言具有同等法律效力;
3. 优先级规则本身就是自然语言陈述,无法自我引用。

v0.4 起,形式化附录与自然语言的一致性**必须**作为发布检查项(见 §16.5)。

## §1 设计目标与原则

### 1.1 一句话定位

**WLWL 是一门"一切皆统一函数调用"的纯动态类型通用编程语言,以 Rust 级别的结构化错误信息为核心,优先面向 AI Coding 场景。**

### 1.2 设计原则(按优先级排序)

1. **统一性(Unification)**:语言里的所有"动作"——变量赋值、运算、控制流、类定义、HTML 标签、SQL 语句——都是**对函数的调用**。这是最高原则。
2. **表达性(Expression-oriented)**:一切都是表达式,任何表达式都有值,包括 `IF`、`WHILE`、`LET`、`TRY`、`MATCH`。
3. **显式优于隐式(Explicit over Implicit)**:必须用 `;` 结束语句;不依赖缩进;不依赖上下文推断;不引入隐式转换;不引入隐式覆盖。
4. **错误前置(Error-first)**:错误必须尽早暴露、必须位置精确、必须给出可操作的修复建议;ERR 默认透明传播,必须显式消费。这是面向 AI Coding 的硬要求。
5. **函数式核心 + OOP 上层(FP core, OOP surface)**:函数是一等公民;类、继承、封装作为组织大型代码的上层建筑。
6. **可读性优于简洁(Readability over Brevity)**:`+(a, b, c)` 比 `a+b+c` 啰嗦,但统一;真要简洁,语法糖永远可以后加。
7. **语法可预测性(Predictability)**:同一语义**仅**保留一种标准写法,不提供多种等价语法糖。语法糖仅作为**实现层**的可选扩展,**不得**进入核心规范。

### 1.3 非目标(Non-goals)

- WLWL **不强制**静态类型检查(注:可**可选**地声明类型注解供文档/AI 工具消费,见 §2.4、§2.7)。
- WLWL **不追求**极致运行性能(本规范不规定实现模型)。
- WLWL **不追求**成为系统编程语言(不需要替代 C/Rust 做底层)。
- WLWL **不追求**最短代码行数。
- **Web 子集技术边界**:Web 子集是**语义子集**,**不**承诺 Web 端运行时与原生运行时性能一致;**不**包含文件 IO、原生扩展、系统调用等能力。多目标编译时,目标间共享核心语义,平台相关能力显式标注。
- **形式化完备性**:本规范**不**追求形式化完备证明(见附录 E);附录 E 是"无歧义参考",不是"数学证明"。
- **异步语义**:v0.4 不引入 async/await;并发语义决策框架见 §17.4。
- **泛型与类型参数化**:v0.4 不引入;见 §17.3。
- **宏系统与元编程**:v0.4 不引入;见 §17.3。
- **多目标编译器后端**:v0.4 不定义目标 AST 形状;见 §17.6。

### 1.4 长期愿景(可分阶段实现)

- 同一份 WLWL 源码编译到 HTML/CSS/JS、SQL、华为/思科交换机配置、Nginx/Apache 配置(来自原始草稿)。
- **语言级 AI 原语**:在标准库提供 `ASK(model, prompt)`、`EMBED(text)`、`COMPLETE(code_context)` 等内置函数(§15.13)。
- **Agent 协议**:在标准库提供 `TASK` / `TOOL` / `CALL_TOOL` / `CONTEXT` 等 Agent 编排原语(§15.14)。
- 上述目标**不进入 v0.4 规范**的强制性条款,仅作为方向保留。

### 1.5 规范优先级体系(本规范新增)

为防止"v0.4 改胖",明确以下优先级(数字越小越优先):

| 级别 | 类别 | 例 |
|------|------|----|
| P0 | 语言身份 | 统一函数调用、显式分号、全大写关键字 |
| P1 | 语义确定性 | ERR 透明传播、真值规则、确定性迭代 |
| P2 | 机器可验证性 | EBNF 文法、内建注册表、错误码总表唯一化 |
| P3 | AI 可操作性 | JSONL 诊断、AST/Patch 协议、机器可读 hint |
| P4 | 工业能力 | 模块系统、包管理、错误码覆盖度 |
| P5 | 便利性 | FORMAT、解构绑定、惯用法 |

**硬规则**:**P5 永远不得凌驾 P0–P2**。例如:
- 不得为了"少打几个字"引入中缀运算符(P5 凌驾 P0)
- 不得为了"看起来漂亮"让 `[]` 同时是空 DICT(P5 凌驾 P1)
- 不得为了"用起来简单"在 §14.2 删字段(P5 凌驾 P2)

### 1.6 已知代价与缓解(本规范新增)

WLWL 审美带来的可量化代价,以及 v0.4 的缓解措施:

| 代价 | 量级 | 缓解 |
|------|------|------|
| **Token 效率**:`+(a, b)` 比 `a + b` 多耗约 50% token;全大写关键字比小写多耗约 5% token | 高 | 附录 J 惯用法固化高频模式;不引入等价中缀 |
| **嵌套深**:`f(g(h(x)))` 嵌套 3 层后阅读疲劳 | 中 | MATCH / 解构绑定 / 命名参数式 DICT 三件套缓解 |
| **学习曲线**:用户来自主流语言时需要切换思维 | 中 | 附录 J 惯用法;示例丰富化;与 Python/TypeScript 类比章节 |

## §2 类型系统

### 2.1 动态优先,渐进可选(Dynamic-first, Optionally Gradual)

v0.2 起的立场,延续到 v0.4:

- **默认行为**:纯动态类型。运行时不做类型检查(除显式的 `TYPE(x)` 查询)。
- **可选能力**:v0.2 起预留类型注解语法槽 `name: Type`(见 §2.4),**仅供文档、IDE、静态分析工具、AI 工具消费**。v0.4 运行时**完全忽略**类型注解。
- **未来兼容性**:此预留保证未来如需引入渐进类型检查时,无需破坏性变更现有代码。
- **运行时契约**:`wlwl.toml` 的 `strict_types: true`(§13.8)开启**运行时边界检查**,见 §2.7。

### 2.2 内建类型(共 9 种)

v0.4 在 v0.3 的 8 种基础上新增第 9 种 `RESULT`,承认 `OK(...)` / `ERR(...)` 是**一等值类型**而非"普通 DICT 包装":

| 类型 | 字面量示例 | 备注 |
|------|------------|------|
| `INTEGER` | `1`, `-42`, `0` | 64 位有符号整数;溢出语义见 §9.5 |
| `FLOAT` | `1.5`, `-3.14`, `0.0` | IEEE 754-2019 binary64;特殊值行为见 §9.5 |
| `STRING` | `"hello"`, `""` | UTF-8 不可变字符串 |
| `BOOLEAN` | `TRUE`, `FALSE` | 关键字,大小写敏感 |
| `NULL` | `NULL` | 表示"无值",关键字 |
| `ARRAY` | `ARRAY(1, 2, 3)` 或 `[1, 2, 3]` | 有序、可变、可嵌套;**空数组只能写 `ARRAY()` 或 `[]`** |
| `DICT` | `DICT(["k": 1])` 或 `["k": 1, "k2": "v"]` | 键值映射;**空字典只能写 `DICT()`**(原因见 §4.5) |
| `FUNCTION` | `FUN(...)` | 一等公民 |
| `RESULT` | `OK(1)`, `ERR("e")`, `ERR([...])` | 错误值,`§2.2.1` 详 |

#### 2.2.1 RESULT 类型

`OK(v)` 产生 `RESULT` 类型的"成功变体",内部携带值 `v`(任意类型);`ERR(e)` 产生"失败变体",`e` **必须**是 STRING 或 DICT(违反 → `E0030`)。

- `TYPE(OK(1))` 返回 `"RESULT"`,`TYPE(ERR("e"))` 返回 `"RESULT"`。
- `IS_OK(x)` / `IS_ERR(x)` 取代 `TYPE(x) = "RESULT"` 判定,前者更清晰(§12.2)。
- `RESULT` 类型不属于"普通可索引容器",不可下标读取;仅可通过白名单函数消费(§12.7)。
- `OK` / `ERR` 是关键字还是宏函数?——**v0.4 定型为构造器宏函数**(非关键字,因为 §3.3 不列入关键字表);等价于 `FUN(OK(x), RESULT_VARIANT("ok", x))` 的语法糖。

### 2.3 DICT 键的相等性规则

- DICT 键使用**严格相等**比较(§10.4)。
- **不**做隐式类型转换:整数键 `1` 与字符串键 `"1"` 是不同的键。
- 仅以下类型可作为 DICT 键:`STRING`、`INTEGER`、以及实现了相等语义的不可变类型(v0.4 仅前两种)。
- 违反(如以 ARRAY/DICT/FUNCTION/RESULT 作键)→ `E0031`。
- `FLOAT` / `NAN` **不得**作 DICT 键;`STR(n)` 后再用作 STRING 键。
- `RESULT` 不得作 DICT 键。

### 2.4 类型注解(Transient,运行时忽略)

- 函数参数、形参、变量绑定**可以**携带类型注解:`name: Type`。
- `Type` 可以是内建类型名(`INTEGER`、`STRING` 等)、自定义类名,或数组/字典的容器类型(具体语法见 §3.5)。
- **v0.4 运行时完全忽略注解**;不存在的类型注解不报错。
- 工具/AI 可以读取注解生成文档、提示、静态分析。
- 任何具体类型注解的语义、形式化定义、模块契约集成,均在 v0.5 及之后讨论。
- **规范推荐**:核心库与第三方库的**公开 API 必须**带类型注解,作为机器可消费契约。

### 2.5 类型查询

通过 `TYPE(x)` 表达式获取值的类型名称(返回 STRING):

```wlwl
LET(t, TYPE(1));             // "INTEGER"
LET(t, TYPE("hi"));          // "STRING"
LET(t, TYPE([1, 2]));        // "ARRAY"
LET(t, TYPE(OK(1)));         // "RESULT"
LET(t, TYPE(ERR("e")));      // "RESULT"
```

完整全局内建注册表见附录 G。

### 2.6 渐进类型的立场说明

> 本节是设计决策的"自留地",向读者和未来贡献者解释 WLWL 为什么**目前**不做渐进类型的运行时检查。

WLWL 的渐进类型立场是 **Transient**(瞬态),不引入 **Natural**(自然)监控(monitoring)。

#### 两种策略对比

- **Natural + monitoring**:在动态边界插入类型检查,确保类型注解被严格执行。形式化完备(graduality 定理可证),但运行时开销大,且会强制改变已工作代码的行为(常见类型注解错误会让本来跑得好好的程序崩溃)。
- **Transient**:不强制类型检查,类型注解仅作 IDE / AI 提示。运行时开销为零,不破坏现有程序行为,但失去形式化保证。

#### WLWL 选择 Transient 的理由(学术依据已全部修正)

基于 **2014–2024 学术界**对渐进类型的实证研究与工业实践综述:

1. **DLS 2014 论文**(Vitousek, Kent, Siek, Baker,"Design and Evaluation of Gradual Typing for Python",DOI `10.1145/2661088.2661101`):对 Python 渐进类型的大规模实证研究,首次明确"transient 语义是工业可行的唯一选择"——对运行时性能、monomorphisation、空间效率的代价评估表明,自然监控在 Python 真实代码上**不可接受**(对解释器有 2×–100× 减速)。
2. **DLS 2017 论文**(Vitousek et al.,"Transient Semantics"):从形式化角度严格证明 transient 不会破坏已工作代码的行为(这是工业语言选用 transient 的根本原因)。
3. **ICFP 2016 论文**(Takikawa, Feltey, Dean, Gardner, Lee, Suzuki,"The Soundness of Gradual Typing",DOI `10.1145/3022670.2951922`):证明任何"自然"渐进类型系统若要保持 soundness 都需要重型数学(step-indexed logical relations),**远超 v0.4 阶段可承受的复杂度**。
4. **ICFP 2024 论文**(Pacak, Erdweg,"Space-Efficient Polymorphic Gradual Typing, Mostly",DOI `10.1145/3674644`):对放宽 parametricity 的 Natural 方案,空间效率仍难保证。
5. **TypeScript 官方设计文档**(Microsoft,2024):明确声明 TypeScript 类型注解**不会**改变运行时行为,这是 TypeScript 工业采用率超越 Python 的核心原因之一(参见 GitHub Octoverse 2024/2025 报告)。

#### 不引入 monitoring 的"坏处"明确化

- 类型注解**可能与运行时实际类型不一致**——`name: INTEGER` 不保证 `name` 一定是 INTEGER。
- AI 工具若依赖类型注解生成代码,**必须**同时插入运行时类型检查(类似 Python 的 `isinstance`)。
- 这跟 Python 3.5+ 的渐进类型行为**完全一致**,有大量先例可参考。

#### 未来路径(从 v0.4 起明确化)

`wlwl.toml` 的 `strict_types: true` 字段开启**运行时边界检查**(§2.7);不开则保持 Transient。该字段的具体行为已在 §2.7 钉死,**不再留为"v0.5 再决定"**。

### 2.7 strict_types 行为(本规范新增)

当 `wlwl.toml` 的 `[features]` 段声明 `strict_types = true` 时,实现**必须**在以下边界进行运行时类型检查(transient cast insertion):

| 边界 | 检查行为 | 触发错误 |
|------|----------|----------|
| **函数入口(public API)** | 形参类型注解与实参 `TYPE` 不一致 | `E0033` |
| **IMPORT 边界** | 导入符号的实际值与契约声明类型不一致 | `E0033` |
| **FFI 边界**(若启用) | 与外部类型转换失败 | `E0033` |

**`E0033`** 错误码(本规范新增,详见 §14.4):
- `errorCategory: type`
- `retryable: false`
- `message`: "type annotation mismatch: expected X, got Y"
- 字段:`expected` / `actual` / `annotation_span` / `value_span`

**关键设计**:
- **不开 strict_types 时,所有边界**不检查,行为与 v0.3 完全一致。
- **`strict_types: true` 仅检查边界,不强制内层代码**;这是与 TypeScript `--strict` 的"transient cast insertion"模式一致。
- **检查不修改运行时行为**:失败的边界调用直接抛 `ERR(E0033(...))`,**不**改写控制流。
- **性能预算**:实现应当为 strict_types 模式提供"非严格模式 ≥ 0% 开销,严格模式 ≤ 10% 开销"的工程目标(不构成规范性约束,但作为 v0.5 实现层 benchmark 目标)。

> **本节是 v0.3"§2.6 未来路径"短决议项的具体落地**。原 v0.3 将 strict_types 留到"v0.4 决定",v0.4 不再推迟。

## §3 词法

### 3.1 字符集与源文件

- 源文件**必须**为 UTF-8 编码(无 BOM 优先;允许 BOM,实现**必须**忽略开头的 BOM 字节序列)。
- 换行符:`\n`、`\r\n`、`\r` 三者均允许;实现**必须**将三者统一视为逻辑换行(在词法阶段前完成规范化)。

### 3.2 标识符

- 标识符**允许**字母(Unicode 字母,含中文)、数字、下划线,首字符**不得**是数字。
- **允许中文标识符**;但**强烈建议**在生产代码中使用 ASCII 标识符以提升 AI 编码效率(参见 §3.8 命名约定)。
- 区分大小写:`Foo` 与 `foo` 是不同标识符。
- 标识符**不得**与关键字(§3.3)同名;与宏函数(§3.4)同名**允许**但产生 W0030 警告(遮蔽宏函数)。

### 3.3 关键字(共 14 个)

```
TRUE  FALSE  NULL
LET   FUN    RETURN
IF    WHILE  FOR
BREAK CONTINUE
CLASS NEW    THIS
```

**修正说明**:v0.3 声称"共 16 个"但仅列出 14 个——`AND` / `OR` / `!` 与 `PANIC` / `TRY` / `OK` / `ERR` / `IS_OK` / `IS_ERR` / `OR_DIE` / `UNWRAP` 属于**宏函数**或**构造器宏**(§3.4),不是关键字。

### 3.4 宏函数(Macro-functions)

**宏函数**是**非一等公民、不可作为值传递**的语法形式。它们在词法上形如普通函数,但有以下差异:

| 差异 | 普通函数 | 宏函数 |
|------|----------|--------|
| 可作值传递 | ✔ | ✘ |
| 接受函数作实参 | ✔ | ✘(除特殊形式) |
| 在 IMPORT 中可导入 | ✔ | ✘(除特殊情形) |
| 可遮蔽/被遮蔽 | ✔ | ✘(产生警告) |

**v0.4 宏函数清单**(本规范**完整**列表;不构成关键字,不允许自由扩展):

| 宏函数 | 引入位置 | 用途 |
|--------|----------|------|
| `IF(cond, then, else?)` | §7.1 | 条件 |
| `WHILE(cond, body)` | §7.2 | 循环 |
| `FOR(var, iter, body)` | §7.3 | 遍历 |
| `RETURN(value?)` | §7.4 | 函数返回 |
| `BREAK()` | §7.4 | 终止循环 |
| `CONTINUE()` | §7.4 | 跳过本次循环 |
| `MATCH(value, clauses, default?)` | §7.6 | 模式匹配 |
| `AND(a, b)` | §9.3 | 短路与 |
| `OR(a, b)` | §9.3 | 短路或 |
| `PANIC(msg)` | §12.4 | 不可恢复错误 |
| `TRY(expr)` | §12.3 | 错误传播 |
| `IS_OK(x)` | §12.2 | 判定成功变体 |
| `IS_ERR(x)` | §12.2 | 判定失败变体 |
| `OR_DIE(expr, default)` | §12.2 | 错误兜底(别名 `UNWRAP_OR`,见 §12.2) |
| `OK(value)` | §2.2.1 | 构造成功变体 |
| `ERR(error)` | §2.2.1 | 构造失败变体 |
| `EXPORT(names)` | §13.2 | 显式导出 |
| `IMPORT(path, names, opts?)` | §13.3 | 显式导入 |
| `MODULE(name?, body)` | §13.1 | 模块名显式声明 |
| `CLASS(name?, parent, members)` | §11.2 | 类定义 |
| `NEW(cls, args...)` | §11.3 | 实例化(接受类值或类名字符串) |
| `THIS` | §11.3 | 指向当前实例 |
| `TYPE(x)` | §2.5 | 类型查询 |
| `GET_PROP(obj, key)` | §11.3 | 属性读取 |
| `SET_PROP(obj, key, value)` | §11.3 | 属性写入 |
| `CALL_METHOD(obj, method, args...)` | §11.4 | 方法调用(底层形式) |
| `ARRAY(items...)` / `ARRAY()` | §4.4 | 数组构造器 |
| `DICT(pairs...)` / `DICT()` | §4.5 | 字典构造器 |

**未来扩表**:新宏函数进入核心规范需经本规范升级;实现层可作为扩展提供,但**不得**改变已规范的宏函数语义。

### 3.5 分隔符

| 符号 | 用途 |
|------|------|
| `(` `)` | 函数调用 / 表达式分组 / 块表达式 |
| `,` | 参数分隔 |
| `;` | **语句结束符,必须** |
| `[` `]` | 数组、字典、下标访问;**类型注解中 ARRAY/DICT 容器标注(`[INTEGER]` 表示 `ARRAY<INTEGER>`)** |
| `:` | 字典键值对分隔;**类型注解分隔(见 §2.4)**;**导入时重命名分隔(见 §13.4)** |
| `.` | 成员访问(对象属性 / 方法 / 链式调用) |
| `"` | 字符串字面量边界 |
| `//` | 单行注释起始 |
| `/*` `*/` | 块注释边界,**可嵌套** |
| `///` | **文档注释**(本规范新增,§3.6) |

### 3.6 注释

#### 单行注释

```wlwl
// 这是单行注释
LET(x, 1);
```

#### 块注释(可嵌套)

```wlwl
/*
   这是块注释
   /* 可以嵌套 */
   结束 */
LET(y, 2);
```

> AI 友好约束:注释中以 `TODO(agent):` 开头的行,在严格模式下输出结构化警告(见 §14.5,W0040)。

#### 文档注释(本规范新增)

`///` 开头的单行注释为**文档注释**,仅出现在声明的**上方一行**;不影响代码语义,仅供工具/AI 消费。

**结构**(参考 Rust doc-comments):

```wlwl
/// 简短摘要
///
/// # 详细说明(可选)
///
/// # 错误:
///
/// - `E0022` 元数不匹配
/// - `E0031` 下标/键类型错误
///
/// # 示例:
///
/// ```wlwl
/// LET(r, my_fn(1, 2));
/// ```
FUN(my_fn(a, b), +(a, b));
```

- **首段**(第一行)为**机器可索引摘要**,工具生成 API 文档时单独提取。
- `# 错误:` 段列出该声明可能抛出的错误码(对应 §13.11 模块接口契约的 `errors` 字段)。
- `# 示例:` 段(可选)嵌入可机检代码块(§16.5)。
- 文档注释不进入运行时,实现层**不得**因文档注释错误报错或警告。
- **非规范建议**:第三方库**必须**为其所有 `EXPORT` 函数提供文档注释。

### 3.7 空白

- 缩进**不影响**语义;实现**应当**在 §16.3 规定的 canonical formatter 行为下处理缩进。
- 多个连续空白等同于一个空白。
- 换行不影响语义;语句必须用 `;` 显式结束。

### 3.8 命名约定(本规范新增)

以下为**惯例性**约定,语言层不强制,工具层(附录 G 内建注册表、§16.3 canonical formatter)应当照此风格生成代码:

| 类别 | 风格 | 示例 |
|------|------|------|
| 常量(模块顶层 `LET`,值不可变) | `UPPER_SNAKE` | `LET(MAX_LEN, 1024);` |
| 函数 / 变量 / 参数 | `lower_snake` | `LET(user_name, "alice");` |
| 类名 | `UpperCamel` | `CLASS("UserAccount", NULL, [...]);` |
| 模块名(命名空间) | `lower-kebab` | `IMPORT("myteam:user-account", ...);` |
| 类成员(属性 / 方法) | `lower_snake` | `"get_area": FUN((self), ...)` |
| 私有成员(约定) | `_leading_underscore` | `"_internal_state": 0` |
| 错误码字段(用户级 DICT) | `lower_snake` | `["kind": "ParseError"]` |

工具(§16.3)对违反惯例的名称产生 **W0050 命名风格建议**(非阻塞)。

## §4 字面量

### 4.1 数值

```wlwl
LET(i, 42);
LET(f, 3.14);
LET(n, -1);
```

- `INTEGER` 字面量语法:`[+-]?[0-9]+`;v0.4 **不**支持二进制/八进制/十六进制/下划线分隔/科学计数(详见 §17.3)。
- `FLOAT` 字面量语法:`[+-]?[0-9]+\.[0-9]+` 或 `[+-]?[0-9]+(\.[0-9]+)?[eE][+-]?[0-9]+`;必须含小数点或指数符。
- 整数溢出与浮点 NaN/Inf 行为见 §9.5。

### 4.2 字符串

使用双引号。支持转义序列:`\n` `\t` `\r` `\\` `\"` `\0`。v0.4 **不**支持字符串模板字面量(理由见 §1.5 P0 优先);需要拼接请用 `+(...)` 或 `FORMAT(...)`(§10.6)。

```wlwl
LET(s, "事屑");
LET(greet, +("hello, ", "world"));
LET(m, FORMAT("hello, {0}!", name));   // §10.6 FORMAT
```

**非 ASCII 大小写转换**:`UPPER(s)` / `LOWER(s)` 对非 ASCII 字符,行为由实现定义;实现**应当**遵循 Unicode SpecialCasing。如未实现,产生 `W0014` 警告。

### 4.3 布尔与空

```wlwl
LET(b, TRUE);
LET(n, NULL);
```

### 4.4 数组

用 `[` `]` 包裹,逗号分隔:

```wlwl
LET(i, [1, 1, 4, 5, 1, 4]);
LET(empty, ARRAY());                 // 空数组(只能这样写,见 §4.5)
LET(mixed, [1, "two", TRUE, NULL]);
```

- **空数组**:本规范定型为 `ARRAY()` 构造器(零参),字面量 `[]` 同样**视为空数组**(消歧规则见 §4.5)。
- 数组字面量中**不得**混用 `[1, "k": 2]` 形式(违反 → `W0020`)。

### 4.5 字典

用 `[` `]` 包裹,键值对用 `:` 分隔,各对之间用 `,` 分隔:

```wlwl
LET(j, ["cat": "nya", "dog": 2]);
LET(empty, DICT());                  // 空字典(只能这样写,见下)
LET(mixed, [1: "one", "two": 2]);
```

#### `[]` 消歧规则(本规范关键决策)

`[]` 在 v0.3 既是"空数组"又是"空字典"——按内容消歧,但空字面量**无内容**,导致不可判定。**v0.4 钉死**:

- `[]` 恒为**空 `ARRAY`**。
- **空 `DICT` 只能**通过 `DICT()` 构造器产生。
- 数组字面量与字典字面量的消歧规则:**第一项是裸值(无 `:`)即为数组**;**第一项是键值对(有 `:`)即为字典**。空字面量 `[]` 由 `ARRAY()` 规则独立处理。

> 另一候选方案曾建议引入 `{}` 或 `[:]` 作为空 DICT 字面量。**否决**:违反 §1.2 第 7 条"同一语义仅一种标准写法"——`DICT()` 是更美学的选择,且不引入新符号。

### 4.6 函数字面量

见 §8.2。

## §5 表达式

### 5.1 一切都是表达式

WLWL 中所有"语句"在求值后都产生一个值。下列形式都是表达式:

- 字面量(§4)
- 函数调用(§5.2)
- 变量引用(§6)
- 控制流(§7):`IF`、`WHILE`、`FOR`、`TRY`、`MATCH`
- 块表达式(§5.3)
- 字段访问 / 方法调用(§5.5)
- 构造器:`ARRAY()`、`DICT()`、`OK()`、`ERR()`

### 5.2 函数调用

**调用形式**:`NAME(arg1, arg2, ..., argN)`

```wlwl
LET(x, +(1, 2));          // 3
LET(y, PRINT("hi"));      // PRINT 返回 NULL
```

**空调用**:`NAME()` 表示无参调用。`FUN()` / `ARRAY()` / `DICT()` 是合法的零参调用形式。

### 5.3 块表达式

用 `(` `)` 包裹的语句序列,值为最后一条表达式的值:

```wlwl
LET(x, (
    LET(a, 1);
    LET(b, +(a, 2));
    +(a, b)
));  // x = 4
```

空块 `()` 的值为 `NULL`。

**重要**:**块表达式的最后一条表达式**自身**仍可加 `;`**(但不是必须)。当块表达式作为另一表达式的子表达式时,其内部语句以 `;` 终止:

```wlwl
LET(x, (
    LET(a, 1);
    LET(b, 2);
    +(a, b)              // 最后表达式无 ;,作为块的值
));
```

### 5.4 求值顺序

- 函数实参在传入前**完全求值**(无惰性求值)。
- 自左向右。
- 如需短路行为,使用 `AND`/`OR`(§9.3),它们是**宏函数**,提供短路语义。
- `IF` 的三个实参按"条件 → 真分支 → 假分支"顺序求值,仅执行所需分支。

### 5.5 字段访问与方法调用语法糖(本规范重新组织,原 §11.4 提升)

`a.b` 与 `a.b(args)` 在词法上等价于:

| 形式 | 等价宏调用 |
|------|-----------|
| `a.b` | `GET_PROP(a, "b")` |
| `a.b(args)` | `CALL_METHOD(a, "b", args...)` |
| `a.b.c` | `GET_PROP(GET_PROP(a, "b"), "c")` |
| `a.b.c(args)` | `CALL_METHOD(GET_PROP(a, "b"), "c", args...)` |

**链式规则**:
- `a.b` 是属性访问,等价 `GET_PROP(a, "b")`;若 `a.b` 是函数且 `b` 后紧跟 `(args)` 才触发方法调用。
- `a.b(args)` 是方法调用,等价 `CALL_METHOD(a, "b", args...)`。
- 链式(`a.b.c.d(args)`)递归应用上述规则。
- **关键决策**:`a.b(args)` 在以下情况产生**歧义**:`a.b` 已经是 `FUN(...)` 函数字面量;此时按"属性访问结果为函数 + 紧跟括号即调用"原则,等价于 `CALL(a.b, args)`。**注意:此情形下 `CALL_METHOD` 不会自动注入 `self`**;需要 self 见 §8.6。

## §6 变量与作用域

### 6.1 变量绑定

**唯一方式**:`LET(name, value)` 表达式。**没有**`var`、`x = 1`、自增自减等语法。

```wlwl
LET(x, 1);
LET(y, +(x, 1));
LET(z, !(FALSE));
```

> `LET` 表达式本身返回 `NULL`;它的"作用"是副作用(命名绑定)。

### 6.2 重新绑定

- 同一作用域内对同一名字再次 `LET`,**默认报错**(`E0021: name 'x' already bound in this scope`)。
- 如需"重赋值"语义,使用 `SET(name, value)` 表达式:

```wlwl
LET(x, 1);
SET(x, +(x, 1));  // x = 2
```

> `SET` 是宏函数,只能作用于**当前函数体内由 `LET` 引入的名字**或**捕获变量**(§6.4)。

### 6.3 词法作用域(Lexical scope)

- **词法作用域**(lexical scoping),即名字绑定由源代码位置决定,与运行时调用顺序无关。
- 引入新作用域的构造:**函数体、块表达式、类体、模块顶层**。
- 子作用域可读父作用域的绑定。
- 子作用域**对父作用域的非捕获绑定只读**;对**捕获绑定可写**(§6.4)。
- 读未定义名字 → `E0020: undefined name 'x'(附最近似候选)`。
- **禁止** `nonlocal` / `global` 关键字。

### 6.4 闭包与捕获变量可写性(本规范重大修订,修复 v0.3 §6.3 vs §8.5 矛盾)

v0.3 同时声明:
- §6.3:"子作用域可读父作用域的绑定,**不可**写(无 nonlocal/global 关键字)"
- §8.5 示例:内层函数 `SET(count, +(count, 1))` 修改外层 `LET(count, 0)`

二者直接矛盾。v0.4 采用**捕获变量 cell 语义**修复:

#### 决策:Cell-based capture

- **LET 引入的每个名字**,实现**必须**在词法环境中创建对应的**cell**(单元)对象。
- cell 持有两样东西:值 + 可变性标志。
- **同一词法位置的 `LET` 在所有引用它的闭包间共享同一个 cell**。
- 闭包**捕获 cell 的引用**(而非值的副本)。
- 因此,闭包内的 `SET` 修改 cell,外层函数与所有共享该 cell 的闭包**都看得到**。
- **未被子作用域捕获的名字**,其 cell 不可从子作用域写入(等价于"无 nonlocal",与 v0.3 行为一致)。

#### 形式

```wlwl
FUN(make_counter(),
    LET(count, 0);                          // 创建 cell,初始 0
    FUN(()                                   // 闭包捕获 count 的 cell
        SET(count, +(count, 1));            // 写 cell
        count                                // 读 cell
    )
);

LET(c, make_counter());
CALL(c);  // 1
CALL(c);  // 2
```

#### 与 v0.3 §6.3 的统一表述

修订后 §6.3 的规则为:

> "子作用域对**未捕获的**父作用域绑定只读;对**捕获的**父作用域绑定(cell)可写。"

#### 边界规则

- **未捕获的父作用域绑定**:子作用域读 OK,`SET` → `E0024: cannot SET non-captured binding 'x' from child scope`(本规范新增)。
- **模块顶层**的 `LET` 是"非捕获"——但因为没有外层闭包,实际上等同模块全局;实现细节不约束。
- **跨函数捕获**:函数 A 创建的 cell,函数 B 闭包捕获 A 的 cell 引用,形成 cell chain;`SET` 仍能找到原 cell(单层 cell,无 chain 概念)。

### 6.5 提升(Hoisting)

- WLWL **不做**变量提升。
- 在 `LET` 之前引用一个名字 → `E0020`,带行号。
- **函数提升**:§8.2 中,函数定义在源代码中出现的位置就是其引入作用域的开始;**不**存在"函数声明在文件顶部"的概念。

### 6.6 遮蔽(Shadowing)规则

- **跨作用域允许**遮蔽:子作用域 `LET` 与父作用域同名,产生新 cell,父作用域 cell 不可见。
- **同作用域禁止**:同作用域内重复 `LET` 同一名字 → `E0021`。
- **遮蔽宏函数 / 关键字** → `W0030` 警告,但**允许**(在 v0.4 谨慎决定;遮蔽关键字会损害可读性,§3.8 命名约定不推荐)。
- **遮蔽全局内建**(见附录 G)→ `E0025: cannot shadow built-in 'PRINT'`(本规范新增),除非声明 `[features] allow_builtin_shadow = true`(本规范新增,默认 false)。

## §7 控制流

### 7.1 条件:`IF`

`IF(cond, then, else)` —— **三元表达式**。`else` 分支可省略,默认值为 `NULL`。

```wlwl
IF(=(x, TRUE),
    (PRINT("x是true")),
    (PRINT("x是false"))
);
```

> `IF` 是宏函数(§3.4)。条件真假规则见 §9.4。
> **`IF` 的求值规则**:先求值 `cond`;若 `cond` 的真值(§9.4)为真,求值 `then` 并返回其值;否则求值 `else`(若有)并返回其值,否则返回 `NULL`。**未求值的分支不执行**(包括其副作用)。

### 7.2 循环:`WHILE`

`WHILE(cond, body)` —— 条件为真时反复执行 body。`WHILE` 表达式的值是**最后一次循环体的值**,若从未执行则为 `NULL`。

```wlwl
LET(x, 2);
WHILE(>(x, 0),
    (PRINT(x), SET(x, -(x, 1)))
);
```

### 7.3 循环:`FOR`(遍历)

`FOR(var, iterable, body)` —— 对 iterable(ARRAY、DICT 的键、STRING 的码点、或可迭代协议对象)逐项执行 body,`var` 在每次迭代中绑定当前项。

```wlwl
FOR(item, [1, 2, 3],
    (PRINT(item))
);

FOR(key, ["a": 1, "b": 2],
    (PRINT(key))
);
```

**DICT 遍历顺序保证**:`FOR` 遍历 DICT 时,键的出现顺序为**插入顺序**(与 Python 3.7+ 语义一致),不依赖实现细节。

**STRING 遍历**(v0.4 明确):遍历 STRING 时,`var` 依次绑定 STRING 的**码点**(`STRING` 视为码点数组);不迭代 grapheme cluster(避免 §9.5 复杂度)。

**可迭代协议扩展点**(v0.4 新增):v0.4 仅规定"ARRAY / DICT / STRING 是内置 iterable";v0.5 引入迭代器协议(`ITER(x)` 返回迭代器值,`NEXT(it)` 返回 `[value, NULL]` 或 `[NULL, NULL]`)——见 §17.2。**当前 v0.4 不暴露迭代器协议**。

`FOR` 表达式的值是 `NULL`。

### 7.4 提前退出

- `RETURN(value)` —— 立即从当前函数返回,值为 `value`(若省略则 `NULL`)。
- `BREAK()` —— 立即终止最近的 `WHILE`/`FOR` 循环。
- `CONTINUE()` —— 立即跳到最近的 `WHILE`/`FOR` 循环的下一次迭代。

```wlwl
FUN(first_positive(nums),
    FOR(n, nums,
        IF(>(n, 0), RETURN(n))
    );
    NULL
);
```

> `RETURN` / `BREAK` / `CONTINUE` 是宏函数(§3.4),只能出现在 `FUN` / `WHILE` / `FOR` 体内,否则 → `E0014: RETURN/BREAK/CONTINUE used outside loop or function`。

### 7.5 解构绑定(本规范新增,采纳 M-06)

`LET` 的**第一参数**支持解构模式。模式复用 ARRAY / DICT 字面量形态。

#### 数组解构

```wlwl
LET([a, b], [1, 2]);        // a = 1, b = 2
LET([head, *rest], [1, 2, 3, 4]);  // head = 1, rest = [2, 3, 4]
LET([_, x, _], [10, 20, 30]);      // x = 20,占位 _
```

#### 字典解构

```wlwl
LET(["x": x, "y": y], ["x": 1, "y": 2]);   // x = 1, y = 2
LET(["name": n], point);                    // 只取 name,其余忽略
```

#### 嵌套解构

```wlwl
LET([[a, b], [c, d]], [[1, 2], [3, 4]]);    // a=1, b=2, c=3, d=4
LET(["user": ["name": n]], response);        // 嵌套
```

#### 规则

- **必须完全匹配**:解构失败(数组长度不足、字典缺键)→ `E0026: destructure pattern mismatch`(本规范新增)。
- **`_` 占位**:表示"忽略该位置"。
- **`*rest`**(数组解构):收集剩余元素为 ARRAY;只能出现在最后一个位置。
- **缺省值**(v0.5 议程):v0.4 **不**支持 `LET([a, b = 0], arr)` 形式;见 §17.2。

#### 与解构相关的语义

- 解构**不是新表达式**;是 `LET` 第一个实参的语法形式。
- 解构不引入新关键字、不引入中缀;与 §1.2 第 7 条"一语义一写法"一致(字面量既作值又作模式,与 Rust 的 `let` 模式同构)。

### 7.6 模式匹配 `MATCH`(本规范新增,采纳 M-07)

`MATCH(value, clauses, default?)` —— 在 `clauses`(ARRAY)中按顺序匹配第一个满足的模式,执行对应分支。

#### 语法

```wlwl
MATCH(value,
    [
        ["pattern_1", result_1],
        ["pattern_2", result_2],
        ...
    ],
    default_expr               // 可选,默认 NULL
);
```

#### 模式形态

- **字面量模式**:`1` / `"foo"` / `TRUE` / `NULL`,按严格相等匹配。
- **构造器模式**:`OK(x)` 匹配 RESULT 成功变体并绑定 `x`;`ERR(e)` 匹配失败变体并绑定 `e`。
- **下划线通配**:`_` 匹配任何值,不绑定。
- **数组模式**:`[a, b, *rest]`,语义同 §7.5。
- **字典模式**:`["k": v]`,语义同 §7.5。
- **嵌套**:模式可任意嵌套。

#### 示例

```wlwl
MATCH(result,
    [
        [OK("ok"),    (PRINT("success"))],
        [OK(data),    (PROCESS(data))],
        [ERR(e),      (LOG_ERROR(e))],
        [_ ,          (PRINT("fallback"))]
    ]
);
```

#### 规则

- **首个匹配胜出**:clauses 按字面顺序求值,**第一个满足的模式**对应的 result 被求值并返回。
- **无匹配无 default** → `E0027: MATCH fell through without match or default`(本规范新增)。
- **无 default 时可省略**;缺省值为 `NULL`。
- 模式绑定**仅在对应 result 内可见**;不在外部作用域。
- 模式中绑定**新名字**在该分支作用域内遮蔽外层(无新 LET)。

#### 与 IF / 函数组合

`MATCH` 是宏函数(§3.4),不是新关键字,不引入 `case` / `switch` 家族。

## §8 函数

### 8.1 函数是一等公民

- 函数可作为参数传递、作为返回值、存放在变量/数组/字典中。
- 函数没有"方法重载",靠参数模式匹配区分(§8.4)。
- **例外**:宏函数(§3.4)不可作为值传递。

### 8.2 函数定义

`FUN(name(params), body)`:

```wlwl
FUN(hello(str),
    (PRINT(+(+("hello ", str), "!")))
);
```

- `name` 可省略,产生**匿名函数**:`FUN((x), (*(x, x)))`。
- `params` 是参数列表,每个参数:
  - `name` —— 必填参数
  - `name = default` —— 默认参数
  - `name: Type` —— **类型注解(Transient,运行时忽略,见 §2.4)**
  - `*rest` —— 剩余参数(收集为数组)
  - 三者可组合,形如 `name: Type = default`

```wlwl
FUN(greet(name, greeting = "hi"),
    (PRINT(+(+(greeting, ", "), name)))
);

greet("alice");                  // "hi, alice"
greet("alice", "hello");         // "hello, alice"
```

> 类型注解在 v0.4 仅为**元数据**,不参与运行时检查;任何语法上合法的注解都不报错。

### 8.3 函数调用

直接用 `name(args...)`,不区分"方法调用"和"普通调用"——但 `a.b(args)` 是对 `a` 的 `"b"` 方法的语法糖,见 §5.5 / §11.4。

### 8.4 函数应用与元数(本规范重大修订,修复 v0.3 公式错误)

v0.3 公式"必填参数数量 ≤ 实际参数数量 ≤ 必填参数数量 + 1(若存在剩余参数)"是**错的**(`*rest` 恰恰意味着无上限;"+1"疑似把默认参数混入)。v0.4 修正:

#### 规则(形式化)

设:
- `R` = 必填参数数量(无默认值、非 `*rest`)
- `D` = 默认参数数量(有默认值、非 `*rest`)
- `H` = `*rest` 是否存在(0 或 1)
- `N` = 形参总数 = `R + D + H`

调用实参数为 `A`,则:

| 形参形式 | 必须满足 |
|----------|----------|
| 无 `*rest` | `R ≤ A ≤ N`(可省略默认参数,按位置覆盖) |
| 有 `*rest` | `A ≥ R`(`*rest` 收集剩余实参为 ARRAY;无上限) |

#### 违反

`E0022: function 'foo' expects N..M args, got K`(带签名、行号、调用点)。

#### 调用方按名字覆盖(本规范删除 v0.3 表述)

v0.3 §8.4 称"按位置/名字覆盖",但调用文法只支持位置参数。v0.4 钉死:

- **位置参数**:按形参顺序填充;默认参数可省略;`*rest` 收集剩余。
- **名字参数**:v0.4 **不**支持 `foo(name="alice", age=30)` 形式;等价做法是传 DICT 作为选项对象:`foo(["name": "alice", "age": 30])`——这正是 §15.13 `std.ai` 已经在用的形式。
- 删除 v0.3 误导性"按名字覆盖"表述。

### 8.5 闭包

函数捕获其定义时的词法环境(具体 cell 语义见 §6.4):

```wlwl
FUN(make_counter(),
    LET(count, 0);
    FUN(() ,
        SET(count, +(count, 1));
        count
    )
);

LET(c, make_counter());
CALL(c);  // 1
CALL(c);  // 2
```

> 闭包 cell 存放在堆上;具体 GC 策略由实现决定,**不在本规范范围**。

### 8.6 NEW / INIT 协议(本规范重大补全,采纳 M-11)

v0.3 §11.3 示例中 `init` 方法只出现一次,但 E0051 已引用。本规范定型:

#### NEW 接受类值或类名字符串

```wlwl
LET(Rect, CLASS("Rectangle", NULL, [...]));  // R 是类值(返回值)
LET(r, NEW(Rect, 10, 20));                   // 接受类值
LET(r2, NEW("Rectangle", 10, 20));            // 接受类名字符串(兼容 v0.3 行为)
```

- **类值**:用 `LET` 接收 `CLASS(...)` 的返回值;`TYPE(Class)` 返回 `"CLASS"`(本规范新增;`CLASS` 是 §3.4 宏函数,其返回值带类型标签)。
- **类名字符串**:按"当前作用域 + 模块导入图"查找;未找到 → `E0028: class 'X' not found`(本规范新增)。

#### INIT 协议

`NEW(cls, args...)` 实际执行:

1. 创建新实例(`[member_keys: default_values]` 的 DICT);
2. 若实例或类包含名为 `"init"` 的方法,等价于 `CALL_METHOD(instance, "init", args...)`;
3. 否则,**丢弃** `args`(不报错,符合 v0.3 行为)。

#### SELF 绑定

类方法在通过 `CALL_METHOD` 调用时,第一个形参名为 `self`(约定)时,**自动**绑定到当前实例:

```wlwl
CLASS("Rectangle", NULL, [
    "width": 0,
    "height": 0,
    "init": FUN((self, w, h),
        SET_PROP(self, "width", w);
        SET_PROP(self, "height", h)
    ),
    "get_area": FUN((self),
        *(GET_PROP(self, "width"), GET_PROP(self, "height"))
    )
]);
```

- `self` 形参命名是**约定**(不强制),但**实现**必须按"首形参即 self"约定注入——即 `CALL_METHOD(rect, "get_area")` 等价于 `CALL_METHOD(rect, "get_area", rect)`(本规范明确)。
- 如果首形参命名为 `self` 以外的词,等价;如果首形参省略 → `self` 不可用,但 `CALL_METHOD` 仍会注入首实参,需用户手动接收。
- **链式语法糖**:`rect.get_area()` 等价于 `CALL_METHOD(rect, "get_area", rect)`,`self` 自动注入。

#### 错误码

- `E0051`:NEW 的实参数与 `init` 形参数不匹配。
- `E0028`:类名查找失败。
- `E0029`:实例化时 init 抛 ERR(原 §12.6 透明传播,实例为半初始化状态——产生 `E0029` 警告,记录半初始化实例)。

## §9 运算符

**核心原则**:一切运算符都是函数,大写命名,中缀仅在语法糖中后加(且**不进入核心规范**,见 §1.2 第 7 条)。

### 9.1 算术

| 函数 | 说明 |
|------|------|
| `+(a, b, ...)` | 至少 2 个参数 |
| `-(a, b)` | 二元 |
| `*(a, b, ...)` | 至少 2 个参数 |
| `/(a, b)` | 二元 |
| `%(a, b)` | 二元 |
| `NEG(a)` | 一元取负 |

#### `+` 的混合类型规则

- 所有参数类型一致时:
  - `INTEGER` / `FLOAT` 做算术加。
  - `STRING` 做字符串拼接。
  - `ARRAY` 做数组合并(返回新数组,非破坏性)。
- **类型不一致时**:**抛出 `E0030` 类型错误**,**不**做隐式转换。
- 如需将元素追加到数组,使用 `PUSH` 而非 `+`(语义清晰、避免歧义)。
- 例外:`INTEGER` 与 `FLOAT` 混合时,允许结果提升为 `FLOAT`,不视为类型不一致(算术常规)。

### 9.2 比较(本规范重大修订,修复 v0.3 §9.2 vs §12.6 矛盾)

v0.3 同时声明"比较返回类型总是 BOOLEAN"和"= 不在白名单 → =(ERR, 1) 返回 ERR"——矛盾。v0.4 钉死:

#### 规则

- 当**两个操作数均非 ERR** 时,`=` / `!=` / `>` / `<` / `>=` / `<=` 返回 `BOOLEAN`。
- 当**任一操作数是 ERR** 时,比较函数透明传播 ERR(§12.6);**不**返回 BOOLEAN。

> 这是"白名单扩展为零判定"的语义统一:比较函数对 ERR 透明,仅当入参全部 OK 时返回 BOOLEAN。

| 函数 | 含义 |
|------|------|
| `=(a, b)` | 等于 |
| `!=(a, b)` | 不等于 |
| `>(a, b)` | 大于 |
| `<(a, b)` | 小于 |
| `>=(a, b)` | 大于等于 |
| `<=(a, b)` | 小于等于 |

### 9.3 逻辑

| 函数 | 短路 | 说明 |
|------|------|------|
| `AND(a, b)` | 是 | 仅当 a 真才求值 b |
| `OR(a, b)` | 是 | 仅当 a 假才求值 b |
| `!(a, b, ...)` | 否 | 逻辑非;可接受多个参数(全部真才真;空参列表返回 TRUE,因 vacuous truth) |

### 9.4 真值规则(本规范补全 OK/ERR 真值,修复 §19 形式化缺位)

下列值视为**假**:

- `FALSE`
- `NULL`
- `INTEGER` 值 `0`
- `FLOAT` 值 `0.0`
- `FLOAT` 值 `NAN`(本规范新增,符合 IEEE 754 的"非数 ≠ 任何数"语义)
- `STRING` 值 `""`(空字符串)
- `ARRAY` 值 `[]`(空数组)

**`DICT` 与 `RESULT` 的真值**(本规范重大补全):

- `DICT`:非空为真,空为假。即 `LEN(d) > 0` 为真,`LEN(d) = 0` 为假。
- `OK(v)`:真值 = `v` 的真值(递归)。即 `IF(OK(0), a, b)` 取 `b`(因 `0` 假)。
- `ERR(_)`:本规范定型为**恒真**——**ERR 永远视为真**。

**设计动机**:
- `IF(OK(0), x, y)` 取 `y` —— 让 `IF(AND(IS_OK(r), condition), ...)` 这种"过滤"模式不必先拆 RESULT。
- `IF(ERR(_), x, y)` 取 `x` —— 让"先捕获 ERR,处理后再判断"模式自然。但**注意**:由于 §12.6 ERR 透明传播,`IF(+(1, ERR("e")), ...)` 不会进入 `IF` 求值,ERR 直接向上冒泡。所以"真值表"适用于"用户已用 `OR_DIE` 或 `UNWRAP` 解构后"。

> **修正 v0.3 §9.4 的内嵌 DICT 一身二职**:v0.3 写"`DICT` 值 `[]`(空字典)"——但 `[]` 已被 v0.4 钉死为 ARRAY(§4.5)。空 DICT 由 `DICT()` 产生。`IF` 的真值表改用"`LEN(d) = 0` 的 DICT"为假。

### 9.5 数值与跨类型语义(本规范重大补全,采纳 X-09 决议)

v0.3 留下大量"未定义行为"——这是 AI 生成代码的幻觉温床。v0.4 钉死:

| 场景 | 规则 | 错误码 |
|------|------|--------|
| `/(INTEGER, INTEGER)`(整除) | **截断除法(truncation toward zero)**;`/(7, 2) = 3`、`/(-7, 2) = -3` | 正常 |
| `/(INTEGER, 0)` | 抛 `E1003: division by zero` | `E1003` |
| `/(FLOAT, 0.0)` | 抛 `E1003`(即使 IEEE 754 允许 Inf) | `E1003` |
| `/(FLOAT, FLOAT)`(FLOAT 除以 FLOAT) | 浮点除法;允许 `Inf` / `NaN` 作为结果 | 正常 |
| `%(a, b)`(`a % b`)| `a - /(a, b) * b`(IEEE 754 语义),符号与被除数一致 | 正常 |
| `%(a, 0)` | 抛 `E1003` | `E1003` |
| `+(INTEGER, INTEGER)` 溢出 | **饱和**到 `INT64_MAX` / `INT64_MIN`;**不**回绕;产生 `W0015: integer overflow, saturated`(本规范新增) | `W0015` |
| `NEG(INTEGER_MIN)`(即 `-(−2^63)`) | 抛 `E0034: integer overflow on negation`(本规范新增) | `E0034` |
| `*(a, b)` 等其他运算溢出 | 同上:饱和 + `W0015` | `W0015` |
| 浮点 NaN 参与运算 | 产生 `NaN` 传播(符合 IEEE 754) | 正常 |
| `FLOAT` 转 `INTEGER`(`INT(3.7)`) | 截断;`INT(3.7) = 3`、`INT(-3.7) = -3` | 正常 |
| `FLOAT` 转 `INTEGER` 越界 | 抛 `E0035: float-to-int overflow`(本规范新增) | `E0035` |
| `INTEGER` / `FLOAT` 转换 | `INT("3.5")` 抛 `ERR(["kind": "ParseError"])`;`INT("3") = 3` | 正常 |
| 缺失的转换函数 | `FLOAT(s)` / `STR(f)` 由 `STR` / `INT` 兼任;详见 §10.3 | — |
| `=(1, 1.0)` | **视为相等**(本规范新增,与 v0.3 模糊地带不同) | 正常 |
| `<` / `>` 对 `STRING` | 按**Unicode 码点序**比较 | 正常 |
| `=` 对含 NaN 的容器 | `=[NaN]` 永不等于自身,按 IEEE 754 | 正常 |
| `NaN` 作 `DICT` 键 | **禁止** → `E0031` | `E0031` |
| 内建名遮蔽(用户) | 默认禁止 → `E0025`(`allow_builtin_shadow = true` 时允许但 W0030) | `E0025` / `W0030` |

**新错误码**:
- `E0033`:strict_types 违例(§2.7)
- `E0034`:NEG 越界
- `E0035`:FLOAT → INTEGER 越界
- `E1003`:除零(已存在,本规范补 E 表)

## §10 数据结构

### 10.1 数组(ARRAY)

| 操作 | 函数 | 说明 |
|------|------|------|
| 取长度 | `LEN(arr)` | 元素数(不递归) |
| 追加 | `PUSH(arr, val)` | 原地,返回 arr |
| 弹出 | `POP(arr)` | 移除末尾,返回该值 |
| 头部插入 | `UNSHIFT(arr, val)` | 原地,返回 arr |
| 头部删除 | `SHIFT(arr)` | 移除首位,返回该值 |
| 切片 | `SLICE(arr, start, end = -1)` | 返回新数组,负数从末尾数;`end = -1` 等价 `end = LEN(arr)` |
| 连接 | `CONCAT(a, b, ...)` | 返回新数组,非破坏性 |
| 包含 | `CONTAINS(arr, val)` | 返回 BOOLEAN |
| 索引查找 | `INDEX(arr, val)` | 返回第一次出现的索引,无则 `-1` |
| 反转 | `REVERSE(arr)` | 原地,返回 arr |
| **下标读取** | `INDEX_GET(arr, i)`(本规范新增,采纳 M-01) | 第 i 个元素;负数从末尾数 |
| **下标写入** | `INDEX_SET(arr, i, val)`(本规范新增,采纳 M-01) | 原地,返回 arr |
| 安全下标 | `AT(arr, i, default)`(本规范新增) | 越界返回 `default`(不抛 ERR) |
| 键值删除(字典) | `REMOVE_KEY(d, key)`(本规范新增,`DEL` 改名避免与删除命令混淆) | 原地,返回 d(键不存在则 NOOP) |

**下标边界**:
- `INDEX_GET(arr, i)`:`-LEN(arr) ≤ i < LEN(arr)`(支持负数);越界 → `E0036: array index out of bounds`(本规范新增,取代 v0.3 完全未定义)。
- `INDEX_SET(arr, i, val)`:同上,越界 → `E0036`。
- `i` 非 INTEGER → `E0031`。

**语法糖**:
- `arr[i]` 等价 `INDEX_GET(arr, i)`
- `arr[i] = v` 等价 `INDEX_SET(arr, i, v)`

> **修正 v0.3 没有此语义空白**:`arr[i] = v` 实际是 `INDEX_SET(arr, i, v)` 的语法糖,不是 `SET(arr[i], v)`——后者无意义。

### 10.2 字典(DICT)

| 操作 | 函数 | 说明 |
|------|------|------|
| 取长度 | `LEN(d)` | 键的数量 |
| 取键 | `KEYS(d)` | 返回 ARRAY(键列表,按插入顺序) |
| 取值 | `VALUES(d)` | 返回 ARRAY(值列表,按插入顺序) |
| 包含键 | `HAS(d, key)` | 返回 BOOLEAN |
| 删除键 | `REMOVE_KEY(d, key)`(本规范**重命名**自 v0.3 的 `DEL`,避免与"删除"操作符歧义) | 原地,返回 d(键不存在则 NOOP) |
| 合并 | `MERGE(a, b, ...)` | b 覆盖 a,返回新字典 |
| 遍历顺序 | `FOR(k, d, ...)` | 按**插入顺序**遍历键(见 §7.3) |
| **下标读取** | `INDEX_GET(d, k)`(本规范新增) | 取键 k 对应的值;不存在 → `E0037: key not found`(本规范新增) |
| **下标写入** | `INDEX_SET(d, k, v)`(本规范新增) | 原地插入或更新,返回 d |
| 安全下标 | `AT(d, k, default)`(本规范新增) | 键不存在返回 `default` |
| 安全删除 | `POP(d, k, default)`(本规范新增) | 返回删除的值,键不存在返回 `default` |

> **重命名决策**:`DEL` 在 v0.3 既是函数名又是工具/CLI 关键字"删除",AI 工具易误识别。本规范**将 `DEL` 重命名为 `REMOVE_KEY`**。v0.3 代码迁移:将 `DEL(d, k)` 替换为 `REMOVE_KEY(d, k)`。`DEL` 在 v0.4 中保留为 v0.3 兼容别名(产生 `W0051` 弃用警告),**v0.5 移除**。

**语法糖**:
- `d[k]` 等价 `INDEX_GET(d, k)`
- `d[k] = v` 等价 `INDEX_SET(d, k, v)`

> **修正 v0.3 §10.2 缺 GET/PUT 的表达力空洞**——v0.3 只 KEYS/VALUES/HAS/REMOVE_KEY/MERGE 五个函数;DICT 值的读取必须依赖 `AT(d, k, NULL)`。v0.4 显式定义 `INDEX_GET` 作为标准读取函数。

### 10.3 字符串(STRING)

| 操作 | 函数 | 说明 |
|------|------|------|
| 长度 | `LEN(s)` | 字符数(按 Unicode 码点) |
| 拼接 | `+(s1, s2, ...)` | 与算术 `+` 共用,过载 |
| 子串 | `SUB(s, start, len = -1)` | 负数从末尾;`len = -1` 等价到末尾 |
| 包含 | `CONTAINS(s, substr)` | 字符串版本 |
| 分割 | `SPLIT(s, sep)` | 返回 ARRAY |
| 替换 | `REPLACE(s, old, new)` | 全部替换,返回新串 |
| 大小写 | `UPPER(s)`, `LOWER(s)` | ASCII 行为确定;非 ASCII 行为由实现定义(§4.2 警告 W0014) |
| 整数 / 字符串 / 浮点 转换 | `STR(x)`, `INT(s)`, `FLOAT(s)`(本规范新增) | `INT` / `FLOAT` 失败抛 `ERR(["kind": "ParseError"])` |
| 裁剪 | `TRIM(s)`, `TRIM_START(s)`, `TRIM_END(s)`(本规范新增) | 去除空白 |
| 前后缀 | `STARTS_WITH(s, pre)`, `ENDS_WITH(s, suf)`(本规范新增) | 返回 BOOLEAN |
| 重复 | `REPEAT(s, n)`(本规范新增) | 返回新串 |
| 填充 | `PAD_START(s, n, c)`, `PAD_END(s, n, c)`(本规范新增) | 长度不足 n 时填充 |
| 拆分码点 | `CODEPOINTS(s)`(本规范新增) | 返回 ARRAY(码点 INTEGER) |
| 码点合成 | `FROM_CODEPOINTS(arr)`(本规范新增) | 返回 STRING |
| 字符串转 ARRAY | `SPLIT(s, "")` | 码点拆分 |

> 字符串**不可变**;任何"修改"返回新串。
> 字符串拼接 + `FORMAT`(§10.6)覆盖 v0.3 仅 `+` 拼接的痛点。

### 10.4 相等性

- `=(a, b)`:
  - `INTEGER` / `FLOAT` / `STRING` / `BOOLEAN` / `NULL` 按值比较;
  - `=` 跨 `INTEGER` / `FLOAT` 时视为相等(如 `=(1, 1.0) = TRUE`);
  - `ARRAY` / `DICT` 递归比较;
  - `FUNCTION` 按引用比较(同一闭包实例);
  - `RESULT`:`OK(a) = OK(b)` 当且仅当 `a = b`;`ERR(e1) = ERR(e2)` 当且仅当 `e1 = e2`(按 §10.4 递归);`OK(a) != ERR(b)`。
- DICT 键的相等性遵循 §2.3 严格相等规则。
- 含 `NaN` 的 FLOAT 永不等于自身(IEEE 754);含 `NaN` 的 ARRAY / DICT 永不等于自身。

### 10.5 高阶集合函数套件(本规范新增,采纳 M-02)

§10.1 / §10.2 仅为命令式原语;**v0.4 新增**纯函数式套件,放在 `wlwl:std.collection`(§15.7)。此处仅规范**签名与语义**;§15.7 给出完整描述。

| 函数 | 签名 | 说明 |
|------|------|------|
| `MAP(arr, f)` | `f: FUNCTION(v) -> v'` | 返回 `[f(a), f(b), ...]` |
| `FILTER(arr, f)` | `f: FUNCTION(v) -> BOOLEAN` | 保留 f(v)=TRUE 的元素 |
| `REDUCE(arr, f, init)` | `f: FUNCTION(acc, v) -> acc'` | 左折叠;空数组返回 init |
| `SORT(arr, cmp?)` | `cmp: FUNCTION(a, b) -> BOOLEAN`(a < b) | 排序,默认按 `<` |
| `SORT_BY(arr, key)` | `key: FUNCTION(v) -> k`,按 k 排序 | |
| `ZIP(a, b, ...)` | | 返回 ARRAY of ARRAY,长度 = 最短 |
| `RANGE(n)` / `RANGE(start, end, step = 1)` | | 整数范围;`step=0` 抛 `E0038`(本规范新增) |
| `ANY(arr, f?)` | | 任一满足(默认恒真) → BOOLEAN |
| `ALL(arr, f?)` | | 全部满足(默认恒真) → BOOLEAN |
| `FIND(arr, f)` | | 首满足 f 的元素;无则 `NULL` |
| `ENUMERATE(arr)` | | 返回 `[0, v0], [1, v1], ...` |
| `TAKE(arr, n)` / `DROP(arr, n)` | | 前 n / 跳过 n |
| `FLAT(arr)` | | 展平一层 |
| `UNIQ(arr)` | | 去重(按 `=`) |
| `GROUP_BY(arr, key)` | `key: FUNCTION(v) -> k` | 按 k 分组为 DICT |
| `JOIN(arr, sep)` | 字符串版本 | ARRAY → STRING |

**与 FOR / WHILE 的关系**:这些函数是 `WHILE` + `IF` + `LET` 的**纯函数式封装**;不引入新关键字;不破坏审美。

**ERR 透明传播**:上述函数对 ERR 输入透明(继承 §12.6 默认行为);`f` 抛 ERR 也透明传播。

### 10.6 字符串格式化 `FORMAT`(本规范新增,采纳 M-09)

`FORMAT(template, args...)` —— 函数式字符串插值,绕开"字符串模板"争议。

**模板语法**:
- `{0}`、`{1}` ... `{N}` 占位,依次替换为 `args[0]`、`args[1]` ...
- `{name}` 占位,从 `args[0]`(必须是 DICT)按 key 取值
- 混合:`FORMAT("hi {0}, age {age}", "alice", ["age": 30])`

```wlwl
LET(name, "alice");
LET(age, 30);
LET(s, FORMAT("hi {0}, you are {1} years old", name, age));
// "hi alice, you are 30 years old"

LET(t, FORMAT("hi {name}, age {age}", ["name": "alice", "age": 30]));
// "hi alice, age 30"
```

- 模板中**未匹配**的 `{...}` → 保留原样。
- 模板解析失败(如 `{` 单独出现)→ `E0039: malformed format template`(本规范新增)。
- `args[i]` 非字符串 / 非 DICT → `STR(args[i])` 转换(STR 语义见 §10.3)。

> **本规范钉死**:v0.4 **不**引入字符串模板字面量(如 `"hi ${name}"`);`FORMAT` 是规范提供的唯一插值机制。这与 §1.5 P0 优先一致。

### 10.7 类型化结果构造(本规范新增)

- `OK(v)` —— 构造 `RESULT` 成功变体;`v` 任意类型。
- `ERR(e)` —— 构造 `RESULT` 失败变体;`e` **必须**是 STRING 或 DICT(违反 → `E0030`)。
- 详见 §2.2.1 / §12.1。

## §11 面向对象

### 11.1 设计取向

OOP 是函数式之上的"组织代码"机制,**不是**核心。类的内部表示就是 DICT + 函数。

### 11.2 类定义

`CLASS(name?, parent, members)`:

- `name`:STRING,类名(可省略,产生匿名类;`name` 存在时作为 `"name"` 成员挂入,便于 `TYPE(instance) = class.name`)。
- `parent`:父类(可为 `NULL` 表示无父类;或父类的类值 / 类名字符串)。
- `members`:DICT,键为属性 / 方法名,值为:
  - 默认值(属性)
  - `FUN(...)` 函数字面量(方法)
  - **可选**:`init` 方法(§8.6 协议)

```wlwl
CLASS("Rectangle", NULL, [
    "width": 0,
    "height": 0,
    "init": FUN((self, w, h),
        SET_PROP(self, "width", w);
        SET_PROP(self, "height", h)
    ),
    "get_area": FUN((self),
        *(GET_PROP(self, "width"), GET_PROP(self, "height"))
    ),
    "scale": FUN((self, factor),
        SET_PROP(self, "width", *(GET_PROP(self, "width"), factor));
        SET_PROP(self, "height", *(GET_PROP(self, "height"), factor))
    )
]);
```

`CLASS(...)` 是**宏函数**,返回值类型是 `CLASS`;可以用 `LET` 接收。

### 11.3 实例化与属性

```wlwl
LET(Rect, CLASS("Rectangle", NULL, [...]));   // 类值
LET(rect, NEW(Rect, 10, 20));                 // 接受类值
LET(area, rect.get_area());                   // 200
rect.scale(2);
```

或用类名字符串:

```wlwl
LET(rect, NEW("Rectangle", 10, 20));
```

**`GET_PROP` / `SET_PROP` 的可用性**:
- 主要用于**类方法内访问 self 的属性**(因方法参数是 `self`,不是 `this`)。
- 对**类成员 / 任意 DICT** 也可以用,但 `INDEX_GET` / `INDEX_SET` 更通用。
- `GET_PROP(obj, k)` 与 `INDEX_GET(obj, k)` **等价**(同样抛 `E0037` 越界);只是命名反映"对象属性 vs 容器下标"的语义意图。

### 11.4 方法调用的链式语法糖

详见 §5.5。这里强调**`a.b(args)` 的 self 注入**:通过 `CALL_METHOD` 调用方法时,`self`(首形参)被自动绑定到调用者。详见 §8.6。

**v0.4 修复 v0.3 §11.4 的 `???` 占位符**:v0.3 写 `CALL_METHOD(CALL_METHOD(GET_PROP(a, "b"), "c"), ???, args)`,`???` 永不解释。v0.4 钉死:`CALL_METHOD` 的第一个非方法名实参是 self(若首形参命名为 `self`);否则首形参接收调用对象。

### 11.5 继承

- `CLASS(name, parent, members)` 中 `parent` 可以是父类的**类值**或**类名字符串**。
- 方法解析顺序(MRO):v0.4 仍用**单链**:子类 → 父类 → NULL。
- **多继承不支持**(v0.5 议程见 §17.2)。

### 11.6 封装

- v0.4 **不**做访问控制。所有属性公开。
- 命名约定:以下划线 `_` 开头的属性 / 方法视为"私有",由文档和工具约定,语言层不强制。

### 11.7 静态属性 / 方法

v0.4 **不**做。`CLASS` 体里只能是属性默认值和方法。需要在类层面共享数据,使用模块顶层 `LET` + DICT。

## §12 错误处理

### 12.1 范式

参考 Rust 的 `Result<T, E>`,但在动态类型下表示为两个构造器:

- `OK(value)` —— 成功,值可以是任意类型(类型为 `RESULT`)
- `ERR(error)` —— 失败,值**必须**是 STRING 或 DICT(描述错误的结构化信息)

### 12.2 触发与传播

| 操作 | 函数 | 说明 |
|------|------|------|
| 不可恢复错误 | `PANIC(msg)` | 立即终止执行,`msg` 必须是 STRING 或 DICT |
| 错误传播 | `TRY(expr)` | 若 expr 求值为 `ERR(...)`,提前从当前函数返回该 ERR;否则取其值 |
| 默认值兜底 | `OR_DIE(expr, default)` 或 `UNWRAP_OR(expr, default)`(本规范新增别名) | 若 expr 是 `ERR`,返回 default;否则取 expr 的值 |
| 主动判断 | `IS_OK(x)`, `IS_ERR(x)` | BOOLEAN |
| **解构成功** | `UNWRAP(x)`(本规范新增) | `UNWRAP(OK(v)) → v`;`UNWRAP(ERR(e)) → PANIC E0100` |
| **提取 ERR 载荷** | `ERR_PAYLOAD(x)`(本规范新增,采纳 M-03) | `ERR_PAYLOAD(ERR(e)) → e`;`ERR_PAYLOAD(OK(v)) → E0030` |
| **包装错误** | `WRAP(err, ctx)`(本规范新增) | `WRAP(ERR(e), "loading config") → ERR(["original": e, "context": "loading config"])` |

```wlwl
FUN(parse_int(s),
    LET(n, INT(s));
    IF(IS_ERR(n), RETURN(WRAP(ERR(["kind": "ParseError", "input": s]), "parse_int")));
    UNWRAP(n)
);
```

**UNWRAP 的精确语义**:
- `UNWRAP(OK(v))` → `v`。
- `UNWRAP(ERR(e))` → 立即 `PANIC`,错误对象满足 §14.2 schema,`code: "E0100"`,`errorCategory: "internal"`,`message: "called UNWRAP on ERR"`,`cause: e`。
- 边界:`UNWRAP(non-RESULT)` → `E0030` 类型错误。

**UNWRAP_OR 的精确语义**(本规范新增,采纳 X-11 别名建议):
- `UNWRAP_OR(OK(v), _)` → `v`。
- `UNWRAP_OR(ERR(_), default)` → `default`。
- 与 `OR_DIE` 完全等价;`UNWRAP_OR` 是**主推名字**(与 Rust `unwrap_or` 对齐,降低 AI 误用),`OR_DIE` 保留为 v0.3 兼容别名,**v0.5 移除**。

**ERR_PAYLOAD 的精确语义**:
- `ERR_PAYLOAD(ERR(e))` → `e`(STRING 或 DICT,原样返回)。
- `ERR_PAYLOAD(OK(v))` → `ERR(["kind": "NotAnError"])`(`E0030` 类型错——`OK` 不是 ERR)。
- `ERR_PAYLOAD(non-RESULT)` → 同上 `E0030`。
- **核心作用**:让"打印一个错误""序列化一个错误""提取错误码"成为可能(修复 v0.3 §12.6 封闭白名单漏洞)。

**WRAP 的精确语义**:
- `WRAP(ERR(e), ctx)` → `ERR(["original": e, "context": ctx])`。
- `WRAP(OK(v), _)` → `OK(v)`(不影响成功值)。
- `WRAP(non-RESULT, _)` → `E0030`。

### 12.3 `TRY` 的关键语义

`TRY(expr)` 在语义上等价于:

```
LET(_tmp, expr);
IF(IS_ERR(_tmp), RETURN(_tmp));
UNWRAP(_tmp)  // 取出 OK 里的值
```

因此它**只能**出现在期望"接收一个值"的位置,比如赋值、函数实参、另一层 `TRY` 的内部。

```wlwl
LET(x, TRY(some_risky_op()));
LET(y, TRY(other_op()));
```

> **修正 v0.3 §12.6 示例自相矛盾**:`LET(r, TRY(ERR("e"))); // r = ERR("e")(传播到当前函数)` 是错的——`LET` 在函数体顶层时,`TRY(ERR(...))` 提前 RETURN,`LET` 永不完成。**v0.4 示例改用 `OR_DIE` 或函数体内演示**(§12.6 末尾)。

### 12.4 `PANIC` vs `ERR`

- `ERR`:**可恢复**,沿调用栈向上传播,通过 `TRY` 或调用方处理。
- `PANIC`:**不可恢复**,打印结构化错误后立即终止(默认 exit code 1,见 §14.6)。用于真正不可处理的内部错误。
- `PANIC(msg)` 的 `msg` **必须**是 STRING 或 DICT,违反 → `E0030`。

### 12.5 错误信息结构

所有 `ERR` / `PANIC` 的载荷**必须**是 STRING 或 DICT。DICT 形式推荐字段见 §14.2。

### 12.6 ERR 透明传播规则

> 这是 WLWL 对错误处理的关键语义,本规范 v0.2 引入,v0.4 修订为**"注册表"模型**取代 v0.3 的"封闭白名单"。

#### 规则

`ERR` 值在**未注册**(§12.7)消费 ERR 的函数中**透明传播**:

- 任何**普通函数**(§12.7 注册表之外的函数)接收到 `ERR` 类型的实参时,**必须**直接返回该 `ERR`,**不**执行函数体,亦不报"参数类型错误"。
- 传播过程**不消耗** `ERR`;原 `ERR` 值原封不动地向上冒泡。
- 透明传播不消耗步;函数调用本身被短路为"返回 ERR"(见附录 E 形式化)。

#### 示例(本规范修正版)

```wlwl
LET(r, +(1, ERR("oops")));     // r = ERR("oops"),+ 本身不被调用
LET(r, LEN(ERR("oops")));      // r = ERR("oops")
LET(r, INDEX_GET(ERR("oops"), "k"));  // r = ERR("oops")(新增的下标读取也透明)
LET(r, IF(TRUE, ERR("e"), 2)); // r = ERR("e")(IF 未注册消费 ERR)
LET(r, OK(+(1, 2)));           // r = OK(3)
LET(r, IS_OK(OK(1)));          // r = TRUE
LET(r, OR_DIE(ERR("e"), 0));   // r = 0
LET(r, UNWRAP_OR(ERR("e"), -1)); // r = -1(别名)
LET(r, ERR_PAYLOAD(ERR(["code": "E0080"])));  // r = ["code": "E0080"](修复 v0.3 痛点)

// 修正 v0.3 错误示例:用 OR_DIE 替代 LET(r, TRY(ERR("e")))
LET(s, OR_DIE(TRY(risky_op()), "fallback"));  // risky_op() 失败时,整个 LET 表达式值为 "fallback"
```

**TRY 修正示例**(对比 v0.3 §12.6 自相矛盾):
```wlwl
FUN(safe_div(a, b),
    LET(q, TRY(/ (a, b)));  // 除零时 b=0 抛 ERR → TRY 提前 RETURN
    /(q, 1)                 // 仅在 b != 0 时执行
);
```

#### 为何如此设计

- 默认传播、显式处理,杜绝错误被静默吞掉。
- 调用方不显式 `TRY` / `OR_DIE` / `UNWRAP`,错误就一直往上冒,直到最外层被 `PANIC` 兜底。
- 强制 AI 生成代码时考虑错误路径(否则测试会立即暴露)。

#### 与 `PANIC` 的区别

`ERR` 透明传播是**软失败**;`PANIC` 是**硬终止**。`PANIC` 不参与透明传播规则。

### 12.7 ERR 消费者注册表(本规范新增,取代 v0.3 封闭白名单)

v0.3 仅有 `IS_OK` / `IS_ERR` / `OR_DIE` / `TRY` 4 个白名单函数,造成"无法打印错误"的痛点。v0.4 改为**注册表机制**:

#### 已注册函数(本规范首次定型,完整列表)

| 函数 | 消费 ERR 时的行为 |
|------|--------------------|
| `IS_OK(x)` | 返回 `BOOLEAN`,不消费 ERR(返回 `FALSE` 时 ERR 信息已观察) |
| `IS_ERR(x)` | 返回 `BOOLEAN`,不消费 ERR(返回 `TRUE` 时 ERR 信息已观察) |
| `OR_DIE(x, default)` / `UNWRAP_OR(x, default)` | ERR 时返回 `default`,OK 时返回 `v` |
| `TRY(x)` | ERR 时提前 RETURN,OK 时返回 `v` |
| `UNWRAP(x)` | ERR 时 PANIC(已消费 ERR 的"观察"动作) |
| `ERR_PAYLOAD(x)` | ERR 时返回载荷 `e`,OK 时抛 `E0030` |
| `WRAP(err, ctx)` | ERR 时包装为新 ERR;OK 时返回 OK |
| `TYPE(x)` | 返回 `"RESULT"`,不消费 ERR |
| `=(x, y)` / `!=(x, y)` | 与 §9.2 一致:操作数均非 ERR 返回 BOOLEAN;任一为 ERR 透明传播(**注意:`=` / `!=` **不**消费 ERR**) |
| `IF(cond, t, e)` | 条件为 OK 或非 RESULT 时正常求值对应分支;**不消费 ERR**(详见下) |

#### `IF` 与 ERR 的精确规则(本规范补充)

`IF` 不在 §12.7 消费 ERR 的函数列表中——`IF(cond, t, e)` 按 §7.1 规则求值:

- `cond` 为 `OK(v)`,真值 = `v` 真值(§9.4);进入 `t` 或 `e`。
- `cond` 为 `ERR(_)`,真值 = TRUE(§9.4);进入 `t`。
- 但 `t` / `e` 表达式求值时,**若自身产生 ERR**,正常传播。

即 `IF` 是**真值判断器**,不消费 ERR 载荷;需要消费 ERR 用 `IS_ERR` + `ERR_PAYLOAD` + 显式解构。

#### 注册表扩展原则

新函数需"消费 ERR"(即不透明传播)时,必须**经本规范升级**加入注册表;实现**不得**在注册表之外消费 ERR。v0.4 注册表共 9 项;未来扩展每加一项,必须在 §18 / 附录 D 给出动机与互操作分析。

### 12.8 错误包装链(本规范新增)

`WRAP(err, ctx)` 详见 §12.2。多次 `WRAP` 形成 `cause` 链,详见 §14.2 `cause` 字段。**WRAP 是 v0.4 新增的"错误链"原语**;`cause` 字段是 v0.4 新增的"错误链"承载字段。

## §13 模块系统

### 13.1 文件即模块

- 每个 `.wl` 源文件是一个模块。
- **模块名解析规则**(优先级从高到低):
  1. 文件内的 `MODULE("explicit_name", ...)` 声明(若存在)
  2. `wlwl.toml` 中 `package.name`(若存在)
  3. 文件名(不含扩展名)
- 跨目录引用见 §13.5、§13.6。

### 13.2 显式 `EXPORT` 名单

模块**必须**通过 `EXPORT(names)` 显式声明哪些名字对外可见,否则一律私有。

```wlwl
// file: math.wl
FUN(add(a, b), +(a, b));
FUN(sub(a, b), -(a, b));
LET(PI, 3.14159);

EXPORT(["add", "PI"]);
```

- `EXPORT` 必须出现在文件**顶层**;`EXPORT` 可多次出现,实现**应当**取并集(便于条件导出)。
- 引用一个**未导出**的名字 → `E0023: 'sub' is not exported by module 'math'`。
- `EXPORT` 可以是 ARRAY(简单名字列表)或 DICT(接口契约,见 §13.11)。
- `EXPORT(["add", "add"])` 视为合法(取并集);`EXPORT` 与 `EXPORT` 之间的冲突以**后声明者为准**,产生 `W0016: duplicate export name`(本规范新增)。

### 13.3 显式 `IMPORT`

`IMPORT(path, names, opts?)` 的三参数形式:

```wlwl
IMPORT(path, names)              // 标准形式
IMPORT(path, names, opts)        // 带选项(预留)
```

其中:
- `path`:STRING,**模块路径**(见 §13.5 路径形式)
- `names`:ARRAY,两种形式:
  - 简单形式:`["add", "PI"]` —— 直接引入同名绑定
  - 重命名形式:`["add": "math_add", "PI": "MATH_PI"]` —— 引入并重命名(见 §13.4)
- `opts`:DICT(可选,v0.4 预留 `lazy` / `type_only` / `capability` 字段,均**未启用**)

#### 重复导入规则

- 同一作用域内,**重复导入同名符号** → `E0021: name 'x' already bound by previous IMPORT`。
- **不**允许隐式覆盖(无论两次 `IMPORT` 的是同一模块还是不同模块)。
- 如需不同模块的同名符号,使用**导入时重命名**(§13.4)。

### 13.4 导入时重命名(本规范重大修订:**删除 AS 函数**)

v0.3 保留了单参数 `AS` 函数作为"已绑定名字的本地别名"——但这与 §1.2 第 7 条"一语义仅一种标准写法"直接冲突:既然 §13.4 的导入时重命名已能覆盖所有合理需求,`AS` 是**冗余**的"第二套名字绑定机制"。

**v0.4 删除 `AS` 函数**(本规范作为 v0.3 §18.2 第 5 项"AS 函数去留"的最终裁决):

- **完全删除** §13.4 末"例外情况:保留单参数 AS"段。
- **删除附录 D 变更日志中 AS 保留项**。
- v0.3 引入 `AS` 的代码**必须**改写为 `LET(b, a)`(等价,直白)。
- 任何引用 `AS` 的代码 → `E0021` 符号未定义(因为它不再是宏函数 / 全局内建)。

#### 导入时重命名(唯一规范途径)

```wlwl
IMPORT("math", ["add": "math_add", "PI": "MATH_PI"]);
// 现在:add 已重命名为 math_add,PI 已重命名为 MATH_PI
// 原名 "add"、"PI" 在当前作用域中**不**被绑定
```

- `alias_name` 可以与 `original_name` 相同(无意义的别名,但语法合法)。
- 多个名字可以一次性重命名,使用 ARRAY 语法。

#### 决策记录(本规范附录 D 引用)

**理由**:
- Go / Rust / TypeScript 等主流语言**全部**采用导入时重命名,**没有**单独 `AS` 函数。
- 单独 `AS` 函数带来"已绑定名字的二次重命名"语义,**难以静态分析**(`AI 友好`目标要求导入行为可静态预测)。
- 导入时重命名**与 IMPORT 紧耦合**,AI 工具解析 IMPORT 即可拿到完整绑定,无需二次扫描。
- 保留两套机制违反 §1.2 第 7 条。

### 13.5 跨目录引用

支持三种路径形式(优先级从高到低):

| 形式 | 示例 | 适用场景 |
|------|------|----------|
| 相对路径 | `IMPORT("./other/foo", ...)`,`IMPORT("../sibling/bar", ...)` | 库内引用、monorepo 内部包 |
| 命名空间路径 | `IMPORT("wlwl:std.io", ...)`,`IMPORT("myteam:utils", ...)` | 标准库、已注册包 |
| 简单名(同目录) | `IMPORT("math", ...)` | 单文件项目 |

#### 路径解析规则

1. **以 `./` 或 `../` 开头**:相对路径,以当前模块所在目录为基准。
2. **以 `xxx:` 开头**(其中 `xxx` 是命名空间前缀):命名空间路径,根据 `wlwl.toml` 的 `[dependencies]` 解析;标准库的命名空间固定为 `wlwl:`。
3. **其他**:先尝试同目录,失败则尝试 `wlwl.toml` 中所有依赖包的根。

#### 跨目录的边界规则

- 跨目录导入时,`IMPORT` 链式递归解析,但**禁止目录外的搜索**(类似 Rust 的 `mod.rs` 边界)。
- 项目根目录(包含 `wlwl.toml` 的目录)是搜索的最高边界。
- 试图越界 → `E0040: module 'foo' not found outside project root`。

### 13.6 命名空间路径(标准库与第三方包)

#### 标准库命名空间

所有标准库模块位于 `wlwl:` 命名空间下:

```wlwl
IMPORT("wlwl:std.io", ["PRINT"]);
IMPORT("wlwl:std.json", ["PARSE", "STRINGIFY"]);
IMPORT("wlwl:std.fs", ["READ_FILE"]);
```

#### 第三方包命名空间

第三方包在 `wlwl.toml` 中通过 `[dependencies]` 注册,使用 `<namespace>:<name>` 形式引用:

```toml
# wlwl.toml
[package]
name = "myapp"
version = "0.1.0"
language_version = "0.4"        # 本规范新增:语言版次

[dependencies]
"myteam:utils" = { path = "../utils" }
"huggingface:client" = "^0.5.0"
```

```wlwl
IMPORT("myteam:utils", ["format_date"]);
IMPORT("huggingface:client", ["Client"]);
```

#### 命名空间冲突规则

- 同一项目内**禁止**注册同名命名空间(可在 `wlwl.toml` 中通过 `[namespaces]` 显式声明)。
- 命名空间命名规则:小写字母、数字、连字符(`-`),首字符必须为字母。
- 冲突 → `E0043: namespace 'myteam' is already registered with different path`。

### 13.7 循环导入

- 检测到循环导入(`A` 导入 `B`,`B` 导入 `A`,形成环)时,抛出 `E0041: circular import detected: A -> B -> A`,**终止加载**。
- v0.4 **不**支持部分加载或延迟加载解决循环依赖。
- 错误信息列出完整环路路径(沿用 v0.3 增强)。

### 13.8 `wlwl.toml` 包清单

#### 基本格式

```toml
[package]
name = "myapp"                          # 必填,小写+连字符
version = "0.1.0"                       # 必填,SemVer
language_version = "0.4"                # 必填(本规范新增),本规范语义版本
entry = "src/main.wl"                   # 必填,入口文件相对路径
description = "A WLWL app"              # 可选
license = "MIT"                         # 可选
allow_builtin_shadow = false            # 本规范新增(§6.6),默认 false

[dependencies]
# 路径依赖(本地开发)
"myteam:utils" = { path = "../utils" }

# 版本依赖(中央仓库,v0.5 启用完整协议)
"huggingface:client" = "^0.5.0"
"json:parser" = "1.2.3"

# 详细约束
"strict:math" = { version = ">=1.0.0, <2.0.0", optional = true }

[namespaces]
# 显式命名空间映射(可选,通常自动推断)
"myteam" = "./vendor/myteam"

[features]
strict_types = false                    # 见 §2.7 渐进类型开关
default_encoding = "utf-8"              # 标准库相关
allow_builtin_shadow = false            # 同 [package],允许在 features 中覆盖
```

#### 字段说明

- **`[package]`** —— 必填段,描述本包。
- **`[dependencies]`** —— 依赖列表。键是 `<namespace>:<name>`,值是约束表达式。
- **`[namespaces]`** —— 显式命名空间到本地路径的映射(可选,默认按 `[dependencies]` 自动推断)。
- **`[features]`** —— 特性开关(本规范仅定型 `strict_types` / `default_encoding` / `allow_builtin_shadow`)。
- **`language_version`**(本规范新增):声明本包依赖的 WLWL 语义版本;实现**必须**在加载时校验,与自身支持的语义版本比较,不兼容 → `E0044: language_version mismatch: package requires X.Y, implementation supports A.B`(本规范新增)。

#### `wlwl.lock`

`wlwl.lock` 是**自动生成**的依赖锁定文件,记录每个依赖的实际版本 / 路径 / 哈希,确保可重现构建。

- 提交到版本控制(类似 `package-lock.json` / `Cargo.lock`)。
- **禁止**手动编辑。
- `wlwl build` / `wlwl run` 优先读 lock,缺失时按 toml 解析并生成 lock。
- **lock 与 toml 不一致**(用户在 lock 之外改了 toml)→ `E0042: lock file inconsistent with wlwl.toml`(本规范新增,补 v0.3 §14.4 编号空洞)。

### 13.9 依赖求解:MVS(本规范定型,采纳 I-05)

v0.3 把"Cargo-style 还是 npm-style"挂起到 v0.4。v0.4 决策:**采用 Cargo 风格的最小版本选择(Minimal Version Selection, MVS)**:

#### 决策依据

- **结果可由 lock 文件独立复现**:MVS 给定 toml + lock 即可预测解析结果。
- **算法可解释**:与 npm / PubGrub 类求解器相比,MVS 是"线性扫描",AI 工具可静态分析。
- **v0.x 阶段不需要 PubGrub**:PubGrub 适合"已有生态冲突压力"的场景(如 npm / cargo 中心化仓库),WLWL v0.4 仅本地路径 + 中央仓库 v0.5 启用,**冲突压力低**,MVS 足够。
- **v0.5 议程**:若中央仓库引入后冲突频繁,**可平滑**升级为 PubGrub。

#### MVS 规则(简化描述,完整算法在 §13.9.1)

- 对每个依赖,选择**满足所有约束的最低版本**。
- 循环依赖(逻辑)→ `E0041`。
- 冲突(无版本满足所有约束)→ `E0045: dependency conflict`(本规范新增)。

#### 13.9.1 MVS 算法骨架(规范性)

```
for each dep in [dependencies] (拓扑序):
    candidates = 满足 dep 约束的版本集合(从注册表 / 路径)
    if candidates is empty: error E0045
    choose min(candidates) by SemVer
    lock.dep = chosen
    if chosen has its own dependencies: append to worklist
```

详细算法在 Cargo 官方文档有同等描述(本规范与之对齐)。

### 13.11 模块接口契约(本规范细化)

v0.3 已定型,本规范进一步明确:

```wlwl
EXPORT([
    "add": ["params": ["INTEGER", "INTEGER"], "returns": "INTEGER", "errors": ["E0022"]]
]);
```

- `params`:ARRAY of STRING,每个元素是参数类型名(类型注解形式,见 §2.4)
- `returns`:STRING,返回类型名
- `errors`:ARRAY of STRING(可选),可能抛出的错误码列表
- `effects`:ARRAY of STRING(可选,本规范新增,见 §17.2 能力系统;v0.4 不强制)

#### 契约执行时点

- v0.4 **不**自动执行契约**(与 §2.4 类型注解一致,Transient 立场)。
- 工具 / AI 读取契约,生成文档、提示、测试用例。
- `strict_types: true` 时,实现**必须**在 IMPORT 边界做运行时检查(§2.7)。

### 13.12 模块作为值(本规范新增,采纳 M-08)

模块是一等值,可作为参数传递、作为返回值、存放在变量中。

- **模块对象类型**:`DICT`(同 §11.1 类内部表示)。
- **构造**:`LET(m, MODULE_REF("wlwl:std.io"))`(本规范新增;语义 = 加载模块但不绑定名字,返回模块对象)。
- **使用**:`m.PRINT("hi")` 等价 `IMPORT("wlwl:std.io", ["PRINT"]); PRINT("hi")` 后的 `PRINT("hi")`,但**绑定名不进入作用域**。

```wlwl
LET(io, MODULE_REF("wlwl:std.io"));
LET(util, MODULE_REF("myteam:utils"));
io.PRINT("hi");
util.format_date(NOW());
```

- **用例**:减少导入名称污染;延迟绑定;动态模块选择(基于配置)。

### 14.1 总则

**所有** WLWL 错误,无论来自词法、语法、运行时还是用户主动 `ERR`/`PANIC`,**必须**符合以下结构化格式。实现**不得**只输出不可解析的自由文本。

### 14.2 标准错误对象[v0.4 增强]

```wlwl
ERR([
    "error_schema_version": "1.1.0",                  // [v0.4 升级]schema 版本
    "code": "E1003",                                  // 错误码
    "severity": "error",                              // "error" | "warning" | "note"
    "errorCategory": "runtime",                       // 13 类之一
    "retryable": FALSE,                                // TRUE/FALSE
    "idempotent": FALSE,                               // [v0.4 新增]操作是否幂等
    "retry_after": NULL,                               // [v0.4 新增]毫秒,NULL 或 INTEGER;仅 retryable=TRUE 时有意义
    "message": "division by zero",                    // 一句话人类描述
    "location": {                                      // [v0.4 重大修订]统一为对象
        "file": "main.wl",
        "line": 42,
        "col_start": 5,
        "line_end": 42,
        "col_end": 12
    },
    "source_line": "LET(x, /(y, z));",                // 出错行的源码
    "hint": "检查除数 z 是否可能为 0",                // 自然语言修复建议
    "suggestion_code": [                               // 机器可执行的修复(沿用 v0.2)
        ["kind": "patch", "description": "...", "patch": [...]]
    ],
    "related": [],                                      // 相关位置
    "trace": [                                          // [v0.4 新增]调用栈
        ["frame": "main", "location": <location>],
        ["frame": "compute", "location": <location>],
        ...
    ],
    "cause": NULL                                       // [v0.4 新增]由 WRAP 形成的链
]);
```

#### `errorCategory` 字段[v0.3 引入,v0.4 保留]

13 类之一:

| 值 | 含义 | 典型错误码 |
|----|------|------------|
| `lexical` | 词法错误 | E0001-E0003 |
| `syntax` | 语法错误 | E0010-E0014 |
| `name` | 名字解析错误 | E0020-E0029 |
| `type` | 类型错误 | E0030-E0039 |
| `module` | 模块解析错误 | E0040-E0045 |
| `oop` | OOP 错误 | E0050-E0051 |
| `test` | 测试框架错误(本规范新增) | E0046-E0049 |
| `io` | 文件系统错误 | E0060-E0063 |
| `json` | JSON 解析错误 | E0070-E0071 |
| `ai` | std.ai 错误 | E0080-E0083 |
| `network` | 网络错误 | E0090-E0094(本规范细分) |
| `runtime` | 通用运行时错误 | E1003 等 |
| `user` | 用户主动抛错 | E0099 |
| `internal` | 内部错误 | E0100-E0102 |

#### `retryable` 字段[v0.3 引入,v0.4 增强]

- `TRUE` —— 操作**可能**在下一次重试时成功(如网络超时、文件锁等待)
- `FALSE` —— 重试**不会**改变结果(如参数类型错误、未定义名字)
- AI 工具应根据 `retryable` 决定是否自动重试,而不是盲目重试所有错误

#### `idempotent` 字段[v0.4 新增]

- `TRUE` —— 重试产生与首次相同结果(GET 请求、查询)
- `FALSE` —— 重试可能产生副作用(POST 写操作)
- AI 工具**应**在 `retryable: TRUE && idempotent: FALSE` 时提示"二次执行需用户确认"

#### `retry_after` 字段[v0.4 新增]

- `INTEGER` —— 建议的重试延迟毫秒数;`retryable: FALSE` 时为 `NULL`
- 与 HTTP `Retry-After` 头对齐;与 gRPC `retryInfo` 兼容

#### `trace` 字段[v0.4 新增]

调用栈;每帧一个 ARRAY,字段:
- `frame`:STRING,函数名(匿名函数为 `<anonymous>`)
- `location`:LOCATION 对象,见上

实现**必须**在错误抛出点附近构建该字段;最少 1 帧,最多由实现定义(建议 ≥ 32)。

#### `cause` 字段[v0.4 新增]

- `NULL` —— 无 cause
- DICT 或 STRING —— 由 `WRAP` 形成的错误链(§12.2 / §12.8)
- 多层 `WRAP` 嵌套为 `DICT["cause"]` 的递归结构

#### `error_schema_version` 字段[v0.3 引入,v0.4 升级]

- 字符串,SemVer 格式
- **v0.4 升为 `"1.1.0"`**(新增 `trace` / `cause` / `retry_after` / `idempotent` 字段,MINOR bump)
- v0.5 之后如增/删字段、字段类型变化,**必须** bump major 版本
- AI 工具**应先检查**此字段再解析,确保兼容性

#### `suggestion_code` 字段(沿用 v0.2)

- ARRAY,每条建议一个 DICT,字段 `kind` / `description` / `patch`(或 `ast_rewrite`)
- AI 工具**优先**用 `suggestion_code` 而非 `hint`
- `patch` 五元组格式(本规范新增,统一为 JSON 文本坐标):
  - `["replace", line_start, col_start, line_end, col_end, "new_text"]`
  - `["insert", line, col, "new_text"]`
  - `["delete", line_start, col_start, line_end, col_end]`

### 14.3 顶层输出格式(CLI)

#### 人类可读(默认)

```
error[E1003]: division by zero
 --> main.wl:42:5
  |
42 | LET(x, /(y, z));
  |          ^^^^^^^
  |
  = hint: 检查除数 z 是否可能为 0
  = fix:  在除法前增加零值守卫(可自动应用)
  = category: runtime
  = retryable: false
  = idempotent: true
  = retry_after: null
  = trace:
   --> main.wl:40:5
  = note: y 在此声明
   --> main.wl:41:5
```

#### JSON(单条,默认 AI 模式)

通过 `--format=json` 输出**单个** JSON 数组(包含该次运行的所有错误),与 v0.2 一致。

#### JSONL(流式,v0.3 引入)

通过 `--format=jsonl` 输出**JSONL** 格式——**每行一条**错误,**无外层数组**。

```jsonl
{"error_schema_version":"1.1.0","code":"E1003","severity":"error","errorCategory":"runtime","retryable":false,"idempotent":true,"retry_after":null,"message":"division by zero","location":{"file":"main.wl","line":42,"col_start":5,"line_end":42,"col_end":12},"source_line":"LET(x, /(y, z));","hint":"...","suggestion_code":[],"related":[],"trace":[],"cause":null}
{"error_schema_version":"1.1.0","code":"E0022","severity":"error","errorCategory":"name","retryable":false,"idempotent":true,"retry_after":null,"message":"function 'foo' expects 2 args, got 1","location":{...},"source_line":"foo(1);","hint":"...","suggestion_code":[],"related":[],"trace":[],"cause":null}
```

**流语义(本规范新增)**:
- 诊断一律写 **stderr**(与程序 stdout 隔离)。
- 每行 JSON 写完立即 **flush**;不缓冲。
- `--format` 只影响格式(人 / JSON / JSONL),**不**影响流选择。

**优势**:
- AI 工具**流式消费**,拿到第一条错误就开始修复,不必等编译器完成
- 不需要解析整个数组,逐行 `json.loads()` 即可
- 适合大型项目的快速迭代

### 14.7 AI 工具约定

- AI 编码工具**应总是**用 `--format=jsonl` 流式消费(优先)或 `--format=json` 批量消费。
- AI 工具**应优先执行** `suggestion_code` 字段的修复,而非仅依赖 `hint` 自然语言。
- AI 工具**应**根据 `hint` 字段生成自然语言建议,作为 `suggestion_code` 不可用时的兜底。
- AI 工具**应**把 `related` 字段内的所有位置都纳入上下文,而不是只看主错误位置。
- AI 工具**应**尊重 `severity`:`warning` 在常规模式下不应阻塞,但在 `strict` 模式下应阻塞。
- AI 工具**应**根据 `retryable` 决定是否自动重试:**仅当 `retryable: TRUE` 时**才重试,否则直接报告失败。
- AI 工具**应当**根据 `idempotent` 判断是否需要二次执行前询问用户(POST 写操作需要)。
- AI 工具**应**根据 `retry_after` 选择重试延迟,而不是固定退避。
- AI 工具**应**根据 `errorCategory` 选择修复策略(如 `io` 类先检查路径与权限,`ai` 类先检查凭据与超时)。
- AI 工具**应**先检查 `error_schema_version` 字段,确保与本规范兼容。
- AI 工具**应**在错误出现时主动消费 `trace` 字段作为调用栈上下文。

### 14.8 语法错误恢复策略(本规范修正 X-04 矛盾)

- 词法/语法错误采用**单错误终止模式**:检测到**第一个**错误后,输出错误信息并终止解析,**不**进行级联错误报告。
- 错误的 `suggestion_code` 字段可提供最多 3 个按置信度排序的修复方案。
- 运行时错误(非词法/语法)**不**受单错误终止约束。

> **修正 v0.3 §16.2 矛盾**:v0.3 写"不应同时输出多个 severity=error 级别的错误"与 §14.3/§14.9 JSON/JSONL 多错误输出矛盾。**v0.4 钉死**:§16.2 的"单错误"限制**仅适用于词法/语法阶段**(本节),JSON/JSONL 多错误输出适用于运行时与多错误收集模式。

### 14.9 JSONL 流式输出

#### 启用

```bash
wlwl check main.wl --format=jsonl
```

#### 协议

- 写 **stderr**(见 §14.3 流语义)
- 每行一条完整的 JSON 对象
- 字段顺序不限
- 末尾**不**加换行外的其他字符
- 错误对象**不**用数组包裹
- 跨错误之间的字段集**完全一致**(schema 稳定性,MINOR 版本不破坏)

#### 与 `--format=json` 的对比

| 维度 | JSON | JSONL |
|------|------|-------|
| 流式 | ❌(整体数组) | ✅(逐行) |
| 解析复杂度 | 一次性 `json.load` | 逐行 `json.loads` |
| 适合场景 | 批量分析 | 实时修复(AI) |
| 工具友好度 | 中 | 高 |

**v0.4 强烈推荐 AI 工具使用 JSONL**。

### 14.10 错误信息 schema 版本化

#### 版本号规则

- 字段:`error_schema_version`,SemVer 格式
- **v0.4 当前**:`"1.1.0"`(v0.3 `"1.0.0"` 升 MINOR)
- **MAJOR** 变化:增/删字段、字段类型变化
- **MINOR** 变化:新增可选字段
- **PATCH** 变化:错误信息文案微调

#### 兼容性策略

- AI 工具解析错误对象时,**应先检查 MAJOR 版本**,若不兼容则降级到自然语言提示
- MINOR bump 旧工具仍可工作(忽略未知字段)
- 任何破坏性变更必须 MAJOR bump,且**至少**经过 2 个 minor 版本的"过渡期"

### 15.9 `wlwl:std.test`(本规范新增,采纳 M-12)

| 暴露 | 签名 | 说明 |
|------|------|------|
| `TEST(name, body)` | `body: FUN(())` | 声明一个测试用例;`name` 为 STRING |
| `ASSERT(cond, msg?)` | | 条件假 → ERR(E0046)(本规范新增) |
| `ASSERT_EQ(a, b, msg?)` | | `a = b` 假 → ERR(E0047)(本规范新增) |
| `ASSERT_NEQ(a, b, msg?)` | | `a != b` 假 → ERR(E0048) |
| `EXPECT_ERR(expr)` | | `expr` 不为 ERR → ERR(E0049) |
| `RUN_TESTS()` | 收集所有 `TEST` 并运行 | 报告通过/失败;返回 ARRAY of DICT |

**示例**:

```wlwl
IMPORT("wlwl:std.test", ["TEST", "ASSERT", "ASSERT_EQ", "RUN_TESTS"]);

TEST("addition is commutative",
    ASSERT_EQ(+(1, 2), +(2, 1))
);

TEST("division by zero is ERR",
    EXPECT_ERR(/(1, 0))
);

LET(report, RUN_TESTS());
// report = [
//   ["name": "addition is commutative", "passed": TRUE, "duration_ms": 0.3],
//   ["name": "division by zero is ERR",  "passed": TRUE, "duration_ms": 0.1]
// ]
```

**`ASSERT` 失败语义**:
- `ASSERT(cond, msg?)`:`cond` 真则返回 `TRUE`;假则抛出 `ERR(["code": "E0046", "cond": cond, "msg": msg])`。
- `ASSERT` 抛出的 ERR **不透明传播**(§12.6),所以 `RUN_TESTS` 用 `TRY` 捕获每个 TEST。
- `RUN_TESTS` 的最终返回 ARRAY,每项是 `["name", "passed", "duration_ms", "error"?]`。

**新错误码**:
- `E0046` `test_assertion_failed` — `ASSERT` 条件假
- `E0047` `test_assertion_eq_failed` — `ASSERT_EQ` 不等
- `E0048` `test_assertion_neq_failed` — `ASSERT_NEQ` 等
- `E0049` `test_expect_err_failed` — `EXPECT_ERR` 输入非 ERR

> **决策**:`std.test` 走"测试也是数据"哲学:测试结果以 ARRAY 形式返回,**不**用 CLI 退出码表达通过/失败。这与 §14.6 退出码的"运行时错误"语义不冲突——测试是用户主动调用的函数,失败时 TEST 函数返回 ERR,程序继续运行。

#### 15.13.1 `ASK` —— 调用 LLM

**签名**:

```wlwl
FUN(ASK(model: STRING, prompt: STRING, opts: DICT = DICT()),
    // 返回 OK(STRING) 或 ERR(...)
)
```

**参数**:
- `model`:STRING,模型标识(本规范**强烈建议** `provider/model_name` 形式,如 `"openai/gpt-4"`、`"anthropic/claude-3"`;v0.4 兼容裸模型名如 `"gpt-4"`,但产生 `W0052` 警告,本规范新增)
- `prompt`:STRING,提示词
- `opts`:DICT,可选配置:
  - `timeout`:INTEGER,毫秒,默认 `30000`
  - `max_tokens`:INTEGER,默认 `4096`
  - `temperature`:FLOAT,默认 **`0.0`**(本规范改 v0.3 的 `0.7` 为 `0.0`;代码生成场景默认应确定性最大;用户可显式覆盖)
  - `system`:STRING,系统提示(可选)
  - `response_schema`:DICT(本规范新增)——结构化输出约束;若提供,实现**应当**用 JSON Schema 等机制强制 LLM 返回符合 `response_schema` 的 DICT;v0.4 此字段**可选**,实现可未实现

**返回**:
- `OK(content: STRING)` —— LLM 响应内容
- `ERR(...)` —— 见错误码

**错误码**:`E0080` 超时 / `E0081` 响应内容超长 / `E0082` 凭据缺失 / `E0083` 模型未找到

**示例**:

```wlwl
LET(r, ASK("openai/gpt-4", "解释 WLWL 的 ERR 透明传播", ["timeout": 60000]));
IF(IS_OK(r),
    (PRINT(UNWRAP(r))),
    (LET(err, ERR_PAYLOAD(r));
     IF(=(GET_PROP(err, "code"), "E0080"),
        (PRINT("LLM 超时,稍后重试")),
        (PRINT(["LLM 失败:", err]))
     )
    )
);
```

- `OK(vector: ARRAY<FLOAT>)` —— 嵌入向量

#### 15.13.4 `ASK_STREAM`(本规范新增,采纳 §15.11.4 短期决议)

**签名**:

```wlwl
FUN(ASK_STREAM(model: STRING, prompt: STRING, callback: FUNCTION(STRING, NULL), opts: DICT = DICT()),
    // 返回 OK(NULL) 或 ERR(...)
)
```

**参数**:
- `model`, `prompt`, `opts`:同 `ASK`
- `callback`:函数,接受 STRING(增量内容),返回 NULL;实现**应当**在收到每个 token / chunk 时立即同步调用

**返回**:
- `OK(NULL)` —— 流式完成
- `ERR(...)` —— 同 `ASK`

**示例**:

```wlwl
LET(parts, ARRAY());
ASK_STREAM("openai/gpt-4", "Write a poem",
    FUN((chunk), PUSH(parts, chunk))
);
LET(full, JOIN(parts, ""));
```

> **同步流**:v0.4 流式是**同步阻塞**(callback 在同一个 OS 线程上调用);异步/并发见 §17.4。

)
```

**参数**:
- `prompts`:ARRAY of [model, prompt] 形式
- `opts`:全局配置(同 `ASK`)

**返回**:
- `OK(answers: ARRAY<STRING>)` —— 顺序与 prompts 对应
- `ERR(...)` —— 任一失败

> **同步批量**:`ASK_ALL` 按顺序同步执行所有调用;并发执行见 §17.4。

## §16 工具设计原则

> **v0.4 升级点**:增 §16.3 canonical formatter 契约、§16.4 AST/Patch 协议、§16.5 一致性测试套件要求。删除 v0.3 §16.2 的"不输出多个 error"矛盾项。

### 16.1 工具的 AI 契约

任何与 WLWL 交互的工具(AI 代理、LSP 客户端、CI、IDE 插件)若要"AI 友好",**必须**:

1. **优先用 `--format=jsonl`** 流式消费错误信息
2. **总是读取 `suggestion_code` 字段**并尝试自动应用
3. **总是把 `related` 字段全部纳入上下文**
4. **总是尊重 `severity` 字段**
5. **总是根据 `retryable` 字段**决定是否重试
6. **总是根据 `idempotent` 字段**决定是否询问用户后重试
7. **总是根据 `retry_after` 字段**选择重试延迟
8. **总是根据 `errorCategory` 字段**选择修复策略
9. **总是优先使用 §14.4 错误码表**做错误分类
10. **总是先检查 `error_schema_version` 字段**
11. **总是消费 `trace` 字段**作为调用栈上下文

### 16.2 工具不应做的事

- 不应在用户未授权时自动修改源码
- 不应忽略 `code` 字段而用自然语言推断错误类型
- 不应假设错误信息是自然语言——必须按结构化字段解析
- 不应对 `retryable: FALSE` 的错误盲目重试
- 不应对 `idempotent: FALSE` 的写操作自动重试

> **删除 v0.3 §16.2 末条**"不应同时输出多个 severity=error 级别的错误"——与 §14.8 / §14.9 矛盾。v0.4 钉死"单错误终止"仅适用于词法/语法阶段。

### 16.3 canonical formatter 契约(本规范新增,采纳 A-04)

#### 必读理由

gofmt 经验证明:**单一规范排版 = AI agent 的 diff 噪音趋零**(模型不再生成格式漂移,评审只看语义)。WLWL 的统一文法使规范排版几乎可以机械推导。

#### 必须规范化的细节(本规范首次定型)

1. **缩进**:4 空格,不接受 tab。
2. **行长度**:≤ 100 字符;超过时,函数调用参数按"每个参数一行"折行,缩进 +8。
3. **分号**:必须;无空语句。
4. **逗号**:必填(无尾随逗号)。
5. **字符串**:`"` 边界;非 ASCII 字面量允许(§3.2);不允许字符串模板(§10.6 决议)。
6. **空白**:运算符两边 1 空格;`,` `;` 前无空格,后 1 空格;`(` `)` 内不强制空格(`CALL(a, b, c)` 与 `CALL( a, b, c )` 都被规范化到前一种)。
7. **块表达式**:多语句块中每条语句独立一行;末表达式**不加** `;`(见 §5.3 决策)。
8. **IMPORT / EXPORT**:每个 `IMPORT` / `EXPORT` 独立一行;**不**合并多 IMPORT。
9. **类定义**:`CLASS(name, parent, [...])` 中 members 数组按"每个成员一行"折行。
10. **空集合**:`ARRAY()` / `DICT()` 不写 `[]`(§4.5 决议)。

#### 实现要求

实现**应当**提供 `wlwl fmt` 命令,行为符合本节规则。**不**符合本节的实现产生 `W0053 格式化偏离警告`(本规范新增)。

### 16.4 AST / Patch 协议(本规范新增,基于 LSP / SARIF 工业实践)

#### 16.4.1 节点稳定 ID(本规范新增)

为支持 AI 多轮编辑,AST 节点**应当**附带:

```json
{
  "node_id": "fn:summarize/body/call:ASK",
  "parent_id": "fn:summarize/body",
  "kind": "Call",
  "span": <LOCATION>,
  "hash": "sha256:..."
}
```

- `node_id`:稳定的语义路径(模块:函数:体:节点形态索引),**不**因源码行号变化而失效。
- `hash`:节点内容 SHA-256;内容变化则 hash 变化,可用于检测并发编辑冲突。

#### 16.4.2 Patch IR(本规范新增)

`suggestion_code` 字段的 `patch` 五元组(§14.2)可表达文本级修改。**AST 级修改**通过 `ast_rewrite` 字段(已沿用 v0.3),格式:

```json
{
  "kind": "ast_rewrite",
  "target_node": "fn:summarize/body/call:ASK",
  "expected_hash": "sha256:...",
  "replacement": <AST JSON>
}
```

#### 16.4.3 机器可读格式(本规范新增)

- **AST 序列化**:JSON 格式,每节点含 `node_id` / `kind` / `span` / `hash` / 子节点。
- **Symbol table 序列化**:JSON,字段 `module` / `name` / `kind` / `type_annotation?` / `span` / `exported?`。
- **Module graph 序列化**:JSON,字段 `modules` (含 `path` / `exports` / `imports`) / `cycles` (本规范要求为空)。
- **Diagnostic 序列化**:JSON,见 §14.2。
- **Semantic diff**:JSON,字段 `before` / `after` / `changed_nodes` / `unchanged_node_ids`。

#### 16.4.4 与 LSP 对齐(本规范建议)

LSP 已成熟,§16.4.3 的字段命名**建议**对齐 LSP 3.17:
- `location` ↔ LSP `Range`
- `severity` ↔ LSP `DiagnosticSeverity`
- `code` ↔ LSP `Diagnostic.code`
- `related` ↔ LSP `Diagnostic.relatedInformation`
- `suggestion_code` ↔ LSP `CodeAction`

### 16.5 一致性测试套件(本规范新增,采纳 A-05)

#### 必读理由

TC39 test262 / Rust reference tests 的经验:**"AI 工具与第三方实现可自证兼容"** 是规范落地的最后一公里。

### 17.4 决策框架:并发模型(本规范新增,采纳 I-02)

v0.4 **不**实现 async/await;仅给决策框架。

#### 三选一

| 模型 | 关键函数 | 与 ERR 传播交互 | 与 BREAK/CONTINUE 交互 |
|------|----------|-----------------|---------------------|
| **A. 结构化并发(nursery)** | `SPAWN(f) → TASK`;`AWAIT(t) → v`;作用域保证无孤儿 | `AWAIT(t)` 时 t 内部 ERR 抛 `E0102` 顶层 | FOR/BREAK 仍在单 task 内 |
| **B. 显式事件循环 + 异步宏** | `ASYNC(f)` / `AWAIT(expr)`;`YIELD()` 显式让出 | ERR 透明传播仍生效(每 task 独立栈) | FOR/BREAK 仍在单 task 内 |
| **C. 维持纯同步 + 语言外并发** | 无;`EXEC(cmd)` 启动进程 | 进程内 ERR 不影响其他进程 | 无影响 |

#### 决策判据

- v0.4 选 **A 或 C**;**B 在 dynamic 语言上**与 ERR 透明传播**互操作性最差**(yield 时栈被切走,ERR 透明传播的"原封不动向上冒泡"难以保证)。
- **A 的优势**:`SPAWN` / `AWAIT` 完全可表达为宏函数 + 全大写,不破坏 §1.2。
- **C 的优势**:实现最简单,Web 目标由宿主承担。
- **v0.5 评审输入**:A 与 C 的具体方案、互操作测试、性能 benchmark。

#### 实施约束(无论选 A/B/C)

- `std.ai` 的 `ASK_STREAM` / `ASK_ALL` 在 v0.4 是**同步**(§15.13.4 / §15.13.5);v0.5 决定是否异步。
- `WITH(resource, body)` 宏函数(资源管理)可在并发模型定型后引入。

### 17.5 决策框架:能力系统(本规范新增)

v0.4 **不**实现完整 capability 系统;**仅在 §13.11 / §13.12 预留 `effects` 字段**。v0.5 评审:

#### 候选方案

| 方案 | 表达 | 检查时机 |
|------|------|----------|
| **A. 声明式 `EFFECTS(...)` 注解** | `FUN(read_file(path): STRING, EFFECTS(["io.read"]), ...)` | 加载期 |
| **B. capability 边界 `WITH_CAP("fs.read", body)`** | 显式开窗 | 运行时 |
| **C. 显式 capability 作为参数** | `FUN(read_file(path, cap: CAP), ...)` | 编译期(类型检查)+ 运行时(传入) |

#### 决策判据

- v0.4 选 **A**;**B** 与 §1.2 第 7 条"一语义一写法"潜在冲突(可能需 `WITH` 与 §1.6 资源管理共用);**C** 改动太大,需 `CAP` 类型,推迟到 v0.5+ 考虑。
- 与"AI 安全性"联动:LLM 生成的代码中,`EFFECTS(["network", "fs.write"])` 是 AI agent 计划工具调用的元数据;与 std.agent(§15.14)集成。
- v0.5 评审输入:A 方案的 lint 工具、conformance 测试用例。

#### v0.4 临时决策

- `wlwl.toml` 的 `strict_capabilities = true` 字段预留(未启用);
- `EXPORT` 的 `effects` 字段可填(无强制,见 §13.11)。

### 17.6 决策框架:多目标编译(本规范新增,采纳 §1.4 长期愿景)

v0.4 **不**实现任何多目标后端;仅给方向。

#### 候选路径

| 目标 | 路径 | 难度 |
|------|------|------|
| **HTML / CSS / JS** | WLWL → AST → typed IR → JS / HTML emit | 中 |
| **SQL** | WLWL → AST → SQL AST(只读子集) | 中 |
| **华为 / 思科交换机配置** | WLWL → AST → DSL emit(模板化) | 中 |
| **Nginx / Apache 配置** | WLWL → AST → conf emit(模板化) | 中 |

#### 架构原则(本规范建议)

- **WLWL 是源语言,不是万能 DSL**——不应让 `HTML(...)` / `SQL(...)` 等"特殊语法"进入核心规范(违反 §1.2 第 7 条)。
- **正确路径**:`WLWL → typed IR → target-specific backend`;target 在 `wlwl.toml` 的 `[targets]` 段声明。
- **目标间共享核心语义**;平台相关能力(网络、文件、原生)在 IR 层标注,backend 决定如何 emit。
- **v0.5+ 议程**:第一阶段仅实现 JS 后端(最小集);SQL / 交换机 / Nginx 是 v0.6+ 议程。

#### v0.4 临时决策

- `wlwl.toml` 的 `targets = ["native"]` 字段预留(本规范新增),v0.4 默认 `["native"]`。
- 未来增加目标:`targets = ["native", "js"]`;实现按 `wlwl build --target=js` 切换后端。
- **关键约束**:任何 target 不得破坏 §2 / §12 的语义;否则产生 W0054 警告(本规范新增)。

### A.3 std.ai 完整示例(本规范修正 v0.3 附录 B.2)

v0.3 附录 B.2 存在以下错误:
1. `GET_PROP(err, "code")` 在 §12.6 透明传播下不成立;
2. `OK(GET_PROP(n, "value"))` 中 `n` 是 `INT(s)` 的 INTEGER,`GET_PROP` 用在 INTEGER 上无意义;
3. `cosine_sim` 未定义未导入。

**v0.4 修正版**:

```wlwl
// file: ai_demo.wl
IMPORT("wlwl:std.io", ["PRINT"]);
IMPORT("wlwl:std.ai", ["ASK", "EMBED"]);

FUN(summarize(text),
    LET(r, ASK("openai/gpt-4", +("请用一句话总结:", text), ["max_tokens": 100]));
    IF(IS_OK(r),
        (PRINT(UNWRAP(r))),
        (LET(err, ERR_PAYLOAD(r));
         LET(code, AT(err, "code", "UNKNOWN"));
         IF(=(code, "E0080"),
            (PRINT("LLM 超时,稍后重试")),
            (PRINT(FORMAT("LLM 失败: {0}", err)))
         )
        )
    )
);

FUN(similarity(a, b),
    LET(va, EMBED(a));
    LET(vb, EMBED(b));
    IF(AND(IS_OK(va), IS_OK(vb)),
        (
            LET(v1, UNWRAP(va));
            LET(v2, UNWRAP(vb));
            COSINE_SIM(v1, v2)                  // 用户自定义函数,见下
        ),
        NULL
    )
);

// 用户自定义函数
FUN(COSINE_SIM(a, b),
    LET(dot, REDUCE(ZIP(a, b),
        FUN((acc, pair), +(acc, *(INDEX_GET(pair, 0), INDEX_GET(pair, 1)))),
        0));
    LET(na, SQRT(REDUCE(MAP(a, FUN((x), *(x, x))), +(ADD, _ADD), 0)));
    LET(nb, SQRT(REDUCE(MAP(b, FUN((x), *(x, x))), +(ADD, _ADD), 0)));
    /(dot, *(na, nb))
);

EXPORT(["summarize", "similarity", "COSINE_SIM"]);
```

## 附录 E:形式化语义(资料性)

> **本附录是 v0.4 形式化附录,small-step CEK 风格(参考 Delaët, Blazy, Merigoux, PPDP 2025)。修复 v0.3 内部缺陷。**
>
> **形式化范围限制**(沿用 v0.3):
> - ✅ 形式化:**核心子集**(LET / IF / WHILE / FOR / FUN / RETURN / BREAK / CONTINUE / 表达式 / 函数调用 / ERR 传播 / 词法作用域 / 模块解析 / MATCH / 解构绑定)
> - ❌ 不形式化:完整 OOP、继承链、std.io / fs / json / ai / web 编译目标
>
> **冲突时优先级**:自然语言为准(§0.7)。

### E.1 目标

1. 为关键语义(尤其 **ERR 透明传播**、**闭包 cell 语义**)提供无歧义参考
2. 让不同实现之间可交叉验证
3. 给未来证明(如类型安全、模块隔离)打基础

### E.2 语法(精简,核心子集)

```
e ::= n                    // 数字字面量
    | s                    // 字符串字面量
    | TRUE | FALSE | NULL  // 常量
    | x                    // 变量引用
    | FN(args, e)          // 函数字面量
    | CALL(e, e*)          // 函数调用(变长参数)
    | LET(p, e)            // 变量绑定(p 是模式,见 §7.5)
    | SET(x, e)            // 变量重赋值
    | IF(e, e, e?)         // 条件(else 可省)
    | WHILE(e, e)          // 循环
    | FOR(x, e, e)         // 遍历
    | RETURN(e?)           // 返回
    | BREAK() | CONTINUE() // 循环控制
    | BLOCK(e*)            // 块表达式
    | OK(e) | ERR(e)       // 错误值构造
    | TRY(e)               // 错误传播
    | IS_OK(e) | IS_ERR(e) // 错误判断
    | OR_DIE(e, e) | UNWRAP_OR(e, e)  // 错误兜底
    | UNWRAP(e)            // 解构成功
    | ERR_PAYLOAD(e)       // 提取 ERR 载荷
    | WRAP(e, e)           // 包装错误
    | INDEX_GET(e, e)      // 下标读取
    | INDEX_SET(e, e, e)   // 下标写入
    | MATCH(e, e, e?)      // 模式匹配
```

### E.3 状态(CEK 风格)

#### 三元组 `<e, σ, κ>`

- `e`:表达式(待求值)
- `σ`:环境(env),`Name → Cell`,其中 `Cell = (Value × Mutability)`
- `κ`:控制栈(continuation),记录**剩余**计算

#### 值(Value)

```
v ::= n | s | TRUE | FALSE | NULL
    | [v, v, ...]                  // ARRAY
    | {k: v, k: v, ...}            // DICT
    | CLOSURE(args, body, σ')      // 闭包:捕获环境
    | OK(v) | ERR(v)               // 错误值
    | CELL(v, mut)                 // 单元(§6.4 闭包语义)
```

**关键变化(v0.4 修复 v0.3)**:环境条目从 `σ(x).value` 改为 `σ(x) = CELL(v, mut)`;`SET` 修改变量等于"修改 cell 的 v,mut 决定是否可写"。

#### 控制栈元素(κ)

```
κ ::= []                          // 结束(HALT)
    | ARG(v*, e*, σ, κ)           // 累积的实参 + 待求值的实参
    | ARGS(e*, σ, κ)              // 仅待求值的实参
    | IF-THEN(e, e, σ, κ)         // 等待 cond 与 then
    | WHILE-COND(e, σ, κ)         // 等待循环条件
    | WHILE-BODY(e, σ, κ)         // 等待循环体
    | FOR-NEXT(x, iterable, e, σ, κ, idx)  // 等待 FOR 推进
    | LET-CONT(p, σ, κ)           // 等待 LET 右值
    | SET-CONT(x, σ, κ)           // 等待 SET 右值
    | TRY-CONT(σ, κ)              // 等待 TRY 内表达式
    | RETURN-CONT(σ)              // 函数返回
    | HANDLE-ERR(σ, κ)            // 等待 ERR 处理(TRY/OR_DIE/UNWRAP_OR)
    | MATCH-CLAUSES(clauses, default, σ, κ)  // 等待 MATCH 主体
```

**关键变化(v0.4 修复 v0.3)**:
- `IF-THEN` 现在三域:`(t, e, σ, κ)`(t 是 then,e 是 else),修复 v0.3 域数不一致。
- 新增 `MATCH-CLAUSES`(§7.6 模式匹配形式化)。
- 删 `BREAK-CONT` / `CONTINUE-CONT`(在 E.x 中单独定义)。

### E.4 求值关系:小步规约

`⟨e, σ, κ⟩ → ⟨e', σ', κ'⟩`:一个求值步。

#### E.4.1 基本规则

```
final(⟨v, σ, κ⟩) = true          // 值是终态,不消耗步

E-Var    ⟨x, σ, κ⟩ → ⟨CELL_VALUE(σ(x)), σ, κ⟩
                         // 取 cell 的当前值(不变更 mutability)
```

**关键变化(v0.4 修复 v0.3 §19.4 E-Lit 自循环)**:
- v0.3 `E-Lit  ⟨n, σ, κ⟩ → ⟨n, σ, κ⟩` 是无限自循环(算 bug);
- v0.4 改为 `final()` 谓词,值不消耗步;无 `E-Lit` 规则。

#### E.4.2 LET 与 cell 创建

```
E-Let    ⟨LET(p, e), σ, κ⟩ → ⟨e, σ, LET-CONT(p, σ, κ)⟩
E-LetVal ⟨v, σ, LET-CONT(p, σ', κ')⟩ → ⟨NULL, σ'[cells := σ'.cells ∪ {p ↦ CELL(v, IMMUTABLE)}], κ'⟩
```

**模式 `p`**:
- `p = x`(普通变量):创建新 cell
- `p = [a, b, ...]`(数组模式):递归解构,**失败 → E0026**(非形式化,在实现层 catch)
- `p = [a, *rest, b]`(剩余):同上
- `p = ["k": v, ...]`(字典模式):递归解构

#### E.4.3 SET(本规范新增 cell 语义)

```

E-SetVal  ⟨v, σ, SET-CONT(x, σ', κ')⟩ →
    if σ'(cells)(x).mut = MUTABLE: ⟨NULL, σ'[cells := σ'.cells[x ↦ CELL(v, MUTABLE)]], κ'⟩

### E.6 ERR 透明传播的形式化(关键,本规范重写)

#### 定义(透明传播)

> **E.定义 1(ERR 透明传播)**:函数 `f` 称为**对 ERR 透明**,若对任意 `σ, κ, v_err, e_1, ..., e_n`,当 `e_i` 求值为 `ERR(v_err)` 时,`CALL(f, e_1, ..., e_n)` 不进入 `f` 的函数体,直接规约为 `⟨ERR(v_err), σ, RETURN-CONT(σ)⟩`。

#### 定理(注册表)

> **E.定理 1(注册表覆盖)**:WLWL 标准库中,任何**不在 §12.7 注册表**的函数对 ERR 透明;注册表中的函数按 §12.7 钉死行为执行。

#### 推论(无错误吞掉)

> **E.推论 1**:若程序执行到顶层仍未被 §12.7 注册表函数显式消费,`ERR` 逃逸到顶层 → `E0102`(未处理的 ERR 逃逸到顶层)。

#### 形式化收益

- **可证明**:ERR 不会在传播过程中被意外吞掉(除非显式调用 §12.7 注册表函数)
- **可验证**:两个不同实现可在同一测试套件下验证 ERR 传播行为(§16.5)
- **可扩展**:新增函数时,只需在 §12.7 注册表显式登记"消费 ERR",其余默认透明

### E.7 范围与限制(诚实声明)

- 本附录是**非形式化证明**(no mechanized proof)。规则用 CEK 风格书写,**未**在 Coq / Rocq / Agda 中机械化。
- E.x 仅覆盖核心子集;OOP、std.io / fs / json / ai / web 等**未**形式化,**仍是**自然语言规范。
- 形式化与自然语言规范**冲突时**,以**自然语言为准**——本附录是参考,不是 source of truth(§0.7)。
- **未来工作**:v0.5 考虑将本附录机械化(用 Coq / Lean / Rocq);OOP / 模块 / std.ai 形式化是 v0.5+ 议程(附录 D 第 6 项)。

## 附录 F:文法(核心子集 EBNF,规范性)

> 本规范首次给出核心子集的 EBNF。完整 EBNF(覆盖 OOP、模块、模式匹配)留待 v0.5。

```
(* ===== 词法 ===== *)
program         = { top_level_form } ;
top_level_form  = import_decl
                | export_decl
                | let_stmt
                | fun_def
                | class_def
                | expression ;

(* ===== 字面量 ===== *)
literal         = INTEGER | FLOAT | STRING | "TRUE" | "FALSE" | "NULL"
                | array_literal | dict_literal ;

array_literal   = "ARRAY" , "(" , [ expression , { "," , expression } ] , ")"
                | "[" , [ expression , { "," , expression } ] , "]" ;
dict_literal    = "DICT" , "(" , [ dict_pair , { "," , dict_pair } ] , ")"
                | "[" , [ dict_pair , { "," , dict_pair } ] , "]" ;
dict_pair       = expression , ":" , expression ;

empty_array     = "ARRAY" , "(" , ")" | "[" , "]" ;
empty_dict      = "DICT" , "(" , ")" ;

(* ===== 表达式 ===== *)
expression      = literal
                | identifier
                | call
                | block_expr
                | if_expr
                | while_expr
                | for_expr
                | match_expr
                | return_expr
                | break_expr | continue_expr
                | try_expr
                | match_expr
                | destructure_let
                | index_get | index_set
                | "." , identifier , { "." , identifier } , [ "(" , [ args ] , ")" ] ;

call            = expression , "(" , [ args ] , ")" ;
args            = expression , { "," , expression } ;

block_expr      = "(" , { statement } , expression , ")" ;

if_expr         = "IF" , "(" , expression , "," , expression , [ "," , expression ] , ")" ;
while_expr      = "WHILE" , "(" , expression , "," , expression , ")" ;
for_expr        = "FOR" , "(" , identifier_or_pattern , "," , expression , "," , expression , ")" ;
return_expr     = "RETURN" , "(" , [ expression ] , ")" ;
break_expr      = "BREAK" , "(" , ")" ;
continue_expr   = "CONTINUE" , "(" , ")" ;
try_expr        = "TRY" , "(" , expression , ")" ;
match_expr      = "MATCH" , "(" , expression , "," , expression , [ "," , expression ] , ")" ;
                (* 第二个 expression 是 clauses 数组 *)

index_get       = expression , "[" , expression , "]" ;
index_set       = expression , "[" , expression , "]" , "=" , expression ;

(* ===== 语句 ===== *)
statement       = let_stmt
                | set_stmt
                | expression_stmt ;

let_stmt        = "LET" , "(" , pattern , "," , expression , ")" , ";" ;
set_stmt        = "SET" , "(" , identifier , "," , expression , ")" , ";" ;
expression_stmt = expression , ";" ;

(* ===== 模式(解构) ===== *)
pattern         = identifier [ ":" , type_annotation ]
                | array_pattern
                | dict_pattern
                | "_" ;

array_pattern   = "[" , [ pattern , { "," , pattern } [ "," , "*" , identifier ] ] , "]" ;
dict_pattern    = "[" , [ STRING , ":" , pattern , { "," , STRING , ":" , pattern } ] , "]" ;

(* ===== 函数 / 类 ===== *)
fun_def         = "FUN" , "(" , [ identifier ] , "(" , [ params ] , ")" , "," , expression , ")" ;
params          = param , { "," , param } ;
param           = identifier [ ":" , type_annotation ] [ "=" , expression ]
                | "*" , identifier ;

class_def       = "CLASS" , "(" , [ STRING ] , "," , expression , "," , dict_literal , ")" ;

(* ===== 模块 ===== *)
import_decl     = "IMPORT" , "(" , STRING , "," , expression , [ "," , expression ] , ")" , ";" ;
export_decl     = "EXPORT" , "(" , expression , ")" , ";" ;

(* ===== 标识符 ===== *)
identifier      = letter , { letter | digit | "_" } ;
letter          = "A" | ... | "Z" | "a" | ... | "z" | <Unicode letter> ;
digit           = "0" | ... | "9" ;
```

### F.1 与附录 E 的关系

- 附录 F 是**表面文法**(syntax);附录 E 是**操作语义**(semantics)。
- 附录 F 的产生式应与附录 E 的 `e ::= ...` 一一对应(若发现不对应,实现以附录 F 为准,附录 E 是形式化参考)。

### J.1 错误处理

```wlwl
// 模式 1:TRY + 函数体内
FUN(safe_compute(x),
    LET(v, TRY(risky_op(x)));
    /(v, 2)
);

// 模式 2:UNWRAP_OR 链
LET(value, UNWRAP_OR(TRY(read_config()), DEFAULT_CONFIG));

// 模式 3:错误链(WRAP)
FUN(load_layer(path),
    LET(content, READ_FILE(path));
    IF(IS_ERR(content), RETURN(WRAP(content, FORMAT("loading {0}", path))));
    PARSE(UNWRAP(content))
);

// 模式 4:模式匹配
LET(msg, MATCH(result,
    [
        [OK("ok"),         FUN((_), "success")],
        [OK(data),         FUN((d), FORMAT("got {0}", d))],
        [ERR(e),           FUN((_), "failed")],
        [_,                FUN((_), "unknown")]
    ]
));
```

### J.2 集合操作

```wlwl
// 模式 1:链式
LET(squared_evens, MAP(FILTER(nums, FUN((n), =(MOD(n, 2), 0))), FUN((n), *(n, n))));

LET(max, REDUCE(nums, FUN((acc, n), IF(>(n, acc), n, acc)), 0));

```
