## Context

`std.collection` 的建数组类成员在 1000+ 元素上仍是**平方级**,根因是语言层
无法线性地逐次追加到数组。L0-A-1 已把现状测完(bench profile / criterion /
10 样本,1k–8k 四档,每元素成本 = 时间均值 ÷ 元素数):

| 组 | 1 000 | 2 000 | 4 000 | 8 000 | 每翻一档(总时间) |
|---|---:|---:|---:|---:|---|
| `collection_map` | 45.36 µs | 73.96 µs | 134.52 µs | 254.16 µs | 3.26 / 3.64 / **3.78** |
| `collection_filter` | 37.47 µs | 49.64 µs | 92.22 µs | 179.45 µs | 2.65 / 3.71 / **3.89** |
| `collection_chunk` | 8.52 µs | 10.66 µs | 19.11 µs | 46.23 µs | 2.50 / 3.59 / **4.84** |
| `collection_window` | 180.16 µs | 454.13 µs | 1 349.90 µs | 3 059.00 µs | **5.04 / 5.95 / 4.53** |
| `r1_build`(R1 建数组链) | 24.55 µs | 35.88 µs | 63.68 µs | 141.45 µs | 2.92 / 3.55 / **4.44** |

每元素成本全部随尺寸上涨 ⇒ 平方级坐实,无一例外。**这不是「某个成员写得不好」,
是两个内建函数的结构性代价。**

## 两个平方级来源(本 ADR 的核心事实)

### 来源一:`PUSH` 全量克隆 —— `wlwl-eval/src/lib.rs:1025-1043`

```
fn builtin_push(_ev, args) {
    Value::Array(a) => {
        let mut a = a.clone();   // ← 深拷贝整个数组
        a.push(item.clone());
```

8 k 的 `MAP` = 2033.3 ms,期间元素克隆总次数 = 8000 次 push × 平均长度 4000
= **32 M 次** ⇒ **~63 ns/元素**。一次闭包调用远不到这个量级,故 `PUSH` 占
`MAP` 成本的 **>99%**。

### 来源二:`DICT` 全量克隆 + 线性查找 —— `lib.rs:1501-1540` + `lib.rs:1426-1428`

```
fn dict_lookup(entries: &[(Value, Value)], key: &Value) -> Option<usize> {
    entries.iter().position(|(k, _)| values_equal(k, key))   // ← 线性扫描 + 深比较
}

fn builtin_index_set(...)  (Value::Dict(entries), key) => {
    let mut out = entries.clone();                            // ← 克隆整个 dict
    match dict_lookup(&out, key) { ... }
```

`Value::Dict` 的表示是 `Vec<(Value, Value)>`(`wlwl-value/src/lib.rs:48`),
**不是哈希表**。⇒ 每次 `INDEX_SET` / `HAS` / `AT_K` 对 DICT 都是 O(n) 克隆 +
O(n) 扫描。n 次插入 ⇒ **O(n²)**,与 `PUSH` 无关。

> ⚠️ **顺带纠正规范 §5.1 的一处断言**:该节写 `DEDUP_BY`「之所以在四位上都平,
> 是它用 `DICT` 记已见键(而非照抄 `UNIQ` 的线性扫),每步 O(1) ⇒ **真正线性**」。
> 在 R1 实现下**这个 O(1) 不成立**(`DICT` 是线性扫描 Vec + 每次写全量克隆)。
> 那张表看起来「平」是因为 n 只取到 100…800(仅 8×),且每元素的 `STR(k)` +
> 闭包开销在那个区间盖过了 n² 项。**这是把「小规模下测不出」误读成「线性」的
> 典型**,与 D11-024 / D11-025 同族。⇒ 该断言须在 M5 收口时改写。

## 由此得到的结论

1. **两条路线不是「殊途同归」,覆盖面不同。** 对 A 类,归层与可变缓冲的收益
   **等价**(都把「O(n) 次长度-n 的拷贝」变成「O(n) 次长度-1 的拷贝」;按 L0 段
   实测,8 k 的 `MAP` 每元素 254 µs → 约 0.1 µs,量级 ~2500×)。但在 B / D 类上
   **只有归层能修**。
2. **⇒ L0-A(归层)是达成「`std.collection` 规模可用性回到线性」的必要路线**,
   不是可选项。**L0-B 无法替代它。**
3. **L0-B 的独立价值在别处**:它覆盖的是 **A 类形态的用户代码**(本仓自己的
   `r1_build` 基准就是 —— 8 k = 1 131.6 ms),这是 L0-A 够不着的。所以两者
   **分工不同而非重复**:L0-A 管标准库成员(含 D 类),L0-B 管用户代码累加器。
4. **L0-B 现措辞有个窟窿**:addendum-00 §2.2 的 β1 写「循环内**只 `PUSH(a, …)`**
   的模式」。但另一条同样主流的写法是 `SET(arr, +(arr, [v]))` —— `CONCAT`,不是
   `PUSH`,β1 按现措辞修不了。⇒ β1 若要覆盖用户代码,范围必须含 B 类。
5. **β3 的否决理由已部分过期**:addendum-00 §2.2 否掉 β3(写时复制)的理由是
   「引用计数 ⇒ 与语言『无 GC / 无 RC』的立场冲突」。但 v0.6 §3.1 / §6.4 已经
   给语言引入了**按引用共享的可变 cell**(`LET MUT` 建可变 cell,`SET` 写 cell,
   闭包按引用共享 —— `lib.rs:8448` E-CloCap 把捕获的 cell 升级为 MUT)。
   ⇒ 这条反对理由被语言自己的历史部分回答,β3 值得在 L0-B 的 ADR 里重提。
6. **「让克隆更便宜」是错的杠杆。** ~63 ns/元素对 `#[derive(Clone)]` 的递归
   enum 克隆(`Value` 含 `String(String)` / `Array(Vec<Value>)` /
   `Dict(Vec<(Value,Value)>)`)是正常的 —— 它是逐元素 match + 递归,不是 memcpy。
   而把 `String` 换成 `Rc<str>` 之类的常因子优化:① 治不了渐进复杂度;
   ② **在 L0 段的基准里根本不生效**(元素是 `Value::Integer`,路径上没有
   `String`)。资源不应投在这里。

## 待裁决的四问

| # | 问题 | 为什么它决定后续 |
|---|---|---|
| **Q1** | `DICT` 要不要从 `Vec<(Value,Value)>` 换成真哈希表? | 这是**来源二**,L0-A 必须靠它(否则 D 类三个成员归层后仍走线性查找)。而它影响面**远大于**「给成员换层」:`Value::Dict` 是语言核心表示,`==`、`STR` 渲染、格式化器、契约表、附录 A 全要一起对齐。**这是整个 M5 里最大的一块,计划此前完全没有把它列成工作项。** |
| **Q2** | L0-B(可变累加器)是否立项?范围含不含 B 类(`CONCAT` / `+`)? | 决定「用户代码的累加器」有没有出路。若立项,须先出独立 ADR —— 它是**语义面**的决定(逃逸分析 + 冻结时机),按 addendum-00 §2.2 的原话「混在补标准库批里做,审不出来」。 |
| **Q3** | 若做 L0-B,漏识别时能否**可观测**? | addendum-00 §2.2 自陈风险「模式识别漏了就退化成原样(**静默的性能回退,不是错误**)。把静默回退变成可测的(计数 / 断言 / 基准守卫),是 L0-B 能否被接受的前提。 |
| **Q4** | `SORT` 归层后,选择排序的「稳定性 + 每轮一次 SLICE+PUSH」这条已写进规范的权衡(`collection.wll:142-148`)还成立吗? | R2 版会用 `Vec::sort_by`(稳定)。规范 §5 的 `SORT_UNSTABLE` 已否决(§14.1),所以 R2 必须是稳定排序 —— 但**归层时的注释与理由需要重写**,否则会留下「R1 选择排序是为了省拷贝」这种对 R2 已失效的解释。 |

## 明确不在本 ADR 范围内

- 不选路线(那是 Q1–Q4 的产物,是业主裁决)。
- 不定 DICT 的具体表示(哈希表?有序?`Rc` 共享?—— 属 Q1 的后续 ADR)。
- 不动 `PUSH` / `+` / `INDEX_SET` 的签名与诊断。
- 不承诺与浏览器 / 其他语言逐位一致;性能承诺沿 §17.7 口径。
