## Context

`std.collection` 的建数组类成员在 1000+ 元素上仍是**平方级**,根因是语言层
无法线性地逐次追加到数组。L0-A-1 已把现状测完(bench profile / criterion /
10 样本,1k–8k 四档,每元素成本 = 时间均值 ÷ 元素数):

| 组 | 1 000 | 2 000 | 4 000 | 8 000 | 每翻一档(总时间) |
|---|---:|---:|---:|---:|---|
| `collection_map` | 45.36 µs | 73.96 µs | 134.52 µs | 254.16 µs | 3.26 / 3.64 / **3.78** |
| `collection_filter` | 37.47 µs | 49.64 µs | 92.22 µs | 179.45 µs | 2.65 / 3.71 / **3.89** |
| `collection_chunk` | 8.52 µs | 10.66 µs | 19.11 µs | 46.23 µs | 2.50 / 3.59 / **4.84** |
| `collection_window` | 180.16 µs | 454.13 µs | 1 349.90 µs | 3 059.00 µs | **5.04 / 5.95 / 4.53** |
| `r1_build`(R1 建数组链) | 24.55 µs | 35.88 µs | 63.68 µs | 141.45 µs | 2.92 / 3.55 / **4.44** |

每元素成本全部随尺寸上涨 ⇒ 平方级坐实,无一例外。**这不是「某个成员写得不好」,
是两个内建函数的结构性代价。**

## 两个平方级来源(本 ADR 的核心事实)

### 来源一:`PUSH` 全量克隆 —— `wlwl-eval/src/lib.rs:1025-1043`

```
fn builtin_push(_ev, args) {
    Value::Array(a) => {
        let mut a = a.clone();   // ← 深拷贝整个数组
        a.push(item.clone());
```

8 k 的 `MAP` = 2033.3 ms,期间元素克隆总次数 = 8000 次 push × 平均长度 4000
= **32 M 次** ⇒ **~63 ns/元素**。一次闭包调用远不到这个量级,故 `PUSH` 占
`MAP` 成本的 **>99%**。

### 来源二:`DICT` 全量克隆 + 线性查找 —— `lib.rs:1501-1540` + `lib.rs:1426-1428`

```
fn dict_lookup(entries: &[(Value, Value)], key: &Value) -> Option<usize> {
    entries.iter().position(|(k, _)| values_equal(k, key))   // ← 线性扫描 + 深比较
}

fn builtin_index_set(...)  (Value::Dict(entries), key) => {
    let mut out = entries.clone();                            // ← 克隆整个 dict
    match dict_lookup(&out, key) { ... }
```

`Value::Dict` 的表示是 `Vec<(Value, Value)>`(`wlwl-value/src/lib.rs:48`),
**不是哈希表**。⇒ 每次 `INDEX_SET` / `HAS` / `AT_K` 对 DICT 都是 O(n) 克隆 +
O(n) 扫描。n 次插入 ⇒ **O(n²)**,与 `PUSH` 无关。

> ⚠️ **顺带纠正规范 §5.1 的一处断言**:该节写 `DEDUP_BY`「之所以在四位上都平,
> 是它用 `DICT` 记已见键(而非照抄 `UNIQ` 的线性扫),每步 O(1) ⇒ **真正线性**」。
> 在 R1 实现下**这个 O(1) 不成立**(`DICT` 是线性扫描 Vec + 每次写全量克隆)。
> 那张表看起来「平」是因为 n 只取到 100…800(仅 8×),且每元素的 `STR(k)` +
> 闭包开销在那个区间盖过了 n² 项。**这是把「小规模下测不出」误读成「线性」的
> 典型**,与 D11-024 / D11-025 同族。⇒ 该断言须在 M5 收口时改写。

## 由此得到的结论

1. **两条路线不是「殊途同归」,覆盖面不同。** 对 A 类,归层与可变缓冲的收益
   **等价**(都把「O(n) 次长度-n 的拷贝」变成「O(n) 次长度-1 的拷贝」;按 L0 段
   实测,8 k 的 `MAP` 每元素 254 µs → 约 0.1 µs,量级 ~2500×)。但在 B / D 类上
   **只有归层能修**。
2. **⇒ L0-A(归层)是达成「`std.collection` 规模可用性回到线性」的必要路线**,
   不是可选项。**L0-B 无法替代它。**
3. **L0-B 的独立价值在别处**:它覆盖的是 **A 类形态的用户代码**(本仓自己的
   `r1_build` 基准就是 —— 8 k = 1 131.6 ms),这是 L0-A 够不着的。所以两者
   **分工不同而非重复**:L0-A 管标准库成员(含 D 类),L0-B 管用户代码累加器。
4. **L0-B 现措辞有个窟窿**:addendum-00 §2.2 的 β1 写「循环内**只 `PUSH(a, …)`**
   的模式」。但另一条同样主流的写法是 `SET(arr, +(arr, [v]))` —— `CONCAT`,不是
   `PUSH`,β1 按现措辞修不了。⇒ β1 若要覆盖用户代码,范围必须含 B 类。
5. **β3 的否决理由已部分过期**:addendum-00 §2.2 否掉 β3(写时复制)的理由是
   「引用计数 ⇒ 与语言『无 GC / 无 RC』的立场冲突」。但 v0.6 §3.1 / §6.4 已经
   给语言引入了**按引用共享的可变 cell**(`LET MUT` 建可变 cell,`SET` 写 cell,
   闭包按引用共享 —— `lib.rs:8448` E-CloCap 把捕获的 cell 升级为 MUT)。
   ⇒ 这条反对理由被语言自己的历史部分回答,β3 值得在 L0-B 的 ADR 里重提。
6. **「让克隆更便宜」是错的杠杆。** ~63 ns/元素对 `#[derive(Clone)]` 的递归
   enum 克隆(`Value` 含 `String(String)` / `Array(Vec<Value>)` /
   `Dict(Vec<(Value,Value)>)`)是正常的 —— 它是逐元素 match + 递归,不是 memcpy。
   而把 `String` 换成 `Rc<str>` 之类的常因子优化:① 治不了渐进复杂度;
   ② **在 L0 段的基准里根本不生效**(元素是 `Value::Integer`,路径上没有
   `String`)。资源不应投在这里。

## 裁决(2026-10-05,业主 Li)

### Q1 · `DICT` 怎么办 → **不改 `Value::Dict`;R2 侧用内部哈希索引 + 末次物化**

**决策**:`Value::Dict(Vec<(Value, Value)>)` 的表示**本批不动**。R2 的
`KEY_BY` / `GROUP_BY` / `DEDUP_BY` 内部改用 `HashMap<String, usize>`
作查找索引 + 一个 `Vec` 维持**插入序**,**在返回前一次性物化**成
`Value::Dict`。键本就是 `STR(k)` 渲染出的字符串(规范 §5),所以索引键用
`String` 即可,**不必给 `Value` 实现 `Hash`**。

**理由**:

1. **换哈希表会破坏可观察的键序。** `DICT` 现在是 `Vec`,**插入序就是可观察序**
   —— JSON 输出、错误载荷(`ERR(["kind": …, "op": …, "reason": …])`)、任务结果
   、契约表里冻结的 `display()` 全都依赖它。换成 `HashMap` 会让这些全部乱序,
   **那是 breaking**,代价远超收益。
2. **它也不必换。** R2 成员是 Rust,内部结构自由 —— 本仓已有先例:
   `HTML_SANITIZE` 内部用 `Vec<Node>` + `u32` 句柄的索引池,只在边界物化。
   ⇒ 在**成员内部**用哈希、在**边界**还原成 `Value::Dict`,即可同时拿到 O(n)
   与逐字节相同的输出。
3. **零新依赖**:`HashMap` 是 std。落点与 §2 的 β2「引入新的运行期表示」不同 ——
   β2 动的是 `Value` 本身,本决策不动。

**明确不做**:改 `Value::Dict` 的表示;给 `Value` 实现 `Hash` / `Eq`。
**这两件影响面远大于「给成员换层」**(`==`、`STR` 渲染、格式化器、契约表、
附录 A 全要一起对齐),若日后要做,另立 ADR。

**已知遗留**:用户代码里 `INDEX_SET` 逐次写 DICT 仍是 O(n²)(那是 §2 来源二
本身,不是成员问题)。按 D12-004 / D12-009 同款口径记为**已知限制**,不阻塞 M5。

### Q2 · L0-B 是否立项 → **立项,但独立于 M5;范围必须含 `CONCAT` / `+` 族**

**决策**:L0-B(可变累加器)**立项,排在 M5 之后,独立批次 + 独立 ADR**。识别判据
**必须同时覆盖** `PUSH(a, x)` 与 `+(a, [x])` 两种追加形态。

**理由**:

1. **不是重复劳动。** M5(L0-A)做完之后,唯一剩下的缺口是**用户代码的累加器** ——
   L0 段实测 `r1_build` 8 k = **1 131.6 ms**,这是 L0-A 结构上够不着的面。
   而且它正是语言规范 §6.6「100 万次简单循环 < 30 s」符合性负载所依赖的形态。
2. **但不该混进 M5。** β1–β3 都是**语义面**决定(逃逸分析 + 冻结时机),
   按 §14.1 的体例(「两条都不是不重要而是没想清楚」→ 先出 ADR)应独立立项;
   且 M5 的目标不依赖它,顺序上可后置。
3. **范围必须含 `+` / `CONCAT`。** 原措辞「循环内**只 `PUSH(a, …)`**」漏掉了
   本仓自己的主流写法 —— `array_higher_order` / `r1_collection_map` /
   `r1_build` 用的全是 `SET(arr, +(arr, [v]))`。只认 `PUSH` 等于修不了用户代码
   最常见的累加器,L0-B 的一半价值就没了。
4. **β3 重提。** 其原否决理由(「引用计数 ⇒ 与语言无 GC / 无 RC 的立场冲突」)已被
   v0.6 §3.1 / §6.4 的按引用共享可变 cell 部分回答(见上文对 §2.2 的更正),
   L0-B 的 ADR 须把 β3 一并重评。

### Q3 · 回退可观测性 → **可观测,三件套;明确不走警告通道**

**决策**:L0-B 必须把「模式识别漏了」从静默回退变成**可测事实**,三件套:

1. **计数器**:eval 侧对「识别成功」与「识别失败」各留一个计数,供测试读取。
2. **基准守卫**:把 L0 段的四档基准扩到**用户代码形态**(`r1_build` 已是第一组),
   L0-B 落地后断言其每元素成本**持平** ⇒ 回退即 CI 变红。
3. **契约测试**:至少钉住「识别失败时输出仍逐字节正确」——
   **性能可以退化,语义不许退化**,这条比性能本身更要紧。

**明确不做**:运行时警告。本仓挂账 **D11-022** 已证 `StdCtx::warnings` 无人排空、
`W0052` 永不浮现 —— **走警告通道等于静默丢弃**。可观测性只能来自
**基准 + 测试 + 计数器**。

### Q4 · `SORT` 归层后的注释与算法 → **重写;R2 用 `Vec::sort_by`(稳定)**

**决策**:R2 `SORT` 用 `Vec::sort_by`(稳定归并 / Timsort),**不得用
`sort_unstable_by`**;`collection.wll:142-148` 那段注释重写。

**理由**:

1. 该注释的理由是「选择排序每轮只有一次 SLICE + 一次 PUSH,总拷贝量 O(n) 而不是
   O(n²)」—— 这是**为不可变数组省拷贝**而写的选择,**在 R2 的 `Vec` 上不再成立**。
   留在 R2 代码里会变成一条错误的解释(与 v0.11.3 计划 §8「两处计划文本与现实不符,
   按现实执行并在此登记」同款要求:不许照抄失效理由)。
2. 比较次数上 `sort_by` 是 O(n log n),比 R1 选择排序的 O(n²) **少一个量级** ——
   归层不只是省拷贝,连比较也降阶。
3. **必须稳定**:§14.1 已否决 `SORT_UNSTABLE` / 选择类原语,而规范承诺 `SORT` 的
   稳定性语义(D11-006 的 D-6)。故只能 `sort_by`,不能 `sort_unstable_by`。
   这条要写进注释,否则日后有人「顺手优化」就会破规范。

### 由此确定的工作项边界(供 L0-A-2 照此执行)

- **L0-A-2(归层第一批)成员 = `MAP` `FILTER` `CHUNK` `WINDOW`** ——
  L0-A-1 实测的每元素成本最高的四个(8 k 档 254.16 / 179.45 / 46.23 /
  3 059.00 µs),且恰好覆盖三种不同形态:逐元素闭包 / 条件追加 / 每轮 `SLICE`。
- **L0-A-3(归层第二批)** = 其余 A 类 + B 类 + D 类;D 类三个
  (`KEY_BY` `GROUP_BY` `DEDUP_BY`) 按 Q1 用「内部哈希 + 末次物化」实现。
- **`SORT` 归到 L0-A-3**,按 Q4 用 `sort_by` 并重写注释。
- **C 类 12 个成员(已线性)不进任何一批** —— 不做无收益的层变更。

## 明确不在本 ADR 范围内

- **不定 `Value::Dict` 的表示**(哈希表?有序?`Rc` 共享?)—— Q1 已裁决「本批不动」,
  若日后要动,另立 ADR。
- 不定 L0-B 的具体实现(逃逸分析怎么写、冻结点选在哪)—— 属 L0-B 自己的 ADR。
- 不动 `PUSH` / `+` / `INDEX_SET` 的签名与诊断。
- 不承诺与浏览器 / 其他语言逐位一致;性能承诺沿 §17.7 口径。
