## Context

规范仓一致性册 §5.4 登记的 **X-04**:语言核心册 §18.3.1 承诺「字典键查找 O(1) 期望」,
而参考实现是线性扫描。§18.6 的偏差登记写明收敛路线是「内部哈希索引 + 插入序物化」,
并加了一句「该表示变更**本批未做**,须另立决策」⇒ 本 ADR 就是那份决策。

这一条是 **v1.0 发布的硬前置**,不是可选优化:

- 总纲 §0.9 的 **D-02**(复杂度上界升为规范性条款)状态仍是「未实现」⇒ 一致性册 §3.5
  发布前置条件的第 1 条(实现状态列无「未实现」/「部分」)过不去;
- 一致性册 §6.2 的 **V-01**(「§18 承诺的每个复杂度上界在参考实现上成立」)把字典那条
  包在里面 ⇒ **X-04 不收敛,V-01 就不可能通过** ⇒ 第 2 条(第 6 章的验证要求已满足)
  同样过不去。

⇒ 收口的关键路径是这一条,不是 V 清单本身。

## 1 实测:四条上界的现状(结构性事实,不需要估算)

| # | 事实 | 出处 |
|---|---|---|
| 1 | 字典载荷是 `Value::Dict(Vec<(Value, Value)>)` —— 线性键值序列 | `wlwl-value/src/lib.rs:129` |
| 2 | 键查找是**线性扫描 + 逐项深比较**:`entries.iter().position(\|(k, _)\| values_equal(k, key))` ⇒ n 键字典的一次查找最多做 n 次深比较 ⇒ **O(n) 最坏** | `wlwl-eval/src/lib.rs:1722`(`dict_lookup`) |
| 3 | 键写入是**克隆整个容器再改**:`builtin_index_set` 的注释逐字写着「In-place semantics are emulated by cloning the container, mutating the clone, and returning the clone」⇒ 每次写都是 **O(n) 拷贝** | `wlwl-eval/src/lib.rs:1852`(`builtin_index_set`) |
| 4 | 键域**封闭**:§2.1 规定键**必须**是 `STRING` / `INTEGER` / `INSTANCE`,`INSTANCE` 按**对象身份**判定(§2.4),其它类型 → `E0031`,`NaN` → `E0031` | 语言核心册 §2.1;`wlwl-eval/src/lib.rs:1726` |
| 5 | 影响面:`Value::Dict(` 在 **175 处 / 26 个文件**(`wlwl-eval/src/lib.rs` 72 处、`wlwl-std/*` 约 90 处、`wlwl-value` 7 处) | 2026-10-22 全 `impl/crates` 统计 |

事实 2 与 3 是**结构性的**,不是估算:查找的比较次数与字典长度成正比、写的拷贝量与
字典长度成正比,两者都与数据分布无关 ⇒ §18.3 的四条字典上界(`d[k]` / `HAS` /
`INDEX_SET` 键已存在 / `INDEX_SET` 新键)**全部不达标**。

⚠ §18.6 的纪律要求「现状」一列有**实测依据**(工作负载计数或基准存档)⇒ 实施阶段的
**S5 计数守卫**必须把上面这两条从「结构事实」升级成「可复现的计数读数」。

## 2 推导:四条上界不可能同时无条件成立

这一节是本 ADR 的核心 —— 它决定了「实现侧怎么改」与「规范侧要不要改口径」两个问题的
分界。

**前提**(规范侧的既有条款,一条都不能动):

- §19.1 值**不可变**,生存期由**绑定**决定;
- §2.1 键域封闭(事实 4);
- §2.5 / §18.3.1 **键序是插入序**,且**可观察**(渲染、JSON、错误载荷都依赖它);
- §18.3.1 明写「O(1) 期望的键查找与插入序**不冲突**:实现**可以**在内部维护一张哈希
  索引指向位置,对外仍按插入序呈现」⇒ 哈希索引是**规范指定的实现方向**,不是实现自选。

**推导**:

1. 写路径:值语义 + 不可变 ⇒ 一次写**必须产出新值** ⇒ n 键字典的一次写至少要搬 n 个
   键值对 ⇒ **Ω(n)**。⇒ 「`INDEX_SET` O(1) 期望」只在**唯一拥有**(旧字典没有别的持有者)
   时才可能 —— 而函数式写法 `LET(d2, INDEX_SET(d, k, v))` 里 `d` 仍被绑定持有 ⇒ **不唯一**
   ⇒ **必拷贝**。
2. 读路径:要 O(1) 期望 ⇒ 要哈希索引 ⇒ 索引要么随字典一起拷贝(写 O(n)),要么**惰性重建**
   (首次查找到的那次 O(n))。
3. 两条合起来 ⇒ **「写 O(1) 期望」与「读 O(1) 期望」不可能同时无条件成立**:想让写便宜就得
   共享索引(读侧要么拷贝要么重建),想让读便宜就得让写拷贝。

⇒ **必有一条只能在摊还 / 期望口径下成立**。这不是实现偷懒,是**值语义 + 不可变 + 插入序
可观察**三条规范条款的联合推论。

⇒ ⇒ **因此规范侧必须有一处「口径写准」**(§18.2 的原则「规范性上界是『必须满足』」讲的是
**强度**,不禁止把「满足」的判据写成可测的;§18.5 要求判定用**确定性工作量计数**)。
⚠ **这不是**把「必须」降成「应当」—— 强度一字不动,变的是「摊还」这个词的适用范围
从隐含变成成文。

## 3 候选形状

| | 形状 | 用户可见面 | 达成的上界 | 代价 |
|---|---|---|---|---|
| **γ1** | **改载荷**:`Value::Dict(Rc<DictInner>)`,`DictInner = { entries: Vec<(Value, Value)>, index: HashMap<DictKey, usize> }`;写路径走 **copy-on-write**(唯一拥有 ⇒ 原地改;被别名 ⇒ 克隆) | 无(可观察面逐条对齐) | 读 O(1) 期望 ✅;写 O(1) 期望(唯一拥有时)✅ / 别名时 O(n) | **175 处 `Value::Dict(` 要机械替换**(一次性、脚本可做)⇒ diff 大,但**只有一种字典表示**,没有「两种表示要长期同步」的负担 |
| **γ2** | **新增变体**:`Value::DictIndexed(Rc<DictInner>)`,普通 `Dict(Vec<..>)` 保留 ⇒ 只在热路径产出新变体 | 无 | 同 γ1 | diff 小,但**两种表示**并存 ⇒ 所有**读**路径都要能处理新变体 ⇒ 要访问器层;`ADR-0032` 的教训正是「可观察面不许分叉」,两种表示的风险同源 |
| **γ3** | **持久化结构**:HAMT + 插入序链(结构共享)⇒ 写不拷贝 | 无 | 读 O(log₃₂ n) 期望;写 O(log₃₂ n) 摊还 ⇒ 实际规模下近似 O(1),**严格意义上不是 O(1)** | 手写 HAMT(键域虽封闭但要有 `DictKey` 的 Hash/Eq 一致性);且「近似 O(1)」对**规范性**上界是**打折** ⇒ 需要业主明确接受 |

⇒ γ3 的「打折」是它的硬伤:§18.3 的上界是**规范性**的,拿「实际规模下近似」去兑
规范性条款,是**弱化** ⇒ **不采纳**。

## Decision

> **Proposed**,待业主裁决:

- **D1 · 走 γ1(改载荷 + copy-on-write + 哈希索引)。** 理由三条:
  1. §18.3.1 已经把实现方向写死成「内部哈希索引 + 插入序物化」⇒ γ1 是**规范指定的
     形状**,γ2/γ3 都是自选;
  2. γ1 只有**一种**字典表示 ⇒ 可观察面(§2.1 的 `TYPE`、`==`、§2.5 的渲染、JSON、
     诊断措辞、插入序)只有**一套**代码路径 ⇒ 不会出现「两种表示的某个面忘了对齐」
     —— 那是 `ADR-0032` 已经吃过一次的亏;
  3. 175 处替换是**机械**的(构造 ⇒ 走构造函数;模式匹配 ⇒ 走访问器),可脚本化、可
     逐文件核对 ⇒ 风险在**编译期**暴露,不在运行期。
- **D2 · 键的哈希与相等必须与 §2.4 逐字对齐。** 键域封闭(§2.1)⇒ `DictKey` 的
  `Hash`/`Eq` 只有三种:`STRING` 按字节、`INTEGER` 按数值、`INSTANCE` 按**身份**
  (`Rc::ptr_eq`)。⚠ **不得**为了哈希而改变可观察的键序(§18.3.1 原文)⇒ 索引只存
  **位置**,呈现仍走 `entries` 的插入序。
- **D3 · 写路径走 copy-on-write,唯一拥有时原地改。** 「唯一拥有」的判定用 `Rc`
  引用计数 ⇒ 命中时 `INDEX_SET` 是 O(1)(改 `entries` 的一格 + 改 `index` 的一格);
  未命中时克隆(结构体 + 索引)⇒ O(n)。⚠ 原地改**只在旧值不可观察时合法**
  (§19.1 的值语义)⇒ 判定必须严格按引用计数,不许「看起来没人用」就改。
- **D4 · 逃逸分析沿用 `ADR-0032` 的既有形状,不为字典另立一套。** `ADR-0032` 已经
  为数组实现了「循环局部累加器 ⇒ 放进 cell ⇒ 原地累积」的识别与三件套守卫。字典的
  写路径若要拿到**摊还 O(1)**,需要同一套机制(`SET(d, INDEX_SET(d, k, v))` 形态下
  `d` 唯一拥有 ⇒ 原地改)。⇒ **复用**,不重写。
- **D5 · 规范侧要补一句「摊还口径」的可判定判据(语言级语义裁决,需业主点头)。**
  提案:在语言核心册 §18.3.1 补一段,写明
  ① **读路径**:索引有效时 O(1) 期望(索引失效的那一次重建计入摊还);
  ② **写路径**:唯一拥有时 O(1);被别名时退化为拷贝,退化的总量计入**序列级**摊还;
  ③ **判定**:用**确定性工作量计数**(比较次数 / 拷贝的元素数),判据是
  「n 次写 + m 次读 ⇒ 总工作量 ≤ c·(n+m)」。
  ⚠ **强度不变**:`必须` 一字不动,变的只是「摊还」的**适用范围从隐含变成成文**
  —— 与「把必须降成应当」是两件事(后者是本轮审计明确驳回的)。
  ⚠ **为什么必须写**:不写 ⇒ 「O(1) 摊还」没有可判定口径 ⇒ 验收只能靠感觉 ⇒
  §18.5「判定必须用确定性工作量计数」就落不了地。
- **D6 · 规范侧的 §18.6 偏差登记在 S5 收口时改写。** 现在那一行写着「该表示变更
  本批未做,须另立决策」⇒ 本 ADR 落地后改成「已收敛 + 收敛路线指向本 ADR」。

## Consequences

**能拿到的**:X-04 / D-02 / V-01 收敛 ⇒ 一致性册 §3.5 发布前置条件的**第 1 条与第 2 条**
都跨过 ⇒ 收口的关键路径打开。

**要付的**:

1. **diff 大**:175 处机械替换(分散在 26 个文件)⇒ 逐文件提交、每笔只碰一个文件的
   那一批,便于回看。
2. **别名退化的代价必须被如实登记**:被别名的字典写仍是 O(n) ⇒ D5 的口径写准之后,
   这不是「违规」,但**必须在 §18.6 的偏差登记里留一行**(「别名下的写是 O(n) 拷贝,
   按 D5 的口径计入摊还」)⇒ 不留行 = 藏起来,那正是本仓台账纪律要防的。
3. **引用计数与循环**:字典进 `Rc` 之后,自引用结构(字典里放自己)会造成引用环 ⇒
   `Rc` 的泄漏。⚠ 值语义下不可变字典**不可能**自引用(要放自己得先有自己)⇒ 实际
   不可达,但**必须有一条守卫**钉住它,否则将来有人加了可变形态就会漏。

**明确不做**:

- 不做持久化结构(γ3)⇒ 不引入手写 HAMT;
- 不新增字典的语法面、不改 §2.1 的键域;
- 不改键序语义(插入序仍是可观察的);
- 不引入新依赖(`cargo-deny` 在 CI 里把关,新依赖要过许可与公告审查 ⇒ 本 ADR
  刻意选「手写 `HashMap` + `Rc`,零新依赖」)。

**验收判据**(三条,缺一不可):

1. **可观察面零变化**:字典的 `TYPE` / `==` / 渲染 / JSON / 诊断措辞 / **插入序**在替换
   前后**逐字节相同** ⇒ 用现有契约测试 + 一条「插入序快照」守卫钉住;
2. **计数守卫绿**(S5)⇒ 且**负向验证**:把索引换回线性扫描,守卫**必须红**
   (只报正向绿灯不算数 —— 这是本仓一贯的纪律);
3. **别名退化如实登记**(见 Consequences 第 2 条)。

## 未决(留给实现阶段,不是本 ADR 的决定)

1. `DictKey` 的哈希函数选型(`FxHash` 风格的自写实现 vs `DefaultHasher`);
2. `Rc` 的强计数 / 弱计数取舍(要不要为循环留一道 `Weak` 兜底);
3. 计数守卫的常数 `c` 取值(要**先采集 10 组重复测量**再定,不能拍脑袋 —— `ADR-0032`
   的同类教训:容差是量出来的,不是猜的);
4. 逃逸分析在字典上的具体形态(直接复用 `ADR-0032` 的数组识别,还是需要单独的判据)。
