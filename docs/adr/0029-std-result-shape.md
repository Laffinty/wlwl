## Context

`addendum-11` 要给 `OK` / `ERR` 一套组合子。它在 §3 列了六个「开写前必须逐条回答」
的裁决点,并在 §6 写下**头号风险**:

> ⚠ **组合子可能成为 §8.2 的旁路**(裁决 §3.5)—— 消费者注册制度是语言级的
> 设计,标准库给它开后门是结构性损伤。

本 ADR 的工作是**把那个风险查清楚**,以及把 §3 的裁决点在**实测**上落定。
结论与计划原文有**五处**不同,全部由下面的实测得出。

## 1. 实测(可复跑)

### 1.1 实参为 `ERR` ⇒ **调用不求函数体**(R1 门面与 R2 内核 alike)

这是本 ADR **最关键**的一条,前一版把它写成「`ERR` 在调用边界被变成 `E0102`」是
**错的**:`E0102` 只在那个 `ERR` 一路浮到顶层时才出现(§8.5)。真实机制是**它直接
成为调用的结果**,函数体根本不执行。

源码依据 `impl/crates/wlwl-eval/src/lib.rs::dispatch_call` —— §8.2 的传播块位于
`user_fn` 分派(R1 `Closure` 与 R2 `NativeFn` **都**在它之后)**之前**,
判据是 `is_err_consumer(name)`,即**被调用者的名字字符串**是否在 §8.3 的注册表里:

```rust
if !whitelisted {                       // whitelisted = is_err_consumer(name)
    if let Some(err) = pending_err { return Ok(Outcome::normal(err)); }
    …
}
if let Some(v) = user_fn { … }          // R1 Closure / R2 NativeFn 都在这后面
```

实测(用与实参**无关**的副作用计数器):

```wlwl
LET MUT(n, 0);
LET(g, FUN((x), (SET(n, +(n, 1)); OK(1))));   // 体内计数,与实参无关
LET(r, IS_ERR(g(ERR(["why": "bad"]))));      // n = 0 —— 体从未执行
LET(s, IS_ERR(g(OK(5))));                    // n = 1 —— 实参是 OK 时体才执行
LET(u, IS_ERR(g(ERR_PAYLOAD(ERR(["a": 1])))));// n = 2 —— 先取载荷再传,体执行
```

§8.3 明文「**本表不新增条目**」⇒ 这不是待修的缺陷,而是**规范承诺的行为**。

### 1.2 R2 `StdFn` **能**接闭包 —— §3.3 的原问题已解

`collection::kernel_map` 早就这么用。⇒ 成员签名可以照 Rust / Scala 那样收函数值。

### 1.3 三条「`ERR` 分支 = 原样透传」的成员**碰巧是对的**

`MAP` / `AND_THEN` / `FLATTEN` 的 `ERR` 分支恰好就是「原样返还 `r`」——而 §8.2 已经
免费提供了这件事。实测四组形状全对(`RESULT_MAP(ERR)` 载荷原样保留、`f` 调用计数
不增;`FLATTEN` 的四种组合)。

⚠ **但这不是「R1 门面可行」的证据** —— 前一版把它当成证据是**空证**:探针里的计数器
之所以没涨,是因为**体压根没执行**,不是因为 `IF` 短路。正确的表述是「它们的 `ERR`
分支由语言层提供」,不是「成员体处理了 `ERR`」。

### 1.4 `IF` 三参确实短路(这一条是**真**证据)

```wlwl
LET MUT(n, 0);
LET(g, FUN((x), (SET(n, +(n, 1)); x)));
LET(y, IF(IS_ERR(<ERR>), OK(1), g(p)));   // n = 0 —— else 支未被求值
```

§22.3 的调用方惯用法**依赖**这条。

## 2. §3.5 的答案:组合子**不是**旁路 —— 但理由是「它们根本接不到 `ERR`」

前一版的结论(不是旁路)成立,理由写错了。正确的理由:

- 组合子**接不到**非消费者拿到的 `ERR`(1.1)⇒ 它们**没有能力**消费注册表外的
  `ERR` ⇒ **不可能**成为旁路。这比「用了已登记的 `IS_ERR` 所以没事」强得多。
- 要让某个函数真的接住 `ERR`,只能扩 §8.3 注册表,而 §8.3 明文「不新增条目」。
  规范 §22.2 把这条钉成**规范性条款**,契约测试做**反向断言**。
- ⚠ **被排除的做法**:把 `ERR` 藏进 `DICT`/`ARRAY` 传给门面(技术上能跑,已实测)。
  §8.2 推论要求「检查并消费一个 `ERR` 值必须在**拥有它的作用域内**进行」,容器
  装盛**不是消费**(§8.5 明文同款)。这属于蓄意造旁路,**不做**。

## 3. 另两条裁决点:答案已经实现了

- **§3.4「`UNWRAP` 失败用什么诊断?」—— 问题不存在。** `UNWRAP` 已是全局内建,
  专用码就是 `E0100`(不是 `E0102`)。规范 §22.4 与契约测试做**否定断言**。
- **§3.6 `RESULT_ALL` 短路** —— 裁决**短路**;契约表钉「返回第一个 `ERR`」。

## 4. 成员面:13 → **9** → **6**(四个已是内建,三条不可实现)

| 计划 §2 列的成员 | 实际状态(2026-10-12 实测) |
|---|---|
| `IS_OK` / `IS_ERR` / `UNWRAP_OR` / `UNWRAP` | ⚠ **已是全局内建**,不复刻(§4b) |
| `RESULT_MAP` / `AND_THEN` / `FLATTEN` | ✅ **W-02 已落地**(原名 `MAP`,见 D5) |
| `RESULT_ALL` / `RESULT_ANY` / `NULL_OR` | 🟡 **W-04 待验**(收集合/普通值,不是收裸 `ERR`,原则上可行但未实测) |
| `OR_ELSE` / `ERR_MAP` / `ERR_OR_ELSE` | ❌ **不可实现**(1.1)。`ERR` 分支要做事,而体不执行 ⇒ 改写为调用方惯用法,规范 §22.3 |

⚠ 计划 §1 的基线表把 `IS_OK` / `IS_ERR` / `UNWRAP_OR` / `UNWRAP` 当成待新增列出,
那是**过时清单**。照计划实现会在 `std.result` 里重复一遍全局内建。

## Decision

> 已裁决(成员面 **6 个可实现 + 3 条不可实现**,不复刻内建):

- **D1 · 组合子是 R1 门面、零 kernel。** 依据 1.1 / 1.3。
- **D2 · 新命名空间 `std.result`**,不塞进 `std.test` / `std.collection`。
- **D3 · 扩展 ERR 消费者登记册 = 语言层变更,本批不做。** §8.3 明文不新增条目。
- **D4 · 不碰全局内建。** 依据 §4 / §4b。
- **D5 · `MAP` 改名 `RESULT_MAP`。** ⚠ `std.collection` 自 v0.10 起即导出 `MAP`,
  两者同作用域 `IMPORT` **硬撞 `E0021`**(不遮蔽、直接报错,实测)。
  `AND_THEN` / `FLATTEN` 对附录 A 全表无冲突。
- **D6 · `OR_ELSE` / `ERR_MAP` / `ERR_OR_ELSE` 判为不可实现**,规范 §22.3 给调用方
  惯用法。依据 1.1 + §2。**不做容器走私。**

## 4b. ✅ **[已裁决 2026-10-12]不复刻** —— 四个已有全局内建不导出

**选择:不做** —— 一个语义一个名字。规范 §22 的成员表**不重复列**这四个名字;
**文档**里写清楚「你要用的是**全局内建**,无需 `IMPORT`」。契约表**不为它们建条目**
—— 它们由既有内建的契约守着。

## Consequences

**能拿到的**:§6 的头号风险在 D1/D6 下**不可能发生**;组合子可用普通函数继续组合。

**要付出的**:

- ⚠ **性能**:三条成员从「一个 R2 调用」变成「一次闭包调用 + 若干 `IF`」。
  计划 §4 的「100 万次 ≥ 200 MB/s(**依赖 00**)」是按 R2 估的,阈值**必须重新测**。
  硬前置 00 的 `L0-B` **仍未立项** ⇒ 本批**没有可依赖的基线**。
  ⚠ 我的建议:**本批不做性能断言**,把吞吐作为**读数**记进 `baseline.txt`,不设闸。
- ⚠ **`MAP` 改名 `RESULT_MAP`** 是**偏离 `addendum-11` §2 原文**的,已在 D5 记录。
- ⚠ **`NULL_OR` 有待验的一角**:若 `v` 是 `ERR`,§8.2 会传播它(而不是返回 `default`)。
  这可能正是想要的语义(`NULL_OR` 不是 `UNWRAP_OR`),但**须在 W-04 实测后写死**。
- ⚠ **W-04 的 `RESULT_ALL` / `RESULT_ANY` 收的是集合**,集合不是 `ERR` ⇒ 体应当会执行。
  同属「原则上可行、须实测」,不在本轮结论内。
- **明确不做**:`OPTIONAL` 类型 / `?` 语法糖 / 宏 / 改 §8.3 消费者 / 改 §8.2 传播
  语义 / 扩展 ERR 消费者登记册(D3)/ 容器走私 ERR(D6)。

## 7. D1 的冻结条件(采纳时附加,2026-10-12)

**D1 不是无条件裁决。** 它冻结在这个前提上:

> **`ADR-0017` Step 3(真 state-machine 续跑)仍未落地。**

前提一旦不成立,1.1 那条实测结论**仍然成立**(它来自 §8.2 的传播实现,与 Step 3 的
缺失无关),但**解法**变了:届时组合子可以直接做挂起形态。

⇒ 复核触发器(与 `ADR-0028` §6 同款判据,**独立于登记表**):

| 判据 | 现状(2026-10-12) |
|---|---|
| `impl/crates/wlwl-eval/src/effect.rs` 存在 | ❌ **不存在** |
| `channel.rs` 里「只有 `Yield(Explicit)` 保存 env」这句消失 | ✅ **还在** |

⚠ **冻结只覆盖 D1(层归属)。** 成员面(6 可实现 / 3 不可实现)、D5 命名、D6 的
「不可实现」结论**都不依赖这个前提** —— 1.1 来自 §8.2 本身。

## 5. 明确排除的选项(以及为什么)

| 选项 | 排除理由 |
|---|---|
| R2 全员(计划 §2 原文) | 实测 1.1:`ERR` 实参让调用不求体,R2 内核在传播块之后分派,同样见不到 |
| 扩 §8.3 注册册 | 规范 §8.3 明文「本表不新增条目」;且属语言层变更(ADR-0023) |
| 容器装盛 `ERR` 走私 | §8.2 推论 + §8.5 明文「装盛不是消费」—— 蓄意造旁路 |
| 在 `std.result` 复刻四个内建 | 一个语义两个名字(§4b) |
| 沿用 `MAP` 这个名字 | 与 `std.collection::MAP` 硬撞 `E0021`(D5) |
| 塞进 `std.collection` | 集合操作与错误组合是两类关注点 |
| 塞进 `std.test` | 组合子是**生产代码**工具,`std.test` 是测试面 |
