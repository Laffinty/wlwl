## Context

`addendum-11` 要给 `OK` / `ERR` 一套组合子。它在 §3 列了六个「开写前必须逐条回答」
的裁决点,并在 §6 写下**头号风险**:

> ⚠ **组合子可能成为 §8.2 的旁路**(裁决 §3.5)—— 消费者注册制度是语言级的
> 设计,标准库给它开后门是结构性损伤。

本 ADR 的工作是**把那个风险查清楚**,以及把 §3 的裁决点在**实测**上落定。
结论与计划原文有四处不同,全部由下面的实测得出。

## 1. 三条实测(可复跑)

### 1.1 R2 `StdFn` **接不到** `ERR` 实参 —— §12.6 在调用边界就传播

```wlwl
IMPORT("wlwl:std.encode", ["HEX_DECODE"]);
PRINT("before");
LET(r, HEX_DECODE(ERR(["kind": "T", "why": "probe"])));
PRINT("after:", r);
```

```
before
error[E0102]: unhandled ERR escaped to top level: [kind: T, why: probe]
```

`after` **一次都没跑**。原生函数根本没看见那个 `ERR` —— 它在**实参求值之后、
进函数体之前**就被 §12.6 拿走了。

⇒ **凡是「按 `ERR` 分支」的成员都不能是 R2。** 计划 §2 写的「层:**R2 全员**」
对 `MAP` / `AND_THEN` / `FLATTEN` / `OR_ELSE` / `ERR_MAP` / `RESULT_ALL` /
`RESULT_ANY` 一律**不成立**。

### 1.2 但 R2 `StdFn` **能**接闭包 —— §3.3 的原问题已解

`collection::kernel_map` 早就这么用:`let f = &args[1]; if !is_callable(f) { … }`。
⇒ 组合子的 `f` **不必**是 R1 展开的调用点,成员签名可以照 Rust / Scala 那样
收函数值。这解掉了计划 §6 的第二条疑虑(「若接不了闭包,组合子就只是语法糖的
另一种写法」)。

### 1.3 R1 门面组合子**可行**

```wlwl
LET(MAP, FUN((r, f), IF(IS_ERR(r), r, OK(f(r)))));
LET(m, MAP(ERR(["kind": "T", "why": "probe"]), FUN((x), TO_UPPER(x))));
```

```
after, IS_ERR(m) = TRUE
payload kept = probe
```

ERR 正确透传、**载荷原样保留**、闭包正常参与。⇒ 可行形态是 **R1
(`wlwl/std/result.wll`)+ 按 `addendum-00` L0-A-3a 那套 kernel 注入**
(或纯 R1 门面,取决于是否需要 `R2` 内核)。

## 2. §3.5 的答案:组合子**不是**旁路,而且做 R2 **才会**成为旁路

ERR 消费者登记册(`wlwl-eval/src/lib.rs`)是一张**内建名字表**,只接受内建名;
`IS_OK` / `IS_ERR` / `OR_DIE` / `TRY` 甚至是 **lexer 关键字**,由 parser 降成
`Expr::IsOk` / `Expr::IsErr` / …,**在 `eval_call` 之前**就消费掉了。

- **走 R1 门面**(D1):组合子只是 `IS_ERR` 的语法展开,用的是**已登记的语言级
  消费者**。它既没新增消费者,也没绕开 §12.6 —— **不构成旁路**。
- **走 R2**(计划原文):要么被 §12.6 提前传播(1.1),要么就得**把登记册从
  「内建名册」扩展到「原生成员名册」** —— 那是**语言层变更**(ADR-0023),
  本批不做。⚠ **真要做 R2 而不扩册,唯一剩下的办法是让成员假装自己是内建**,
  那才是旁路。

⇒ §6 的头号风险**在 R1 形态下不存在**;它恰恰是「为了留在 R2 而硬凑」时才会
出现的东西。

## 3. 另两条裁决点:答案已经实现了

- **§3.4「`UNWRAP` 失败用什么诊断?」—— 问题不存在。** `UNWRAP` **已经是
  全局内建**,签名就写着 `UNWRAP(x) -> v / E0100 (不可捕获)`
  (`registry.rs:489`)。计划担心的「不能复用 `E0102`」早已做到:`E0100` 是专用码。
- **§3.6 `RESULT_ALL` 短路** —— 裁决**短路**。理由:成员形参都是**已求值的值**
  (wlwl 无惰性),短路只能靠调用方把副作用放在 `f` 里;但契约表仍要钉住
  「返回第一个 `ERR`」这个可观察语义。

## 4. 成员面:13 → **9**(四个已是全局内建)

| 计划 §2 列的成员 | 实际状态(2026-10-12 实测) |
|---|---|
| `IS_OK(v)` | ⚠ **已是全局内建**(`IS_OK(x) -> BOOLEAN`) |
| `IS_ERR(v)` | ⚠ **已是全局内建**(`IS_ERR(x) -> BOOLEAN`) |
| `UNWRAP_OR(r, d)` | ⚠ **已是全局内建**(`UNWRAP_OR(x, default) -> v`) |
| `UNWRAP(r)` | ⚠ **已是全局内建**(`UNWRAP(x) -> v / E0100`) |
| `MAP` `AND_THEN` `FLATTEN` `OR_ELSE` `ERR_MAP` `ERR_OR_ELSE` `RESULT_ALL` `RESULT_ANY` `NULL_OR` | ✅ **真正新增,9 个** |

⚠ 计划 §1 的基线表写「组合子 **0**」—— 就**组合子**而言没错,但它接着把
`IS_OK` / `IS_ERR` / `UNWRAP_OR` / `UNWRAP` 当成待新增列了出来。这是**过时
清单**,不是「这四个不存在」。**照计划实现会在 `std.result` 里重复一遍全局内建**
—— 同一语义两个名字,读者无从判断该用哪个。

**建议:只做 9 个,不复刻内建。** 若认为 `IS_OK` / `IS_ERR` 这类谓词**应该**
出现在 `std.result` 的文档目录里(便于按命名空间查),可在规范里**引用**而
**不导出成员**。

## Decision

> 待业主裁决 §4 的成员面;以下四条在「9 个」的前提下成立。

- **D1 · 组合子是 **R1 门面**(混合模块),不是 R2 全员。** 依据 §1.1 / §1.3。
  形态照 `addendum-00` L0-A-3a:门面 `LET(MAP, FUN(…))` + 需要时注入 R2 内核。
- **D2 · 新命名空间 `std.result`**,不塞进 `std.test` / `std.collection`。
  组合子是**生产代码**的通用控制流工具,与「测试面」性质不同。
- **D3 · 扩展 ERR 消费者登记册 = 语言层变更,本批不做。** 依据 §2。
  「组合子要能接非消费者拿到的 `ERR`」这个要求,已由 R1 门面的 `IS_ERR` 满足。
- **D4 · 只做 9 个新成员,不碰全局内建。** 依据 §4。

## 4b. 待业主裁决(唯一开放问题)

**`IS_OK` / `IS_ERR` / `UNWRAP_OR` / `UNWRAP` 这四个已存在的全局内建,要不要在
`std.result` 里再导出一份?**

- **不做(我的建议)**:一个语义一个名字。`std.result` 文档里**引用**它们即可。
  重复导出会让调用方在 `IS_ERR(x)` 与 `IMPORT("wlwl:std.result")` 后的
  `IS_ERR(x)` 之间无从选择,且后者的存在本身会诱使人以为内建版「不够用」。
- **做**:好处是 `std.result` 的成员面自洽(谓词 / 投影 / 兜底三类齐全),
  代价是上面那两条。

## Consequences

**能拿到的**:§6 的头号风险在 D1 下**不存在**;组合子可用普通函数继续组合;
`addendum-11` §5 落点 8 要求的「把 `reference.md` §9.1 里那句
`AT_K(ERR_PAYLOAD(BASE64_DECODE(s)), "kind", "?")` 改写成组合子写法」**仍然
做得到** —— 只是新写法是 R1 门面而不是 `IMPORT` 后的成员调用。

**要付出的**:

- ⚠ **性能**:`MAP` / `AND_THEN` 从「一个 R2 调用」变成「一次闭包调用 + 一次
  `IF`」⇒ 多一层解释器开销。计划 §4 的「100 万次 ≥ 200 MB/s(**依赖 00**)」这条
  阈值**必须重新测**,不能沿用 —— 它是按 R2 估的。`addendum-11` 的硬前置写的是
  「00(R0 治本)」,而 `L0-B` **仍未立项**,所以这条性能断言在本批**没有可依赖的
  基线**。⚠ 我的建议:**本批不做性能断言**,把 `MAP` / `AND_THEN` 的吞吐作为
  **读数**记进 `baseline.txt`,不设闸 —— 设一个没有基线的闸,只会逼着人改实现
  去凑数。
- ⚠ **命名空间是混合的**:与 `std.collection` / `std.math` / `std.test` 同款
  (R1 门面 + 可选 R2 内核),要登记进 `LANG_SOURCES` 并过
  `stdlib_dual_track` 那几道守门测试。
- **明确不做**:`OPTIONAL` 类型 / `?` 语法糖 / 宏 / 改 §8.3 的消费者 /
  改 §12.6 传播语义 / 扩展 ERR 消费者登记册(D3)。

## 5. 明确排除的选项(以及为什么)

| 选项 | 排除理由 |
|---|---|
| R2 全员(计划 §2 原文) | 实测 1.1:`ERR` 在调用边界就没了,成员见不到它 |
| 把登记册扩到原生成员 | 语言层变更(ADR-0023),且会永久扩大语言面 —— 为一个命名空间不值得 |
| 在 `std.result` 复刻四个内建 | 一个语义两个名字(§4b) |
| 塞进 `std.collection` | 集合操作与错误组合是两类关注点;混了之后 `std.collection` 的文档会同时讲两件事 |
| 塞进 `std.test` | 组合子是**生产代码**工具,`std.test` 是测试面 |
