## Context

`addendum-09` §3 列了**六个语义裁决点**,原文写着「**开写前必须逐条回答**」。
本 ADR 就是那份回答。裁决之前的只读调查发现了三件计划没预见的事,它们改变了
其中两条的形状,所以先记在这里。

### 事实 1 ⚠ 旧两成员**零行为契约覆盖** —— §3.6「不许动」当时没有守卫

`addendum-09` §3.6 要求 `PARSE` / `STRINGIFY`「一条都不许动」(照 Go
`encoding/json/v2` 保留旧行为的体例)。W-01 开工前的全仓实测:

| 已有测试 | 覆盖什么 | **不**覆盖什么 |
|---|---|---|
| `src/json.rs` 8 条单元测试 | 走**内部函数** `std_parse_inner` | **不经 `wrap()` 边界、不经解释器**;期望值取自 `serde_json` 自己(即实现的依赖,不是独立裁判) |
| `stdlib_appendix_a_sync.rs` | 成员**清单**与附录 A 镜像对账 | 任何行为 |

⇒ **经 wlwl 程序能观察到的行为,一条都没被钉住。** W-02 要新增
`JSON_TOKENIZE` / `JSON_LOCATE` / `JSON_VALIDATE`,它们必然自带一套 JSON 语法
判定;一旦新词法层与旧 `PARSE` 对同一输入给出不同结论,当时没有任何东西会发现。

### 事实 2 失败口径的**不对称是必然的**,不是疏漏

规范 §11 已有一条现成裁决:「**新成员用 `ERR` 值**,载荷是
`[kind, op, reason]`」—— `std.fs` / `std.process` / `std.compress` / `std.encode`
全部照办。而旧两成员走 `E0070` / `E0071` **诊断**(中止整个程序),
它们是 v0.3 时代的遗留,且 §3.6 不许动。

⇒ **`std.json` 这个命名空间内部将同时存在两套失败口径。** 这不是没想清楚,
是「不许动旧成员」的直接后果。**必须写进规范**,否则下一个「顺手统一一下」的
人会去改 `PARSE`,而那正是 §3.6 禁止的。

### 事实 3 🔴 冻结过程中抓到一个真缺陷(D13-016)

写冻结契约时逐条核对数值边界,实测:

| 输入(JSON 合法) | Python `json`(独立裁判) | 本实现 |
|---|---|---|
| `9223372036854775807`(i64::MAX) | 精确 | `9223372036854775807` ✅ |
| `9223372036854775808`(= 2⁶³) | 精确 | `9.223372036854776e+18` ⚠ |
| `-9223372036854775809` | 精确 | `-9223372036854775808` 🔴 **值被改了** |
| `18446744073709551615`(u64 上界) | 精确 | `1.8446744073709552e+19` 🔴 |

根因:`json_to_value` 的规则是 `n.as_i64()` 命中 ⇒ `INTEGER`,否则 `as_f64()`
⇒ `FLOAT`。超出 i64 范围的整数**静默变成浮点并丢精度**,而且 `-9…809` 变成了
`-9…808` —— **不只是类型变了,是值变了**。

按 §3.6 本批**不修**;已登记 **D13-016**,并由 `json_contract.rs` 的
`known_defect_d13_016_integer_beyond_i64_loses_precision` **把缺陷本身冻住** ——
使它不会在无人在意时变得更糟,也不会被「顺手改一下」而无记录地消失。

## Decision

> 六个裁决点逐条落定如下。

### D1 · token 流**不算**重开「不做流式」

规范里**明写「本批仍不做流式解析」**,把 token 流定位为**诊断与定位工具**;
`PARSE` 的输入仍是整串。

**排除的另一条**:把 `JSON_TOKENIZE` 说成流式解析。那等于在没有流式基础设施
的情况下许一个做不到的诺 —— 而 `std.sync` 那份的教训正是「承诺与架构硬边界
不符」(`channel.rs:310` 写明 `E0064`「不是调出来的阈值,是当前架构的硬边界」)。

### D2 · `JSON_GET` 的路径类型用 `ARRAY`

`JSON_GET(d, ["a", 0, "b"])`。**排除**新语法:那是**语言面**的变更
(`docs/spec/wlwl-spec-v0.11.md`),不在本批的九个落点之内。

### D3 · `JSON_MERGE` 语义逐字写死

**对象递归深合并;数组整体替换(不拼接)。**

**排除「顶层替换」**:它会让 `{"a":{"x":1}}` + `{"a":{"y":2}}` 丢掉 `x`,
而这正是配置事故里最常见的形状。**排除「数组拼接」**:拼接不可逆,
且与「merge 是覆盖语义」的直觉相反。含糊的 merge 是配置事故的常见源 ——
所以这条必须各有正反各一条契约用例(落 W-04)。

### D4 · schema 未知关键字 → **`E0030`**,不静默忽略

依据两条,同向:

1. 规范 §12.1 立的纪律就是「**半张表比没有更糟**」—— 静默忽略会让调用方
   以为约束生效了;
2. `addendum-13` 的 `HTML_SANITIZE` 已经为 policy 里的未知键**选过 `E0030`**
   (D13-009),是仓内现成先例。

**排除静默忽略**:代价就是上面那条,收益只是向前兼容 —— 而 schema 子集是
本批**新**定义的,没有向后兼容的历史包袱。

### D5 · 错误消息形态 = 规范 §11 既有体例 **加** 位置

`ERR([kind: "JsonError", op: <成员名>, path, line, column, reason])`

即在 §11 已有的 `[kind, op, reason]` 上**加** `path` / `line` / `column` ——
后者正是本批最有价值的产出(现在报错不带位置)。

⚠ **并把事实 2 的不对称一并写进规范**:`PARSE` 仍报 `E0070`、`STRINGIFY` 仍报
`E0071`,**这是规格的一部分,不是待清理的债**。

### D6 · `PARSE` / `STRINGIFY` 不动 —— 且**先补冻结基线**

W-01 的第一份交付是 `impl/crates/wlwl-eval/tests/json_contract.rs`:
只钉旧两成员、零新成员,10 条用例,分六组 —— RFC 8259 合法语法面 / RFC 8259
「不应接受」清单(24 条**全部** `E0070`)/ 数值种类映射 / `STRINGIFY` 可观察面 /
边界误用 / round-trip 恒等。**它是 W-02 的前置**,不是可选项。

## Consequences

**能拿到的**:W-02 起的每一次改动都有基线可比;D13-016 有了钉子;新成员的失败
口径有一条仓内一致的先例可循;`std.json` 内部的两套失败口径被写成规格而不是
隐患。

**明确不做**(与 `addendum-09` §0 的非目标一致):JSON 语法扩展 / YAML / TOML /
CBOR / MessagePack / 流式解析 / JSON Schema 全量 / 自动映射生成。
**不修** D13-016(§3.6 边界)。

**留给实现阶段、不是本 ADR 的决定**:

1. `JSON_TOKENIZE` 的 token `kind` 取值表(几个?叫什么?)—— 建议先照 RFC 8259
   §2 的六个值(`lbrace`/`rbrace`/`lbracket`/`rbracket`/`colon`/`comma`/`string`/
   `number`/`true`/`false`/`null`)加上 `eof`,但这是可讨论的;
2. `JSON_LOCATE` 的 `line` / `column` 是**字节**还是**字符**列 —— 本批输出一律
   是 ASCII 之外的 UTF-8,这条会实际影响结果,必须在 W-03 逐字节冻结前定;
3. schema 子集里 `enum` 与 `type` 同时出现时的裁决顺序。

## D7 · W-02 实施期追加的三个决定(2026-10-14)

§「留给实现阶段」里第 2 条(`JSON_LOCATE` 的 `column` 单位)在 W-02 开工前落定,
连带的两个也一并定。三条都**有实测依据**,不是选口味。

### D7.1 偏移一律**码点**,不是字节

**依据**:全语言唯一的字符串切分原语是 `SUB(s, start, len?)`,规范 §10.5 明写
「**按码点**」;而整份语言规范里「字节偏移 / byte offset」出现 **0 次**。

⇒ 发字节偏移等于发一个**用户用不了**的数字:喂不进 `SUB`,也不是 `CODEPOINTS`
的下标。故 `JSON_TOKENIZE` 的 `start`/`end`、`JSON_LOCATE` 的 `offset`/
`token_start` 一律**码点 0 基**;`line`/`column` **1 基**,`column` 也是码点列。
契约用一条 `é`(UTF-8 占 2 字节、码点占 1)把这件事钉死:断 `end` 不断 `start`,
因为 `start` 在两种单位下都是 1,断它等于什么都没断。

### D7.2 `ERR` 载荷必须带 `offset`

⚠ 这条**不在** D5 的字段清单里,是实施时发现的:**`JSON_VALIDATE` 报的是
`line`/`column`,而 `JSON_LOCATE` 的实参是 `offset` —— 没有 `offset`,这套 API
自己转不过弯**,用户得把行列反算回码点下标,而本批不提供那个反算。
`line`/`column` 给人看,`offset` 给机器接下一棒,三个一起给。

(是 clippy 的 `field 'offset' is never read` 把它指出来的 —— 那不是死代码,
是「算了但没出口」。)

### D7.3 `path` 在 W-02 三个成员里**不出现**

D5 的字段清单里有 `path`,但 `JSON_TOKENIZE` / `JSON_VALIDATE` **只做语法**:
前者连结构都不看,后者不看 schema ⇒ 没有路径可言。塞一个恒为 `NULL` 的 `path`
只会让人以为「路径是空的」而不是「此处无路径」。`path` 从 `JSON_CHECK`(W-05)
与路径族(W-04)才开始有。

## W-02 实施期实测:`serde_json` 比 RFC / Python **更严**的三处

`JSON_VALIDATE` 与 `PARSE` 是**同一份语法的两套判定**(一套 serde_json、一套本仓
手写词法器),两套一旦分叉,「先验后用」就失去意义。开工前的边界探测实测:

| 输入 | `serde_json`(⇒ `PARSE`) | Python `json` | 词法层 |
|---|---|---|---|
| `\uD800` / `\uDC00`(孤立代理) | **拒** | 收 | **拒** |
| `\uDD1E\uD834`(代理对换序) | **拒** | 收 | **拒** |
| 嵌套 **200** 层 | **拒**(上限 128) | 收 | **拒**(`MAX_DEPTH = 128`) |
| `1e400`(f64 溢出) | **拒** | 收(`inf`) | **拒** |

⇒ 这三条**必须照样严**,否则词法层比 `PARSE` 宽松。孤立代理那条 serde 是对的:
代理项必须成对,单独出现不是合法标量值,编不成 UTF-8;Python 收它是因为它的
`json` 产出的是 Python `str`(可以装孤立代理)。

⚠ **这三条是写词法器之前测出来的**。若先写实现再对账,`1e400` 与深度上限这两处
很可能被「照 Python 写」的习惯带偏 —— 而那时候代码已经通过了它自己的单测。
