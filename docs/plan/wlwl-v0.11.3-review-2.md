#### R2-001 [P1] 字典取值的「键类型不符」报 `E0037`,规范要求 `E0031`

- **规范条款**:`docs/spec/wlwl-spec-v0.11.md:377`(§4.5)—— 「字典按键取值,**键类型不符产生 `E0031`**,键不存在产生 `E0037`」
- **实现侧**:`impl/crates/wlwl-eval/src/lib.rs:1742-1748` —— `builtin_index_get` 的 `Value::Dict` 分支只有「找到 / 没找到」两路,没找到一律 `E0037`;**没有**键类型判定。数组分支(`:1696-1705`)反倒有正确的 `E0031` 检查 ⇒ **两条路径不一致**
- **复现**:
  ```
  PRINT(INDEX_GET(["a": 1], TRUE));
  → error[E0037]: INDEX_GET: dict key TRUE not found      [exit=1]
  ```
  `1.5` / `[1]` / `NULL` / `1.0` 均得 `E0037`(应为 `E0031`)
- **修法**:改实现 —— Dict 分支入口加键类型闸门(非 `STRING`/`INTEGER` → `E0031`),缺键仍走 `E0037`。⚠ **必须与 R2-002 同批决策**,否则两处语义互相矛盾

#### R2-002 [P1] 字典键的「必须为 `STRING` 或 `INTEGER`」未被实现

- **规范条款**:`docs/spec/wlwl-spec-v0.11.md:170`(§2.1)—— 「**键的约束**:字典的键**必须**是 `STRING` 或 `INTEGER`。NaN **不得**作键(`E0031`)。」
- **实现侧(缺陷形态)**:`impl/crates/wlwl-eval/src/lib.rs` 的 `Expr::Dict` 字面量求值与 `INDEX_SET` 的 Dict 分支 —— 键值**不做任何类型校验**,原样进容器;`KEYS` / `VALUES` 再把它吐回程序
- **复现**:
  ```
  LET(d, ["a": 1, TRUE: 2]); PRINT(KEYS(d));
  → [a, TRUE]                                               [exit=0]

  PRINT(INDEX_SET(["a": 1], TRUE, 2));
  → [a: 1, TRUE: 2]                                         [exit=0]
  ```
  `[[1]: "x"]` 与 `[NULL: "x"]` 同样被接受。后果:这类字典直到 `wlwl:std.json` 的 `STRINGIFY` 才炸,报的是**别的码**(`E0030: expected string dict key, got boolean`)⇒ 规范要求在**构造点**报 `E0031`,实现把错误推迟到了另一个子系统的另一个码
- **修法**:改实现 —— 字面量求值与 `INDEX_SET` 各加一道键类型闸门。⚠ **这是语言语义变更**(既有程序可能依赖宽松键类型)⇒ 须走可见面申报
- ⚠⚠ **[2026-10-20 实施期订正 —— 闸门的「允许集」比原文窄一格,但不是随意选的]**:
  按 §2.1 字面把允许集取成「只有 `STRING` / `INTEGER`」会**删掉一个仓内刻意做出来的语言能力**:
  - `R10-012` 有一族**刻意**的测试(`r10_012_instances_work_as_dict_keys` 等,4+ 条)明确要求
    「`DICT` 用**实例**当键时,同实例命中、异实例不命中」——按**身份**判定;
  - `impl/crates/wlwl-cli/tests/conformance.rs` 的 OOP 夹具(`oop_identity.wll`)也拿实例当字典键;
  - 而**语言规范里没有任何一条**说实例可以当键(§2.1 只列 `STRING` / `INTEGER`)⇒
    严格讲,那些程序用的是**规范未定义的行为**(§0.4:「一个 WLWL 程序是符合本规范的,
    当且仅当它只使用**本规范定义的**语法形式与语义」)⇒ 实现拒绝它们**不违反** §0.4。
  ⇒ **两条路都可行,但代价不同**:
  - (a) **按 §2.1 字面收紧** ⇒ 删掉「实例当键」这个能力(连带改 4+ 条既有测试与 OOP 夹具)⇒ **产品取舍**;
  - (b) **把 `INSTANCE` 加进允许集** ⇒ 能力保留,闸门只拦「错类型」(布尔/浮点/数组/字典/null)⇒
    **审计的真正缺陷(`E0037` 冒充 `E0031`)**照样修掉了。
  ⇒ **本次落地取 (b)**:实现侧允许 `STRING` / `INTEGER` / `INSTANCE`,其余一律 `E0031`;
    ⚠ 而「`INSTANCE` 到底该不该是合法键类型」这条**规范侧**问题**已于 2026-10-20
    裁决**:规范 **§2.1 补上这一句**(键类型集合 = `STRING` / `INTEGER` / `INSTANCE`,
    `INSTANCE` 按**对象身份**判定)⇒ 实现与规范**逐条对齐**,「实现比规范宽」那条
    缺口**已消除**。
    ⚠ 换句话说:**闸门是按「规范已列的 + 仓内刻意的」取的,不是按「规范已列的」一刀切的**
    —— 而那把「仓内刻意的」**收进规范**这一步,是业主裁决,不是实现自行放宽。
- **实施结果(2026-10-20)**:✅ 已修。构造点(字面量 / `INDEX_SET`)与取值点(`INDEX_GET`)三处都有闸门;`BOOLEAN` / `FLOAT`(含 `1.0` 与 `NaN`)/ `ARRAY` / `DICT` / `NULL` 一律 `E0031`;`STRING` / `INTEGER` / `INSTANCE` 照旧可用。契约 `eval_dict_key_contract.rs` 逐条钉住(含「实例当键仍然合法」这条反向守卫)。

#### R2-003 [P1] `*name` 剩余形参未限制在末位,第二个 rest 形参被静默丢弃

- **规范条款**:`docs/spec/wlwl-spec-v0.11.md:436`(§5.2 形参表)—— 「`*name` | 剩余参数;收集多余的实参为**新数组**。只**可以**出现在末位」
- **实现侧**:`impl/crates/wlwl-parser/src/lib.rs:1453` —— 形参循环对**任意位置**的 `*` 一律接受,没有「必须是最后一个」的检查;多于一个 rest 时只绑第一个。⚠ **对比**:同一解析器里**模式侧**的同一约束**是被强制的**(`:1124-1131`,且有测试 `parse_let_rest_must_be_last` @ `:3876`)⇒ 形参侧与模式侧行为不一致
- **复现**:
  ```
  LET(f, FUN((*rest, a), [rest, a])); PRINT(f(1, 2, 3));
  → error[E0022]: function expects 1..2 argument(s), got 3      [exit=1]

  LET(f, FUN((*a, *b), [a, b])); PRINT(f(1, 2, 3));
  → error[E0020]: undefined name `b`                            [exit=1]
  ```
  按 §5.3「有剩余参数:`实参数 ≥ R`;超出固定形参的实参收集为剩余数组」,第一条**应当合法**;第二条是**静默未绑定** —— `b` 在函数体里成了未定义名,错误延迟到运行时才暴露
- **修法**:改实现 —— 形参解析循环跟踪 `is_rest` 是否已出现,重复出现或 `*` 后仍有形参时报语法错(照模式侧 `parse_pattern` 的既有做法)

#### R2-004 [P2] 前导 `+` 的整数字面量不被接受

- **规范条款**:`docs/spec/wlwl-spec-v0.11.md:100`(§1.6 的 EBNF 是规范性的)—— 「`int_literal = [ "+" | "-" ] int_lit .`」
- **实现侧**:`impl/crates/wlwl-parser/src/lib.rs:767` —— 一元 sugar 分支只判 `TokenKind::Minus`,**无** `TokenKind::Plus` 的对等分支(`Plus` token 存在,`impl/crates/wlwl-lexer/src/lib.rs:102`,但只走「调用 `+(...)`」)
- **复现**:
  ```
  PRINT(+5);
  → error[E0011]: expected ')', got Integer(5)                   [exit=3]
  PRINT(-5);
  → -5                                                        [exit=0]
  ```
  即 `-x` 被 desugar 成 `-(0, x)`,而规范明列的同形 `+x` 被拒。影响面窄,但属「规范说的合法形式实现不收」
- **修法**:改实现 —— 给 `TokenKind::Plus` 加一条与 `Minus` 对称的 sugar 分支(`+(0, x)`),复用 `Minus` 分支已有的「不接 `(`」判定

#### R2-005 [P2] `${…}` 插值内不允许嵌套字符串字面量,与 §1.8 文法冲突

- **规范条款**:`docs/spec/wlwl-spec-v0.11.md:122-124, 130` —— 「`interpolation = "${" Expression "}"`」「`${...}` 内的表达式按**完整表达式语法**求值」;字符串字面量是 `Expression` 的合法组成
- **实现侧**:`impl/crates/wlwl-lexer/src/lib.rs:707-717` —— `read_interp_body` 在插值体内遇到 `"` 即返回 `E0001`;该处注释自称「per spec grammar」,**与 §1.8 文法实际不符**
- **复现**:
  ```
  PRINT("${ERR("x")}");
  → error[E0001]: nested string literal inside `${...}` interpolation is not allowed  [exit=3]
  ```
  ⚠ 这是**词法层**限制,绕不开 —— `"${"x"}"`、`"${ERR("boom")}"` 一律在词法期被拒
- **修法**:改实现 —— 把插值体的字符串扫描从「见 `"` 即报错」改为「跳过配对的嵌套字符串字面量后继续计数 `{}` 深度」

#### R2-006 [P2] `E0020` 诊断的「最近候选名」有两处缺口:候选池没有全局内建名、候选名不写进 `hint`

> ⚠⚠ **[2026-10-20 实施期订正]**:本条原来的**证据是错的**。原文写「全仓 grep
> `did you mean|nearest|candidate|levenshtein|closest` **零命中**」—— **不成立**:
> 机制**本来就有**(`levenshtein` + `similar_names` + `Suggestion::Note`),只是
> **接线有两处缺口**。结论不变(仍是 P2、仍要修),但**修法与证据都换了**。

- **规范条款**:`docs/spec/wlwl-spec-v0.11.md:275`(§3.2)—— 「读一个不存在的名字产生 `E0020`(**附最近候选名**)。」
- **实现侧(订正后)**:
  - 候选机制**存在**:`impl/crates/wlwl-eval/src/lib.rs` 的 `levenshtein` + `similar_names` + `undefined_name` 里的 `Suggestion::Note { description: "did you mean one of: …" }`。
  - **缺口 ①**:候选池只取 `self.env.names()`(**作用域可见名**)⇒ 拼错**内建**名时一个候选都给不出来 —— 而「把内建名打错」恰恰是最常见的 `E0020` 来源。
  - **缺口 ②**:`suggestion_code` **只**出现在 JSON 形态;**人类可读形态**里唯一会渲染的字段是 `hint`(`render_human` 打成 `= hint: …`)⇒ 候选名在终端里**根本看不见**。
- **复现(订正后)**:
  ```
  LET(FOO, 1); PRINT(FOOO);
  → error[E0020]: undefined name `FOOO`                       [exit=1]
     ⚠ 文本形态里**没有**任何候选名(JSON 形态的 suggestion_code 里有 "did you mean one of: FOO?")

  PRINT(LENGTH);        ← 拼错的是**全局内建**
  → error[E0020]: undefined name `LENGTH`                     [exit=1]
     ⚠ 连 JSON 形态里也没有候选 —— 池里只有作用域的名字,`LEN` 是内建、不在池中
  ```
- **修法**:改实现 —— ① 候选池改为「作用域可见名 **+ 全局内建名**」(内建名册用 `registry::resolved_builtin_names()`,它与规范附录 G 有逐条签名锁 ⇒ 不另立名字表);② 候选名**同时写进 `hint`**(文本形态与 JSON 形态都看得见);③ 候选名**必须长得像标识符**(内建注册表里**也收录了运算符 token** —— 不滤掉的话,未定义名 `a` 会收到「did you mean one of: -, /, >?」这种荒唐提示);④ 编辑距离上限**随目标长度缩放**(`max(1, min(3, len/2))`),否则单字母目标会被长名字淹没。
- **实施结果(2026-10-20)**:✅ 已修。`PRINT(LENGTH)` 的文本形态现在给出 `= hint: did you mean one of: LEN?`;契约 `undefined_name_carries_the_nearest_candidate` 同时钉住「内建拼错有候选」「作用域拼错有候选」「候选进 `hint`」三件事。

#### R2-007 [P1] 括号序列之后不接受后缀链 —— 实现**不符合**附录 A 的文法(实施期改判)

> ⚠⚠ **[2026-10-20 实施期改判]**:本条原判「**无法判定** —— 规范内部自相矛盾」。
> **实施期补到了一条决定性条文** ⇒ 矛盾其实**不在**「规范 vs 规范」之间,而在
> 「规范 vs 实现」之间 ⇒ **实现是那个不一致的一方** ⇒ 由 P3 级「无法判定」升为 P1。

- **规范条款(四处,三条说「可以」)**:

#### R2-009 [P1] 容器类型上的约束:**复合类型 + 约束**写在括号内时报的码与文案都不对

> ⚠⚠ **[2026-10-20 实施期订正]**:本条**原来的判据与复现都错了**。原文说「`ARRAY[T: Comparable]` 漏网」——
> **不对**:规范 §2.6 事实 ③ 说的是「`BoundedVar` 只能跟在**裸标识符**后」,而 `ARRAY[T: Comparable]`
> 里的 `T` **就是裸标识符** ⇒ 该形态**合法**。把它当成缺陷会让实现**比规范严**
> (那也是偏离,而且会打掉仓内既有测试 `an_explicit_constraint_parses_in_both_positions`
> —— 它的名字就叫「两个位置都认」)。⇒ 下面这一段是订正后的版本。

- **规范条款(三处,互相印证)**:
  1. `docs/spec/wlwl-spec-v0.11.md:1898-1899`(附录 A 注 ③)—— 「`BoundedVar` 只能跟在**裸标识符**后,给容器加约束报 `E0010: a type constraint may only follow a bare type variable`」
  2. **附录 A 文法**(`:1854`)—— `TypeArg = Type | BoundedVar .` ⇒ `BoundedVar` **明确是类型实参的合法成分**
  3. **§5.2.1**(`:460`)—— 「语法是**裸标识符 + 显式约束**,在**顶层注解与方括号内的类型参数**两处都认」
  ⇒ 三处合起来说:**`ARRAY[T: Comparable]` 合法**(T 是裸标识符);**`ARRAY[ARRAY[INTEGER] : Comparable]` 非法**(约束跟在**复合类型**后)
- **实现侧(缺陷形态)**:`impl/crates/wlwl-parser/src/lib.rs` 的 `E0010` 检查只扫描 `parse_expr` 之后**剩余的 token**(`p.pieces[p.pos..]`);写在 `[...]` **括号内部**的 `:` 被类型实参解析器吃掉 ⇒ 顶层那一关看不到它 ⇒ 括号内报的是**类型实参解析器自己的** `E0012`(`expected `,` or `]` in type expression, got `:``)—— **码与文案都不是规范说的那条**
- **复现(订正后)**:
  ```
  LET(x: ARRAY[INTEGER] : Comparable, [1]);        → error[E0010]: a type constraint may only follow a bare type variable …  [exit=3]  ← 括号外正确
  LET(x: ARRAY[ARRAY[INTEGER] : Comparable], [1]);   → error[E0012]: expected `,` or `]` in type expression, got `:`                [exit=3]  ← ⚠ 缺陷形态:应是 E0010
  LET(x: DICT[STRING, ARRAY[INTEGER] : Comparable], …); → 同上                                                        [exit=3]  ← 同上
  LET(x: ARRAY[T: Comparable], [1]);               → OK: parsed                                                        [exit=0]  ← **合法**,不是缺陷
  ```
- **修法**:改实现 —— 把 `E0010` 检查**下沉到类型实参解析层**(`TypeArg` 解析处):凡 `TypeArg` 位置出现「**复合类型 + 约束**」即报 `E0010`(规范逐字文案);而「**裸标识符 + 约束**」仍放行
- **实施结果(2026-10-20)**:✅ 已修。两种形态**都**报 `E0010` + 规范逐字文案;`ARRAY[T: Comparable]` / `DICT[STRING, T: Comparable]` / `T: Comparable` **仍然合法**(契约 `r2_009_a_bounded_type_variable_inside_brackets_stays_legal` 反向守着「不许过严」)。⚠ 另有一处**往返一致**的硬证据:缺陷形态下 `wlwl sig` 对 `LET(x: ARRAY[T: Comparable], [1]);` 产出 `EXPORT x : ARRAY[T: Comparable]` —— 按附录 E.1「渲染与解析必须往返一致」,那行是**合法签名**;若禁掉它,`sig` 自己产出的签名自己的解析器读不回来。

## 6 复核四:六项悬置技术债的最优解

**已核实**:六项的现状全部有**本机实测输出**或 `文件:行`;期望值取自规范原文 / RFC / 仓内基准文档,不抄实现输出。

### 6.1 `D13-050` · `std.net` 未特判 1xx / 204 / 304 —— **须单独立项**

**现状**:`impl/crates/wlwl-std/src/net.rs:1006-1047` 的 body 定界**完全不看状态码**;全文件 grep `204|304|1xx` **零命中**。本机夹具服务器实测:

| 请求 | 当前结果 |
|---|---|
| `204 No Content`(无 CL) | **ERR** |
| `204` + `Content-Length: 0` | OK |
| **`204` + `Content-Length: 5` + `hello`** | **OK —— 而且 body 读出了 `"hello"`** |
| `304 Not Modified` | **ERR** |
| `100 Continue` | **ERR** |

三者 ERR 原因逐字相同:`reason: response has neither Content-Length nor Connection: close — refusing to guess the body length (ADR-0028 D3)`。

⚠⚠ **实测暴露了比台账记的更隐蔽的偏差**:台账只记了「204 会 ERR」,而 **`/204cl5` 居然把 body 读了出来** —— RFC 9112 §6.3 第 1 条说这些响应**本就无 body(无论头里写了什么)**。⚠ **且 HEAD 响应同样适用** —— `HTTP_REQUEST("HEAD", url)` 是可达的(`net.rs:1200` 只校验 method 是合法 token)。

**建议**:**按完整语义做,不要分两批** —— 1xx ⇒ **跳过、继续读下一个响应**(否则 `103 Early Hints` 这类服务器会让客户端把中间响应当终响应);204/304/HEAD ⇒ 终响应、body 恒空、**忽略 `Content-Length`**。这是**可观察语义变更** ⇒ 属 **breaking**,须单独立项,立项前置件是**冻结现状测试** + 规范 **§21.4** 条款(⚠ 原写「§21.5 拒绝表」是**重写后失效的交叉引用** —— 重写前 §21.5 才是「`HTTP_*` 的形态」,重写后拒绝表在 **§21.4**、§21.5 成了「示例」)。⚠ **业主 2026-10-20 裁决「所有修复工作都必须在 v0.11.3 内,不顺延至下个版本」** ⇒ 本条**本批内完成**,且四条规则(1xx / 204 / 304 / HEAD)**一次做完**。

### 6.2 `D13-051` · `MOVE` 对文件型符号链接按内容展开 —— **建议「保持 + 成文」,不改成「原样重建」**

**现状**:`impl/crates/wlwl-std/src/fs.rs:685-722` 的 `move_path` **先试 `rename`**(成功即返回,链接原样保留),**只有跨设备失败**才走 `copy_tree`(`:751-798`),而 `copy_tree_body` 的核心是(`:791-795`)「`is_dir()` ⇒ 递归展开;否则 `std::fs::copy` ⇒ 跟随、拷目标内容」。

⚠⚠ **本机实测的同设备 / 跨设备对照(本条最硬的证据)**:

| MOVE 场景 | 走的代码 | 链接在目的地的结果 |
|---|---|---|
| D: → C:(跨设备) | `copy_tree` 回退 | **实体目录**(链接被按内容展开);外部哨兵 `outside\keep.txt` **仍在**(未被误删) |
| D: → D:(同设备) | `rename` | `LinkType=Junction`, `Attributes=Directory, ReparsePoint` ⇒ **链接原样保留** |

⇒ **同一个成员、同一份输入,链接语义随「源与目标是否同一设备」而变 —— 而任何一处规范文本都没写这件事。**

**建议**:**保持「按内容展开」,并把这个分裂写进规范**(与 `:282-284` 已有的半句并列)。理由:「原样重建」在 Windows 上没特权/开发者模式就**根本没有定义**(退化成展开或失败),而 `MOVE` 的结果**不应该取决于「这台机器能不能建符号链接」这种环境事实**;「跳过并报错」是功能倒退。⚠ **这仍是产品取舍,需要你一句确认**。

### 6.3 `D13-052` · `WRITE_BYTES` 无上限 —— **限 64 MiB**(已裁决落地)

**现状**:读侧 `fs.rs:827` `MAX_READ_BYTES = 1 MiB`(写死常量),**先量后读**;写侧 `fs.rs:883-906` 的 `write_bytes` **无任何长度判断**。**实测**:

```
WRITE_BYTES 写出 2 MiB → FILE_SIZE = 2097152
READ_BYTES 读它 → error[E0102]: ... READ_BYTES caps one read at 1048576 bytes
```

⇒ **`WRITE_BYTES` 写出的文件,`READ_BYTES` 读不回来。** 而 `WRITE_BYTES` 是本语言**唯一**能写出文件内容的成员(§2.3 成员表全表没有第二个)。

**建议**:**限 64 MiB** —— 依据是 `compress.rs:34` 的 `MAX_DECOMPRESSED = 64 MiB`,**仓内已声明**的「语言值字节数组」上限,**不另立数字**(照 `D13-021`「口径直接复用,不另立」的先例)。**不取 1 MiB**(那会删掉「写大文件」这个能力,且与 §2.3:296-298「大载荷待在文件里」自相矛盾);**不放更底层**(写路径的放大发生在**调用方构造 `ARRAY[INTEGER]`** 时)。⚠ **必须同时改规范**:`:269` 现在写着「本成员尚无上限……已登记待立项」—— 改代码不改这句,下一个人会照旧文案以为没上限。⚠ 残余必须成文:**任何 > 1 MiB 的写上限都无法建立「写出来的读得回来」**(该方向性契约只有把写上限压到 ≤ 1 MiB 才成立)⇒ 真正的修法是**流式写 / 分段读成员**;**本册不做** —— 记为**已知边界**(两个成员各自的策略上限),**不是待修缺陷**。

### 6.4 `N-029` · `ENV_SET` 到不了子进程 —— **建议维持不继承**

**现状**:`env.rs:18-37` 已有两份环境的对照表;`env.rs:110` 写 `ctx.env`,而 `process.rs:78-80` 的子进程环境**唯一**来源是 `for (k, v) in extra_env` ⇒ `ctx.env` **从不**被合并。**实测**:无 `opts.env` 时子进程里 `%VAR%` **原文未展开**;有 `opts.env` 时展开成功 ⇒ `opts.env` 通道有效。

**建议**:**维持不继承(A)**。理由三条:
1. **规范自己已经这么写了**:`stdlib-spec:1958` 的成员表行是**规范性**的「**仅本进程可见**」⇒ 改成继承不是「实现向规范靠拢」,而是**改规范**,且改的是成员表里最短、最醒目的一格。
2. `opts.env` 已经是那条通道,而且它**不依赖语句执行顺序**。
3. ⚠ **我要修正台账的一条论证**:`build-plan.md:463` 与 `stdlib-spec:1974-1976` 说继承会让子进程环境「取决于**语句执行顺序**」、与「可复现」冲突 —— **这一条其实不成立**:确定性程序的语句顺序是固定的,跨次运行仍可复现。**真正的反对理由是隐式状态** —— 子进程环境成了「此前 `ENV_SET` 次数」的函数,而本语言明写「显式值传递、无隐藏状态」(`stdlib-spec:2022-2025` 引 `ADR-0027` A1)。**结论不变,但理由应当换成这一条**,否则将来有人会用「我的程序是确定性的」把它辩过去。

⇒ 若你确实要 `ENV_SET` 影响子进程,**走「显式开关」(`PROCESS_RUN` 的 opts 加 `"inherit_env": TRUE`,默认 `FALSE`),不要走无条件继承**。

### 6.5 `N-024` / `N-026` 后续账 —— **一项不做、一项本批内做**

- **`by_start` 的 O(n) 缓冲**(`regex.rs:1090` / `:1143`,每起点 4 字节 ⇒ 把输入内存翻倍):**建议不做**。它**不改变渐近阶**(输入本就是 O(n)),换成哈希表只是把「稠密 O(1) 查表」换成「哈希 + 可能再哈希」,而 `slots` 已是 O(不同起点数) ⇒ **净收益为负**。`regex.rs:1136-1140` 的注释已把这件事写透(「**别把它当成「find_all 现在是 O(1) 内存」**」)。⇒ **只把这句话提升为规范条款**(§16 现在只承诺线性时间,没写内存形状),零风险。
- **`add` 里 `Split` 分支的 3 次克隆**(`regex.rs:1199` / `:1203` / `:1209`):**值得做,本批内做**(业主 2026-10-20 裁决「不顺延至下个版本」),手段固定为 `caps` 拆成「整体匹配对(零分配)+ 捕获槽位(`Rc<Vec<..>>`,写时复制)」+ `prio` 改内联 `[u8; 64]`(`PRIO_MAX = 64` 是编译期常量)。理由:这是仓内**自己写明的**「近处的路」(`benches/baseline.txt:626`),是把 1.64 MB/s 往 20 MB/s 推的**唯一近路**;「懒惰 DFA」是另一种架构。⚠ 它要动 `Thread` 的**表示**(波及 8–10 处构造点)⇒ 结构性重构,**本批内完成**。

### 6.6 `N-017` · CSS 转义绕过 —— **建议不降级,只补成文**

**现状**:`sanitize/css.rs:159-215` 已按「原文 ∪ 解码后的原文」扫描;契约 `sanitize_contract.rs:677-724` 钉了 **21 条 payload(19 条真绕过)+ 5 条不误拒**;规范 `:1509-1517` 已把这条**写成规范条款**。

### 10.3 C-3 `D13-052` —— `WRITE_BYTES` 限 **64 MiB**

| 项 | 结果 |
|---|---|
| 裁决 | 限 **64 MiB**;**不取 1 MiB**(会删掉「写大文件」这个能力,且与「大载荷待在文件里」自相矛盾) |
| 数值来源 | `MAX_WRITE_BYTES` **直接引用** `std.compress` 的 `MAX_DECOMPRESSED` —— **不另立数字**(照 `D13-021` 的做法:另立会让同一份输入在三个成员里得到三种接受集) |
| ⚠ 真正的风险点 | `std::fs::write` 会**截断**目标文件 ⇒ 上限**必须在落盘之前**判,否则「超限」的表现是「原文件被清空」而不是「原封不动」 |
| 守卫 | 判定逻辑用**参数化的 cap** 覆盖(判定表逐档 + 「原文件原封不动」);**上限值本身**另有一条守卫钉住它与 `MAX_DECOMPRESSED` 同值 |
| 契约 | `the_write_bytes_cap_is_written_down`(**哪儿都能跑**):规范里不许再写「本成员尚无上限」 |
| 规范 §2.2 | 增「**写得出 ≠ 读得回**」:`READ_BYTES` 一次只读 1 MiB ⇒ 大于 1 MiB 的文件写得出来、读不回来;**流式写 / 分段读成员本册不做**(记为**已知边界**,非缺陷) |
| 负向验证 | ① 守卫整个去掉 ⇒ `write_bytes_refuses_an_array_over_the_cap` **FAILED**;② 守卫挪到落盘之后 ⇒ 同一测试 **FAILED**,`left: [1, 1, 1, 1, 1]` vs `right: [79, 82, 73, 71, 73, 78, 65, 76]`(= `ORIGINAL` 被截断)⇒ **「原文件被清空」这个方向照不出来**那条教训被躲开;还原后全绿 |
