# 11 · `RESULT` 组合子(把 §8 的消费者名单变成可链的形态)

> **层级** L2 · **硬前置** 00(R0 治本)
> **状态** 🟡 **W-01 / W-02 已成文,2026-10-12** —— `ADR-0029`(已 Accepted,同日修订);**规范登记** 本批**不在** §14 清单里 —— 由本方案首次提出

## 0. 契约摘要

- **目标**:给 `OK` / `ERR` 一套**组合子**,让「先算一步、错了就提前退出、
  成功就继续」这类控制流不必每次都手写 `ERR_PAYLOAD` + 分支。
- **非目标**(违反即范围事故):
  - **不改 §8.2 的传播语义**。「非消费者拿到 `ERR` 就在调用边界抛出」这条
    是语言语义,组合子**不得**成为绕过它的后门。
  - **不新增 `OPTIONAL` 类型**。wlwl 用 `NULL` 表示「没有」,不引入 Rust 的
    `Option` —— 那需要语言层的「缺失」与「空」的区分,见 §3.2。
  - **不引入 `?` / `unwrap` 语法糖**(语言变更)。
  - **不把组合子做成宏**。它们是普通 `StdFn`,可被普通函数组合。
  - 不改 12 个 §8.3 消费者的**任何**一个(它们是语言面,不是标准库面)。
- **为什么值得做**:`std.encode` 的规范里已经写着调用方要用
  `AT_K(ERR_PAYLOAD(BASE64_DECODE(s)), "kind", "?")` 来查错误载荷 ——
  **每次都要这么写一遍**,说明缺一层组合。

## 2. 成员面

**命名空间裁决建议:新建 `std.result`,不塞进 `std.test`。**
理由:`std.test` 是测试面(6 成员,`TEST` / `ASSERT` / …),组合子是**生产代码**
的通用控制流工具。混在一起会让「测试专用」与「语言通用」两个性质不同的面
纠缠。

**层:R1 门面 or R2?** 组合子只在 `OK` / `ERR` 上做投影,**不构建新容器** ——
理论上 R1 可行。但 §0.2 的 R2 立场是「直通 `Value` 不经 `wrap()` / compat」,
而 `OK` / `ERR` 在 eval 侧有特殊表示 ⇒ 保留「R2」。

> ⚠ **[2026-10-12 实测推翻了这条,并于同日修订]** → `ADR-0029` D1。原因是两个实测结论:
> ① R2 `StdFn` **能**接闭包(`collection::kernel_map` 早就这么用),所以签名可以照 Rust / Scala 收函数值;
> ② **实参为 `ERR` ⇒ 该调用不求函数体**,`ERR` 直接成为调用结果。§8.3 明文「本表不新增条目」。
> 判据是**被调用者的名字字符串**(`dispatch_call` 里的 `is_err_consumer(name)`),而传播块位于
> `user_fn` 分派(R1 `Closure` 与 R2 `NativeFn` **都**在其后)**之前**
> ⇒ **R1 门面与 R2 内核同样接不到 `ERR` 实参**。
> ⚠ 前一版把这条写成「`ERR` 在调用边界变成 `E0102`」是**错的**:`E0102` 只在它浮到顶层时出现(§8.5)。

| 成员 | 层 | 语义要点 |
|---|---|---|
| ~~`IS_OK(v)`~~ | — | ⚠ **已是全局内建**(`IS_OK(x) -> BOOLEAN`),不复刷见 §4 |
| ~~`IS_ERR(v)`~~ | — | ⚠ **已是全局内建**(`IS_ERR(x) -> BOOLEAN`),不复刷见 §4 |
| `RESULT_MAP(r, f)` | R1 | `OK(x)` → `OK(f(x))`;`ERR` **原样透传**(不碰 `f`)。⚠ 原名 `MAP`,与 `std.collection::MAP` 硬撞 `E0021`,改名见 `ADR-0029` D5 |
| `AND_THEN(r, f)` | R1 | `OK(x)` → `f(x)`(可返回 `OK` **或** `ERR`);`ERR` 原样透传 |
| `FLATTEN(r)` | R1 | `OK(OK(x))` → `OK(x)`;`OK(ERR(e))` → `ERR(e)` |
| ~~`UNWRAP_OR(r, default)`~~ | — | ⚠ **已是全局内建**,不复制见 §4 |
| ~~`UNWRAP(r)`~~ | — | ⚠ **已是全局内建**(`E0100` 专用码),不复制见 §4 |
| ~~`OR_ELSE(r, fallback)`~~ | ❌ | **不可实现** —— `ERR` 分支要调 `fallback`,而体不执行。惯用法见规范 §22.3 |
| ~~`ERR_MAP(r, f)`~~ | ❌ | **不可实现**,同上 |
| ~~`ERR_OR_ELSE(r, e)`~~ | ❌ | **不可实现**,同上 |
| `RESULT_ALL(rs)` | **R2** | 全部 `OK` → `OK(解包后的数组)`;任一 `ERR` → **第一个** `ERR`(短路);空数组 → `OK([])` |
| `RESULT_ANY(rs)` | **R2** | 任一 `OK` → **第一个** `OK`(原样不拆壳,短路);全 `ERR` → **第一个** `ERR`;空数组 → `OK(NULL)` |
| `NULL_OR(v, default)` | R1 | `NULL` → `default`。**明确不是 `UNWRAP_OR`** —— `NULL` 不是 `ERR`;`ERR` 实参按 §8.2 原样返还 |

> ⚠ **前三条的 `ERR` 分支不在成员体内执行** —— §8.2 保证体不执行,而「原样返还」恰好
> 就是这三条在 `ERR` 上应有的行为,所以 `ERR` 分支是**免费的**。详见规范 §22.2。
> ⚠ **W-04 实测另翻两面**:① §8.2 那堵墙对**容器里的 `ERR` 元素同样成立**
> ——`ANY(rs, FUN((x), IS_ERR(x)))` 与 `MAP(rs, FUN((x), x))` 都得 `E0102`,
> 因为逐元素调用本身就是一次带 `ERR` 实参的调用;② 但成员**收数组**(数组不是
> `ERR`)时整个数组原样到达,可以逐个读 `Value::Err` 而**全程不调任何闭包**,
> 所以 `RESULT_ALL` / `RESULT_ANY` **可实现**,且**刻意不接受谓词参数**。
> ③ 这两个**归 R2**:它们要把 n 个载荷收成新数组,而 R1 累加链实测每翻一倍约 ×3
> (n=250→4000:27→765 ms)。`NULL_OR` 不建数组,留 R1。详见 `ADR-0029` D7 / D8。

## 3. 语义裁决点(开写前必须逐条回答)

1. **命名空间归属**(§2)。新建 `std.result` vs 塞进 `std.collection`。
   > ✅ **[2026-10-12 已裁决 → `ADR-0029` D2]** —— **新建 `std.result`。**组合子是**生产代码**的通用控制流工具,与 `std.test`(测试面)性质不同;塞进 `std.collection` 则让那一篇文档同时讲两件事。

2. **`OPTIONAL` 要不要?** §0 非目标说「不引入」。但组合子族一旦成型,
   `NULL` 的「可能没有值」与「空字符串 / 空数组」在 `MAP` 一族里就撞上了。
   → 裁决:本份**只做 `RESULT`**,`NULL` 侧只给 `NULL_OR` 一个最小成员;
   「要不要 `OPTIONAL`」单独立项(它需要语言层区分「缺失」与「空」)。
   > ✅ **[2026-10-12 已裁决 → `ADR-0029` D1/D3]** —— **实测把这一条翻了两面**:
   > ① R2 `StdFn` **能**接闭包(`collection::kernel_map` 早就这么用),所以成员签名可以照 Rust / Scala 收函数值;
   > ② 但**实参为 `ERR` ⇒ 调用不求函数体**(§8.2),`ERR` 直接成为调用结果;判据是**被调用者的名字**,
   > 且 §8.3 明文「本表不新增条目」⇒ **§2 写的「层:R2 全员」全员不成立**,R1 门面**同样**接不到;
   > ③ 三条 `ERR` 分支为「原样透传」的成员(`RESULT_MAP` / `AND_THEN` / `FLATTEN`)**碰巧是对的** ——
   > §8.2 免费提供了「原样返还」。⚠ 但这是**空证的反面**:探针里计数器没涨是因为**体压根没执行**,
   > 不是因为 `IF` 短路。真正证明 `IF` 短路的是另一条探针(else 支调用计数 = 0)。
   > ④ 剩下三条(`OR_ELSE` / `ERR_MAP` / `ERR_OR_ELSE`)**不可实现**,改写为调用方惯用法(规范 §22.3)。
   > ↳ 项目 6 的「若接不了闭包……」这条疑虑**已排除**;真正的新疑虑是**性能**(见下方 Consequences)。

3. **`MAP(r, f)` 收什么形态的 `f`?** wlwl 能不能传函数值?
   (§15 提到 OOP 的 `CALL_METHOD`,语言有闭包 `FUN`。) → 需确认 `StdFn`
   能不能接闭包 —— 若不能,组合子必须写成 R1 形态(调用点展开)。
   > ✅ **[2026-10-12 问题不存在]** —— `UNWRAP` **已是全局内建**,签名就写着
   > `UNWRAP(x) -> v / E0100 (不可捕获)`(`registry.rs:489`)。计划担心的「不能复用 `E0102`」早已做到:专用码就是 `E0100`。
   > ↳ 本条从「待裁决」移出,不需要新诊断码。

4. **`UNWRAP` 失败用什么诊断?** 建议 `E00xx` 专用码(如 `E00xx: UNWRAP on
   ERR`)。**不能复用 `E0102`**(那是「ERR 逃逸到顶」)—— 两者含义不同,
   混用会让调用方分不出「我没接住」和「我没消费」。
   > ✅ **[2026-10-12 已裁决 → `ADR-0029` D3/D6]** —— **R1 形态下不构成旁路,但理由要改**:
   > 组合子**接不到**非消费者拿到的 `ERR`(§8.2 + §8.3「不新增条目」)⇒ 它**没有能力**消费
   > 注册表外的 `ERR` ⇒ **不可能**成为旁路。这比「只是 `IS_ERR` 的语法展开」强得多。
   > ⚠ **相反**:要让成员真的接住 `ERR`,只能扩 §8.3 注册表(规范明文不新增,属语言层变更),
   > 或者把 `ERR` 藏进容器走私 —— 后者违反 §8.2 推论与 §8.5「装盛不是消费」,**不做**。

5. **§8.2 传播会不会被绕过?**(§0 非目标第 1 条)关键:组合子**必须**接收
   非消费者拿到的 `ERR` 吗?—— 建议**必须**,否则 `MAP` 就成了 §8.2 的旁路,
   整条消费者注册制度就漏了。**这条要有专门用例。**
   > ✅ **[2026-10-12 已裁决 → `ADR-0029` D6]** —— **计划这条要求不成立,方向反了。**
   > 计划要求「组合子**必须**能接非消费者拿到的 `ERR`,且接了不得抛 `E0102`」。
   > 实测:**组合子接不到** —— 实参为 `ERR` 时调用不求函数体,`ERR` 直接成为调用结果。
   > ⇒ 「接了就不得抛 `E0102`」自动成立(它连函数体都没进),但「必须能接」**做不到**。
   > ⇒ §0 非目标第 1 条(不改 §8.2 传播语义)因此**被满足**,而不是被违反。
   > ⚠ 契约测试把这条钉成**反向断言**:「组合子接不到 `ERR` 实参」+「§8.3 注册表未新增条目」。

6. **`RESULT_ALL` 遇到 `ERR` 时要不要把其余结果也求值完?** 短路还是全部求值
   —— 求值顺序与副作用(例如 `ASK` 这类有副作用的成员)有关。→ 裁决短路。
   > ✅ **[2026-10-12 已裁决]** —— 返回**第一个** `ERR`。注意实参都是**已求值**的值
   > (wlwl 无惰性),短路只能由调用方把副作用放在 `f` 里;契约表固定的是「返回第一个 `ERR`」这个可观察语义。

## 6. 风险与已知代价

- ✅ ~~⚠️ **组合子可能成为 §8.2 的旁路**~~ —— **已消解(裁决 §3.5 / `ADR-0029` D6)**:
  实参为 `ERR` 时调用不求函数体,组合子**接不到**非消费者拿到的 `ERR` ⇒ **没有能力**
  消费注册表外的 `ERR` ⇒ 不可能是旁路。契约测试改钉**反向断言**(传播块位置 /
  注册表无条目 / 闭包体副作用计数为 0)。
- ✅ ~~⚠️ **`MAP` 收什么形态的 `f`**~~ —— **已消解(裁决 §3.3)**:`collection::kernel_map`
  证明闭包可传。
- ⚠️ **成员面 6 缩到 3 又加回 3,净 6 条**:`OR_ELSE` / `ERR_MAP` / `ERR_OR_ELSE`
  不可实现(W-02 裁决),W-04 再加回 `NULL_OR` / `RESULT_ALL` / `RESULT_ANY`。
  代价:「错了就兜底」这一族**没有库成员**,只有规范 §22.3 的三行惯用法 —— 这是
  §8.2 推论的必然结果,不是实现偷懒,但**必须在 skill 里写清楚**,否则用户会去找不存在的成员。
- ✅ ~~⚠️ **W-04 三条尚未实测**~~ —— **已实测并落地**(见 §7 W-04 行)。要点:
  `NULL_OR` 遇 `ERR` 按 §8.2 **传播**而非返回 `default`(这是对的:`NULL_OR` 不是
  `UNWRAP_OR`,拿默认值吞错误才是错的);`NULL` / `""` / `[]` 三者互不相等,
  且语言**没有 `IS_NULL`**,判别器只能写 `==(TYPE(v), "NULL")`。
- ⚠️ **`UNWRAP` 会炸**。它必须**显眼**(名字 + 文档 + 专用诊断 `E0100`),
  且 skill 反模式要写「生产路径不用 `UNWRAP`」。
- **明确不做**:`OPTIONAL` 类型 / `?` 语法糖 / 宏 / 改 §8.3 消费者 / 改 §8.2 传播语义 /
  扩 ERR 消费者登记册 / **容器装盛 `ERR` 走私**。
