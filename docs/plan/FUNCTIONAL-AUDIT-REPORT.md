## 1. 结论摘要

标准库的**功能面整体健全**：214 个注册成员全部被用例触达，RFC 向量、冻结随机向量、精确十进制/分数、时序响应定界、净化幂等等高风险契约逐条对齐，工具链 25 项检查全绿。

但审计发现 **1 项 P1、3 项 P2、3 项 P3 功能缺陷**，以及 **4 项 P3 文档一致性问题**。其中最需要处理的是：

> **F-01（P1）**：`std.io::PRINT` / `PRINT_ERR` 的**容器渲染与全局内建 `PRINT` 不一致**，且未在规范中登记。同一份程序只要加一行 `IMPORT("wlwl:std.io", ["PRINT"])`，数组/字典/`RESULT` 的输出形态就整体改变（`[1, 2, 3]` → `[1,2,3]`，`[a: 1]` → `{"a":1}`，`OK(1)` → `1`）。这与 stdlib §1「与全局内建同名同语义」的冻结声明直接冲突，且**静默无诊断**。仓库自带的 `examples/showcase.wll` 正是这样导入的。

**（业主复核）** 上述结论全部复现。F-01 另补两点第三方未给的事实：① 根因是 `std.io` 仍走 `wrap` 的 **serde_json 中间表示**（全局内建走 `Value::display()`），这是 **ADR-0022 尚未落地**在六个 R2 模块上的直接后果；② 随包示例实测输出为 `round-trip: {"name":"wlwl","ok":true}` —— **JSON 风格 + 小写 `true`**，与语言规范 §2.5 的 `TRUE`/`FALSE` 口径相反。

## 2. 审计方法与判定纪律

### 2.1 第三方审计的纪律

1. **黑盒**：只通过 `wlwl.exe` 的 CLI 行为判定；审计过程不读取实现源码，`stdlib/*.wll` 作为**被测对象**而非可读材料，成员契约一律以规范为准。
2. **期望值来源**：正向用例的期望值**手写自规范**（RFC 4648/4231 公开向量、规范示例、冻结向量），**不从实现输出反推**。凡规范未钉死处（如 JSON token 的 `text` 语义），只断言规范确实规定的那部分。
3. **交叉核对**：哈希 / KDF / 压缩类成员用**独立实现**（Python `hashlib` / `hmac` / `argon2-cffi` / `zlib` / `gzip`）产出的向量核对，验证「按标准实现」而非「只会解开自己写的东西」。
4. **偏差隔离**：凡实测与规范不符者，一律不修改期望值去迁就实现；正向用例保留规范期望（失败即失败），另建 `dev/` 偏差基线固化实测行为，两者并存。
5. **沙箱**：文件系统用例的 CWD 固定在 `audit/tmp`，每次套件运行前清空，避免残留状态污染判定。
6. **诊断码口径**：反向用例断言的是**规范指派的诊断码**，不是实现实际吐出的码——这正是 F-03 被判为缺陷的依据。

### 2.2 业主复核的纪律

1. **判现象仍用黑盒**：每条复核先写最小复现 `.wll`，用本仓 release 二进制跑，**只看 stdout / stderr / 退出码**；读源码只发生在「现象已复现」之后，用于定位根因与给出修复落点。
2. **定性看条文，不看直觉**：每条都回到规范的**具体行**，核对「规范到底钉死了什么」。
   复核推翻的三条定性（F-04 / F-05 / F-06）**全部源于此**——它们的现象都成立，但规范在那一点上**没写字**，把「没写」当「违规范」就会把一处文档缺口错派成实现缺陷。
3. **不改期望值迁就实现**：与第三方同口径。修复方案一律指向「让实现回到规范」，规范确需改的（§4.1 已有的 FORMAT 两路径体例）单独标出并说明理由。
4. **修复方案必须落到 `file:line`**：只写「改一下实现」不算方案。
5. **先读已有的裁决再提方案**：ADR-0022 / ADR-0025 / 历史档里已登记的约束（尤其「已推迟立项」类）必须被采信，否则会把旧账当新账。

## 3. 缺陷清单

### F-01（P1）`std.io::PRINT` / `PRINT_ERR` 的渲染与全局内建不一致，且未登记

- **规范依据**
  - stdlib §1：「与全局内建**同名同语义**的三个成员（冻结例外，见 §0.8；语义以语言规范 §10.2 为准）」
  - 语言规范 §2.5：「`PRINT` 与 `STR` 将值渲染为文本：布尔为 `TRUE`/`FALSE`，空为 `NULL`，**数组为 `[e1, e2, ...]`，字典为 `[k: v, ...]`**」
  - stdlib §4.1 仅登记了**一处**刻意差异（`FORMAT` 对 `RESULT` 的渲染），未涉及 `std.io`。
- **现象**

  | 值 | 全局内建 `PRINT` | `std.io::PRINT` |
  |---|---|---|
  | `[1, 2, 3]` | `[1, 2, 3]` | `[1,2,3]` |
  | `["a": 1, "b": "x"]` | `[a: 1, b: x]` | `{"a":1,"b":"x"}` |
  | `OK(1)` | `OK(1)` | `1` |
  | `["b": 1, "a": 2]` | `[b: 1, a: 2]` | `{"a":2,"b":1}`（键序亦被改写为字典序） |
  | `PRINT_ERR` | — | 同样走 JSON 风格 |

  补充实测：同族的 `std.format::FORMAT` 对容器的渲染**与全局一致**（`[1, 2, 3]` / `[a: 1]`），说明差异出在 `std.io` 的渲染路径，而非「std 边界统一用 JSON」这一策略。
- **复现**

  ```
  // t.wll
  IMPORT("wlwl:std.io", ["PRINT"]);
  PRINT([1, 2, 3]);
  ```
  `wlwl.exe run t.wll` → `[1,2,3]`；删掉该 `IMPORT` 后同一程序 → `[1, 2, 3]`。
- **影响**：静默改变输出格式，任何依赖容器文本输出的程序在「加不加这行 IMPORT」之间行为不同；仓库自带示例 `examples/showcase.wll` 即导入 `std.io::PRINT`。
- **建议**：二选一 —— (a) 让 `std.io::PRINT` 复用 eval 侧渲染（与 §2.5 一致）；(b) 若 JSON 风格是刻意选择，则在 §1 写明，并把 `std.io` 排除出「同名同语义」的冻结声明。**不建议**维持现状（既违规范，又未登记）。

#### 复核（业主，2026-10-20）

**结论：✅ 成立。现象逐字复现，定性（P1 实现缺陷）准确。** 补出根因、架构依据与影响实证，并把建议收敛到唯一一支。

**1）复现（本仓 HEAD release 二进制）**

| 程序 | 输出 |
|---|---|
| `IMPORT("wlwl:std.io", ["PRINT"]); PRINT([1,2,3]);` | `[1,2,3]` |
| `PRINT([1,2,3]);` | `[1, 2, 3]` |
| `IMPORT("wlwl:std.io", ["PRINT"]); PRINT(["a":1,"b":"x"]);` | `{"a":1,"b":"x"}` |
| `PRINT(["a":1,"b":"x"]);` | `[a: 1, b: x]` |
| `IMPORT("wlwl:std.io", ["PRINT"]); PRINT(["b":1,"a":2]);` | `{"a":2,"b":1}`（**键序被改写为字典序**） |
| `PRINT(["b":1,"a":2]);` | `[b: 1, a: 2]` |

**2）规范依据核对 —— 原文比第三方报告引的更强**

- stdlib §1 成员表 `PRINT` 行的语义列**逐字**写着：「依序渲染实参(**语言规范 §2.5**),以空格分隔输出到标准输出」。
  ⇒ **规范不是「默认同名同语义」，而是点名引用了 §2.5** ⇒ 容器渲染必须与 §2.5 一致，这不是解释权问题。
- ⚠ **§0.8「冻结例外」的措辞要消歧**（第三方未展开，易被后续读者误读为语义豁免）：§0.8 原文是
  「**新增命名空间不得重导出全局内建同名成员**（既有 `std.io` / `std.format` 冻结为例外,不扩充）」
  ⇒ 豁免的是「**可以重导出**」这件事，**不是**「语义可以不同」。§1 表格点名 §2.5 就是反证。

**3）根因（第三方未给，复核定位）**

| 路径 | 渲染实现 | 落点 |
|---|---|---|
| 全局内建 `PRINT` | `args.iter().map(v => v.display())` | `impl/crates/wlwl-eval/src/lib.rs:1278` |
| `std.io::PRINT` | `crate::wrap` → `Value → serde_json::Value` → `json_to_print_string` → serde_json 默认 `Display` | `impl/crates/wlwl-std/src/lib.rs:563` / `impl/crates/wlwl-std/src/io.rs:87` |

serde_json 落底额外带来**三个**可观察差异，正好对上表中的三行差异：

1. **紧凑分隔符** ⇒ `[1,2,3]`；
2. `serde_json::Map` 是 **BTreeMap**（本仓未开 `preserve_order`，见 `impl/Cargo.toml:46`）⇒ **字典键序被改写为字典序**（`{"a":2,"b":1}`）；
3. JSON **无 `RESULT` 变体** ⇒ `Value::Ok(v)` 在 `values_to_json` 里被摊平成载荷 `v`（`impl/crates/wlwl-std/src/json.rs:494`）⇒ `OK(1)` → `1`。

**4）⚠ 实现自带的单测把偏离锁死了（第三方未提）**

`impl/crates/wlwl-std/src/io.rs:148` 的 `print_formatting_matches_builtin()`：

- 注释写：「The std PRINT and the builtin PRINT **must agree** on null/boolean/array/dict formatting **so the user does not see a behaviour shift after IMPORT**」；
- 断言写：`assert_eq!(json_to_print_string(&arr), "[1,2]")` ⇒ **断言的是 JSON 风格**。

⇒ **注释与断言互相矛盾**：测试**名字与意图**说「必须一致」，**断言**却把不一致锁成契约。这是这道缺陷能长期存在的直接原因。

**5）架构依据（第三方未提，修复方案的锚）**

- ADR-0022（Accepted 2026-10-01）Decision 4/5：「**跨界类型只有 `Value`**：原生实现内部用什么中间表示是实现自由……但**边界上不再有任何转换层**」；「`lib.rs:11-17` 的『std 边界拒绝闭包值』契约**废止**」；Consequences：「**函数值可过界**,回调型原生 API 可表达」。
- 但 `impl/crates/wlwl-std/src/compat.rs:3-6` 自述：io / fs / json / format / ai / agent **六个模块**的函数体仍以 serde_json 为中间表示，由 `lib.rs` 的 `wrap` 统一转换。
- ⇒ **ADR-0022 对这六个模块尚未落地；F-01 是其直接可观察后果**（`std.format` 之所以对得上，正是因为它已走直通路径）。

**6）影响实证（第三方只举了示例文件名，复核给出实际输出）**

`impl/examples/showcase.wll` 第 15 行导入 `std.io::PRINT`、第 38 行打印 `PARSE` 出来的字典，实测输出：

```

round-trip: {"name":"wlwl","ok":true}
```

⇒ 随包示例输出的是 **JSON 风格 + 小写 `true`**，而语言规范 §2.5 的显示口径是 `TRUE`/`FALSE`、字典是 `[k: v]`。

**7）第三方补充论点的复核：✅ 成立**

### F-02（P2）`JSON_CHECK` 的 `type` 不接受多值数组

### F-03（P2）`WRITE_FILE` 写失败报 `E0061` 而非 `E0062`，且消息误导

- **规范依据**
  - stdlib §2.0：「`WRITE_FILE(path, text) -> NULL` | 写 UTF-8 文本；父目录必须已存在 | **写失败 → `E0062`**（原生诊断）」
  - 语言规范 §11.2：「`E0061` | 文件 | **文件不存在**」
- **现象**：向不存在的目录写入时——

  ```
  error[E0061]: WRITE_FILE: file not found (audit_no_such_dir/x.txt): 系统找不到指定的路径。 (os error 3)
  ```
  实为**写失败**，却用了「文件不存在」的码，消息也写成 "file not found"。
- **影响**：按码分流（`E0061`=读不存在 / `E0062`=写失败）的调用方会误判故障类别；`READ_FILE` 的 `E0061` 语义被污染，无法区分「读不到」与「写不进」。
- **建议**：`WRITE_FILE` 失败路径改用 `E0062`，消息区分「父目录不存在 / 写入失败」。

#### 复核（业主，2026-10-20）

**结论：✅ 成立，现象与定性均准确。** 根因定位到**共用映射函数**；并补出一处第三方未提、**不改就会留下新不一致**的问题：`E0062` 在错误注册表里的语义与 stdlib §2.0 对不上。

- **复现**：`WRITE_FILE("audit_no_such_dir/x.txt", "hello")` → `error[E0061]: WRITE_FILE: file not found (audit_no_such_dir/x.txt): 系统找不到指定的路径。 (os error 3)` ✅
- **规范核对**：三处互相印证 ✅
  - stdlib §2.0 表：`WRITE_FILE` … **写失败 → `E0062`**（原生诊断）；
  - stdlib §2.3：「v0.3 的三个原生成员（`READ_FILE` / `WRITE_FILE` / `EXISTS`）用**原生诊断**口径（终止运行，**`E0060`–`E0062`**），它们**冻结不许动**」；
  - 语言规范 §11.2：「`E0061` | 文件 | 文件不存在」。
- **根因（第三方未给）**：`impl/crates/wlwl-std/src/fs.rs:67` 的 `io_error_to_std` 是 `READ_FILE` 与 `WRITE_FILE` **共用**的映射：

  ```rust

      let (code, label) = match e.kind() {
          ErrorKind::NotFound => (ErrorCode::E0061, "file not found"),
          ErrorKind::PermissionDenied => (ErrorCode::E0062, "permission denied"),
          _ => (ErrorCode::E0060, "I/O error"),
      };
  ```

  ⇒ 父目录不存在在**写侧**同样落进 `ErrorKind::NotFound` ⇒ 写失败被标成「文件不存在」。

- ⚠ **附带发现（第三方未提，必须一并修）**：`E0062` 在错误注册表的语义注释是「**file permission denied**」（`impl/crates/wlwl-error/src/lib.rs:125`），而 stdlib §2.0 把它定义为「**写失败**」。
  ⇒ **两册对同一个码的口径不一致**。只改 `fs.rs` 不改这里，**改完仍然对不上**（下一次还会有人按「权限不足专用码」去理解它）。

#### 修复方案（业主补）

1. **实现** —— `impl/crates/wlwl-std/src/fs.rs`：把 `io_error_to_std` 拆成两个入口：
   - `read_io_error`：`NotFound → E0061`、`PermissionDenied → E0062`、其余 `→ E0060`（**读侧行为一字不变**）；
   - `write_io_error`：**任何写失败一律 `E0062`**，消息按 kind 区分「父目录不存在 / 权限不足 / 其他写失败」。
2. **消息建议**：`WRITE_FILE: cannot write (path): parent directory does not exist` / `WRITE_FILE: cannot write (path): permission denied` / `WRITE_FILE: cannot write (path): <os error>`。
3. **错误码语义对齐（必做）**：`impl/crates/wlwl-error/src/lib.rs:125` 的 `E0062` 注释改为「写侧失败（父目录不存在 / 权限不足 / 其他）」，与 stdlib §2.0 一致；若 `impl/crates/wlwl-error/src/snapshots/wlwl_error__tests__codes_io.snap` 随之变化，一并重录。
4. **规范侧**：stdlib §2.0 / §2.3 补一句「`E0062` = **写侧失败**（**含父目录不存在**）」，避免下次又被当成「权限不足专用码」。
5. **契约测试**：
   - `WRITE_FILE` 写向不存在的父目录 ⇒ 断言 **`E0062`** 且消息含「parent directory」；

### F-04（P2）`ASK_STREAM` 的 `callback` 形参无法传入闭包

- **规范依据**：stdlib §9：「`ASK_STREAM(model, prompt, callback, opts?) -> STRING` | **流式推理**（实现侧当前整收集为单块，返回整段文本）」
- **现象**：
  - `ASK_STREAM("gpt-4", "hello", FUN((chunk), TRUE))` → `error[E0030]: std argument: expected json-representable value, got function`
  - `ASK_STREAM("gpt-4", "hello", NULL)` → 可用，输出 `[mock-stream:gpt-4] echo (h=0x4f9f2cab) :: hello`
- **影响**：规范记载的调用形态不可用 ⇒ **流式回调契约不可达**；该成员实际只能走「整收集为单块」的退化路径，成员表里的 `callback` 形参无对应实现。
- **建议**：std 边界放行 `FUNCTION` 实参（或把 `callback` 收进 `opts` 字典）；若当前形态确为「不支持回调」，应在 §9 写明「`callback` 形参保留、当前不接受函数值」。

#### 复核（业主，2026-10-20）

**结论：⚠ 现象成立，但定性修正为 P3（文档缺口），不是 P2 实现缺陷。** 根因是**早已登记的架构约束**，第三方把它当成新缺陷会误导下一批的排期。

- **复现**：两条均 ✅ —— 传闭包 → `error[E0030]: std argument: expected json-representable value, got function`；传 `NULL` → `[mock-stream:gpt-4] echo (h=0x4f9f2cab) :: hello`。
- **根因（第三方未给）**：`crate::wrap` 的 `values_to_json` 在**进成员体之前**做 `Value → serde_json::Value` 转换，函数值不可 JSON 表示 ⇒ 直接被拒（`impl/crates/wlwl-std/src/json.rs:503`：`other => return Err(bad("json-representable value", type_name(other)))`）。
- ⚠ **定性修正的依据 —— 这是已登记的架构约束，不是新缺陷**：
  - ADR-0022 Context 段逐字写着：「serde_json::Value 装不下 `FUNCTION` / `TASK` / `CHANNEL` / `CLASS` / `INSTANCE` —— **函数值过不了界**，回调型 API（排序键、断言体、**流式回调**）在原生侧无法表达」；

  - ⇒ **现象成立、但不是新缺陷**；**定级 P2 → P3（文档缺口）**。
  - ⇒ 第三方「流式回调契约不可达」的判断在事实上成立，但**把它记成 P2 实现缺陷，等于把一条已排期项（P4-D1b-001）重新开成新缺陷**。

#### 修复方案（业主补）

**本批只做文档。**

1. stdlib §9 表 `ASK_STREAM` 行的**失败列**补：「`callback` 当前只接受 `NULL`（传函数值 → `E0030`）；真流式回调形态见 §9.2」。

### F-05（P3）`MODE` 对 INTEGER 数组返回 FLOAT

- **规范依据**：stdlib §7.5：「`MODE(arr) -> v` | **出现次数最多的值**」；同节「混装静默提升：`ARRAY[INTEGER]` 与 `ARRAY[FLOAT]` 混装不报 `E0030`，与既有 `SUM` 同口径」——即**纯** INTEGER 数组不应被提升。对照 `std.collection::SUM([1,2,3])` 保持 INTEGER。
- **现象**：`MODE([1, 1, 2])` → `1.0`（`TYPE` 为 `FLOAT`）；`MODE([1.0,1.0,2.0])` → `FLOAT`（一致）。由于 §2.4 规定 `==(1, 1.0)` 为 `TRUE`，**数值本身正确**，只有 `TYPE` 可见差异。
- **影响**：低。仅在按 `TYPE` 分支或做类型标注序列化时可见。
- **建议**：与 `SUM` 对齐，纯 INTEGER 输入返回 INTEGER 元素。

#### 复核（业主，2026-10-20）

**结论：⚠ 现象成立，但不是违规范 —— 应定性为「规范缺口 + 与同族 `SUM` 的类型口径不一致」。** P3 维持。第三方那条「即**纯** INTEGER 数组不应被提升」是**从条文推出的推论，不是条文本身**。

- **复现**：`MODE([1,1,2])` → `1.0` / `TYPE` = `FLOAT`；`MODE([1.0,1.0,2.0])` → `FLOAT`；`SUM([1,2,3])` → `6` / `INTEGER`；`==(1, 1.0)` → `TRUE`。四項均 ✅。
- ⚠ **规范到底钉死了什么（逐字）**：
  - stdlib §7.5 表：`MODE(arr) -> v` | **出现次数最多的值**；**并列取先出现者**；全部只出现一次 ⇒ 无众数 | `[]` → `NULL`
    ⇒ 返回类型写作 `v`（泛型），**只钉死了「取哪个值」，没有钉死元素的静态类型**。
  - 同节「混装静默提升」句：约束的是 `INTEGER` 与 `FLOAT` **混装**时的行为，**没有**说纯 INTEGER 数组的返回类型。
  - **对照两兄弟**：`MEDIAN` 的同节条目**明写**「偶数长度取中间两个的平均（**走 `f64`**,整数 `/` 会截断）」⇒ `MEDIAN` 返 `FLOAT` 是**规范授权**的；
    `SUM` 的条目（stdlib §5）写「求和 / 求积；**整数 / 浮点按语言规范 §2.2 提升**」⇒ §2.2 下整数加整数仍是整数 ⇒ `SUM` 返 `INTEGER` **有规范推导链**；
    `MODE` **没有**这条推导链 ⇒ **规范在 `MODE` 与 `MEDIAN` / `SUM` 之间是不对称的**。
  - ⇒ 结论：把「规范没写」当成「实现违规范」，会把一处**规范缺口**错派成实现缺陷。
- **根因（第三方未给）**：`impl/crates/wlwl-std/src/stats.rs` 的整族统计走 `f64` —— `series()`（stats.rs:42-58）把 `Value::Integer(i)` 直接转成 `f64`（非数值元素报 `E0030`「element must be INTEGER or FLOAT」），**原始 `Value` 的类型在这一步就丢了**；`mode` 最终 `Ok(Outcome::normal(Value::Float(x)))`（stats.rs:191）⇒ **返回类型由内核表示决定，与输入类型无关**。

#### 修复方案（业主补）

**先定规范，再改实现 —— 两步都要，且第一步是语义裁决。**

1. **规范先行**（stdlib §7.5）：给 `MODE` 补一句类型口径。
   **建议口径**：「**返回数组中那个元素的原值**（原样保留其静态类型）」——与条目的字面「出现次数最多的值」一致，也与 `MEDIAN` 明写的「走 `f64`」形成对照，把两兄弟的不对称消掉。⚠ 这是**语义裁决**，需业主拍板（见 §9 裁决清单）。
2. **实现**（裁决为「返回原值」后）：`impl/crates/wlwl-std/src/stats.rs::mode` 定出胜出元素后**回查原数组**取其 `Value` 原样返回（而不是返回 `f64` 转换结果）。
   - **不必动桶结构**：`buckets` 里已经存着**首次出现的下标** `i`（stats.rs:163 `buckets.insert(mode_key(x), (i, x, 1))`）⇒ 按 `i` 回查原数组即可。
   - ⚠ **但混装必须按 §2.2 提升**：若输入里只要有**一个** `FLOAT`，返回值就取 `FLOAT` 形态。**否则 `[1, 1.0]` 会返回 `INTEGER` 的 `1`**，与 §2.2「混装提升为浮点」相悖。
   - ⇒ 结果：纯 `INTEGER` 数组返 `INTEGER`、纯 `FLOAT` 数组返 `FLOAT`、混装按 §2.2 返 `FLOAT`。
3. **契约测试**：`MODE([1,1,2])` → `1` / `INTEGER`；`MODE([1.0,1.0,2.0])` → `1.0` / `FLOAT`；`MODE([1,1.0])` → 混装口径（按裁决）；`MODE([])` → `NULL`；`MODE([1,2])` → 全只出现一次 ⇒ `NULL`；`MODE([2,1,2,1])` → 并列取先出现者 `2`。
4. ⚠ **连带检查（必须做，防止顺手扩大）**：`MEDIAN` / `VARIANCE_*` / `STDDEV_*` 同样由 f64 内核产生返回类型。
   - `MEDIAN` 规范已明写「走 `f64`」⇒ **保持 FLOAT**，不动；
   - 方差 / 标准差按定义就是实数 ⇒ **保持 FLOAT**，不动；
   - ⇒ **本批只动 `MODE`**。
5. **若业主裁定「保持现状（返 FLOAT）」**：则**改规范** —— §7.5 给 `MODE` 补「返回值走 `f64`（与 `MEDIAN` 同口径）」，并把「与 `SUM` 的返回类型不一致」登记为**已知限制**（同 D13-011 的体例）。
   ⇒ **两条路都行，但必须选一条并写进规范** —— 现状是「规范没写、实现也没说」，这才是最坏的状态。

### F-06（P3）`LIST_DIR` 与 `WALK_DIR` 的返回路径形状不一致，且规范未钉死前者

- **规范依据**：stdlib §2.2：`LIST_DIR(p)` 只写「列目录（不递归），**结果排序**」；`WALK_DIR(p, pattern?, follow?)` 写「递归，返回**相对 `p`** 的路径（用 `/`），**排序**」——只有 `WALK_DIR` 的形状被钉死。
- **现象**（实测基线 `dev/d02`）：

  ```
  LIST_DIR("fs_shape/a")  →  ["fs_shape/a/b"]          # 带输入路径前缀
  WALK_DIR("fs_shape")     →  ["a", "a/b"]              # 相对输入路径，且含目录条目
  ```
- **影响**：两个兄弟成员坐标系不同，`LIST_DIR` 的结果不能当「目录内条目名」直接用（与 `WALK_DIR` 的结果也无法直接比较）；属易错面。
- **建议**：在 §2.2 明确 `LIST_DIR` 的形状（建议：与 `WALK_DIR` 同为相对 `p`），并明确是否包含目录条目。

#### 复核（业主，2026-10-20）

**结论：⚠ 现象成立，定性是「文档缺口」而非实现缺陷；且第三方建议的方向要改 —— 本复核建议「钉文档，不改实现」。**

- **复现**：`LIST_DIR("fs_shape/a")` → `["fs_shape/a/b"]`；`WALK_DIR("fs_shape")` → `["a", "a/b"]` ✅（与第三方 `dev/d02` 基线一致）。
- **规范核对**：§2.2 `LIST_DIR(p)` 条目**只**写「列目录(不递归),**结果排序**」⇒ 形状**未钉死** ✅；`WALK_DIR` 明写「返回**相对 `p`** 的路径(用 `/`)」✅。
- **根因（第三方未给）**：`impl/crates/wlwl-std/src/fs.rs:374` 的 `out.push(spec(&e.path()))` 推的是**输入路径 + 条目名**的完整路径；`walk_dir` 推的是相对 root 的路径。⇒ 确系两套坐标系。
- ⚠ **建议修正**：第三方建议「与 `WALK_DIR` 同为相对 `p`」。
  **本复核建议相反：先钉文档，不改实现。** 理由：改 `LIST_DIR` 的返回形状是**改变可观察语义**的 breaking 变更（虽为 v0.11.3 新成员、尚未冻结），会把已写的调用方全部打断；而规范**现在缺的恰恰是形状定义** —— 缺的是文档，不是实现。

#### 修复方案（业主补）

**推荐路线：钉文档（不改实现）。**

1. **规范**（stdlib §2.2 `LIST_DIR` 条目）补全三件事：
   - 返回「**以 `p` 为前缀的完整路径**（用 `/`）」；
   - 「**含目录条目本身**」；
   - 「**排序**」（已有）；
   并补一句对齐提示：「⚠ 与 `WALK_DIR` 的**相对路径坐标系不同** —— 跨成员比较前先归一（`LIST_DIR` 的每项去掉 `p` 前缀即得相对路径）」。
2. **附录 A 镜像不变**（成员面未动）。
3. **契约测试（把现状钉住，防将来无声漂移）**：`LIST_DIR` 返回的**每项都以 `p` + `/` 开头**、**已排序**、**含子目录条目**；`WALK_DIR` 返回的**每项都不以 `p` 开头**、用 `/`。
4. **备选路线（不推荐）**：若业主要求两兄弟坐标系统一 ⇒ 改 `LIST_DIR` 为相对 `p`，走 §0.8 四件套 + CHANGELOG 标 **breaking** + 本册 §2.2 条目要改。**本复核不推荐**，理由如上。

### F-07（P3）「did you mean」提示的候选顺序逐次不同（非确定性诊断文本）

- **现象**：同一文件 `PRINT(NOPE);` 连跑 8 次，hint 的**候选集合恒为** `{TYPE, POP, SCOPE, NOT}`，但**排列 8 次全不相同**：

  ```
  POP, SCOPE, NOT  /  TYPE, SCOPE, POP  /  NOT, POP, TYPE  /  NOT, SCOPE, POP
  POP, NOT, TYPE   /  TYPE, NOT, SCOPE  /  SCOPE, NOT, POP /  NOT, TYPE, POP
  ```
- **影响**：诊断文本不确定 ⇒ 逐字节比对 stderr 的门禁会随机红；与本语言「可复现」的第一卖点相悖（不影响程序语义，但影响工具链）。语言规范 §11.1 未对 hint 排序作规定，故不判为违规范。
- **建议**：候选排序改为确定性（按名称字典序或距离 + 字典序）。

#### 复核（业主，2026-10-20）

**结论：✅ 成立，但第三方报告有一处事实错误：候选「集合」并不恒定 —— 变的不是排列，是「选哪几个」也在变。** 影响面比第三方写的大一档。**并建议把优先级提到 P2。**

- **复现**（本机 8 次，顺序与集合**都**变）：

  | 次 | 候选 |
  |---|---|
  | 1 | `POP, SCOPE, TYPE` |
  | 2 | `SCOPE, POP, TYPE` |
  | 3 | `TYPE, POP, NOT` |
  | 4 | `NOT, TYPE, SCOPE` |
  | 5 | `SCOPE, TYPE, POP` |
  | 6 | `POP, NOT, SCOPE` |
  | 7 | `POP, NOT, TYPE` |
  | 8 | `NOT, SCOPE, POP` |

  ⇒ **集合在四种不同子集之间跳变**（`{POP,SCOPE,TYPE}` / `{TYPE,POP,NOT}` / `{NOT,TYPE,SCOPE}` / `{POP,NOT,SCOPE}`）。
  ⇒ **恒定的只是「最多 3 个候选」这个数量上限**，**不是集合**。第三方报告写的「候选集合恒为 `{TYPE, POP, SCOPE, NOT}`」**与实测不符** ⇒ 本条影响面比报告写的大一档：不仅排列随机，**选哪几个**也随机。
- **根因（第三方未给）**：`impl/crates/wlwl-eval/src/lib.rs:81` 的 `similar_names` 遍历候选池 `HashSet<String>`（Rust `HashSet` 的迭代序**每进程随机**）⇒ `scored` 的初始序随机；`scored.sort_by_key(|(d, _)| *d)`（lib.rs:10099）是**稳定排序**，同距离项保持随机初始序；随后 `scored.truncate(max)`（lib.rs:10100）⇒ **既随机化「选哪 3 个」，也随机化「这 3 个的排列」**。
- **规范核对**：语言规范 §11.1 未对 hint 排序作规定 ⇒ **不判违规范**（第三方这点正确）✅

#### 修复方案（业主补）

1. **实现** —— `impl/crates/wlwl-eval/src/lib.rs::similar_names` 改为**全序**：按 `(编辑距离, 名字字典序)` 排序，**再** `truncate(max)`。
   ⚠ 排序键**必须含名字**（把 `sort_by_key(|(d, _)| *d)` 换成按 `(d, n)` 元组比较的 `sort_by`）—— 否则同距离项之间仍是随机序。
   ⚠ `truncate` 保持在**全序之后** ⇒ 集合也随之确定。
2. **不必**把候选池从 `HashSet` 换成 `BTreeSet`：全序后 HashSet 的随机迭代序已不影响结果，而换掉会给每次诊断引入 O(n log n) 开销。
3. **契约测试**：对同一未定义名**重复产生诊断 ≥ 50 次**，断言 hint 字符串**逐字节相同**。
   ⚠ 这条测试是这道缺陷能长期潜伏的直接原因 —— 现有单测（`wlwl-eval/src/lib.rs:15897` 的 `p3_008_undefined_name_suggests_similar`）只断言「**有** hint」，不断言「hint **稳定**」。
4. **规范侧（可选）**：语言规范 §11.1 补一句「`E0020` 的候选提示按 **(编辑距离, 名字字典序)** 排序」——把确定性写进规范，避免将来有人再改成随机序。
5. **优先级建议：P3 → P2**。理由：它会让**任何逐字节比对 stderr 的门禁随机红**，而本仓的契约机制（stdlib §0.8 的四件套、ADR-0025 的基准守卫、各 crate 的 insta 快照）**正是靠逐字节冻结**建立的；一道随机诊断文本会直接污染那套机制。修复面则只有**一处排序键**。

## 5. 规范已声明的「尖角」复核（不判为缺陷，但调用方须知）

这些行为**符合规范文本**，只是设计上偏尖：

- **§8.5（非末条语句的 `ERR` 被静默丢弃）**：语句位置的 `ERR` 值只有「是最后一条语句」时才走 `E0102` 顶层逃逸，否则**无任何诊断地丢弃**。规范已把它写成「已知限制」。本审计的多条用例必须改写为 `IS_ERR` / `ERR_PAYLOAD` 消费后才能观察到错误。
- **§8.3（`==` / `!=` 对 `ERR` 是「透传而非消费」）**：因此 `==(OK(1), ERR("e"))` 不会得到 `FALSE`，而是把 `ERR` 透传出来——「OK 与 ERR 永不相等」这条只能通过 `IS_ERR` 观察。
- **§4.1（`FORMAT` 的两条路径刻意不同）**：全局 `FORMAT("{0}", OK(1))` → `OK(1)`；`std.format::FORMAT` 同参 → `1`。规范明文登记，实测一致。
- **§0.9（release 构建无条件忽略 `WLWL_STD_SRC`）**：实测确认——环境变量被忽略（`--std-src` 显式 flag 生效），与「debug 门控 / release 无条件忽略」一致。
- **`std.rand` 显式播种 + 抽签返回 `[值, 新状态]`**：`DICT` 不可变，若只返标量则状态永不前进。实测冻结向量 `SEED("fixed-seed")` → `INT_RANGE` 两次得 `15 99`，与规范 §17.2 一致。
- **`std.net` 明文 HTTP only、不跟随重定向、拒绝歧义框架**：实测全部符合（见 §6）。

### 复核（业主，2026-10-20）

**抽查 4 条，全部符合规范文本 ⇒ 「不判为缺陷」的判断成立。** 抽查项与结果：

| 条款 | 抽查方式 | 结果 |
|---|---|---|
| §8.5 | `LET(x, ERR("e")); PRINT("reached-end");` | ✅ 输出 `reached-end`，**退出码 0**，无任何诊断 ⇒ 确实静默丢弃 |
| §8.3 | `PRINT(==(OK(1), ERR("e")));` | ✅ `error[E0102]: unhandled ERR escaped to top level: e` ⇒ **透传而非返回 `FALSE`** |
| §4.1 | 全局 `FORMAT("{0}", OK(1))` vs `std.format::FORMAT("{0}", OK(1))` | ✅ `OK(1)` vs `1`，与 §4.1 明文登记逐字一致 |
| §0.9 | 置 `WLWL_STD_SRC` 后跑 release 二进制 | ✅ 环境变量被忽略，程序正常执行（退出码 0） |

其余两条（`std.rand` 冻结向量、`std.net` 行为族）**未抽查**（需要独立实现交叉核对，本轮未做）⇒ 维持第三方结论，不作独立背书。

## 10. 本批落地状态（2026-10-20 实施）

11 条**全部落地**：**5 条 breaking 行为变更 + 1 条确定性修复 + 5 条纯文档条目**（规范文本修订:标准库规范 **8** 处 + 语言规范 **2** 处 + **4** 册 ADR）。实施方式 = **多 agent 并行**（按**文件级互不重叠**切分，6 个实施 agent + 2 个文档 agent 分两波）。

### 10.1 行为变更（5 条 breaking + 1 条修复）与各自的**负向验证**

| 项 | 改了什么 | 负向验证（把实现改回缺陷形态，确认守卫**会红**） |
|---|---|---|
| **F-01** | `std.io` 整模块移出 `wrap` 的 serde_json 中间表示，渲染走 `Value::display()`（**与全局内建同一个函数**） | 改回紧凑分隔符 ⇒ crate 内 3 条 + 进程级 2 条**全红** |
