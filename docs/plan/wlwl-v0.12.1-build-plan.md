## 0 本文档的契约

### 0.1 这份文档是什么 / 不是什么

**是**：一份**逐条裁决台账**——需求清单的每一条都落到「做 / 不做 / 归谁」，每条工作项自带验收命令与证伪命令，执行者不需要回头翻需求清单。

**不是**：① 不是需求清单的复述；② 不是「全部照做」的许诺——60 条里有 **19 条当场判为不做或改判**（§4）；③ 不是规范文本——规范侧要改的条款在 §5 列成**待写条款**，由规范仓 v1.0.4 批次执行。

### 0.2 状态标记（全文统一）

| 标记 | 含义 |
|---|---|
| **已实测** | 本轮用 `wlwl.exe`（`impl/target/release/wlwl.exe`，v0.12.0 `980b0ca` 构建）跑出来的读数，附复现命令 |
| **已核实** | 读过规范／源码原文得出的事实，附 `文件:行号` |
| **待裁决** | 需要业主拍板才能施工，**不阻塞**其它工作项 |
| **推导** | 由已实测／已核实的事实推出，**未单独实测** |

⚠ **每条「已实测」的结论都带一条可重跑的命令**——命令红了以命令为准。

### 0.3 怎么读、怎么改

- **执行者**（agent）：从 §3 的批次表进；每个工作项的「验收」是**可粘贴的命令**，「反向守卫」是**改回去必须变红**的验证。
- **业主**：§4 是「不做什么」的清单（**这是本轮最需要您确认的部分**），§6 是「要您拍板的 4 件事」。
- **改本文档**：新增工作项**追加**到对应批次末尾并给它编号；**不要**重排既有编号（§7 的台账按编号引用）。

### 0.4 交付形态（收口时必须齐三件）

1. 实现仓：`impl/` 侧全部工作项落地 + 门禁全绿；

## 1 结论摘要

### 1.1 一句话结论

> **60 条需求里，真正要动规则侧的只有 3 处**，其余 57 条要么是实现侧闭环、要么**当场判为不做**；而这 3 处**没有一条是「新增能力」**——全是**规范自相矛盾或规范与实现事实不符**，因此**落在一致性册 §3.4 例外 2（规范缺陷修复）之内**，**不构成破坏性变更**，**可以做成 v1.0.4（修订版本）而不是 v1.1.0**。

### 1.2 「规则侧改动」的最终账

| # | 需求 | 规则侧要改什么 | 性质 | 版本落点 |
|---|---|---|---|---|
| **S-1** | **B-1**（嵌套闭包挂起点静默死亡） | 并发册 §17.0 的 E0014 条款**扩到「嵌套闭包内」**；语言册 §11.2 的 E0014 触发条件**与之对齐**（现状两处**互相矛盾**） | **例外 2**（规范缺陷修复：并发册已说「指名该成员」，语言册却说 E0014「只」用于 YIELD） | v1.0.4 |
| **S-2** | **B-2**（多 acceptor 语义未定义） | 并发册 §17.0 / 系统册 §21.6 **补一条 accept 的并发语义**（单 acceptor 独占 vs 竞争） | **例外 2**（规范文本缺口：现状「唤醒全部等待者 + 落选者拿 NULL」在规范里**无任何条款覆盖**） | v1.0.4 |
| **S-3** | **D-1**（正则编译缓存） | 文本册 §16 的**实现注**说「参考实现每次调用都重新编译」——把这条**从实现注升为规范性要求**（或反向：明确「模式对象可安全缓存复用」） | **例外 3**（勘误：现状是实现事实与规范意图不符，且**不引入新的自由度**——缓存是纯实现细节） | v1.0.4 |

⚠ **这 3 处都不新增成员、不新增诊断码、不改既有成员的可观察语义** ⇒ **附录 A 表体不动** ⇒ 附录 A 逐字对拍门禁（CI `check-appendix-a`）不受影响 ⇒ **实现侧不需要「追镜像」**。

### 1.4 三个最重要的裁决（为什么与需求清单预期不同）

**① A 组（TLS）——本轮判为「不做」，但不是拒绝，是「前提不成立」。**
需求清单把 A-1/A-2 列为 P0 阻塞项。核实后：TLS **必须**破 `ADR-0028 D3` + `ADR-0022` 的**零新增第三方依赖**纪律（规范册 §21.1 / §21.8 四处明写「不做 TLS」「零新增第三方依赖」），而 `rustls` 这类实现是**数千行、需持续跟 CVE** 的外部代码。**在 v0.12.1 这一个版本里引入它，是拿「一个版本的交付确定性」换「一个 P0 清单项」**——不划算。**替代路径本轮就交付**：把 TLS 做成**应用层可插拔**（§3 批次 C），TinyPage 用外部 TLS 终结器（nginx / caddy / 隧道）跑 wlwl 明文后端——这本来就是规范的原设计（系统册 §21.1「调用方自备隧道 / 反代」）。

**② 需求清单说「零新增规则侧改动」，但实测发现规范内部**已经有两处矛盾**。**
B-1 的规范条款（并发册 §17.0）要求 E0014「**指名该成员**」，而语言册 §11.2 写「E0014 在并发下**只**用于一个位置：`YIELD` 在任务体外」。**两处正面矛盾**——实现按前者做（v0.12.0 已改文案），语言册那行就是过时的。**这不是「新增能力」，是「规范自己跟自己打架」** ⇒ 例外 2 修掉，成本极低。

**③ 需求清单有 8 条的事实前提已被 v0.12.0 改写**（H-1 修好了、H-2/H-3 有全局内建、B-6 已由 §17.9 覆盖）。**照单全收会做无用功**——例如 H-1「IF 第三实参不支持多语句组」实测**已正常**，再排一个批次就是白干。

## 4 明确不做 / 改判清单（**本轮最需要业主确认的部分**）

### 4.1 A 组 TLS —— 本轮不做（**建议**）

**事实**：
- 规范册四处明写「不做 TLS」（系统册 `:681` `:683` `:750` `:779`），安全册 `:306` 明写「对称/非对称加密不做」；
- `ADR-0028 D3` + `ADR-0022` 的**零新增第三方依赖**纪律（N-8）；
- 实现侧**默认构建里没有任何 TLS 栈**——`rustls 0.23.46` / `ring 0.17.14` **只在 `real-ai` feature 下**通过 `reqwest` 传递进来（`impl/crates/wlwl-std/Cargo.toml:37`）；
- `deny.toml` 已登记 4 条 rustls advisory 的豁免（`:72-75`）——说明这条依赖链**已经在门禁里带着已知风险**。

**我的判断**：TLS **不是「实现一个功能」，是「引入一条需要长期跟 CVE 的外部依赖 + 破一条 ADR 纪律」**。仓内已有破例先例（`addendum-07` 引 `zstd`/`flate2` 时做过显式裁决），但那是**纯压缩库**——TLS 的攻击面与维护成本高一档。

**替代路径（本轮就交付）**：wlwl 后端**只监听明文**，由外部终结器（nginx / caddy / 云 LB）终止 TLS 并回源。**这本来就是规范的原设计**（系统册 §21.1「调用方自备隧道 / 反代」）。TinyPage 的「单进程双端口 + 自带 TLS」形态 ⇒ 改成「wlwl 双端口 + 反代双端口」。

**如果业主要 TLS**，那它是一个**独立立项**（不是 v0.12.1 的一个批次），需要：① 破零依赖纪律的 ADR 裁决；② `std.tls` 或 `std.net` 扩成员的**附录 A 变更**（⇒ 触发 N-1 的「新成员」路径 ⇒ 版本落点重算）；③ `rustls` 升版本 + advisory 门禁重跑。

### 4.2 B-3 / B-4 / B-5 —— 受 `ADR-0017` Step 3 阻塞，本轮不做

**事实**：`docs/active/addendum-12-sync-primitives.md` §0.1（2026-10-07 实测）已把这条写死——「段重跑」架构下，「抢不到要挂起、醒来要越过阻塞点继续」的成员**不成立**（唤醒时从段首重来 ⇒ 阻塞点前的用户代码**再执行一遍**）。`ADR-0017` Step 3 的实测规模：`runtime.rs` **2411 行**（ADR 估 718 ⇒ **3.4 倍**），`lib.rs` **27242 行**不在 ADR 的文件清单里。

⇒ **W-03 / W-04 / W-05 移出 v0.12.1 硬路径**，登记为路线图项（§6 Q2/Q3）。

### 4.3 B-6 —— 不做（**规范已覆盖且实现正确**）

R-7 实测：任务失败被 `AWAIT` ⇒ 调用点重抛（`E0100`，退出码 1）；无人 `AWAIT` ⇒ stderr 写一行报告，退出码仍 0 ⇒ **完全符合并发册 §17.9**（N-14）。

⚠ 需求清单描述的「`AWAIT` 返回 NULL 无法区分」是 **B-1 的下游症状**（任务被静默杀掉 ⇒ 终值是 NULL）——**修好 W-01，B-6 自动消失**，不需要单独做。

### 4.4 I 组 —— 排期口径（本轮只答复，不实现）

| ID | 答复 |
|---|---|
| I-1 HTTP/2 | **不在规划内**。HTTP/2 的多路复用依赖「一条连接上并发多个流」——与「单线程协作调度 + 段重跑」的架构直接冲突。**建议**：HTTP/1.1 + 多连接（Keep-Alive）足够 |
| I-2 WebSocket | **不在 v0.12.x 规划内**。管理端实时预览可先用 SSE 或长轮询（`HTTP_*` 已有 `timeout` 预算机制） |

| I-4 brotli | **不排期**。`std.compress` 已有 zstd/gzip/zlib/raw deflate；brotli 的收益是「比 gzip 小 20%」，对一个静态站点生成器**不构成瓶颈** |

## 6 需要业主拍板的 4 件事

> 每条给出**我的倾向**与**理由**，可否决。

### Q1（**最需要您拍板**）TLS（A 组）本轮不做，走「外部 TLS 终结器 + wlwl 明文后端」

**我的倾向**：**本轮不做 TLS**。

**理由**：① 它不是功能，是「引入需长期跟 CVE 的外部依赖 + 破 ADR-0028/0022 纪律」，代价被需求清单低估；② 规范**本来就设计成**「调用方自备隧道 / 反代」；③ TinyPage 的「自带 TLS」形态可平移成「反代形态」，迁移成本落在部署侧而非语言侧。

**若您否决**，TLS 就是一个**独立立项**（不是 v0.12.1 的一个批次），且会连带触发附录 A 变更 ⇒ 版本落点从 v1.0.4 变 v1.1.0。

### Q2 B-3 / B-4 / B-5（共享状态 / 可推进循环 / 非阻塞出站）移出 v0.12.1

**我的倾向**：**移出**，登记路线图。

**理由**：`ADR-0017` Step 3 的实测规模（`runtime.rs` 2411 行、`lib.rs` 27242 行）远超 ADR 的估算（718 行），它是**独立立项**的量级；`addendum-12` 已因它受阻一年多。**塞进 v0.12.1 会让本批的交付确定性崩掉**。

**注**：这三条是需求清单里的 P0，但它们**不阻塞** TinyPage 迁移——清单 §0.2 已实测跑通一个纯 wlwl 的 HTTP 服务（8 并发全 200），用的就是「单 acceptor + 展开链」这个 workaround。

### Q3 规范版本落点：v1.0.4（修订）还是 v1.1.0（次版本）？

**我的倾向**：**v1.0.4**。

**理由**：本批三处都是**规范缺陷修复/勘误**（N-5 例外 2/3），**不新增成员、不新增诊断码、不改既有成员的可观察语义** ⇒ 附录 A 不动 ⇒ 不构成「新增能力」⇒ 按 N-2 走修订版本（条件满足：§0.9 有登记行 + 发布说明显式列出）。

**何时该用 v1.1.0**：若 Q1 被否决（做 TLS ⇒ 新增成员）⇒ **必须**升 v1.1.0（N-3）。

### Q4 批次 C 的落地形态：应用层库 vs 新增规范成员

**我的倾向**：**应用层库**（不进 `std.*`，不碰附录 A）。

**理由**：系统册 §21.6.5（N-16）明写「原生层只搬字节……HTTP 的解析与响应构造是**调用方**的事」⇒ HTTP 协议层本来就该在 WLWL 代码里；而 `std.net` 扩成员的代价是**附录 A 变更 + 逐字对拍门禁 + 规范成员表逐册同步**（N-7）——收益仅是「别人也能 import」。

**⚠ 代价要说清**：这意味着 **W-10…W-21 这些原语不在标准库里**——TinyPage 要**自己写一遍**（或我们把这份实现**作为参考实现**交给 TinyPage）。**这是本计划里最需要您确认的取舍**：wlwl 侧「提供标准库成员」vs 「提供参考实现 + 保持规范冻结」。
