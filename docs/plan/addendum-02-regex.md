# 02 · RE2 式线性正则(零第三方依赖手写)

> **层级** L1(可并行) · **前置** 无 · **被依赖** 无
> **状态** 未动工 · **已有调研** v0.11.3 计划附录 B(本份不重造结论)

## 0. 契约摘要

- **目标**:给 wlwl 第一条模式匹配能力,且**执行时间对输入线性**。
- **非目标**(违反即范围事故):
  - **不做回溯引用** `(?P=…)` / **不做 lookahead / lookbehind** —— 与线性时间
    **互斥**,不是「以后再加」。
  - **不做 PCRE 兼容**,不做「兼容某个方言」的承诺。
  - 不做 Unicode 字素簇语义(沿 `std.str` 的**码点**坐标系,与 `CHAR_AT` /
    `INDEX_OF` 一致)。
  - 不做反向正则(不匹配「不含 X」)、不做零宽断言。
  - **不加捕获组回填数组**语义之外的命名组支持(命名组可做,但要走裁决点)。
- **为什么排 L1**:主流 stdlib **全员标配**(Go `regexp` / Python `re` /
  JS 字面量 / Java `regex` / C++ `<regex>`),而 wlwl **零模式匹配能力** ——
  校验类需求(邮箱 / URL / 词法模式)现在无处落脚。这是「功能清单里唯一的
  全员标配空白」。

## 2. 成员面

**层:R2 全员**(NFA 模拟的每步都要分配状态集,R1 的解释器层会二次收费)。

| 成员 | 层 | 语义要点 |
|---|---|---|
| `RE(pattern)` | R2 | 编译成模式对象。**语法错 → 原生诊断 `E0030` 带行列**,不是 `ERR` 值(与 `HTML_SANITIZE` 的「永不因内容失败」同族,但**编译期**失败是另一回事) |
| `RE_TEST(re, s)` | R2 | 整串是否**完全**匹配(锚定) |
| `RE_SEARCH(re, s)` | R2 | 找**第一个**子串匹配,返 `NULL` 或 `["matched": …, "start": …, "end": …]` |
| `RE_FIND_ALL(re, s)` | R2 | 全部非重叠匹配,返 `ARRAY` |
| `RE_REPLACE(re, s, repl)` | R2 | 替换;`repl` 里 `$1` / `${name}` 引用捕获组 |
| `RE_SPLIT(re, s)` | R2 | 按匹配切分 |
| `RE_GROUP_COUNT(re)` | R2 | 捕获组个数(供调用方在解码侧索引,免得每个成员各返回一种形状) |

**统一的返回值形状**(与 `ERR` 消费者的 `RESULT` 家族无关,本族是**普通
`OK` 值**):所有 `RE_*` 返回**成功值或 `NULL`**,唯一的原生诊断是
`E0030`(元数 / 类型 / 模式编译错)。理由:正则不匹配是**正常的**业务分支,
不是错误 —— 把它做成 `ERR` 会逼调用方到处 `ERR_PAYLOAD`。

## 3. 语义裁决点(开写前必须逐条回答)

1. **编译期 vs 运行期的失败分界**:`RE("(")` 是 `E0030` 中止,还是返回一个
   「编译失败的模式对象」?→ 建议**前者**(`E0030` 中止),因为模式串通常是
   字面量,编译失败是**程序员的错**不是数据的问题。但若模式来自用户输入,
   调用方需要能「试编译不中止」⇒ 可能需要一个 `TRY_RE` 变体。**裁决**。
2. **左最长 vs 最早匹配**:RE2 的语义是**左最长**(不是 POSIX 的左most-
   earliest 也不是 PCRE 的贪婪回溯)。wlwl 必须明确选一个并写进规范 ——
   这是会改变可观察结果的语义差异,不是实现细节。
3. **空匹配的推进规则**:`RE_FIND_ALL("a*", "bab")` 会不会无限循环?
   规则必须写死(RE2 的做法:空匹配处停在原位,`FIND_ALL` 特殊处理)。
4. **大小写不敏感**:`(?i)` 内联标志做不做?若做,它与 `std.text` 的 Unicode
   简单大小写是不是同一套?(注意:ASCII-only 与 Unicode 折叠**结果不同**,
   这正是 `std.text` 存在的原因。)
5. **`.` 匹配什么**:码点全集?排除换行?`(?s)` / `(?m)` 标志?→ 锚点
   `^` / `$` 在多行模式下的语义必须明写。
6. **Unicode 类别**:`\p{L}` / `\w` 之类的类别要不要?**若要,又是 UCD 数据
   问题** ⇒ 与 03 共用生成器输入与「不做半张表」裁决(全局 G2)。
   → 建议**本批不做** `\p{…}`,`\w` 明确定义为 ASCII。

契约表 `tests/regex_contract.rs`(新),**期望值取自 RE2 官方测试语料与 POSIX
规范,不是实现输出**:

| 组 | 用例 | 备注 |
|---|---|---|
| 语法 | 字符类 / 量词 / 分组 / 交替 / 锚点 逐条 | 取自 RE2 语法表的最小用例 |
| 语义 | 左最长、`$` / `^` 在多行下、空匹配推进 | 逐条裁决点对齐 |
| 负例 | 回溯引用 / lookahead 写进去 → `E0030` | **必须拒**,否则线性承诺破 |
| **复杂度** | 病态输入(`(a*)*b` 之类经典指数爆炸模式)在 10 000 字符上 **≤ 50 ms** | **这条是本成员存在的理由**,必须钉 |
| 性能 | 10 KB 语料 ≥ 20 MB/s | 新基准,入 `baseline.txt` L1 段 |
| 确定性 | 同输入跑两次,匹配序列逐字节相同 | 本语言卖点 |

> 复杂度那条**不能省**。没有它,一个回溯引擎也能让常规用例全绿 —— 而那正是
> 本成员明确不做的形态。

## 6. 风险与已知代价

- ⚠️ **量级** ≳ `HTML_SANITIZE`(附录 B 的原判)。而 `HTML_SANITIZE` 实际做到
  远超预估(七道缺陷、四道静默)。**按 `HTML_SANITIZE` 的实际耗时重估排期**,
  不要按附录 B 的旧估。
- ⚠️ **左最长语义一旦定死就不可改**(改它 = breaking)。裁决点 §3.2 必须在写
  第一行代码前定。
- ⚠️ 若最终支持 `\p{…}`,就引入 UCD 数据依赖 ⇒ **必须与 03 共用生成器**,
  且要定 Unicode 版本(全局 G1)。建议本批**不做**(§3.6)。
- **明确不做**:回溯 / lookahead / lookbehind / PCRE 兼容 / Unicode 类别 /
  反向正则 / 零宽断言 / 字素簇。
