## 0. 契约摘要

- **目标**:给 wlwl 第一条时间能力,并把「测超时不用真等」做成**语言级形态**
  而不是各家测试框架里的一个 helper。
- **非目标**(违反即范围事故):
  - **不做时区数据库**(tzdata / IANA zoneinfo)。理由与实体表同款:半张时区表
    比没有更糟(跨 DST 边界算错,且没有任何报错)。见 §3.1。
  - **不做日历 / 日期算术的 R1 实现**。日历成员一律 R2,理由见 §3.2。
  - 不做夏令时推断、不做 `CRON` 表达式(那是调度器,不是时间)。
  - 不改语言的挂起语义(§17 真挂起是 v0.9 既有形态,本份只接入不改写)。
- **为什么排 L1 第一**:wlwl 现在**写不出任何带超时/定时/时间戳的程序**。
  `SCOPE` / `STEP` / `SPAWN` / 真挂起是 v0.9 的能力,却没有任何时间源可挂 ——
  这是「并发做完了、时间没做」的典型半截状态。

## 2. 成员面

**层:R2 全员**(时间必然要宿主时钟,R1 拿不到)。

| 成员 | 层 | 语义要点 | 失败口径 |
|---|---|---|---|
| `NOW()` | R2 | 墙钟。**不保证单调**,会被 NTP 调整;测「经过多久」一律用 `MONOTONIC` | 永不失败 |
| `MONOTONIC()` | R2 | 单调钟,只在进程内有意义(重启归零);**不受墙钟调整影响** | 永不失败 |
| `SINCE(t)` | R2 | 从 `t` 到现在经过的秒数(f64)。**实测的差值走这个,不走 `NOW` 相减** | 永不失败 |
| `SLEEP(d)` | R2 | 挂起当前任务 `d` 秒。**在假时钟 bubble 内瞬时完成** | `d < 0` → `E0030` |
| `TIMEOUT(d, body)` | R2 | 跑 `body`,超过 `d` 秒则放弃并抛错。生产代码与测试**同一个函数** | — |
| `TEST_BUBBLE(body)` | R2 | 在**气泡**内跑 `body`:时间走假时钟,气泡内全部任务阻塞时时钟瞬时前进。生产路径与测试路径**同一份实现** | — |
| `ADVANCE(d)` | R2 | 仅气泡内有效:把假时钟拨快 `d` 秒,并唤醒到期的等待者 | 非气泡内 → `E0030` |
| `WAIT_BLOCKED()` | R2 | 等到**当前气泡内所有任务都阻塞**为止。对应 Go `synctest.Wait` | 非气泡内 → `E0030` |

**失败的统一口径**:`SLEEP` / `ADVANCE` / `WAIT_BLOCKED` 的误用是**元数 / 类型 /
上下文错**三类原生诊断(`E0022` / `E0030`),**不是** `ERR` 值 —— 理由同
`std.encode`:把「参数写错」和「运行期结果不好」混成一个 kind,调用方就没法分。

## 3. 语义裁决点(开写前必须逐条回答)

1. **时间戳的数据形状**:`NOW()` 返回什么?`STRING`(ISO-8601)?`DICT`?
   自定义 `DATETIME`?wlwl 的类型系统很小(`INTEGER` / `FLOAT` / `STRING` /
   `ARRAY` / `DICT` / `BOOLEAN` / `NULL` / `OK` / `ERR` / 8.3 消费者)——
   **新增一个内建类型是语言变更**,不是标准库扩张。→ 建议先用 `FLOAT`
   (Unix 秒)或 `STRING`,把「要不要 `DATETIME` 类型」单独立项。
2. **假时钟的实现落点**:它需要 eval 侧提供一个「可替换的时间源 + 阻塞检测
   钩子」。这是**宿主 / 调度器**的改动,不是 `wlwl-std` 一个 crate 能关起门
   做完的。→ 必须在开工前确认落点(eval 侧 `StdHost` 扩展?还是全局内建?),
   否则会做成「只能在 `std.test` 里用」的半形态。
   ⚠️ **[2026-10-06]** 已逐个查过三个候选各自要动谁、代价多大,并定位了
   调度器侧必须改的那一处(`scheduler_run_until_idle` 现在分不出「全阻塞」与
   「没事做」)⇒ 答案见 **§3.6(b) 与 §3.6(c)**,**待业主在甲 / 乙之间拍板**。
3. **`TIMEOUT` 的失败形态**:超时是 `ERR([kind: Timeout])` 还是原生 `E00xx`?
   建议 **`ERR` 值**(它是可预期的运行期结果,调用方多半要处理它)——
   但这与 `std.test` 现有的 `EXPECT_ERR` 体例要对齐。
4. **`TEST_BUBBLE` 放 `std.time` 还是 `std.test`?** 它只在测试里有意义。
   建议**放 `std.time`**(与 Go 一致:气泡是时间形态,不是测试形态),
   `std.test` 不新增成员。
5. **与 `STEP` 的关系**:`STEP` 是确定性调度(§17),气泡是虚拟时间。两者组合
   会不会让「确定性」这个卖点变得不可测?→ 需要一条组合用例钉住。
   ⚠️ **[2026-10-06 实测更正]本题前提不成立** —— `STEP` **不存在**(附录 G /
   语言规范 / 实现都没有,详见 §3.6(a))。改问「气泡与 `SCOPE` 嵌套的关系」,
   建议见 §3.6(d)5。

#### (b) 落点三候选的代价(逐个查过“谁要动”)

- **候选甲 · `StdHost` 加方法**(例如 `fn clock(&mut self) -> &mut dyn Clock`)。
  证据:`StdHost` 当前**只有** `ctx` / `call` / `diag` 三个方法(已核),加一个要动
  **仓里每一个实现者**(eval 侧 host + `wlwl-std` 的测试 host + 可能的外部实现者)。
  **语义最干净**:气泡与时钟是**宿主能力**,不是「一次调用的参数」。
- **候选乙 · `StdCtx` 加字段**。证据:`host.ctx()` **已经存在**,所以这条路
  **不需要改任何 trait**,只要往 `StdCtx` 加一个时钟字段。ADR-0024 §4 说
  「气泡机制在调度器(R0)开一个小口,由 R2 成员消费」—— 这条路正是那个「小口」。
  **代价**:虚拟时钟这个**调度器概念**进了 `StdCtx`,而它当前的定位是
  `argv` / `env` / 工作目录 / 测试注册表。
- **候选丙 · 全局内建**(与 `PRINT` / `LEN` 同表)。**不推荐**:那样 `std.time`
  就不成其为命名空间(违反 ADR-0023 的命名空间纪律),「成员面 +N」的记账也落空。

> ✅ **[2026-10-06 业主定:气泡(B 阶段)取候选甲。]** 且**第一批成员(A1 / A2)根本不需要
> 这个选择** —— 见 §3.7 的三片重切:纯读成员在 `wlwl-std` 内直读系统时钟,与
> `RANDOM_BYTES` 直读 `getrandom` 同款。
>
> **记录者的推荐:候选甲。** 理由是「谁拥有时钟」这个问题必须在代码里只有一个
> 答案 —— 而 `StdCtx` 是「std 原语运行的上下文」,把一个调度器级的虚拟时钟塞进去,
> 会让将来「气泡外的时间从哪来」这个问题在类型上就说不清。候选甲的代价
> (每个实现者加一个方法)在**本仓内是可数的**(已核:实现者就两处)。
> 代价可数 + 语义干净,故选它。**但这一条是设计取舍,不是技术必然。**

#### (c) 调度器现状:气泡要动的地方已逐条定位

- **`scheduler_run_until_idle`(lib.rs:7960)只是把 run queue 排空就返回。**
  ⇒ **「所有任务都阻塞了」与「没事可做了」这两种情况现在完全不可区分**
  (两者都是「队列空了」)。synctest 语义恰恰要判前者 ⇒ **这是气泡最核心的一处改动**,
  不是加成员那么简单。
- `TaskState` 已有 `Suspended { reason: YieldReason }`;现有 `YieldReason` 变体是
  `Explicit` / `AwaitingChild` / `ReceivingOn` / `SendingOn`
  ⇒ **缺一个「等时钟」这一类**(否则挂起原因里没法表达「我在等虚拟时钟」)。
- 🎯 **`detect_deadlock_l1`(runtime.rs:848)只把 `ReceivingOn` / `SendingOn`
  当死锁候选**,并在注释里明确排除「纯 `YIELD` / 等子任务」那两类
  ⇒ 「等时钟」若**单列为一个新的 `YieldReason`**,就**天然不进死锁候选集**。
  ⇒ **ADR-0024 开放问题 2 的「真死锁与等时钟必须可区分」这一条,已经免费拿到了** ——
  这是本轮调查最有用的一条结论。
- `Scope { tasks, cancelled, channels }` + `outstanding_tasks()` ⇒
  ADR-0024 开放问题 1 的「气泡内 `SPAWN` 出去的任务归不归气泡」可以在 Scope 树上
  判定(建议:**气泡 = Scope 的一个属性**,气泡退出时该 scope 的树整体归还给真实时钟)。

#### (d) 五问的建议答案(待业主拍板)

1. **时间戳形状** → **`NOW() -> INTEGER`(Unix 毫秒)**。
   理由:wlwl 的类型系统里没有 `DATETIME`,而**新增一个内建类型是语言变更**,
   不是标准库扩张(ADR-0023 的纪律);而「秒」会引入 ±1 s 的量化误差,
   直接污染「缓存 5 秒过期」这类真实语义 ⇒ 取毫秒,`INTEGER` 里精确无损。
   **ISO-8601 字符串本份不做** —— 那是格式化层的事。
2. **落点** → 见 (b),**记录者推荐候选甲**。
3. **`TIMEOUT` 的失败形态** → **`ERR([kind: "Timeout"])` 值**。
   理由:**仓内已有同款先例** —— `AWAIT` 一个被取消的任务就返回
   `Value::Err(Dict { kind: "Cancelled", .. })`;超时是可预期的**运行期结果**,
   调用方多半要 `IS_ERR` 分支处理它,而原生诊断会**终止运行**。
4. **`TEST_BUBBLE` 放哪** → **`std.time`**(与 Go 一致:气泡是**时间形态**,
   不是测试形态),`std.test` 不新增成员。
5. ~~与 `STEP` 的关系~~ → **前提不成立**(见 (a))。**改问:气泡与 `SCOPE` 嵌套
   的关系。** 记录者建议:**气泡内不再开气泡**(嵌套 = 两层虚拟时钟,语义面翻倍而
   收益近零);`RUN_TESTS` **不默认开气泡**(默认开会让既有测试的时间语义突然变可
   复现,那是 breaking 级的行为变化)。

### 3.7 三片重切(2026-10-06 业主批准):第一批成员**不需要**这个选择

§3.6 调查完之后又发现一件更根本的事,它让「落点」这个问题在**第一批成员上根本
不成立** ⇒ 本份的排期据此重切(同时写进 `ADR-0024` §6,那里是批准的正本)。

**耦合错在哪**:ADR-0024 草案第 1 条写「**时间成员只进气泡语义**」。但
`NOW()` / `MONOTONIC()` 是**纯读** —— 「读系统时钟」与「有没有虚拟时钟」毫无关系;
气泡只改变*读什么*,不改变*能不能读*。

**而且仓里已经有同款形状的先例**:`RANDOM_BYTES` / `RANDOM_HEX` 直接调
`getrandom::fill`、**不经宿主**(W-04,`encode.rs`),当时写进规范的理由是
「`std.encode` 是熵源」。**`std.time` 是时间的源,同款。**

| 片 | 内容 | 宿主 / 调度器改动 | 依赖 |
|---|---|---|---|
| **A1** | `NOW()` + `MONOTONIC()`(纯读) | **零** —— `wlwl-std` 直读 `SystemTime` / `Instant` | 无 |
| **A2** | `SLEEP(ms)`(挂起任务而非阻塞线程) | 一个新 `YieldReason` 变体 + park/wake(小) | 无 |
| **B** | 假时钟气泡 | 「队列空 ⇒ 判**全阻塞** ⇒ 推进虚拟时钟」这一处分支 + 时钟接缝 | A2 |

**为什么这样更优**:B 是整件事里唯一有真实设计风险的部分(§5 开放问题 1–5 仍未逐条
收敛)。切成三片后 **B 的不确定性不再阻塞 GAP-4 的闭合** —— 日志 / TTL / 超时 /
耗时测量先拿到手。反过来若先做 B,A1 的价值被压到最后一刻。

**A1 不浪费**:它在 `wlwl-std` 内落一个**时钟接缝**(成员只调 `now_ms(host)`,不直接
摸 `SystemTime`;`host` 形参 A1 阶段以 `_host` 占位)⇒ **B 阶段只换函数体,不改签名、
不改调用点**。

**同步定下的三条口径**(批准时一并确认):
1. `NOW() -> INTEGER`(Unix **毫秒**);`MONOTONIC()` 同取**毫秒**、起点是**进程启动**
   ⇒ **绝对值无意义,只有差值有效**(规范必须写死这条)。**ISO-8601 字符串本批不做**
   (格式化层的事);**亚毫秒测量不支持**(两成员单位统一为 ms 是刻意的:这样
   `SLEEP(ms)` 与时钟差值能直接对齐)。
2. `TIMEOUT` 的失败形态取 **`ERR([kind: "Timeout"])` 值** —— 仓内已有同款先例
   (`AWAIT` 被取消的任务就返回 `Err{kind:"Cancelled"}`),而原生诊断会**终止运行**。
3. `TEST_BUBBLE` 归 **`std.time`**;**气泡内不再开气泡**;**`RUN_TESTS` 不默认开气泡**
   (默认开是 breaking 级行为变化)。

**一条纪律**(与 W-02 的熵源单向依赖同族):**绝不能**给 `std.time` 的成员加「可注入
时钟」后门 —— 那等于让 CSPRNG 成员可被降级成可预测源。B 阶段的时钟替换**只能**
走宿主(候选甲)。

### 3.8 A2(`SLEEP`)的落定前置:一个**真实的设计疙瘩**(2026-10-06 只读调查)

A1 落地后,A2 的 `SLEEP(ms)` 是 W-01 剩下的唯一一块,本轮**没有开工** —— 因为
它有一个必须由业主裁决的取舍。调查结论写在这里,好让裁决随时可做。

**疙瘩的形状**:调度器的运行循环是「把 run queue 排空就返回」
(`scheduler_run_until_idle`,lib.rs:7960)。`SLEEP` 需要「挂起本任务,到点唤醒」,
于是队列空的那一刻就得决定**干什么**:

| 候选 | 做法 | 代价 |
|---|---|---|
| **甲 · 真阻塞** | 队列空且存在挂起的睡眠者时,`thread::sleep` 到最近的那个唤醒时刻,再唤醒 | **会连带拖住正在做阻塞式 IO 的任务** —— `std.ai` / `std.agent` 的 `reqwest` 正是 blocking 的。一个任务在等 HTTP 响应时,整条调度器停摆到最近的 `SLEEP` 到点 |
| **乙 · 队列空即返回** | 睡眠者登记唤醒时刻,但**不**阻塞等待;谁去推进真实时间,谁负责唤醒 | `SLEEP` 在别的任务还跑着的时候**到点不一定被唤醒** —— 语义随调度时序漂移,而「确定性调度」是本语言的卖点 |
| **丙 · IO 完成回调** | 引入完成事件,唤醒由事件驱动 | 改动面大(要动 `Outcome` / `Signal` 契约与所有阻塞 IO 成员),且与 §17 的结构化并发形态要重新对齐 |

**记录者的建议:甲**,并把它的代价**明写进规范**而不是藏起来 —— 理由是
「SLEEP 期间不调度其他任务」是一条**可被文档化的确定性规则**,比乙的
「到点不一定唤醒」好解释;丙的正确但太大,不该塞进 W-02 的尾巴。

> ⚠️ **甲的代价有一个前提要写清**:它只在**没有阻塞式 IO 在途**时才是纯收益。
> 而 `std.ai` 的 `real-ai` 路径**就是**阻塞式 reqwest ⇒ 这两件事在同一个
> 运行时里共存,谁先谁后会决定行为。**这不是实现细节,是语言级取舍。**
> 若选甲,规范必须同时写明「`SLEEP` 与阻塞式 IO 不可同时依赖其及时性」。

**另注**:`SLEEP` 若要「只挂起任务而不阻塞线程」,还需要一个新的
`YieldReason` 变体(现有的是 `Explicit` / `AwaitingChild` / `ReceivingOn` /
`SendingOn` / `CancellationCheck`)。按 `std.regex` 那次实测的教训,这个新变体
**不要**加进 `detect_deadlock_l1` 的死锁候选集 —— 「等时钟」天然该与
「互相等待」可区分,否则真死锁会被误报成时钟问题。

### 3.9 A2 落定(业主 2026-10-06:**甲**)+ 实施契约

**裁决:甲(真阻塞到最近唤醒时刻)。** 代价按 §3.8 写进规范,不藏。

实施前又挖出一个**必须先定的子问题**,记录在此 —— 它是 §3.8 没覆盖到的:

> **`SLEEP` 怎么知道「我在任务内」?** 计划写它「仅任务内可用」,但
> `StdHost` 只有 `ctx` / `call` / `diag` 三个方法,而 `StdCtx`
> (`argv` / `env` / `warnings` / `source_file` / `tests`)**没有任何任务或作用域
> 字段**(已核)。⇒ 成员**无法自己判断**,而这个判断决定它该「挂起任务」还是
> 「阻塞线程」。

**建议的解法:给 `StdCtx` 加一个 `task_depth: Option<u32>` 字段**,由 eval 侧在
跑任务体时置 `Some(depth)`、顶层时置 `None`。

⚠️ **这条与 §3.6(b) 给「时钟」的裁决不矛盾,但要说清为什么不同**:时钟是
**调度器概念**,塞进 `StdCtx` 会让「谁拥有时钟」在类型上说不清(所以时钟走
`StdHost` 加方法);而「当前调用在不在任务内」是**逐次调用的上下文事实**,
正是 `StdCtx` 的本职(`argv` / `env` 就是同一类)。**一个是状态,一个是上下文
—— 这条界线就是判据。**

#### 实施契约(四处改动 + 一条纪律)

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `wlwl-value` | `YieldReason` 加 `Sleeping(u64)` —— **截止时刻用单调毫秒**(与 `MONOTONIC()` 同源)⇒ B 片换时钟时**自动跟随**,不用改这里 |
| 2 | `wlwl-value` | `StdCtx` 加 `task_depth: Option<u32>`(见上) |
| 3 | `wlwl-std/src/time.rs` | `SLEEP(ms)`:元数 / 类型 / `ms < 0` → `E0030`;`task_depth` 为 `Some` 时返 `Signal::Yield(Sleeping(deadline))`,为 `None` 时**直接阻塞线程**(顶层跑 `SLEEP` 就是阻塞,不需要挂起) |
| 4 | `wlwl-eval` | ① 步进结果里给 `Sleeping(d)` 一个分支:置 `TaskState::Suspended{reason}`(照 channel-op 的现成先例);② 运行队列排空后扫任务里的 `Suspended{Sleeping(d)}`,有则**阻塞到最早的截止时刻**再把它们置回 `Pending` 并入队 |

**纪律(来自 `std.regex` 那次实测的教训)**:新变体 **不要** 加进
`detect_deadlock_l1` 的死锁候选集 —— 那个函数只认 `ReceivingOn` / `SendingOn`,
所以「等时钟」天然不会进候选集,**真死锁与「等时钟」因此可区分**。
这条正好也回答了 **ADR-0024 §5 开放问题 3** 的前半(`SLEEP` 一侧):超时参数走
**单调时钟**(`Sleeping` 的截止时刻就是这么记的),而 `CHANNEL_*` 超时那一侧仍
待 12(同步原语)落地时统一裁决 —— 记在 ADR §5,不猜。

#### 为什么这一轮没有直接写实现

不是「没时间」,是**上面那个子问题会决定第 3 处的形态**(成员是「查 `task_depth`
再决定」还是「一律挂起、由顶层驱动兜底」),而它属于「宿主接口要不要开这个口」
这一类 —— 与 §3.6(b) 同一族判断,**不该由我单方面定**。写清契约之后,
无论你选哪种形态,余下都是机械改动。

## 6. 风险与已知代价

- ⚠️ **气泡需要 eval / 调度器侧改动**,工作量可能超过「一个标准库命名空间」的
  常态。先落 `NOW` / `MONOTONIC` / `SLEEP` 三条**纯 R2 无依赖**的,再单独评估
  气泡 —— 免得气泡的复杂度把三条简单成员一起卡住。
- ⚠️ **不做时区**意味着 `NOW()` 出来的墙钟是 UTC 或本地,取决于决策。
  必须写明,否则调用方会默认本地时区然后算错。**半张时区表比没有更糟**。
- ⚠️ 气泡与 `STEP` 的组合语义未验证(§3.5),可能触碰「确定性」这个卖点 ——
  这条要在第一份用例里就试,不要留到最后。
- **明确不做**:时区库 / 日历 / `CRON` / 定时器对象 / 睡眠排序。
