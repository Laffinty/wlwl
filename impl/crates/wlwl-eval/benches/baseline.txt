# [v0.11.3 M5 / addendum-00 L0-A-1] `std.collection` 规模基线(R0 治本前置)
# ===================================================================
#
# 口径(§17.7):
#   测什么   成员**自身**的成本。被测数组一律由 `RANGE` 建 —— 自 v0.11 M5 起
#            `RANGE` 已沉 R2(规范 §5 层列「混合(R1 门面 + R2 `RANGE`)」,锁测试
#            `range_is_bound_straight_to_the_r2_kernel`),线性且便宜。另有一条
#            `r1_build` 单独量 R1 建数组链。两笔成本必须分开,理由见下。
#   相对谁   同机同编译档;归层前(本段)vs 归层后(待补)并排对照
#   环境     AMD Ryzen 5 4500 6-Core(单线程,§17.7:CPU 密集任务不获并行加速)
#            / rustc + cargo 1.96.0 / Windows MSVC
#   档位     [profile.bench] debug = true, opt-level = 3
#   LTO      **否**(`lto = "thin"` 只写在 [profile.release],bench 档不继承它)
#   样本     warm-up 1 s,measurement 2 s,sample-size **10**(**比 M1/M2/M3 段的
#            20 样本更粗**,故本段与前面三段**不可逐位比较**,只看量级与形状)
#   基准     impl/crates/wlwl-eval/benches/collection.rs(5 组 × 4 档 = 20 条)
#   取数     cargo bench -p wlwl-eval --bench collection -- \
#              --warm-up-time 1 --measurement-time 2 --sample-size 10
#
# ── 为什么口径是「成员自身」而不是「构造 + 成员全链」────────────────────
#
# addendum-00 §4 原表写的是「构造数组 + `MAP` 全链」。**那个口径测不出归层的
# 收益**:若被测数组也用 R1 `+(arr, [v])` 建,建数组的平方级(Σn 次全量拷贝,
# 即下面 `r1_build` 那一组)会盖过成员自身的成本 —— 于是成员沉没沉 R2,曲线
# 都是平方的,数字无法归因到归层,也就没有「归层前后对照」可言。
# 拆成两组之后:`collection_*` 四组的改善**才是 L0-A(归层)的收益**;
# `r1_build` 那一组是 L0-B(治本)的对象 —— **归层不动它**。
#
# ── 成员自身:每元素成本随尺寸上涨 ⇒ 平方级坐实 ────────────────────────
#
#   组 / 档位         1 000       2 000       4 000       8 000    每翻一档(总时间)
#   ──────────────────────────────────────────────────────────────────────────
#   map                45.36 µs    73.96 µs   134.52 µs   254.16 µs   3.26 / 3.64 / 3.78
#   filter             37.47 µs    49.64 µs    92.22 µs   179.45 µs   2.65 / 3.71 / 3.89
#   chunk               8.52 µs    10.66 µs    19.11 µs    46.23 µs   2.50 / 3.59 / 4.84
#   window            180.16 µs   454.13 µs  1 349.90 µs 3 059.00 µs   5.04 / 5.95 / 4.53
#                          (每元素成本 = 时间均值 ÷ 档位元素数)
#
#   绝对时间均值(ms):map    45.36 /  147.91 /   538.08 /  2 033.3
#                      filter 37.47 /   99.27 /   368.87 /  1 435.6
#                      chunk   8.52 /   21.32 /    76.43 /    369.9
#                      window 180.16 /  908.26 / 5 399.6 / 24 472
#
# 「每翻一档」那一列是相邻两档的**总时间**之比:线性 ⇒ 2,平方 ⇒ 4。
# 四组的该列都**趋近或越过 4**(chunk 与 window 的高档已在 4 以上),
# 即每元素成本随尺寸线性上涨 ⇒ 总成本 O(n²)。**归层前的现状:平方级,无一例外。**
#
# 逐组的形状差异是有信息量的,不是噪声:
#   * filter 比 map **便宜**(同 n 下 0.71×)。唯一差别是输出长度 —— filter 只留
#     一半元素(n/2)、map 输出 n 个 ⇒ 成本主要出在**建结果数组**上。
#   * chunk 比 map **便宜 5.5×**(同 n 下 0.18×)。它输出 n/10 个 10 元素块,
#     外层只累积 800 次(n = 8 000)而不是 8 000 次 ⇒ 同为平方,常数小一个量级。
#   * window 比 map **贵 12×**(同 n 下 4.82×),且每翻一档冲过 4。它的输出
#     本身就是 Θ(n·k)((n-k+1) 个窗口 × k 个元素),**再叠上 PUSH 的 O(当前
#     长度)拷贝** ⇒ 实测指数落在 **n^2.2 ~ n^2.6**。规范 §5.1 的原话「它不是
#     实现没写好,是这个成员的定义本身要产出 Θ(n·k) 个元素」与本段一致。
#     要线性窗口就得惰性化,那是 `std.iter` 的事(规范 §14,阻塞于批次 B)。
#
# ── R1 建数组链(D11-012 根因;L0-B 的对象,归层不动它)──────────────────
#
#   档位          1 000        2 000        4 000        8 000     每翻一档
#   时间(均值)   24.55 ms    71.77 ms   254.73 ms  1 131.6 ms   2.92 / 3.55 / 4.44
#   每元素成本    24.55 µs     35.88 µs     63.68 µs    141.45 µs
#
# ── 与规范 §5 已有那张表的关系(不重复造数据)──────────────────────────
#
# 规范 §5 已记 `CHUNK` / `WINDOW` 的四档(n = 625/1250/2500/5000 →
# 29/57/165/644 ms 与 335/1164/5177/20 502 ms),但那是 **debug 档、端到端 CLI、
# 每档取 2–3 次最小值**。本段是 **bench 档(opt-level 3)、criterion、10 样本**,
# 档位也不同。⇒ **两者不可逐位比较,只可比形状**:两者都指向平方级(规范表的
# 「≈ 4×(平方)」与本段 3.59 ~ 4.84 的「每翻一档」互相印证)。
# 本段相对那张表的增量价值有三项:
#   ① 补上规范表**没有**的 `MAP` / `FILTER` 曲线 —— §5.1 的「局限」段只断言
#      它们平方级,没给数;
#   ② 口径可与 M5 / M1 / M2 / M3 段**并排**(同 harness、同档位);
#   ③ 归层后重跑一次即得**同方法学的前后对照** —— 那正是 ADR-0023 §v0.x 5
#      「层归属变更须附基准数据」要的那份数据。
#
# ── 结论:本段对计划目标值的影响(两条,L0-A-2 开工前须知)──────────────
#
# ① **目标值只对「成员自身」口径有意义。** addendum-00 §4 的 8 k 档目标
#    (map / filter ≤ 2 ms、chunk ≤ 5 ms、window ≤ 50 ms)在本口径下**可达** ——
#    沉 R2 后是单趟扫描 + 一次 `Vec` 分配,量级在几十~几百 ns/元素。
#    但若按原口径「构造 + 成员全链」验收,**四条全部不可达**:光 `r1_build`
#    在 8 000 元素上就是 1 131.6 ms,比 map / filter 的 2 ms 目标高**两个
#    数量级**,而归层**不修建数组**。
# ② **归层成员 ≠ 端到端变快。** 两笔平方级分开后可见:8 000 元素上
#    `r1_build` 1 131.6 ms 与 `collection_map` 2 033.3 ms **同量级**,
#    端到端 ≈ 两者相加 ≈ 3.2 s,**仍是平方**。⇒ addendum-00 §0 的契约目标
#    「让 `std.collection` 的**规模可用性回到线性**」**单靠 L0-A 达不到**,
#    必须配 L0-B(治本:β1 识别式累加器 / β2 差分列表 / β3 写时复制 三选一)。
#    计划把 L0-B 划为「独立立项」,于是**本份的目标与手段不一致** ——

# ── 三条要照实说的结论 ──────────────────────────────────────────────
#
# ① **`ENUMERATE` / `ZIP` / `FLAT` 三组:平方级消除,8 k 档 2 300~2 650×。**
#    每元素成本从「涨 10 倍」翻成「降 4.8 倍」,线性承诺成立。
#
# ② **`UNIQ` 仍平方级,而这是**预期之内**的,不是归层失败。**
#    R1 有**两笔**平方成本:`PUSH` 重建(归层消掉)与 `INDEX(out, v)` 的
#    **线性成员查找**(消不掉)。所以它的曲线只是从「10 倍区间的两笔叠加」
#    压到「4.1 倍区间的单笔」—— 量级降了 8.4×,形状仍是涨。
#    查找那笔**不能顺手改哈希**:`values_equal` 要求 `1` 与 `1.0` 判等、
#    `TRUE` 与 `1` **不**判等、`Dict` 判等**无序**、闭包判等是**结构**的,
#    而 `Value` 没有 `Hash`;更硬的一点是 `Float(NaN)` 在 `values_equal`
#    下**与自身不等**(所以 R1 的 `UNIQ([NaN, NaN])` 留两个),按位哈希却
#    会把它们合并 —— 那是**可观察的行为差异**。
#    ⇒ **把 `UNIQ` 做成线性是一次独立的设计裁决**(要给 `Value` 定哈希
#    语义),不是归层顺手能带的事。理由已逐字写进 `collection.wll` 与
#    `collection.rs` 的注记。
#
# ③ **`JOIN` 的「29×」不能当成亮点读。** 它的 R1 绝对成本本来就小
#    (8 k 档 75.66 ms,是 `ZIP` 的 1/123),因为 `+(s, …)` 是 `String`
#    拼接 = 逐次 **memcpy**,带宽高反而把平方藏住了 —— R1 的每元素成本在
#    1 k…8 k 上是 9.84/8.39/7.76/9.46 µs,**基本持平**,总时间的比值只从
#    1.70 爬到 2.44,要到更大的 n 才显出平方。机制上它确实是逐次全量拷贝,
#    归层后换成一次 `String::push_str` 累加、每元素成本降到 0.32 µs 且**下降**,
#    形状确实改善了 —— 但**收益幅度被 R1 的小基数放大了**,不拿它当主要战果。
#
# ── 语料的一处自我更正(留档,别照抄)─────────────────────────────
#
# `FLAT` 的第一版语料是 `FLAT([arr, arr])` —— **只有 2 个顶层元素**,
# R1 只做 2 次 `CONCAT`,量到的根本不是平方级(1 k…8 k 是 2.6/3.0/7.9/
# 11.8 ms,比值毫无规律)。改用 `FLAT(ENUMERATE(arr))`(n 个二元组数组)
# 才真正压到平方级(R1 前:129.4/548.3/2 307.3/9 813.7 ms,比值
# 4.24/4.21/4.25)。**语料压不到目标形态时,量出来的「前后对比」是没有
# 含义的** —— 与 L0-A-1「单点算不出每字节成本」同族。
