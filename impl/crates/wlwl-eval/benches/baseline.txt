# 1) R1 `RANGE` 的每元素成本(实测,release 档,同一台机器,端到端 CLI):
#
#      n = 10 000   3 623 ms      0.36 ms/元素
#      n = 40 000  86 036 ms      2.15 ms/元素
#
#    每元素成本随 n **超线性**上涨(4x 的 n → 6x 的每元素成本)。
#    根因是 R1 用 `PUSH` 建数组,而 wlwl 数组不可变 —— 每次 `PUSH` 都
#    复制整个数组;`RANGE` / `MAP` / `FILTER` / `FLAT` / `UNIQ` /
#    `ENUMERATE` / `GROUP_BY` / `JOIN` 全走这条路。
#
# 2) 与 R2 的对比(Phase I1 / B6 行,同一 bench 文件):
#
#      R2: simple_loop_1m = RANGE(1, 1 000 001, 1) + 100 万次 FOR
#          = 536.57 ms(I1)/ 551.44 ms(B6)整体
#      R1: 光是**构造**那个 100 万元素的区间就远超 30 秒 —— 而
#          语言规范 §6.6 的预算正是「100 万次简单循环 < 30 s」。
#
#    也就是说:§6.6 的符合性工作负载在 M3-1 之后**跑不完**,而且时间
#    全部消耗在循环开始**之前**。
#
# 3) 因此本节的新 bench 工作量按「跑得完」定(100–20k),**不与上面
#    Phase I1 / B6 的绝对数字可比** —— 那两行的 `RANGE` 是原生 Rust
#    循环,这里是解释器里的 `WHILE` + `PUSH`。它们的用途是**回归探测**
#    (R1 侧再变慢会立刻变红),不是跨层比较。
#
# 4) 待补:criterion 20 样本的完整行。R1 的新 bench 单次迭代已在秒级到
#    十秒级,20 样本需要相当长的墙钟时间;这一节先记**端到端实测**与
#    结论,完整 criterion 行在裁决落地后按新工作量补齐(裁决会改
#    工作量)。
